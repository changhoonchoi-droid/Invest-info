Claude Code 고급

Claude Code 고급 기능을 쓰면 자주 하는 절차는 스킬로, 반드시 지켜야 할 규칙은 Hooks로, 탐색처럼 단순한 일은 서브에이전트로 나눠 맡길 수 있습니다. 화면과 동작을 바꾸는 모드, 노트북을 닫아도 돌아가는 클라우드 세션·Projects·루틴도 쓸 수 있습니다. 스킬 → Hooks → 검증 루프 → 서브에이전트 순서로 기본 틀을 먼저 익히고, 그다음 모드·플러그인과 클라우드 병렬 작업, 대규모 작업 요령으로 넘어가세요.

최근 바뀐 점

  • 10월 1일 공식 발표된 모드(Mods)는 Claude Code의 화면·프롬프트·도구 호출을 바꾸는 플러그인입니다. 데스크톱 앱에서 말로 설명하면 만들어 주고, 플러그인으로 설치하면 모든 세션에서 쓸 수 있습니다.
  • 클라우드 세션은 클라우드 가상 머신에서 GitHub 저장소를 복제해 작업합니다. 노트북을 닫아도 계속 진행되고, 휴대폰 Code 탭에서 방향을 바꾼 뒤 Create PR로 마무리할 수 있습니다.
  • Claude Code Projects(베타, Pro·Max 순차 제공)는 하나의 대화가 작업마다 클라우드 브랜치 스레드를 만들어 병렬로 처리하고, PR 관리와 매일 도는 루틴까지 맡습니다.
  • 같은 과제를 루프와 그래프 구조로 비교한 실험에서는 코드 검사 루프가 가장 빠르고 쌌고, 그래프는 토큰이 4배 넘게 들었습니다. 그래서 기본은 루프 하나로 하고 검사기부터 만들라는 권고가 나왔습니다.

입문

1. 스킬로 작업 방법 가르쳐 두기

스킬은 Claude에게 어떤 작업 방법을 한 번 적어 두면 관련 요청이 올 때 자동으로 적용되는 마크다운 파일(SKILL.md)입니다. 커밋, 리뷰, 보고서 형식처럼 매번 같은 방식으로 해야 하는 일에 씁니다. 모든 대화에 항상 불러오는 CLAUDE.md와 달리, 요청과 맞을 때만 불러와 컨텍스트를 아낍니다.

  1. 모든 프로젝트에서 쓸 개인 스킬이면 홈 디렉터리의 .claude/skills에, 팀과 함께 쓸 프로젝트 스킬이면 저장소 루트의 .claude/skills에 두기로 정합니다.
  2. 그 폴더 아래에 스킬 폴더를 만들고 SKILL.md 파일을 둡니다. 직접 만들기 어려우면 Claude에게 만들어 달라고 요청합니다.
  3. SKILL.md의 설명(description)에 이 스킬을 언제 써야 하는지 분명히 적습니다. Claude는 이 설명을 보고 스킬을 고릅니다.
  4. 본문에 작업 순서와 지켜야 할 기준을 적습니다.
  5. 세션을 재시작합니다.
  6. /를 입력해 만든 스킬이 목록에 보이는지 확인합니다.
  7. 관련 작업을 요청해 스킬이 자동으로 적용되는지 확인합니다.
예시
커밋하기 전 점검 절차를 이 프로젝트의 .claude/skills 아래 SKILL.md로 만들어 줘. description에는 언제 이 스킬을 써야 하는지 적어 줘.
  • 스킬은 재시작해야 같은 세션에서 인식됩니다.
  • Claude가 같은 실수를 하면 다시 시키기보다 CLAUDE.md나 스킬에 적어 두면 반복을 막을 수 있습니다.
  • 스킬에는 해야 할 일 목록보다 어떻게 판단할지(원칙)를 적는 편이 효과적입니다.
  • 팀에서 스킬이 많아지면 첫 스킬을 내놓기 전에 소유자·검토자·폐기·테스트 방식을 정해 두세요.

2. CLAUDE.md·스킬·훅 한 번에 세팅하기

하네스 엔지니어링은 AI가 일하기 좋은 환경을 미리 설계하는 방법입니다. CLAUDE.md는 짧은 목차(권고), 스킬은 필요할 때 불러오는 절차, Hooks는 어길 수 없는 규칙(강제)으로 역할을 나눕니다. 새 프로젝트를 시작할 때 한 번에 틀을 잡아 두면 이후 작업이 안정적입니다.

  1. Claude 데스크톱의 Claude Code 탭에서 뉴세션을 누르고 작업 폴더를 만들어 엽니다.
  2. 앱 목적, 기술 스택, 디자인 시스템 같은 프로젝트 정보를 정리합니다.
  3. 프로젝트 정보와 함께 'CLAUDE.md는 200줄 이내 목차로, 반복 절차는 스킬로, 반드시 지킬 규칙은 훅으로 만들어 달라'는 프롬프트를 입력합니다.
  4. 생성된 CLAUDE.md, 스킬, 훅 구조를 파일 탭에서 확인합니다.
  5. 세션을 재시작합니다.
  6. /를 입력해 만든 스킬(예: 클린업)이 프로젝트 범위 스킬로 보이는지 확인합니다.
예시
이 프로젝트에 하네스를 세팅해 줘. CLAUDE.md는 200줄 이내 목차로 만들고, 커밋·리뷰·클린업은 스킬로, 비밀 파일 보호와 편집 후 자동 코드 정리는 훅으로 만들어 줘.
  • 영상에서는 속도를 위해 권한을 모두 허용하고 권한 건너뛰기 모드로 실행했습니다. 회사 업무 폴더라면 권한 요청을 켜 둔 채 진행하는 편이 안전합니다.
  • /init으로 만든 CLAUDE.md는 그대로 두지 말고 직접 규칙을 추가해 다듬어야 효과가 있습니다.
  • 배포처럼 위험한 작업은 자동 적용에 맡기지 말고 슬래시로 직접 호출하게 두세요.

3. Hooks로 편집 후 자동 서식 맞추기

Hooks는 Claude Code가 일하는 특정 시점(도구 실행 전·후, 작업 종료 등)마다 정해 둔 명령을 반드시 실행하는 기능입니다. CLAUDE.md에 적은 지시는 가끔 지켜지지 않지만, Hook은 예외 없이 실행됩니다. 파일을 고칠 때마다 서식을 맞추는 것이 가장 쉬운 첫 활용입니다.

  1. /hooks를 입력하거나 settings.json을 열어 Hook 설정을 시작합니다.
  2. 이벤트로 PostToolUse를 고릅니다.
  3. matcher를 Edit 또는 MultiEdit로 지정합니다.
  4. 실행 명령에서 파일 확장자를 확인해 맞는 포매터를 실행하게 합니다.
  5. TypeScript는 Prettier, Go는 Go format, Python은 Ruff처럼 프로젝트에서 쓰는 도구를 연결합니다.
  6. 파일 하나를 고쳐 달라고 요청해 서식이 자동으로 맞춰지는지 확인합니다.
예시
파일을 편집할 때마다 .py 파일이면 Ruff로 서식을 맞추는 PostToolUse Hook을 .claude/settings.json에 추가해 줘. matcher는 Edit와 MultiEdit로 해 줘.
  • 사용할 수 있는 이벤트는 UserPromptSubmit, PreToolUse, PostToolUse, Notification, Stop입니다.
  • Stop 이벤트에 세션 종료 요약을, Notification에 작업 완료 알림을 거는 식으로도 씁니다.
  • 실행한 명령을 기록하는 Hook을 두면 나중에 무엇을 했는지 추적하기 쉽습니다.

4. Hooks로 위험한 작업 막고 팀과 공유하기

PreToolUse Hook은 Claude가 도구를 실행하기 직전에 검사해서 위험한 명령을 막습니다. rm -rf가 들어간 명령, 운영 설정 폴더 쓰기, main 브랜치 커밋처럼 절대 일어나면 안 되는 일을 강제로 차단할 때 씁니다. 프로젝트 설정 파일에 넣어 저장소에 올리면 팀 전체가 같은 규칙을 씁니다.

  1. 이벤트가 PreToolUse인 Hook을 만듭니다.
  2. Hook 스크립트가 stdin으로 받는 JSON에서 도구 이름과 입력을 검사하게 합니다.
  3. 막아야 하는 경우 stderr에 차단 이유를 남기고 종료 코드 2로 끝내게 합니다.
  4. 허용하는 경우 종료 코드 0으로 끝내게 합니다.
  5. 이 Hook을 프로젝트 수준 설정인 .claude/settings.json에 넣습니다.
  6. .claude/settings.json을 저장소에 커밋합니다.
  7. 팀원이 저장소를 받으면 같은 Hook이 자동으로 적용되는지 확인합니다.
예시
rm -rf가 들어간 명령은 PreToolUse Hook에서 종료 코드 2로 막고, 막은 이유를 stderr에 남기도록 .claude/settings.json에 설정해 줘.
  • stderr에 이유를 남기면 Claude가 그 메시지를 받아 다른 방법으로 바꿔 시도합니다.
  • 프로젝트 스크립트는 CLAUDE_PROJECT_DIR 환경 변수로 경로를 적으면 작업 폴더가 바뀌어도 동작합니다.
  • 비밀 파일(.env 등)이나 건드리면 안 되는 폴더를 보호하는 데에도 같은 방식을 씁니다.

5. verify 스킬로 검증 루프 만들기

Claude Code는 테스트와 린터를 스스로 돌리지만, 그것만으로는 변경이 실제로 의도대로 동작하는지 알 수 없습니다. 사람이 브라우저에서 클릭해 보던 확인 절차를 스킬로 만들어 두면, Claude가 직접 앱을 실행해 확인하고 실패하면 고쳐 다시 확인합니다. 기준이 측정 가능할수록 Claude가 더 오래 혼자 일할 수 있습니다.

  1. Claude Code에 포함된 verify 스킬을 처음 사용합니다.
  2. Claude가 앱을 실행하고 변경 사항을 앱에서 직접 확인하는 과정을 지켜봅니다.
  3. 성공한 확인 절차가 프로젝트에 스킬로 저장되는지 확인합니다.
  4. 생성된 스킬에 확인 항목을 추가합니다(예: Chrome DevTools MCP로 레이아웃 시프트를 재는 성능 트레이스).
  5. 스킬에 언제 실행할지, 실패하면 무엇을 할지, 항목별 통과 기준을 적습니다.
  6. UI 변경을 요청해 Claude가 서버 실행, 페이지 열기, 클릭, 스크린샷, 성능 측정을 하고 실패 시 고쳐 다시 확인하는지 봅니다.
예시
버튼 배치를 바꾼 뒤 verify 스킬로 서버를 띄워 페이지를 열고, 클릭과 스크린샷으로 의도대로 동작하는지 확인해 줘. 실패하면 고쳐서 다시 확인해 줘.
  • 웹은 브라우저, 백엔드는 엔드포인트 호출, 모바일은 iOS 시뮬레이터로 확인 절차를 만들 수 있습니다.
  • 내가 직접 보고 고칠 점을 알려 주고 있다면, 그 기준(성능 예산, 접근성 체크리스트, 디자인 시스템 규칙)을 스킬에 넣으세요.
  • 검증 명령을 사람과 에이전트가 똑같이 실행할 수 있게 만들어 두면 CI에서도 그대로 돌릴 수 있습니다.
  • 예전 방식: Playwright MCP를 연결해 Claude가 앱을 실행·확인하게 했습니다. 지금은 verify 스킬로 시작해 절차를 스킬로 남기는 방식이 공식 안내입니다.

6. 서브에이전트를 작은 모델로 돌리기

서브에이전트는 메인 Claude가 일부 작업을 떼어 맡기는 보조 에이전트입니다. 코드베이스를 읽기만 하는 탐색 작업에는 비싼 모델이 필요 없으므로, 작은 모델로 돌리면 한도와 비용을 아낄 수 있습니다. 커밋 전 코드 리뷰처럼 따로 검사하는 역할을 맡기기에도 좋습니다.

  1. 코드베이스를 읽기만 하는 서브에이전트를 정합니다(예: 탐색용, 리뷰용).
  2. 커스텀 서브에이전트의 frontmatter에서 모델을 Sonnet으로 지정합니다.
  3. 모든 서브에이전트의 기본 모델을 한 번에 바꾸려면 settings.json에 CLAUDE_CODE_SUBAGENT_MODEL 환경 변수를 설정합니다.
  4. 작업을 맡겨 탐색은 서브에이전트가, 수정은 메인 모델이 하는지 확인합니다.
  5. 커밋 전에는 서브에이전트 코드 리뷰어로 점검하게 하고 커밋 메시지를 만들게 합니다.
예시
코드베이스를 읽기만 하는 탐색용 커스텀 서브에이전트를 만들고, frontmatter에서 모델을 Sonnet으로 지정해 줘.
  • 읽기 전용 서브에이전트는 Sonnet, 경우에 따라 Haiku까지 써도 됩니다.

7. 말로 모드 만들어 플러그인으로 설치하기

모드(Mods)는 Claude Code의 모습과 행동 방식을 바꾸는 작은 프로그램입니다. 토큰 사용량 표시, 턴마다 다음 할 일 추천 카드처럼 창·버튼 같은 화면 요소는 모드로만 만들 수 있습니다. 데스크톱 앱에 모드 제작 스킬이 들어 있어 코드를 몰라도 말로 설명하면 됩니다.

  1. Claude Code 데스크톱 앱의 좌측 상단 코드 탭으로 들어갑니다.
  2. 로컬 옆 버튼에서 폴더 열기로 프로젝트 폴더를 만들어 엽니다.
  3. 만들고 싶은 모드를 말로 설명해 요청합니다.
  4. 핫 리로딩 안내가 나오면 Enable for this session을 누릅니다.
  5. 잘 보이는지 확인해 달라고 요청해 결과를 봅니다.
  6. 같은 대화에서 방금 만든 모드를 모든 세션에서 쓸 수 있게 플러그인으로 설치해 달라고 요청합니다.
  7. 다른 세션이나 프로젝트를 열어 모드가 적용되는지 확인합니다.
예시
토큰 사용량을 아이콘과 함께 보여 주는 모드를 만들어 줘.
  • 플러그인으로 설치하지 않으면 모드는 만든 대화 안에서만 작동합니다.
  • 스킬·MCP가 밖에서 지식과 도구를 건네는 방식이라면, 모드는 작업 환경 자체를 바꿉니다.
  • 다음 작업 추천 모드는 '턴이 끝날 때마다 할 일 세 가지를 카드로 띄우고 누르면 바로 실행'처럼 동작을 구체적으로 적어 요청하면 됩니다.

8. 모드 코드를 직접 짜서 적용하기

모드는 플러그인의 hook.json에 modules 키를 넣어 TypeScript 파일을 가리키게 하고, 그 파일의 함수를 Claude Code 내부 이벤트에 등록해 만듭니다. 화면에 그리는 내용, 프롬프트, 도구 호출을 이벤트마다 지켜보거나 고치거나 대신 처리할 수 있습니다. 예시로 답변 속 이메일 주소를 마우스를 올릴 때만 보이게 숨깁니다.

  1. 플러그인의 hook.json에 modules 키를 추가하고 TypeScript 파일을 가리키게 합니다.
  2. 그 파일에서 렌더 이벤트(render)에 함수를 등록합니다.
  3. 이벤트 데이터로 들어오는 답변 텍스트에서 이메일 주소를 찾습니다.
  4. 주소마다 $send 객체로 마우스를 올릴 때만 보이는 블록을 만듭니다.
  5. next를 호출하지 않고 결과를 직접 반환해 Claude Code가 내 버전을 그리게 합니다.
  6. plugin dir 플래그로 플러그인 폴더를 지정해 Claude Code를 시작하거나, 데스크톱 앱은 글로벌 설정 파일에 폴더를 추가합니다.
  • 함수는 $send 객체, 이벤트, next 세 값을 받습니다. next에 넘긴 값이 실제로 수행되고, 호출하지 않고 반환하면 내가 처리합니다.
  • 폴더를 감시하므로 파일을 저장하면 현재 세션에 바로 반영됩니다.
  • 렌더를 바꾸는 것은 화면만 바꾸므로 모델은 실제 이메일 주소를 그대로 씁니다. 모델에게도 숨기려면 다른 방법이 필요합니다.
  • 모드는 자체 샌드박스에서 Claude Code가 노출한 이벤트만 보며, 플러그인이라 마켓플레이스 저장소로 공유할 수 있습니다.

9. 클라우드 세션에 작업 맡기고 퇴근하기

클라우드 세션은 내 컴퓨터가 아니라 클라우드 가상 머신에서 GitHub 저장소를 복제해 별도 브랜치에서 작업하는 Claude Code입니다. 노트북을 닫아도 계속 진행되고 휴대폰에서 질문에 답할 수 있어, 큰 리팩터링이나 퇴근 전 맡겨 두는 일에 알맞습니다. 여러 세션을 동시에 돌려 병렬로 처리할 수도 있습니다.

  1. GitHub 계정을 연결하고 GitHub에서 접근을 승인합니다.
  2. Claude GitHub App을 설치하고 접근을 허용할 저장소를 고릅니다.
  3. 데스크톱 앱에서 Local 대신 Cloud를 선택합니다.
  4. 저장소, 환경, 시작할 브랜치를 고릅니다.
  5. Claude에게 작업을 맡기고 노트북을 닫습니다.
  6. 휴대폰 Claude 앱의 Code 탭에서 질문에 답하거나 방향을 조정합니다.
  7. 변경 내용(diff)을 검토하고 필요하면 코멘트를 남깁니다.
  8. 문제가 없으면 Create PR을 눌러 GitHub에 풀 리퀘스트를 엽니다.
  • 세션은 저장소를 새로 복제해 시작하므로 커밋·푸시한 내용만 씁니다. 개인 설정, 스킬, 플러그인이 필요한 작업은 로컬에서 돌리세요.
  • 기본 환경에 없는 도구는 사용자 지정 환경에서 네트워크 범위, 환경 변수, 설정 스크립트를 정해 추가합니다.
  • 터미널에서 teleport 플래그를 붙여 claude를 실행하면 클라우드 세션을 내 컴퓨터로 가져와 이어 할 수 있습니다.
  • Remote Control은 내 컴퓨터에서 도는 세션에 연결하는 방식이라 컴퓨터가 켜져 있어야 합니다. 비용은 플랜 한도에 로컬 세션과 합산됩니다.

10. Projects로 여러 작업 병렬 처리하기

Claude Code의 Project는 Claude가 여러 작업을 조율하는 하나의 지속적인 대화입니다. 작업마다 클라우드의 별도 브랜치에서 도는 스레드를 만들어 병렬로 처리하므로, 여러 세션이나 저장소에 걸친 큰 목표에 적합합니다. PR 관리와 병합까지 한 프로젝트 안에서 할 수 있습니다(베타, Pro·Max 순차 제공).

  1. 데스크톱 앱 또는 웹 앱에서 Claude 탭을 엽니다.
  2. 새 프로젝트를 만들고 이름, Claude가 달성할 목표, 관련 저장소나 폴더를 입력합니다.
  3. 열린 메인 대화에서 코드베이스 탐색과 개선안 제안을 요청합니다.
  4. Claude가 찾은 내용을 보고 진행할 작업에 합의합니다.
  5. 작업마다 생긴 스레드 카드를 눌러 진행 상황을 보고, 필요하면 말을 걸어 방향을 바꾸거나 중단합니다.
  6. threads 탭에서 내 답을 기다리는 스레드를 확인합니다.
  7. overview의 pull requests 탭에서 PR 상태를 보고, 준비되면 Claude에게 병합을 요청합니다.
예시
이 저장소의 코드베이스를 둘러보고 개선할 점을 제안해 줘.
  • 코디네이터는 낮은 노력 수준으로 두고, 스레드는 작은 모델을 기본으로 쓰다가 복잡한 작업에서만 바꾸면 한도를 아낍니다.
  • library 탭에 목업·디자인 명세를 넣으면 모든 스레드가 함께 봅니다.
  • 로컬 파일이나 도구가 필요한 작업은 그 스레드를 내 컴퓨터에서 실행하게 요청합니다.
  • 같은 저장소에서 로컬 세션 여러 개를 동시에 돌릴 때는 세션마다 worktree를 나눠 서로 파일을 덮어쓰지 않게 하는 방식이 실무에서 쓰입니다.

11. 루틴으로 매일 점검 자동화하기

루틴은 프롬프트, 저장소, 커넥터, 트리거를 정해 두면 Anthropic 관리형 인프라에서 Claude Code 세션을 자동으로 실행하는 기능입니다. 일정(매일·매주)이나 GitHub 이벤트·웹훅으로 시작되며, 노트북이 꺼져 있어도 동작합니다. 매일 성능 점검, 주간 문서 갱신 PR처럼 사람이 시키지 않아도 먼저 일하게 할 때 씁니다.

  1. 무엇을 계기로 시작할지(일정, GitHub 이벤트, 웹훅·API 호출) 트리거를 정합니다.
  2. 어떤 저장소와 자료를 볼지 컨텍스트를 정합니다.
  3. 필요하면 모니터링 서비스 같은 외부 서비스를 Claude에 연결합니다.
  4. 결과를 어떻게 받고 조종할지(PR로 받기, 조사 스레드로 대기 등)를 정합니다.
  5. Claude에게 매일 도는 점검 루틴을 만들어 달라고 요청합니다.
  6. 루틴이 만든 세션을 웹·CLI·데스크톱에서 열어 결과를 보고 이어서 지시합니다.
예시
모니터링 지표를 보고 매일 성능 저하를 점검하는 루틴을 만들어 줘. 저하를 발견하면 조사 스레드를 열어 기다려 줘.
  • 루틴이 저하를 발견하면 조사 스레드를 열어 프로젝트에서 기다립니다.
  • 피드백을 매일 모아 중요도별로 분류하고, 확신이 높은 것만 고치게 하는 식으로도 쓸 수 있습니다.
  • 반복 업무는 루틴·루프로, 단계를 미리 알 수 없는 일은 동적 워크플로로 맡기는 구분이 권장됩니다.

12. 큰 작업은 검사기 붙인 루프로 맡기기

코드 변환·역공학·대규모 수정처럼 큰 작업은 AI의 설명을 믿지 말고, 원본과 결과를 코드로 비교하는 검사기를 먼저 만든 뒤 통과할 때까지 반복시키는 것이 핵심입니다. 실험에서는 코드 검사 루프가 복잡한 그래프 구조보다 빠르고 저렴했습니다. 구조를 늘리기 전에 검사기와 종료 조건부터 설계합니다.

  1. 작업 단위를 하나로 좁힙니다(예: 가장 오래 도는 함수 하나, 화면 하나).
  2. 원본과 새 결과의 출력을 비교하는 테스트를 먼저 만들게 하고, 원본으로 통과하는지 확인시킵니다.
  3. 같은 입력에는 같은 출력이 나와야 한다는 기준을 주고, 원본 코드와 테스트는 고치지 못하게 합니다.
  4. 푸시·배포·삭제는 하지 말라고 프롬프트에 명시합니다.
  5. 작업을 실행시키고, 다르면 빠진 예외를 보완해 다시 비교하게 합니다.
  6. 속도가 중요하면 조건별 측정표를 만들게 하고, 나쁜 숫자는 그대로 에이전트에게 돌려줍니다.
  7. 검증 통과·최대 반복 횟수·시간/비용 한도·진전 없음 중단을 종료 조건으로 겹쳐 겁니다.
예시
이 Python 함수를 PyO3와 maturin을 쓰는 Rust 모듈로 옮겨 줘. 먼저 원본과 새 함수의 출력을 비교하는 테스트를 만들어 원본으로 통과시키고, 원본 코드와 테스트는 고치지 마. 푸시·배포·삭제는 하지 마.
  • 테스트를 모두 통과해도 여러 스레드에서 원본보다 느린 경우가 있었습니다. 정확성은 테스트로, 속도는 측정으로 따로 확인하세요.
  • 그래프(여러 단계·여러 에이전트)는 병렬 후 취합, 독립 검증, 단계별 다른 모델·권한, 사람 승인, 장시간 저장·재개가 필요할 때만 씁니다.
  • 앱 역공학은 읽기 → 사양서(spec.md) 작성 → 사양서만 보고 다시 만들기 → 원본과 비교를 반복하는 같은 원리입니다.
  • 만드는 AI와 검사하는 AI를 분리하면 자기 결과에 관대해지는 문제를 줄일 수 있습니다.
