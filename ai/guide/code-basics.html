1. 권한 규칙으로 안전선 정하기

Claude Code는 파일 수정이나 명령 실행처럼 영향이 있는 작업을 하기 전에 권한을 묻습니다. 연구에서는 권한 요청의 97%가 그대로 승인될 만큼 확인 요청이 많아 피로가 쌓였습니다. 그래서 늘 막을 일, 늘 물어볼 일, 늘 허용할 일을 규칙으로 미리 정해 두면 안전과 속도를 함께 챙길 수 있습니다.

  1. Claude가 절대 하면 안 되는 동작(예: 운영 환경 변경)을 골라 deny 규칙에 적습니다.
  2. 자동으로 넘기지 말고 매번 확인받고 싶은 동작은 ask 규칙에 적습니다.
  3. 확인 없이 진행해도 되는 예외 동작은 allow 규칙에 적습니다.
  4. deny·ask·allow 규칙이 다른 판단보다 먼저 적용된다는 점을 기억하고, 규칙끼리 겹치지 않는지 확인합니다.
  5. 실제로 작업을 맡겨 보고 막히는 동작을 살펴 규칙을 조금씩 넓힙니다.
  • 처음에는 허용 범위를 좁게 시작하고, 거부되는 항목을 보며 넓혀 갑니다.
  • 읽기 전용 작업이나 되돌릴 수 있는 작업은 자동 모드에서도 분류기를 거치지 않고 바로 진행됩니다.
  • 회사 관리자가 정한 규칙은 개발자가 직접 지울 수 없습니다.

2. 클라우드 세션으로 작업 맡겨 두기

클라우드 세션은 내 컴퓨터가 아닌 클라우드의 가상 머신에서 Claude Code가 작업하는 방식입니다. 노트북을 닫아도 작업이 계속되므로 큰 리팩터링이나 마이그레이션, 퇴근 전에 맡겨 두는 일에 알맞습니다. Pro, Max, Team 플랜과 Enterprise 프리미엄 좌석 또는 Chat + Claude Code 좌석에서 쓸 수 있습니다.

  1. 작업할 코드를 GitHub 저장소에 올려 둡니다.
  2. 데스크톱 앱, 브라우저, 터미널, 휴대폰, Slack 가운데 편한 곳에서 클라우드 세션을 시작합니다.
  3. 맡길 작업을 설명하고 시작합니다. Claude가 저장소를 복제해 따로 브랜치를 만들어 작업합니다.
  4. 노트북을 닫거나 외출해도 되며, Claude가 질문하면 휴대폰으로 답하거나 작업 방향을 바꿉니다.
  5. 필요하면 다른 작업도 세션을 따로 열어 동시에 돌립니다.
  6. 작업이 끝나면 변경 내용을 검토하고 PR을 만듭니다.
  • 사용량은 로컬 세션과 함께 플랜 한도에 합산되며 가상 머신 비용은 따로 없습니다.
  • Remote Control은 클라우드 세션과 다릅니다. 내 컴퓨터에서 돌고 있는 세션에 연결하는 방식이라 컴퓨터가 켜져 있어야 합니다.

3. 코드 전에 디자인 시안 먼저 잡기

Claude 디자인으로 화면 시안을 먼저 살펴본 뒤 구현으로 넘어가는 방식입니다. 바로 코드부터 짜지 않고 짧게 디자인을 다듬으면 결과가 더 좋아집니다. 앱 온보딩처럼 화면 흐름이 중요한 작업에 알맞습니다.

  1. Claude 디자인에 작업할 저장소를 연결합니다.
  2. 만들 화면(예: 앱 온보딩)의 시안을 요청합니다.
  3. 마음에 들지 않는 부분은 시안에 댓글을 달아 피드백합니다.
  4. 세부 사항은 시안을 직접 고쳐 다듬습니다.
  5. 클릭형 프로토타입으로 실제 화면 흐름을 눌러 보며 확인합니다.
  6. 확정한 디자인을 바탕으로 구현을 진행합니다.
예시

4. 자동 모드에 우리 회사 환경 알려주기

자동 모드에서는 Claude가 자기 행동을 스스로 승인하지 않습니다. 별도 분류기가 사용자의 메시지와 도구 호출만 보고 사용자의 의도에 맞는지 판단합니다. 기본 설정은 작업 디렉터리와 git 리모트만 내부 자원으로 보므로, 회사의 GitHub 조직이나 클라우드 저장소 같은 인프라를 따로 알려 줘야 제대로 판단합니다.

  1. 관리자라면 관리형 설정(managed settings)에 환경을 정의합니다. 여기에 정한 내용은 모든 개발자가 그대로 물려받습니다.
  2. 개발자라면 사용자 설정(user settings)에 자기 항목을 추가합니다.
  3. environment 필드에 GitHub 조직, 클라우드 버킷, 내부 서비스 등을 쉬운 영어 문장으로 설명합니다.
  4. environment를 설정하면 기본 항목이 바뀌므로 기본 문자열도 함께 넣어 남겨 둡니다.
  5. 더 세밀하게 정하려면 예외는 allow에 적고, 명시적으로 요청하지 않으면 막을 동작은 soft deny, 무조건 막을 동작은 hard deny에 적습니다.
  6. 확실히 막을 동작은 deny 규칙으로, 자동 모드에서도 확인받을 동작은 ask 규칙으로 따로 지정합니다.
예시
Our GitHub organization is acme-corp. Our internal services run on *.internal.acme.com. Our cloud bucket acme-data is trusted.
  • 처음에는 좁게 설정하고, 거부되는 항목을 보며 점차 넓힙니다.
  • 도구 결과는 서버 측 프로브가 숨은 악성 지시를 먼저 검사합니다. 프로브와 자동 모드를 함께 켠 평가에서는 프롬프트 인젝션 공격 성공률이 0으로 떨어졌습니다.
  • 운영 인프라 변경처럼 위험이 큰 작업은 사람이 직접 검토하거나 자체 평가를 만들어 확인합니다.
  • 개발자는 관리자가 설정한 항목을 지울 수 없습니다.
