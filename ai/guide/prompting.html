프롬프트·활용 요령

이 분야에서는 AI에게 일을 잘 맡기는 요령을 다룹니다. 맥락을 주는 질문법, 답을 검증하는 법, 작업에 맞는 모델과 노력 수준 고르기, 프로젝트 규칙을 문서로 남기기, 비용과 컨텍스트 줄이기, 평가로 품질 재기까지 포함합니다. 처음이라면 위에서부터 차례로 보세요. 앞의 두 가이드는 모든 AI 도구에 통하는 기초이고, 뒤로 갈수록 Claude Code를 쓰는 사람에게 맞는 응용입니다.

프롬프트 작성법, 컨텍스트 관리, 결과 품질 높이기, 비용·사용량 관리 · 영상 16개 기반 · 2026-10-23 갱신

최근 바뀐 점

  • 10월 1일 Anthropic이 Claude Code '모드(Mods)'를 공식 발표했습니다. 모드는 작업 신호를 듣고 지켜보거나 고치거나 대신 처리하면서 작업 환경 자체를 바꾸는 작은 프로그램입니다.
  • Opus 5.5가 나왔습니다. Opus 5보다 토큰당 20% 저렴하고, Pro·Max·Team 요금제에서는 같은 한도로 25% 더 쓸 수 있으며, 기본 effort는 medium입니다.
  • Claude Code에서 /claude-api prompt-audit를 실행하면 CLAUDE.md와 스킬의 지침을 Opus 5.5에 맞게 다듬을 수 있습니다.
  • Claude 공식 채널이 산책하며 녹음한 음성 메모를 Claude에 보내 브랜드 스타일에 맞는 슬라이드로 만드는 활용법을 소개했습니다.

입문

1. 맥락을 알려 주고 더 나은 답 받기

AI는 사용자 메시지, 올린 문서, 대화 기록을 모두 보고 답을 한 단어씩 만들어 냅니다. 그래서 내가 누구이고 어떤 결과를 원하는지 알려 줄수록 답이 좋아집니다. 메일 초안, 보고서, 기획안 등 거의 모든 요청에 쓸 수 있는 기본기입니다.

  1. 내가 누구이고 지금 무슨 작업을 하는지 먼저 적습니다.
  2. 어떤 결과가 좋은 결과인지(분량, 형식, 읽을 사람 등) 적습니다.
  3. '더 좋게 만들어'나 '실수 없이 만들어' 같은 막연한 주문은 빼고 구체적인 조건만 남깁니다.
  4. 가격이나 뉴스처럼 최신 정보가 필요하면 웹 검색을 해 달라고 요청합니다.
  5. 초안을 여러 버전으로 받거나 다른 어조로 다시 써 달라고 요청합니다.
  6. 마음에 드는 버전을 골라 고칠 점을 이어서 요청합니다.
예시
저는 마케팅팀 직장인이고 다음 주 신제품 출시 안내 메일을 쓰고 있습니다. 읽을 사람은 기존 거래처 담당자이고, 좋은 결과는 5문장 이내로 핵심 일정과 혜택이 바로 보이는 메일입니다. 서로 다른 어조로 세 가지 버전을 써 주세요.
  • AI는 정해진 답을 꺼내는 게 아니라 새로 만들어 냅니다. 그래서 같은 요청으로도 여러 버전을 받아 볼 수 있습니다.
  • 모델은 학습 시점 이후의 일을 검색 없이는 확실히 알지 못합니다. 웹 검색을 했다고 넘겨짚지 말고 직접 물어보세요.
  • AI가 자신 있게 말하거나 결과물이 깔끔하다고 해서 내용이 맞다는 뜻은 아닙니다.

2. AI 답변을 검증하며 쓰기

AI는 그럴듯하지만 사실이 아닌 내용을 만들어 내기도 하고(환각), 사용자가 듣고 싶어 하는 말에 맞춰 주기도 합니다(아첨). 신뢰는 켜고 끄는 스위치가 아니라 다이얼처럼 조절하는 것입니다. 질문이 얼마나 중요한지에 따라 확인 강도를 달리하세요.

  1. 틀렸을 때 어떤 일이 생기는지 스스로 묻고, 얼마나 꼼꼼히 확인할지 정합니다.
  2. 질문하기 전에 '모르면 모른다고 말해 달라'고 미리 말해 둡니다.
  3. 원하는 답을 흘리지 말고 중립적으로 질문합니다.
  4. 답의 근거가 된 출처를 요청합니다.
  5. 받은 출처를 직접 열어 그 내용이 실제로 있는지 확인합니다.
  6. 숫자, 출처, 건강·법률·돈 문제는 믿을 만한 출처로 다시 확인합니다.
예시
이 결정에 대한 가장 강력한 찬성과 반대 논거는 무엇인가요? 근거가 되는 출처도 함께 알려 주시고, 모르면 모른다고 말해 주세요.
  • 파티 주제 브레인스토밍은 검증할 필요가 적지만, 상사에게 보일 슬라이드의 통계는 반드시 확인합니다.
  • AI는 실제로 없는 출처를 그럴듯하게 지어낼 수도 있습니다.
  • 잘 알려진 주제는 비교적 정확합니다. 반대로 사소한 세부 사항, 최근 사건, 비공개 정보는 틀리거나 지어낼 가능성이 높습니다.
  • AI는 자기가 얼마나 확실한지 늘 알려 주지 않습니다. 최종 판단은 사람이 합니다.

3. 음성 메모로 발표 자료 초안 만들기

빈 슬라이드 앞에서 막막할 때 쓰는 방법입니다. 하고 싶은 말을 먼저 음성으로 다 녹음하고, 정리와 서식은 Claude에게 맡깁니다. 서식 작업 시간을 줄이고 내용에 집중할 수 있습니다.

  1. 산책하거나 이동하는 동안 휴대폰 음성 메모로 발표에서 하고 싶은 말을 모두 녹음합니다.
  2. 녹음을 글로 받아 적습니다.
  3. 받아 적은 글을 Claude에게 보내 발표 자료로 만들어 달라고 요청합니다.
  4. 만들어진 슬라이드에서 작은 수정은 직접 고칩니다.
  5. 구성이나 흐름을 바꾸는 큰 수정은 댓글로 Claude에게 요청합니다.
  • 영상에서는 Claude가 회사 브랜드 스타일을 이미 알고 있어서 폰트나 템플릿을 따로 찾을 필요가 없었습니다.
  • 정리되지 않은 말이라도 일단 다 쏟아내는 것이 핵심입니다. 구조는 나중에 잡아도 됩니다.

4. 작업 종류에 맞게 모델·effort 고르기

AI 작업 비용은 모델, effort(추론 노력), 캐시 세 가지로 정해집니다. 작업 성격에 맞춰 모델과 effort를 고르면 품질은 지키면서 비용과 사용 한도를 아낄 수 있습니다.

  1. 할 일이 열린 작업(심층 조사, 복잡한 분석, 오래 걸리는 에이전트 작업)인지, 반복 작업(문서 요약, 메일 초안, 보고서 데이터 추출)인지 구분합니다.
  2. 반복 작업이면 Opus나 Sonnet을 기본으로 씁니다.
  3. 열린 작업이면 Fable 5.1을 고르고 effort를 medium으로 시작합니다.
  4. Claude Code에서는 /effort로 노력 수준을 정합니다.
  5. 결과가 부족하면 effort를 한 단계씩 올립니다. 여러 파일이나 프로젝트 전체를 바꾸는 수정에는 high를 씁니다.
  6. 탐색처럼 일부 작업만 맡는 서브에이전트에는 더 저렴한 모델부터 써 봅니다.
  • 토큰 단가가 아니라 작업 하나당 비용으로 비교합니다. 더 똑똑한 모델은 적은 단계로 끝내서 총비용이 오히려 낮을 수 있습니다.
  • Opus 5.5는 Opus 5보다 토큰당 20% 저렴하고, 같은 버그 수정을 약 30% 빨리 끝냈으며, 5시간 한도도 덜 썼습니다(약 4% 대 6%).
  • 강한 모델일수록 낮은 effort로 시작해 필요할 때 올립니다.
  • 예전 방식: 5월 영상에서는 effort를 X high로 권장했습니다. 지금은 Opus 5.5 기본값인 medium으로 시작해 필요할 때 올리는 방식을 권합니다.

5. CLAUDE.md에 규칙 적어 실수 막기

Claude가 같은 실수를 반복하면 매번 다시 시키지 말고, CLAUDE.md나 스킬에 규칙으로 적어 둡니다. 새 모델이 나오면 이 지침을 새 모델에 맞게 다듬어 두면 좋습니다.

  1. Claude가 실수하면 무엇이 잘못됐는지 한 문장으로 정리합니다.
  2. 다시 시키는 대신 그 규칙을 CLAUDE.md나 해당 스킬에 적어 둡니다.
  3. 규칙은 꼭 필요한 것만 짧게 적고, 서로 부딪히는 지침이 없는지 확인합니다.
  4. 새 모델로 바꿨다면 Claude Code에서 /claude-api prompt-audit를 실행합니다.
  5. CLAUDE.md와 스킬 지침이 새 모델(예: Opus 5.5)에 맞게 조정됐는지 확인합니다.
예시
/claude-api prompt-audit
  • /claude-api prompt-audit는 API를 쓰지 않고 Claude Code만 써도 쓸 수 있습니다.
  • 지침은 최소한만 주고, 필요한 정보는 모델이 스스로 찾아오게 하는 편이 낫다고 권합니다.
  • 지침끼리 부딪히면 모델이 엉뚱한 값을 쓸 수 있습니다. 실제로 프로모션 배수 3.1 대신 1.35를 쓴 사례가 있었습니다.

6. Claude에게 인터뷰받아 스펙 만들기

결과를 처음부터 자세히 정해 주는 대신, Claude가 사용자에게 질문하며 요구사항을 끌어내게 하는 방법입니다. 모델이 강해질수록 제약을 줄이고 질문을 받는 쪽이 더 좋은 스펙을 만듭니다.

  1. Claude Code에서 Shift+Tab을 눌러 auto mode로 전환합니다.
  2. /effort로 노력 수준을 정합니다.
  3. 프롬프트에는 만들 것의 관심 영역(예: 대상 사용자)만 적고, 결과는 지나치게 정하지 않습니다.
  4. 프롬프트에 ask user question 도구를 쓰라고 분명히 적습니다.
  5. Claude가 띄우는 질문에 차례로 답합니다.
  6. 답이 끝나면 Claude가 쓴 스펙을 직접 검토합니다.
예시
회사 동료들끼리 점심값을 나누는 앱을 만들고 싶어. 대상 사용자는 같은 팀 직장인이야. ask user question 도구로 나에게 질문하면서 요구사항을 정리한 뒤 스펙을 써 줘.
  • 스펙은 긴 마크다운보다 정보가 빽빽한 HTML 파일로 받으면 검토하기 쉽습니다. 토큰은 더 들 수 있지만 반복 수정이 줄어듭니다.
  • 스펙을 빠르게 여러 번 다듬을 때는 /fast 모드가 유용합니다.
  • 예전 방식: 예전에는 플랜 모드로 계획부터 세웠지만, 최신 모델에서는 플랜 모드 대신 오토 모드를 씁니다.

7. 긴 작업의 컨텍스트·비용 줄이기

시스템 프롬프트와 도구가 계속 늘어난 에이전트는 비효율적인 경로로 돌거나 서로 부딪히는 지침 때문에 틀립니다. 기본부터 단순하게 하고 필요한 정보만 그때그때 불러오면 토큰과 비용이 줄고 결과는 정확해집니다.

  1. 지금 시스템 프롬프트에 서로 부딪히는 정책이나 규칙이 없는지 점검합니다.
  2. 도구와 서브에이전트를 줄이고 단순한 기본 기능에서 다시 시작합니다.
  3. 늘 필요하지 않은 지침은 스킬로 떼어 내 필요할 때만 불러오게 합니다(점진적 공개).
  4. 많은 데이터를 다루는 계산은 코드 실행에 맡겨 대화에 오가는 토큰을 줄입니다.
  5. 매번 똑같이 들어가는 긴 앞부분은 프롬프트 캐싱으로 비용을 줄입니다.
  6. 구조를 바꿀 때마다 평가를 다시 돌려 실제로 나아졌는지 확인합니다.
  • 코드 실행을 쓰면 토큰과 비용은 줄지만, 턴 수는 비슷하고 응답 시간은 덜 줄 수 있습니다.
  • 오래 도는 에이전트는 도구 검색, 프로그램 방식 도구 호출, 컴팩션으로 컨텍스트를 가볍게 유지합니다.
  • Fable 5.1은 캐시 읽기 비용이 Fable 5보다 75% 낮아서 캐시를 잘 쓸수록 절감 폭이 커집니다.

8. 평가(evals)로 결과 품질 재기

평가는 내 용도에서 AI가 얼마나 잘하는지 재는 체계적인 테스트입니다. '왠지 좋아진 것 같다'는 느낌을 확인할 수 있는 숫자로 바꿔 줍니다. 프롬프트를 고치거나 새 모델로 옮길지 정할 때 근거가 됩니다.

  1. 내 작업에서 성공이 무엇인지 기준을 먼저 적습니다.
  2. 공개 벤치마크 대신 실제 내 작업으로 테스트 사례를 만듭니다.
  3. 형식이나 특정 문구처럼 엄격하게 맞는지 볼 항목은 코드 기반 채점기로 검사합니다.
  4. 글의 품질처럼 뉘앙스가 있는 항목은 모델 기반 채점기(LLM 판정)로 평가합니다.
  5. 지금 상태로 평가를 돌려 기준 점수를 기록합니다.
  6. 프롬프트나 구조를 하나씩 바꿀 때마다 평가를 다시 돌려 점수를 비교합니다(힐 클라이밍).
  7. 새 모델이 나오면 이 평가부터 백그라운드로 돌려 옮길지 판단합니다.
  • 판정 모델도 환각할 수 있으니 채점기 여러 개를 함께 씁니다.
  • 평가가 없으면 사용자 불만이 나올 때까지 문제를 모르고, 한 곳을 고치다 다른 곳을 망가뜨릴 수 있습니다.
  • 모델만 바꿨는데 테스트 에이전트 성공률이 약 20% 오른 사례도 있습니다.
  • 지금 안 되는 작업은 지워 버리지 말고 남겨 두세요. 다음 모델이 잘하게 될 분야의 신호입니다.

9. 내 사용 패턴으로 모드 추천받기

모드(Mods)는 Claude Code의 모습과 행동 방식을 바꾸는 작은 프로그램입니다. 10월 1일 공식 발표됐습니다. 내 세션 기록을 분석시켜 비용을 아끼고 집중을 돕는 모드를 추천받아 만들 수 있습니다.

  1. Claude Code에서 세션 로그를 최대한 훑어 내가 자주 반복하는 말과 작업을 찾아 달라고 요청합니다.
  2. 흐름을 돕고, 비용을 아끼고, 집중하게 해 줄 모드 다섯 개를 추천해 달라고 요청합니다.
  3. 추천마다 붙은 패턴과 근거를 읽고 마음에 드는 번호를 고릅니다.
  4. 고른 번호의 모드를 만들어 달라고 요청합니다.
예시
Claude Code 세션 로그를 최대한 훑어서 내가 자주 반복하는 말과 작업을 파악해 줘. 그걸 바탕으로 흐름을 돕고 비용을 아끼며 집중하게 해 줄 모드 다섯 개를 추천해 줘.
  • 추천에는 내 사용 패턴과 그 근거가 함께 나옵니다.
  • 스킬과 MCP가 밖에서 지식과 도구를 건네준다면, 모드는 작업 환경 자체를 바꿉니다.
  • 영상에서는 창이나 버튼 같은 화면 요소는 모드로만 만들 수 있다고 설명합니다. 토큰 사용량 표시처럼 비용 관리에 쓰는 모드도 실습했습니다.
