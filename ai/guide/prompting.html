프롬프트·활용 요령

이 분야에서는 AI에게 내 상황을 알려 주는 법, 답을 검증하는 법, 컨텍스트와 모델·사용량을 아껴 쓰는 법을 배울 수 있습니다. 먼저 ①~③ 입문 가이드로 대화의 기본기를 익히고, 이어서 ④~⑦에서 프롬프트를 다듬고 결과 품질을 높인 뒤, ⑧~⑩에서 컨텍스트와 모델·비용 관리, 평가까지 단계적으로 보세요.

프롬프트 작성법, 컨텍스트 관리, 결과 품질 높이기, 비용·사용량 관리 · 영상 53개 기반 · 2026-11-12 갱신

최근 바뀐 점

  • Claude Fable 5.2가 출시되어, 기본은 중간 노력 수준의 Opus 5.5로 시작하고 크고 모호한 장기 작업에만 Fable을 쓰라는 선택 기준이 나왔습니다.
  • Fable은 토큰당 가격이 Opus의 두 배, Sonnet은 Opus의 절반이라, 메인 세션은 Fable이 맡고 세부 작업은 서브에이전트에 Sonnet을 쓰는 분업 방식이 소개되었습니다.
  • AI가 추천하는 쪽을 그대로 따르기 쉽다는 Anthropic 연구가 나와(분석가의 86%가 에이전트가 기운 쪽을 선택), 결정 전에 내 우선순위부터 정하는 요령이 제안되었습니다.
  • 회의 전사, 영어 메일, 보고서 포맷 스킬화 등 업무 시간을 줄이는 활용 사례가 소개되었습니다.

입문

1. AI에게 내 맥락 알려 주고 대화 시작하기

AI는 내가 누구이고 무슨 일을 하는지 알수록 더 잘 답합니다. 완벽한 프롬프트보다 상황과 기준을 충분히 알려 주는 것이 핵심입니다. 처음 AI를 쓰는 분이 가장 먼저 익힐 기본기입니다.

  1. 무료 요금제로 먼저 시작하고, 한도에 자주 막힐 때 유료로 넘어갑니다.
  2. 완전 처음이면 ChatGPT 앱의 보이스 모드로 말하듯 질문해 봅니다.
  3. 어느 정도 익숙하면 Claude 데스크톱 앱으로 컴퓨터 속 파일을 보여 주며 나를 파악하게 합니다.
  4. 내가 누구인지, 무슨 작업 중인지, 좋은 결과가 어떤 모습인지 먼저 알려 줍니다.
  5. 관련 파일이나 캡처를 많이 붙여 상황을 보여 줍니다.
  6. 하루 30분 정도 AI에게 묻고, AI가 나에게 질문하도록 유도하는 습관을 들입니다.
예시
나는 중견 제조업체 영업팀 대리야. 지금 다음 주 고객 제안서를 준비 중이고, 좋은 결과물은 한 장짜리 요약과 핵심 근거 세 가지야. 시작하기 전에 필요한 정보를 나에게 먼저 질문해 줘.
  • AI는 시간이 지나도 나를 기억하지 못할 수 있으니 중요한 맥락은 새 대화에서도 다시 알려 줍니다.
  • 새 채팅에서는 이전 내용을 가져오라고 요청하거나, 작업별로 프로젝트를 나눠 쓰면 편합니다.
  • 구독료 기준은 금액이 아니라 쓰다가 한도에 막히는지 여부입니다.

2. 회사 일에 쓰기 전 학습 설정 끄기

ChatGPT에서는 내 대화가 모델 개선에 쓰일 수 있어, 회사 업무에 쓰기 전에 설정을 확인해야 합니다. 몇 번의 클릭으로 끌 수 있습니다.

  1. ChatGPT 설정(Settings)을 엽니다.
  2. Data controls로 들어갑니다.
  3. Improve the model for everyone 항목을 끕니다.
  4. 개인정보와 기밀 정보는 설정과 관계없이 입력하지 않습니다.
  • 회사 일에 쓰기 전에 반드시 먼저 끕니다.
  • 회사의 AI 사용 규정이 있다면 그것을 우선합니다.

3. AI 답변 믿어도 되는지 검증하기

AI는 그럴듯하지만 사실이 아닌 내용(환각)을 만들거나, 내가 원하는 답에 맞춰 동의(아첨)하기도 합니다. 신뢰는 스위치가 아니라 다이얼처럼, 질문의 중요도에 따라 조절하세요.

  1. 틀렸을 때 어떤 일이 생기는지 스스로 묻고 확인 강도를 정합니다.
  2. 미리 모르면 모른다고 말해 달라고 허용합니다.
  3. 주장마다 근거가 되는 출처를 요청합니다.
  4. 제시된 출처를 직접 열어 실제로 그 내용이 있는지 확인합니다.
  5. 의심스러우면 얼마나 확신하는지, 틀릴 만한 부분이 있는지 묻습니다.
  6. 새 대화를 열어 그 답변의 오류를 찾아 달라고 하거나, 다른 AI로 교차 검증합니다.
예시
아래 답변에서 숫자·날짜·인용마다 근거 출처를 알려 줘. 확실하지 않은 부분은 모른다고 말해도 괜찮아. 틀릴 가능성이 높은 부분도 짚어 줘.
  • 숫자·날짜·인용, 최신 사건, 마이너한 주제는 특히 다시 확인하세요.
  • AI가 없는 출처를 그럴듯하게 만들 수 있으니 링크를 직접 열어 봅니다.
  • 깔끔한 문단이나 자신 있는 말투가 정확성의 증거는 아닙니다.
  • 브레인스토밍은 느슨하게, 상사에게 보일 통계·건강·법률·금전 문제는 반드시 확인합니다.

4. 중립적으로 물어 편향·아첨 피하기

질문에 내가 원하는 답을 흘리면 AI가 그쪽으로 맞춰 주기 쉽습니다. 중립적으로 묻고, 한쪽으로 치우친 답은 다시 균형을 요청하는 방법입니다.

  1. 원하는 결론을 드러내지 않고 질문합니다.
  2. 찬성과 반대 논거를 모두 요청합니다.
  3. 답이 한쪽으로 치우쳤다고 느끼면 바로 반박하고 더 균형 잡힌 접근을 요청합니다.
  4. 근거를 모아 달라고 하고 링크를 직접 확인합니다.
  5. 같은 질문을 다른 각도에서 다시 물어봅니다.
예시
이 결정에 대한 가장 강력한 찬성 논거와 반대 논거는 무엇인가요? 어느 쪽도 편들지 말고 근거와 함께 알려 주세요.
  • 정치 외의 일반 대화에도 똑같이 유용합니다.

5. 말로 하고 싶은 일 프롬프트로 다듬기

타이핑 대신 길게 말하면 시간이 줄고 생각도 정리됩니다. 음성 입력 도구나 앱의 받아쓰기로 두서없이 말한 뒤, AI에게 프롬프트로 다듬어 달라고 하는 방법입니다.

  1. Typeless 같은 음성 입력 도구나 ChatGPT의 받아쓰기로 하고 싶은 요청을 두서없이 말해 입력합니다.
  2. 입력된 문장을 드래그로 선택합니다.
  3. Typeless의 Ask Anything 단축키를 누릅니다.
  4. 무엇이든 물어보세요 칸에 프롬프트를 다듬어 달라고 말합니다.
  5. 약 3초 후 나온 프롬프트를 필요하면 고쳐서 AI에 입력합니다.
예시
더 잘 알아듣는 프롬프트로 다듬어 줘. 타겟·톤·결과물 형식을 구체적으로 넣어 줘.
  • '더 짧게', '더 친근하게' 같은 수정도 같은 방식으로 요청할 수 있습니다.
  • Typeless 무료 사용량은 주당 8,000단어이며, 전문 용어는 가끔 틀릴 수 있습니다.
  • 휴대폰 음성 메모로 생각을 쏟아낸 뒤 Claude에 보내 발표 자료로 만드는 방식도 서식 걱정을 줄여 줍니다.

6. 메일·보고서를 상황 맞춰 쓰게 하기

영어 메일, 보고서처럼 매번 비슷하게 반복되는 글은 받는 사람과 목적을 알려 주면 품질이 달라집니다. 형식은 스킬이나 메모리로 굳혀 두면 매번 같은 포맷이 나옵니다.

  1. 받는 사람의 직급을 프롬프트에 적습니다.
  2. 나와 받는 사람의 관계를 적습니다.
  3. 메일이 끝난 뒤 무엇이 일어나야 하는지를 적습니다.
  4. 자주 쓰는 보고서 형식은 스킬이나 메모리로 저장해 매번 같은 포맷으로 나오게 합니다.
  5. AI 티가 나는 문장은 다듬는 전용 스킬로 고칩니다.
  6. 중요한 문서는 직접 읽고 고친 뒤 보냅니다.
예시
영어 메일 초안을 써 줘. 받는 사람은 미국 지사 부사장이고, 나와는 처음 연락하는 사이야. 메일을 읽은 뒤 다음 주 화요일까지 일정 회신을 하는 것이 목표야.
  • 번역기는 문장을 바꾸고, 현지 직원은 맥락을 바꾼다는 점을 기억하세요.
  • 회의는 전사로 기록해 요약·후속 작업까지 맡기는 방식이 권장됩니다.

7. AI를 과외 선생님으로 공부하기

새 분야를 배울 때 AI에게 선생님 역할을 맡겨 커리큘럼을 만들게 하는 방법입니다. 이해 없이 복사만 하면 실력이 늘지 않으니 질문을 이어 가는 것이 중요합니다.

  1. 배우고 싶은 분야를 말합니다.
  2. 네가 앞으로 과외 선생님으로서 나를 공부할 수 있도록 도와줘라고 요청합니다.
  3. AI가 만들어 주는 커리큘럼을 받습니다.
  4. 답변을 이해하면서 질문과 문제를 이어 갑니다.
  5. 답을 받으면 '진짜 맞나?', '내 상황은?', '다른 관점은?'으로 검증합니다.
예시
네가 앞으로 과외 선생님으로서 나를 공부할 수 있도록 도와줘. 나는 마케팅 직무 5년 차이고 데이터 분석을 처음 배워. 4주 커리큘럼부터 만들어 줘.
  • 답변을 이해하지 않고 복사·붙여 넣기만 하면 실력이 늘지 않습니다.
  • 책을 읽은 뒤 AI에게 저자 역할을 시켜 질문해 볼 수 있습니다.
  • AI가 만든 학습 자료도 공개 전에 원문과 대조해 검수하세요.

8. 에이전트 추천에 휘둘리지 않고 결정하기

Anthropic 연구에서 사람들은 에이전트가 기운 쪽을 86% 따랐고, 스스로 결정했다고 착각하기 쉬웠습니다. 결정을 AI에게 넘기지 않도록 순서를 정하는 방법입니다.

  1. 에이전트가 방법을 추천하기 전에 내 우선순위부터 묻게 합니다.
  2. 결정이 어려우면 작고 저렴한 모델로 여러 버전의 프로토타입을 병렬로 만듭니다.
  3. 프로토타입을 보고 내가 결정한 뒤 프로토타입은 버립니다.
  4. 결정한 내용을 에이전트에게 전달합니다.
  5. 에이전트가 고른 안에 대해 "What would change your advice?"라고 묻습니다.
  6. 답을 보고 다른 안이 최적이 되는 조건이 현재 상황에 해당하는지 판단합니다.
예시
추천을 하기 전에, 내 우선순위를 파악하기 위해 먼저 질문해 줘. 그리고 네가 고른 안에 대해 What would change your advice? 를 알려 줘.
  • 추천 답을 그대로 선택하는 습관이 가장 쉬운 함정입니다.
  • 프로토타입은 결정용이므로 최고 모델을 쓸 필요가 없습니다.

9. Claude Code 컨텍스트 아껴 쓰기

컨텍스트는 Claude의 작업 기억으로, 읽은 파일·실행한 명령·주고받은 메시지가 모두 공간을 차지합니다. 한도에 가까워지면 자동 압축되며 세부 내용이 사라질 수 있어 관리가 필요합니다.

  1. 같은 기능 작업을 이어갈 때는 /compact로 대화를 압축합니다.
  2. 새 기능을 시작할 때는 /clear로 비웁니다.
  3. 요청은 구체적으로 해서 불필요한 파일 탐색을 줄입니다.
  4. 관련 없는 MCP 서버는 끕니다.
  5. 답만 필요한 조사는 서브에이전트에 맡깁니다.
  6. 자주 쓰는 작업 방법은 스킬(SKILL.md)로 만들어, 필요할 때만 불러오게 합니다.
  • MCP 서버는 기본적으로 모든 도구를 컨텍스트에 올립니다.
  • 스킬은 이름과 설명만 먼저 불러와 컨텍스트를 아낍니다.
  • 서브에이전트는 별도 컨텍스트 창을 쓰고 요약만 돌려줍니다.
  • 컨텍스트는 최소한만 주고 모델이 알아서 찾게 하는 방식이 최근 권장됩니다.

10. 작업에 맞는 모델과 노력 수준 고르기

작업 비용은 모델, effort(추론 노력), 캐시 세 가지로 정해집니다. 기본은 중간 노력 수준의 Opus 5.5로 시작하고, 결과가 부족하면 먼저 노력 수준을 올리는 것이 최근 기준입니다.

  1. 작업이 열린 작업(심층 조사, 장시간 에이전트)인지 범위가 분명한 반복 작업인지 구분합니다.
  2. 일단 중간 노력 수준의 Opus 5.5로 시작합니다.
  3. 결과가 부족하면 모델을 바꾸기 전에 effort를 단계적으로 올립니다.
  4. 크고 모호한 장기 작업은 Fable, 범위가 분명한 작업은 Sonnet을 씁니다.
  5. 요약·분류·라우팅 같은 대량 작업은 Haiku를 씁니다.
  6. 서브에이전트는 저렴한 모델부터 적용합니다.
  • Fable은 토큰당 가격이 Opus의 두 배, Sonnet은 Opus보다 빠르고 가격이 절반입니다.
  • 토큰 단가가 아니라 작업당 비용으로 비교합니다. 똑똑한 모델이 적은 단계로 끝내 총비용이 낮을 수 있습니다.
  • 여러 파일에 걸친 수정에는 effort high가 필요할 수 있습니다.
  • 예전 방식: Fable 5.1을 medium effort로 시작하는 안내가 있었으나, 최근(11월)에는 Opus 5.5 medium을 시작점으로 권합니다.
  • Haiku의 가용성과 사용 한도는 요금제마다 다릅니다.

11. Claude Code 첫 프롬프트와 인터뷰로 스펙 만들기

Claude Code는 승인·자동 수락·계획 모드를 Shift+Tab으로 전환합니다. 모델이 강력해질수록 제약을 줄이고, Claude가 질문해 요구사항을 끌어내게 하는 것이 최근 권장 방식입니다.

  1. Shift+Tab으로 원하는 모드(승인 / 자동 수락 / 계획)로 전환합니다.
  2. /effort로 노력 수준을 설정합니다.
  3. 프롬프트에서 만들 앱의 관심 영역(예: 대상 사용자)만 주고 결과는 과하게 지정하지 않습니다.
  4. 프롬프트에 ask user question 도구를 쓰라고 명시합니다.
  5. Claude가 띄우는 질문에 차례로 답합니다.
  6. 답변이 끝나면 Claude가 작성하는 스펙을 확인합니다.
  • '더 좋게 만들어', '실수 없이 만들어' 같은 프롬프트는 피합니다.
  • 자동 수락 모드에서도 명령 실행은 허락을 묻습니다.
  • 빠르게 스펙을 반복할 때는 /fast 모드가 유용합니다.
  • 실수가 나오면 다시 시키지 말고 CLAUDE.md나 스킬에 적어 같은 실수를 막습니다.
  • 예전 방식: 계획 모드를 먼저 쓰는 것이 중요했지만, 최신 모델에서는 오토 모드를 쓰는 추세입니다.

12. 평가로 프롬프트와 모델 개선하기

프롬프트를 고치거나 모델을 바꿀 때 느낌에 의존하면 다른 곳이 망가져도 모릅니다. 작은 평가 세트를 직접 만들어 결과를 비교하는 방법입니다.

  1. 통제 사례, 이전에 실패한 엣지 케이스, 사람에게 넘기거나 거절해야 할 사례를 담은 평가 세트를 만듭니다.
  2. 예시 테스트 케이스를 한두 개 만들고 Claude에게 더 늘려 달라고 요청합니다.
  3. 현재 프롬프트로 평가를 돌려 실패 유형을 확인합니다.
  4. 사실과 다른 역할 설명과 불필요한 내용을 지우고, 역할·가이드라인·정책·말투를 XML 태그로 구분합니다.
  5. 출력 형식을 정하는 출력 계약을 추가합니다.
  6. 모델과 effort 설정을 바꿔 가며 같은 작업을 여러 번 돌립니다.
  7. 통과율, 토큰, 비용, 지연 시간을 비교해 기준에 맞는 모델과 설정을 고릅니다.
예시
내가 만들려는 제품은 고객 문의 답변 봇이야. 예시 테스트 케이스 두 개를 줄 테니, 비슷한 유형과 엣지 케이스까지 50개로 늘려 줘.
  • 공개 벤치마크는 내 용도와 다를 수 있으니 직접 만든 평가가 더 중요합니다.
  • 토큰당 가장 싼 모델이 아니라 성공 한 건당 가장 싼 모델을 고릅니다.
  • 실행마다 편차가 있으니 한 번의 결과로 단정하지 않고, 인프라 실패와 모델 실패를 구분합니다.
  • 금지 항목을 길게 나열하는 방식은 피합니다.
