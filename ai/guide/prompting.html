프롬프트·활용 요령

1. 회사 업무 전 학습 사용 설정 끄기

ChatGPT는 기본 설정에서 내 대화가 모델 개선에 쓰일 수 있습니다. 회사 일에 AI를 쓰기 전에 가장 먼저 해 둘 안전 설정입니다.

  1. ChatGPT 설정(Settings)을 엽니다.
  2. Data controls로 들어갑니다.
  3. Improve the model for everyone 항목을 끕니다.
  4. 개인정보와 기밀 정보는 설정과 무관하게 입력하지 않는 습관을 들입니다.
  • 회사 일에 쓰기 전에 반드시 먼저 끕니다.
  • 설정을 껐더라도 기밀 정보는 입력하지 않는 편이 안전합니다.

2. 맥락을 충분히 주고 AI와 대화하기

완벽한 프롬프트보다 중요한 것은 내가 누구이고 무슨 작업을 하며 어떤 결과를 원하는지 알려 주는 것입니다. 맥락이 쌓일수록 답이 내 상황에 맞아집니다.

  1. 내가 누구이고 무슨 작업 중인지, 좋은 결과가 어떤 것인지 적어 알려 줍니다.
  2. 관련 파일과 캡처 같은 자료를 가능한 한 많이 붙입니다.
  3. 타이핑이 번거로우면 음성 입력으로 길게 말해 요청합니다.
  4. 초안을 여러 버전으로 요청하거나 다른 어조로 다시 써 달라고 합니다.
  5. 작업별로 프로젝트를 나눠 쓰고, 새 채팅에서는 이전 내용을 가져오라고 요청합니다.
  6. 나온 답은 직접 읽고 판단해 고칩니다.
예시
나는 제조업체 영업팀 3년 차 대리야. 내일 팀장님께 보고할 월간 실적 요약을 쓰려고 해. 첨부한 엑셀을 보고 A4 반 장 분량으로 핵심 3가지만 정리한 초안을 두 가지 버전으로 써 줘.
  • 하루 30분, AI에게 질문하고 AI가 나에게 질문하게 하는 습관이 맥락을 쌓습니다.
  • 음성 받아쓰기는 ChatGPT가 가장 정확하다는 평가가 있습니다.
  • 자신 있는 말투나 깔끔한 결과물이 정확성의 증거는 아닙니다.

3. 말로 프롬프트 만들고 다듬기

Typeless 같은 음성 입력 도구로 두서없이 말하면 군더더기를 지운 문장으로 입력해 줍니다. 말한 요청을 더 잘 알아듣는 프롬프트로 다듬는 데 씁니다.

  1. Typeless로 하고 싶은 요청을 두서없이 말해 입력합니다.
  2. 입력된 문장을 드래그로 선택합니다.
  3. Ask Anything 단축키를 누릅니다.
  4. 무엇이든 물어보세요 칸에 '더 잘 알아듣는 프롬프트로 다듬어 줘. 타겟·톤·결과물 형식을 구체적으로 넣어 줘'라고 말합니다.
  5. 약 3초 후 나온 프롬프트를 필요하면 고쳐서 AI에 입력합니다.
예시
더 잘 알아듣는 프롬프트로 다듬어 줘. 타겟·톤·결과물 형식을 구체적으로 넣어 줘.
  • 같은 방식으로 '더 짧게', '더 친근하게' 같은 수정도 요청할 수 있습니다.
  • 무료 사용량은 주당 8,000단어이고, 전문 용어는 가끔 틀릴 수 있어 개인 사전에 등록하면 도움이 됩니다.

4. 영어 메일을 현지 직원처럼 쓰기

번역기는 문장만 바꾸지만 맥락을 알려 주면 AI가 현지 직원처럼 상황에 맞는 메일을 씁니다. 해외 거래처나 본사에 메일을 쓸 때 유용합니다.

  1. 받는 사람의 직급을 프롬프트에 적습니다.
  2. 나와 받는 사람의 관계를 적습니다.
  3. 메일이 끝난 뒤 무엇이 일어나야 하는지를 적습니다.
  4. 초안을 받고 직접 읽어 고칩니다.
예시
받는 사람은 미국 본사의 VP이고, 나와는 이번 분기 처음 연락하는 사이야. 이 메일을 읽은 뒤 금요일까지 샘플 출하 일정을 회신받는 게 목표야. 정중하되 간결한 영어 메일을 써 줘.
  • 번역기는 문장을 바꾸고, 현지 직원은 맥락을 바꾼다는 점을 기억하세요.
  • AI 티가 나는 문장은 다듬고, 중요한 문서는 직접 읽고 고칩니다.

5. AI를 과외 선생님으로 쓰기

새 분야를 배울 때 AI에게 과외 선생님 역할을 맡겨 커리큘럼을 만들고 질문을 이어 가는 방법입니다. 이해하며 따라가야 실력이 늘어납니다.

  1. 배우고 싶은 분야를 말합니다.
  2. 네가 앞으로 과외 선생님으로서 나를 공부할 수 있도록 도와줘라고 요청합니다.
  3. AI가 만들어 주는 커리큘럼을 받습니다.
  4. 답변을 이해하면서 질문과 문제를 이어 갑니다.
  5. 책을 읽은 뒤에는 AI에게 저자 역할을 시켜 질문해 봅니다.
예시
네가 앞으로 과외 선생님으로서 나를 공부할 수 있도록 도와줘. 나는 마케팅 직군이고 데이터 분석 기초를 배우고 싶어. 4주 커리큘럼부터 만들어 줘.
  • 답변을 이해하지 않고 복사·붙여 넣기만 하면 실력이 늘지 않습니다.
  • AI가 준 답은 '진짜 맞나?', '내 상황은?', '다른 관점은?'으로 검증합니다.

6. AI 답변 검증하며 쓰기

AI는 그럴듯하지만 사실이 아닌 내용을 만들거나(환각), 내가 원하는 답에 맞춰 주기도(아첨) 합니다. 질문의 중요도에 따라 확인 강도를 조절하는 방법입니다.

  1. 틀렸을 때 어떤 일이 생기는지 스스로 묻고 확인 강도를 정합니다.
  2. 미리 모르면 모른다고 말해 달라고 허용합니다.
  3. 주장마다 근거가 되는 출처를 찾아 달라고 요청합니다.
  4. 제시된 출처를 직접 열어 실제로 그 내용이 있는지 확인합니다.
  5. 원하는 답을 흘리지 말고 이 결정에 대한 가장 강력한 찬성과 반대 논거는 무엇인가요?처럼 중립적으로 질문합니다.
  6. 의심스러운 답은 얼마나 확신하는지 묻거나, 새 대화에서 오류를 찾아 달라고 하거나 다른 AI로 교차 검증합니다.
예시
이 답변의 각 주장마다 근거 출처를 찾아 줘. 확실하지 않은 부분은 모른다고 말해도 괜찮아. 그리고 틀릴 가능성이 있는 부분을 짚어 줘.
  • 브레인스토밍은 느슨하게, 숫자·날짜·인용·출처·건강·법률·금전 문제는 반드시 확인합니다.
  • AI가 실제로 없는 출처를 그럴듯하게 만들어 낼 수도 있습니다.
  • 최신 정보는 웹 검색을 했는지 직접 물어봅니다.
  • 환각이 줄수록 확인을 건너뛰기 쉬우니 주의합니다.

7. 에이전트 추천에 휘둘리지 않고 결정하기

연구에서 분석가들은 에이전트가 기운 쪽을 86% 따랐지만 출처로 밝힌 사람은 15%뿐이었습니다. 추천을 그대로 고르는 함정을 피하는 방법입니다.

  1. 에이전트가 방법을 추천하기 전에 내 우선순위부터 묻게 합니다.
  2. 결정이 어려우면 작고 저렴한 모델로 여러 버전의 프로토타입을 병렬로 만듭니다.
  3. 프로토타입을 보고 내가 결정한 뒤 프로토타입은 버립니다.
  4. 결정한 내용을 에이전트에게 전달합니다.
  5. 에이전트가 고른 안(A)에 대해 What would change your advice?라고 묻습니다.
  6. 답을 보고 다른 안(B)이 최적이 되는 조건이 현재 상황에 해당하는지 판단합니다.
예시
추천하기 전에 먼저 내 우선순위를 물어봐 줘. 그리고 네가 고른 안에 대해 What would change your advice?
  • 추천 답을 그대로 선택하는 습관이 가장 쉬운 함정입니다.
  • 프로토타입은 결정용이므로 최고 모델을 쓸 필요가 없습니다.

8. Claude Code 컨텍스트 아껴 쓰기

컨텍스트는 Claude의 작업 기억이며 읽은 파일, 실행한 명령, 메시지가 모두 공간을 차지합니다. 한도에 가까워지면 자동 압축되어 세부가 사라질 수 있어 직접 관리하는 것이 좋습니다.

  1. 같은 기능 작업을 이어갈 때는 /compact로 대화를 압축합니다.
  2. 새 기능을 시작할 때는 /clear로 컨텍스트를 비웁니다.
  3. 요청은 구체적으로 해서 불필요한 탐색을 줄입니다.
  4. 관련 없는 MCP 서버는 끕니다.
  5. 답만 필요한 조사는 서브에이전트에 맡겨 요약만 돌려받습니다.
  • MCP 서버는 기본적으로 모든 도구를 컨텍스트에 올립니다.
  • 스킬은 이름과 설명만 먼저 불러와 컨텍스트를 아낍니다.
  • 최신 모델에서는 컨텍스트를 최소한만 주고 모델이 알아서 찾게 하는 방식도 권장됩니다.

9. Claude에게 인터뷰시켜 스펙 만들기

결과를 과하게 지정하는 대신 Claude가 질문해 요구사항을 끌어내게 하는 방법입니다. 모델이 강력해질수록 제약을 줄이는 쪽이 낫다는 것이 핵심입니다.

  1. Shift+Tab으로 auto mode로 전환합니다.
  2. /effort로 노력 수준을 설정합니다(권장 X high).
  3. 프롬프트에서 만들 대상의 관심 영역(예: 대상 사용자)만 주고 결과는 과하게 지정하지 않습니다.
  4. 프롬프트에 ask user question 도구를 쓰라고 명시합니다.
  5. Claude가 띄우는 질문에 차례로 답합니다.
  6. 답변이 끝나면 Claude가 작성하는 스펙을 확인합니다.
예시
친구들과 식비를 나누는 앱을 만들고 싶어. 주요 사용자는 20대 직장인이야. ask user question 도구를 써서 필요한 것을 나에게 질문한 뒤 스펙을 작성해 줘.
  • '더 좋게 만들어', '실수 없이 만들어' 같은 프롬프트는 피합니다.

10. 작업별 모델과 effort 골라 비용 줄이기

작업 비용은 모델, effort(추론 노력), 캐시 세 가지로 정해집니다. 토큰 단가가 아니라 작업당 비용으로 비교하고, 낮은 설정에서 시작해 필요할 때 올립니다.

  1. 작업이 열린 작업(심층 조사, 복잡한 분석)인지 반복 작업(문서 요약, 메일 초안)인지 구분합니다.
  2. 열린 작업이면 Fable 5.1을 고르고 effort를 medium으로 시작합니다.
  3. 결과가 부족하면 effort를 단계적으로 올립니다.
  4. 반복 작업이면 Opus나 Sonnet을 기본으로 쓰고 필요할 때만 Fable로 바꿉니다.
  5. 여러 파일에 걸친 수정처럼 큰 작업에는 high를 씁니다.
  6. 탐색만 하는 서브에이전트는 저렴한 작은 모델부터 적용합니다.
  • Opus 5.5는 Opus 5보다 토큰당 20% 저렴하고 Pro·Max·Team 한도가 25% 더 늘었습니다. 기본 effort는 medium입니다.
  • Claude Code에서 /claude-api prompt-audit를 실행하면 CLAUDE.md와 스킬 지침이 Opus 5.5에 맞게 조정됩니다.
  • 더 똑똑한 모델이 적은 단계로 끝내 총비용이 낮아질 수 있습니다.
  • 구독료 기준은 금액이 아니라 쓰다가 한도에 막히는지 여부입니다. 무료로 불편이 없으면 무료를 씁니다.

11. 내 용도에 맞는 모델을 평가로 고르기

공개 벤치마크는 방향만 알려 주므로 내 작업으로 작은 평가(eval)를 직접 만들어 모델을 비교하는 방법입니다. 새 모델이 나올 때마다 반복할 수 있습니다.

  1. 입력과 성공 기준을 가진 테스트 작업을 모아 평가 데이터 세트를 만듭니다.
  2. 최종 결과뿐 아니라 올바른 단계를 거쳤는지도 점검하는 채점기를 작업마다 붙입니다.
  3. 응답 비교에는 LLM 심사를, 특정 도구 호출이나 인자 확인에는 코드 기반 평가를 씁니다.
  4. 모델과 생각(thinking)·노력(effort) 설정을 바꿔 가며 각 작업을 여러 번 돌립니다.
  5. 로그를 열어 API·도구 호출 실패 같은 인프라 문제를 모델 실패와 분리합니다.
  6. 통과율, 토큰, 비용, 지연 시간을 비교해 중시하는 기준에 맞는 모델과 설정을 고릅니다.
  • 토큰당 가장 싼 모델이 아니라 성공 한 건당 가장 싼 모델을 고릅니다.
  • 결과 편차가 크면 작업 정의나 평가가 불명확하다는 신호입니다.
  • 예시 테스트 케이스 한두 개를 주고 Claude에게 늘려 달라고 하면 50개 정도까지 쉽게 만들 수 있습니다.
  • 프롬프트 캐싱 등 컨텍스트 엔지니어링으로 비용·성능 곡선 자체를 이동시킬 수 있습니다.

12. 기존 프롬프트를 평가로 개선하기

모델을 바꾼 뒤 성능이 떨어진 프롬프트를 평가 세트로 진단하고 정리하는 방법입니다. 실패 유형을 하나씩 고치며 결과를 비교합니다.

  1. 통제 사례, 이전에 실패한 엣지 케이스, 사람에게 넘기거나 거절해야 할 사례를 담은 평가 세트를 만듭니다.
  2. 현재 프롬프트로 평가를 돌려 실패 유형을 확인합니다.
  3. 사실과 다른 역할 설명과 웹에서 복사된 불필요한 내용을 지웁니다.
  4. XML 태그로 역할·가이드라인·정책·말투를 구분해 구조를 만듭니다.
  5. 출력 형식을 정하는 출력 계약을 추가합니다.
  6. 평가를 다시 돌려 실패 유형을 하나씩 고치고 결과를 비교합니다.
  • 가이드라인·정책·데이터를 사람이 구분하기 어려우면 모델도 구분하기 어렵습니다.
  • 실행마다 편차가 있으니 한 번의 결과로 단정하지 않습니다.
  • 금지 항목을 길게 나열하는 방식은 피합니다.
  • 실패 원인이 모델 문제가 아니라 프롬프트 안의 상충하는 정책일 수 있습니다.
