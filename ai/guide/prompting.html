1. 구체적으로 질문해 원하는 답 얻기

AI에게 막연히 묻지 않고 상황·대상·형식을 구체적으로 말하는 가장 기본적인 방법입니다. 처음 만난 똑똑한 친구에게 설명하듯 쓰면 한 번에 쓸 만한 답이 나옵니다.

  1. 내 상황과 대상을 먼저 적습니다 (예: 70대 부모님과 2박 3일 서울 여행, 조용하고 걷기 편한 곳).
  2. 표로 정리해 줘처럼 원하는 결과 형식을 말합니다.
  3. 말투나 읽는 사람을 정합니다 (예: 엄마가 딸에게 말하듯 따뜻하게).
  4. 답을 받은 뒤 이어서 질문해 내용을 고치거나 보탭니다.
  5. AI가 되물으면 그 질문에 답해 줍니다.
  6. 답이 짧으면 지금보다 두 배로 답변해 줘처럼 분량을 조정합니다.
  7. 마지막에 이거 최신 내용 맞아? 출처가 어디야로 점검합니다.
예시
70대 부모님과 2박 3일 서울 여행을 가려고 해. 조용하고 걷기 편한 곳 위주로 일정을 표로 정리해 줘. 말투는 엄마가 딸에게 말하듯 따뜻하게 부탁해.
  • 타이핑이 귀찮으면 음성 입력을 쓰고, 체크 표시 후 화살표를 눌러 보냅니다.
  • 의료·법률·금융 정보는 틀릴 수 있으니 다른 자료로 재확인합니다.

2. POWER 5원칙으로 프롬프트 쓰기

프롬프트를 페르소나·아웃컴·와이(이유)·예시·제한 사항 다섯 요소로 나눠 쓰는 틀입니다. 처음부터 구체적으로 쓸수록 한 번에 원하는 결과가 나올 가능성이 높습니다.

  1. P(페르소나): AI에게 역할을 줍니다 (예: 너는 10년 경력의 영양사이자 개인 트레이너야).
  2. O(아웃컴): 원하는 결과를 구체적으로 씁니다 (예: 주간 식단 계획, 저녁 운동 루틴).
  3. W(왜): 필요한 이유와 내 상황·목표를 알립니다 (예: 30대 직장인, 두 달 동안 5kg 감량).
  4. E(예시): 원하는 형식의 예시를 붙여 넣습니다. 없으면 생략합니다.
  5. R(제한 사항): 피할 것을 알립니다 (예: 전문 용어는 빼 줘, 200자를 넘기지 마).
  6. 작성한 내용을 한 번에 요청하고 결과를 확인합니다.
예시
너는 10년 경력의 영양사이자 개인 트레이너야. 30대 직장인이 두 달 동안 5kg을 빼려고 하고, 저녁에만 운동할 수 있어. 주간 식단 계획과 저녁 운동 루틴, 진행 상황 체크표를 만들어 줘. 전문 용어는 빼고 쉬운 말로 써 줘.
  • 다섯 가지를 모두 쓸 필요는 없고 최소 두세 가지를 포함하면 좋습니다.
  • 다섯 가지 중 예시를 구체적으로 줄수록 원하는 결과에 가까워집니다.

3. 대화로 결과 다듬고 긴 글 단계별로 쓰기

한 번에 완벽한 프롬프트를 쓰기 어려울 때 대화하듯 나눠 요청해 결과를 원하는 방향으로 맞추는 방법입니다. 긴 글은 구조를 먼저 확정한 뒤 본문으로 넘어가면 흐름이 안정됩니다.

  1. 역할을 먼저 말합니다 (예: 너는 10년차 주부야).
  2. 다음 메시지에 결과물을 요청합니다 (예: 10명 집들이, 3시간 안에 끝낼 요리 5가지).
  3. 마음에 들지 않는 부분은 제한 사항으로 바꿉니다 (예: 잡채는 요리하기 싫어).
  4. 긴 글이면 구조를 먼저 만들어줘라고 요청하고 순서를 고칩니다.
  5. 구조가 확정되면 대본으로 만들어 줘라고 요청합니다.
  6. 마지막에 지금까지 내용을 한 번에 정리해 줘로 최종본을 받습니다.
예시
제미나이를 주제로 유튜브 영상을 만들고 싶어. 구조를 먼저 만들어줘. 분량은 5분 정도로 하고, 초등학생도 이해할 수 있게 써 줘.
  • 분량이나 글자 수를 지정하면 결과가 더 맞게 나옵니다.
  • 결과가 아쉬우면 이게 최적의 동선이 맞아?처럼 다시 점검을 요청합니다.

4. 음성으로 말해서 프롬프트 만들기

타이핑 대신 길게 말해 입력하면 시간이 줄고 생각도 정리됩니다. 음성 입력 도구 Typeless는 군더더기를 지워 정돈된 문장으로 바꿔 줍니다.

  1. Typeless로 두서없이 하고 싶은 요청을 말해 입력합니다.
  2. 입력된 문장을 드래그로 선택합니다.
  3. Ask Anything 단축키를 누릅니다.
  4. 무엇이든 물어보세요 칸에 '더 잘 알아듣는 프롬프트로 다듬어 줘. 타겟·톤·결과물 형식을 구체적으로 넣어 줘'라고 말합니다.
  5. 약 3초 후 나온 프롬프트를 필요하면 고쳐서 AI에 입력합니다.
예시
더 잘 알아듣는 프롬프트로 다듬어 줘. 타겟·톤·결과물 형식을 구체적으로 넣어 줘.
  • 같은 방식으로 '더 짧게', '더 친근하게' 같은 수정도 요청할 수 있습니다.
  • 전문 용어는 가끔 틀릴 수 있으니 개인 사전에 등록하거나 확인합니다.
  • 무료 사용량은 주당 8,000단어입니다.

5. 내 정보와 맥락을 AI에게 알려 주기

AI의 답은 내가 준 맥락만큼 좋아집니다. 나에 대한 정보와 작업 상황을 충분히 알려 주고, 회사 일에 쓰기 전에 학습 설정을 점검하는 방법입니다.

  1. 무료 버전으로 먼저 써 보고, 한도에 막힐 때 유료로 넘어갑니다.
  2. 하루 30분 정도 AI에게 질문하고 AI가 나에게 질문하도록 유도합니다.
  3. 내가 누구이고 무슨 작업 중인지, 좋은 결과가 어떤 것인지 알려 줍니다.
  4. 파일·캡처 같은 자료를 많이 붙여 줍니다.
  5. 회사 일에 쓰기 전 ChatGPT 설정(Settings)의 Data controls에서 Improve the model for everyone을 끕니다.
  6. 개인정보와 기밀 정보는 입력하지 않습니다.
  • 완벽한 프롬프트보다 상황과 기준을 충분히 알려 주는 것이 중요합니다.
  • AI가 준 답은 직접 읽고 판단해야 합니다.
  • 작업별로 프로젝트를 나눠 쓰고, 새 채팅에서는 이전 내용을 가져오라고 요청할 수 있습니다.

6. 반복 업무를 프로젝트·Gems로 저장하기

자주 하는 작업의 역할·지침·예시를 한 번 저장해 두면 매번 긴 프롬프트를 쓰지 않고 주제만 넣어도 같은 형식으로 결과가 나옵니다. ChatGPT의 프로젝트와 제미나이의 Gems가 대표적입니다.

  1. 반복되는 작업(대본, 이메일, 보고서 등)을 정합니다.
  2. ChatGPT는 프로젝트를, 제미나이는 Gems를 새로 만듭니다.
  3. 지침에 역할·목표·형식·추가 조건을 적습니다.
  4. 원하는 결과의 예시를 두세 개 붙입니다.
  5. 내 기존 글을 예시 파일로 주면 말투까지 분석해 지침을 만들어 주기도 합니다.
  6. 새 채팅에서 주제만 입력해 같은 형식으로 나오는지 확인합니다.
  7. 원치 않는 표현은 '이렇게는 쓰지 마'라고 지침에 추가합니다.
  • 예시 없이 묻는 것(제로샷)보다 예시를 주는 것(퓨샷)이 원하는 결과에 가깝습니다.
  • ChatGPT 프로젝트는 유료 버전에서 쓸 수 있고, 제미나이 Gems는 무료 계정으로도 만들 수 있습니다.

7. AI 답변 검증하고 환각 줄이기

AI는 그럴듯하지만 사실이 아닌 내용을 만들거나 사용자가 원하는 답에 맞춰 줄 수 있습니다. 질문의 중요도에 따라 확인 강도를 조절하고 출처를 직접 확인하는 방법입니다.

  1. 틀렸을 때 어떤 일이 생기는지 스스로 묻고 확인 강도를 정합니다.
  2. 미리 모르면 모른다고 말해 달라고 허용합니다.
  3. 주장마다 근거가 되는 출처를 요청합니다.
  4. 제시된 출처를 직접 열어 실제로 그 내용이 있는지 확인합니다.
  5. 이 결정에 대한 가장 강력한 찬성과 반대 논거는 무엇인가요?처럼 중립적으로 질문합니다.
  6. 의심스러우면 얼마나 확신하는지, 틀릴 만한 부분이 있는지 묻습니다.
  7. 새 대화를 열어 그 답변의 오류를 찾아 달라고 하거나 다른 AI로 교차 검증합니다.
예시
이 결정에 대한 가장 강력한 찬성 논거와 반대 논거를 각각 알려 줘. 모르는 부분은 모른다고 말해도 괜찮아.
  • 숫자·날짜·인용·최근 사건은 특히 다시 확인합니다.
  • AI가 실제로 없는 출처를 만들어 낼 수도 있습니다.
  • 자신 있는 말투나 깔끔한 결과물은 정확성의 증거가 아닙니다.
  • 가격·뉴스 같은 최신 정보는 웹 검색을 했는지 직접 물어봅니다.

8. AI 답을 내 이해로 바꿔 쓰기

AI가 만든 결과를 그대로 전달만 하면 내가 줄 수 있는 가치가 없습니다. AI를 과외 선생님으로 세우거나 빈 문서에서 한 줄씩 함께 쓰며 내용을 이해하는 방법입니다.

  1. 에이전트를 많이 돌려 관련 자료를 모읍니다.
  2. 여러 AI로 자료를 검증해 핵심만 추립니다.
  3. 완성된 보고서는 그대로 두고 빈 문서를 새로 엽니다.
  4. 문제 정의, 해결안, 검증 등 섹션 양식을 정합니다.
  5. AI가 한 문단 쓰면 읽고 모르는 부분을 질문하며 한 줄씩 채웁니다.
  6. 새 분야를 배울 때는 네가 앞으로 과외 선생님으로서 나를 공부할 수 있도록 도와줘라고 요청해 커리큘럼을 받습니다.
예시
네가 앞으로 과외 선생님으로서 내가 에이전트 메모리를 공부할 수 있도록 도와줘. 커리큘럼부터 만들어 줘.
  • 30장 보고서를 그대로 전달하면 내가 줄 가치가 없습니다.
  • 답변을 이해하지 않고 복사·붙여 넣기만 하면 실력이 늘지 않습니다.
  • 책을 읽은 뒤 AI에게 저자 역할을 시켜 질문해 볼 수 있습니다.

9. 에이전트 추천에 휘둘리지 않고 결정하기

연구에서 분석가들은 에이전트가 기운 쪽을 86% 따랐고, 자기 결정이라고 착각하기 쉬웠습니다. 추천을 그대로 받아들이지 않고 내 기준으로 결정하게 하는 방법입니다.

  1. 에이전트가 방법을 추천하기 전에 내 우선순위부터 묻게 합니다.
  2. 결정이 어려우면 작고 저렴한 모델로 여러 버전의 프로토타입을 병렬로 만듭니다.
  3. 프로토타입을 보고 내가 결정한 뒤 프로토타입은 버립니다.
  4. 결정한 내용을 에이전트에게 전달합니다.
  5. 에이전트가 고른 안(A)에 대해 What would change your advice?라고 묻습니다.
  6. 답을 보고 안(B)이 최적이 되는 조건이 현재 상황에 해당하는지 판단합니다.
예시
추천하기 전에 내 우선순위부터 물어봐 줘. 그리고 네가 고른 안에 대해 What would change your advice?
  • 추천 답을 그대로 선택하는 습관이 가장 쉬운 함정입니다.
  • 프로토타입은 결정용이므로 최고 모델을 쓸 필요가 없습니다.

10. 작업에 맞는 모델과 effort 고르기

작업 비용은 모델, effort(추론 노력), 캐시로 정해집니다. 작업 성격에 따라 모델과 노력 수준을 고르면 품질을 지키면서 사용량을 아낄 수 있습니다.

  1. 작업이 열린 작업(심층 조사, 복잡한 분석)인지 반복 작업(요약, 메일 초안)인지 구분합니다.
  2. 기본 시작점으로 중간 노력 수준의 Opus 5.5를 씁니다.
  3. 결과가 부족하면 모델을 바꾸기 전에 먼저 effort를 단계적으로 올립니다.
  4. 크고 모호한 장기 작업은 Fable, 범위가 분명한 작업은 Sonnet, 요약·분류 같은 대량 작업은 Haiku를 씁니다.
  5. 여러 파일에 걸친 수정에는 high를 씁니다.
  6. 탐색만 하는 서브에이전트는 작은 모델로 돌려 비용을 아낍니다.
  • 토큰 단가가 아니라 작업당 비용(성공 한 건당 비용)으로 비교합니다.
  • Fable은 토큰당 가격이 Opus의 두 배이고, Sonnet은 Opus의 절반입니다.
  • 가용성과 사용 한도는 요금제마다 다릅니다.
  • 예전 방식: 모델을 먼저 바꿔 보았지만, 최근에는 노력 수준을 먼저 올리라고 안내합니다.

11. 내 용도에 맞게 평가로 모델 비교하기

공개 벤치마크는 방향만 알려 주므로, 내 작업으로 작은 평가를 직접 만들어 모델과 설정을 비교하는 방법입니다. 새 모델이 나올 때마다 같은 절차를 반복할 수 있습니다.

  1. 입력과 성공 기준을 가진 테스트 작업을 모아 평가 데이터 세트를 만듭니다.
  2. 예시 케이스 한두 개를 주고 Claude에게 더 늘려 달라고 요청합니다.
  3. 최종 결과뿐 아니라 올바른 단계를 거쳤는지도 점검하는 채점기를 붙입니다.
  4. 도구 호출 확인에는 코드 기반 평가를, 응답 비교에는 LLM 심사를 씁니다.
  5. 모델과 생각·노력 설정을 바꿔 가며 각 작업을 여러 번 돌립니다.
  6. 로그에서 인프라 실패와 모델 실패를 분리합니다.
  7. 통과율, 토큰, 비용, 지연 시간을 비교해 기준에 맞는 조합을 고릅니다.
  • 결과 편차가 크면 작업 정의나 평가가 불명확하다는 신호입니다.
  • 판정 모델도 틀릴 수 있으니 여러 채점기를 조합합니다.
  • 평가 없이 수정하면 다른 곳이 망가져도 알기 어렵습니다.

12. Claude Code 컨텍스트 아껴 쓰기

컨텍스트는 Claude의 작업 기억으로, 읽은 파일·명령·메시지가 모두 공간을 차지합니다. 한도에 가까워지면 세부 내용이 사라질 수 있어 관리 요령이 필요합니다.

  1. 같은 기능 작업을 이어갈 때는 /compact로 압축합니다.
  2. 새 기능을 시작할 때는 /clear로 비웁니다.
  3. 요청은 구체적으로 해서 불필요한 탐색을 줄입니다.
  4. 관련 없는 MCP 서버는 끕니다.
  5. 답만 필요한 조사는 서브에이전트에 맡깁니다.
  6. 반복되는 작업 방법은 스킬로 만들어 필요할 때만 불러오게 합니다.
  • MCP 서버는 기본적으로 모든 도구를 컨텍스트에 올립니다.
  • 스킬은 이름과 설명만 먼저 불러와 컨텍스트를 아낍니다.
  • 실수가 나오면 다시 시키지 말고 CLAUDE.md나 스킬에 적어 같은 실수를 막습니다.
  • 최신 모델에서는 컨텍스트를 최소한만 주고 모델이 알아서 찾게 하는 방식을 권합니다.
