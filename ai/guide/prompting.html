프롬프트·활용 요령

이 분야에서는 AI에게 원하는 답을 받아 내는 질문법과 답을 검증하는 요령, 작업에 맞는 모델과 effort를 골라 비용과 사용량을 아끼는 방법을 다룹니다. 처음이라면 '더 나은 답 얻기'와 '답변 검증하기'로 기본을 익히세요. 그다음 음성 메모로 발표 자료 만들기 같은 실전 활용을 해 보고, 모델·effort 고르기와 비용·컨텍스트 관리로 넘어가면 됩니다.

1. AI에게서 더 나은 답 얻기

AI는 사용자의 메시지와 첨부 문서, 대화 기록 전체를 보고 다음 단어를 예측하며 답을 만듭니다. 그래서 내가 누구이고 어떤 결과를 원하는지 알려 줄수록 답이 좋아집니다. 메일 초안, 보고서 문장, 아이디어 정리처럼 AI에게 글을 맡길 때 매번 쓰는 기본기입니다.

  1. 내가 누구이고 지금 어떤 작업을 하는지 먼저 적습니다.
  2. 좋은 결과가 어떤 모습인지(분량, 어조, 독자 등)를 함께 적습니다.
  3. 가격이나 뉴스처럼 최신 정보가 필요하면 웹 검색을 했는지 묻거나 검색을 요청합니다.
  4. 검색 결과로 답했다면 제시된 출처를 열어 내용이 맞는지 확인합니다.
  5. 초안을 여러 버전으로 받거나 다른 어조로 다시 써 달라고 요청합니다.
  6. 틀리면 문제가 되는 사실은 직접 다시 확인합니다.
예시
저는 마케팅팀 3년 차 대리이고, 다음 주 신제품 출시를 거래처에 알리는 메일을 쓰고 있습니다. 정중하지만 너무 딱딱하지 않게, 5문장 안으로 써 주세요. 어조를 달리한 버전 3개를 보여 주세요.
  • AI는 학습 시점 이후의 사실을 검색 없이는 확실히 알지 못합니다. 웹 검색을 했으리라 단정하지 말고 직접 물어보세요.
  • AI는 정해진 답을 꺼내는 게 아니라 매번 새로 만들기 때문에 여러 버전을 요청할 수 있습니다.
  • 자신 있는 말투나 깔끔한 결과물이 정확하다는 증거는 아닙니다.

2. AI 답변을 검증하며 쓰기

AI는 그럴듯하지만 사실이 아닌 내용을 지어내거나(환각), 사용자가 듣고 싶은 말에 맞춰 주기도 합니다(아첨). 질문이 얼마나 중요한지에 따라 확인 강도를 다이얼처럼 조절하면 됩니다. 숫자, 출처, 건강·법률·금전 관련 답은 반드시 확인하세요.

  1. 이 답이 틀리면 어떤 일이 생기는지 스스로 묻고 확인 강도를 정합니다.
  2. 질문하기 전에 모르면 모른다고 말해 달라고 미리 말해 둡니다.
  3. 원하는 답을 흘리지 말고 중립적으로 질문합니다.
  4. 답의 근거가 되는 출처를 요청합니다.
  5. 제시된 출처를 직접 열어 그 내용이 실제로 있는지 확인합니다.
예시
이 결정에 대한 가장 강력한 찬성과 반대 논거는 무엇인가요? 근거가 되는 출처도 함께 알려 주고, 확실하지 않은 부분은 모른다고 말해 주세요.
  • 파티 주제 브레인스토밍은 크게 확인할 필요가 없지만, 상사에게 보일 슬라이드의 통계는 반드시 확인합니다.
  • AI가 실제로 없는 출처를 그럴듯하게 지어낼 수도 있으니 링크와 문서를 꼭 열어 봅니다.
  • 잘 알려진 주제는 비교적 정확하지만, 마이너한 세부 사항이나 최근 사건, 비공개 정보는 틀릴 가능성이 높습니다.
  • AI는 자기가 불확실한 부분을 항상 알려 주지 않습니다. 판단은 사용자 몫입니다.

3. 음성 메모로 발표 자료 만들기

빈 슬라이드 앞에서 막막할 때, 하고 싶은 말을 먼저 음성으로 녹음하고 Claude에게 발표 자료로 만들어 달라고 하는 방법입니다. 서식은 AI에게 맡기고 사람은 내용에 집중할 수 있습니다.

  1. 산책하거나 이동하는 동안 휴대폰 음성 메모로 발표에서 하고 싶은 말을 모두 녹음합니다.
  2. 녹음을 글로 받아 적습니다.
  3. 받아 적은 글을 Claude에게 보내고 발표 자료로 만들어 달라고 요청합니다.
  4. 결과물에서 오타나 문구처럼 작은 수정은 직접 고칩니다.
  5. 구성 변경처럼 큰 수정은 댓글로 Claude에게 요청합니다.
예시
아래는 제가 음성 메모로 녹음한 발표 내용을 받아 적은 글입니다. 이 내용을 바탕으로 발표 슬라이드를 만들어 주세요.
  • 영상에서는 Claude가 회사 브랜드 스타일을 이미 알고 있어 폰트나 템플릿을 따로 찾지 않았습니다.
  • 처음부터 정리된 글을 쓰려고 하지 말고 생각나는 대로 모두 말하는 것이 요령입니다.

4. 작업에 맞는 모델과 effort 고르기

작업 비용은 모델, effort(추론 노력), 캐시 세 가지로 정해집니다. 더 똑똑한 모델이 적은 단계로 일을 끝내 오히려 총비용이 낮을 때도 있습니다. 작업 종류에 따라 모델과 effort를 고르면 품질과 사용량 사이에서 균형을 잡을 수 있습니다.

  1. 작업이 열린 작업(심층 조사, 복잡한 분석, 긴 에이전트 작업)인지 반복 작업(문서 요약, 메일 초안, 보고서 데이터 추출)인지 구분합니다.
  2. 반복 작업이면 Opus나 Sonnet을 기본으로 씁니다.
  3. Opus 5.5는 기본 effort인 medium으로 시작합니다.
  4. 여러 파일이나 프로젝트 전체를 바꾸는 작업이면 effort를 high로 올립니다.
  5. 열린 작업이면 Fable 5.1을 고르고 effort를 medium으로 시작합니다.
  6. 결과가 부족할 때만 effort를 한 단계씩 올립니다.
  7. 탐색처럼 정해진 일만 하는 서브에이전트는 작은 모델로 돌려 비용을 아낍니다.
  • 토큰 단가가 아니라 작업 한 건당 비용으로 비교합니다. Opus 5.5는 필요한 토큰이 적어 작업당 비용이 Opus 5보다 약 40% 낮습니다.
  • 강력한 모델일수록 낮은 effort로 시작해 필요할 때 올립니다. Fable 5.1 medium은 Fable 5 max와 비슷한 결과를 약 5분의 1 비용으로 냈습니다.
  • 예전 방식: 일상 작업도 Opus 5로 돌렸지만, 지금은 더 빠르고 저렴한 Opus 5.5가 일상 모델로 권장됩니다. 같은 버그 수정에서 5시간 한도를 약 4%만 썼습니다(Opus 5는 약 6%).
  • 관리자는 조직 설정에서 사용할 수 있는 모델, effort 상한, 기본값을 정할 수 있습니다.

5. CLAUDE.md를 새 모델에 맞게 다듬기

새 모델이 나오면 예전 모델에 맞춰 쓴 CLAUDE.md와 스킬 지침이 잘 맞지 않을 수 있습니다. Claude Code의 점검 명령으로 지침을 Opus 5.5에 맞게 조정할 수 있습니다.

  1. CLAUDE.md가 있는 프로젝트에서 Claude Code를 엽니다.
  2. /claude-api prompt-audit를 실행합니다.
  3. CLAUDE.md와 스킬 지침이 Opus 5.5에 맞게 조정된 내용을 확인합니다.
예시
/claude-api prompt-audit
  • API를 쓰지 않고 Claude Code만 써도 이 명령을 쓸 수 있습니다.

6. 긴 작업의 비용·컨텍스트 줄이기

오래 실행되는 에이전트 작업은 컨텍스트가 쌓일수록 비용이 늘고 성능이 떨어지기 쉽습니다. Claude 플랫폼의 프롬프트 캐싱, 도구 검색, 프로그램 방식 도구 호출, 컴팩션으로 비용을 줄이고 컨텍스트를 가볍게 유지할 수 있습니다. 개발자나 에이전트를 직접 구성하는 사람에게 맞는 내용입니다.

  1. 작업 비용이 모델, effort, 캐시 세 가지로 정해진다는 점을 먼저 확인합니다.
  2. 같은 내용을 반복해서 보내는 작업에는 프롬프트 캐싱을 적용해 비용을 줄입니다.
  3. 도구가 많은 에이전트는 도구 검색을 써서 필요한 도구만 컨텍스트에 불러옵니다.
  4. 프로그램 방식 도구 호출로 중간 결과가 컨텍스트에 쌓이지 않게 합니다.
  5. 대화가 길어지면 컴팩션으로 컨텍스트를 압축해 작업을 이어 갑니다.
  • 캐시를 많이 쓰는 긴 에이전트 작업에는 Fable 5.1이 특히 유리합니다. 캐시 읽기 비용이 Fable 5보다 75% 낮아 긴 작업에서 최대 약 45%까지 비용이 줄어듭니다.
  • 세션에서는 어드바이저 전략으로 적은 비용에 품질을 높이는 방법도 소개했습니다. 자막이 없어 구체적인 설정 방법은 정리하지 못했으므로 공식 영상에서 직접 확인하세요.
