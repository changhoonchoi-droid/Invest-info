1. 맥락을 알려 주고 더 나은 답 받기

AI는 사용자 메시지, 올린 문서, 대화 기록 전체를 보고 다음 단어를 예측하며 답을 만듭니다. 그래서 내가 누구이고 무슨 일을 하는지 알려 줄수록 답이 좋아집니다. 정해진 답을 꺼내는 게 아니라 새로 만들어 내는 것이므로, 여러 버전을 요청해 고를 수도 있습니다.

  1. 내가 누구이고 지금 무슨 작업을 하는지 첫 메시지에 적습니다.
  2. 좋은 결과가 어떤 모습인지(분량, 대상 독자, 형식 등)를 함께 알려 줍니다.
  3. 가격·뉴스처럼 최신 정보가 필요하면 웹 검색을 했는지 묻거나 검색해 달라고 요청합니다.
  4. 검색 결과로 답했다면 제시된 출처를 직접 열어 내용이 맞는지 확인합니다.
  5. 초안이 나오면 여러 버전으로 다시 써 달라거나 다른 어조로 바꿔 달라고 요청합니다.
  6. 틀리면 곤란한 사실은 직접 다시 확인한 뒤 사용합니다.
예시
저는 중견 제조사의 마케팅팀 대리이고, 다음 주 팀장님께 올릴 신제품 홍보 메일 초안을 쓰고 있습니다. 대상은 기존 거래처 구매 담당자이고, 좋은 결과는 5문장 안팎의 정중하지만 간결한 메일입니다. 어조를 달리한 초안 3가지를 써 주세요.
  • AI가 웹 검색을 했다고 단정하지 말고 직접 물어보세요. 모델은 훈련 시점 이후의 사실을 검색 없이는 확실히 알지 못합니다.
  • 자신 있는 말투나 깔끔한 결과물은 정확성의 증거가 아닙니다.
  • '더 좋게 만들어', '실수 없이 만들어'처럼 막연한 요청보다 구체적인 상황과 기준을 주는 편이 낫습니다.

2. AI 답변을 검증해 환각 줄이기

AI는 그럴듯하지만 사실이 아닌 내용을 만들거나(환각), 사용자가 듣고 싶은 말에 맞춰 동의하는(아첨) 경우가 있으며, 어느 때나 똑같이 확신 있게 말합니다. 숫자·출처·건강·법률·금전처럼 틀리면 곤란한 내용을 다룰 때 이 순서로 확인하면 됩니다.

  1. 틀렸을 때 어떤 일이 생기는지 스스로 묻고 확인을 얼마나 꼼꼼히 할지 정합니다.
  2. 질문하기 전에 모르면 모른다고 말해 달라고 미리 허용합니다.
  3. 원하는 답을 흘리지 말고 찬성과 반대를 함께 묻는 식으로 중립적으로 질문합니다.
  4. 주장마다 근거가 되는 출처를 찾아 달라고 요청합니다.
  5. 제시된 출처를 직접 열어 그 내용이 실제로 있는지 확인합니다.
  6. 답이 의심스러우면 얼마나 확신하는지, 틀릴 만한 부분이 어디인지 묻습니다.
  7. 새 대화를 열어 그 답변의 오류를 찾고 출처가 맞는지 확인해 달라고 합니다.
  8. 중요한 작업은 믿을 만한 자료와 교차 확인합니다.
예시
이 결정에 대한 가장 강력한 찬성과 반대 논거는 무엇인가요? 주장마다 근거가 되는 출처를 붙여 주시고, 모르는 부분은 모른다고 말해 주세요.
  • 파티 주제 브레인스토밍은 느슨하게, 상사에게 보일 슬라이드의 통계는 반드시 검증하세요. 신뢰는 스위치가 아니라 다이얼입니다.
  • 숫자·날짜·인용, 잘 알려지지 않은 주제, 최근 사건에서 환각 가능성이 높습니다.
  • AI가 실제로 없는 출처를 그럴듯하게 만들어 낼 수도 있으니 링크는 꼭 열어 보세요.
  • 환각이 줄어들수록 확인을 건너뛰기 쉬워지니 오히려 더 주의하세요.

3. AI 답변의 편향 점검하기

AI는 인터넷의 방대한 글을 학습하면서 고정관념이나 정치적 편향, 언어별 품질 차이를 보일 수 있습니다. 답이 한쪽으로 치우쳤다고 느낄 때 균형 잡힌 답을 다시 끌어내는 방법입니다.

  1. 답변이 한쪽으로 치우쳤다고 느끼면 바로 그 점을 짚어 반박합니다.
  2. 더 섬세하고 균형 잡힌 접근으로 다시 답해 달라고 요청합니다.
  3. 듣기 좋은 말보다 솔직한 논의를 원한다고 분명히 말합니다.
  4. 근거를 모아 달라고 하고, 받은 링크를 직접 열어 확인합니다.
  5. 같은 질문을 다른 관점에서 다시 물어 답의 깊이와 성의가 비슷한지 비교합니다.
예시
방금 답변은 한쪽 입장에 치우친 것 같습니다. 저는 솔직한 논의를 원합니다. 양쪽 관점을 같은 깊이로 정리하고, 각 주장의 근거 자료 링크를 붙여 주세요.
  • 정치 주제가 아닌 일반 업무 대화에서도 똑같이 유용합니다.
  • 같은 주제를 두 관점으로 나눠 묻는 '짝지은 질문'은 Anthropic이 편향을 평가할 때 쓰는 방식이기도 합니다.

4. 음성 메모로 발표 자료 만들기

빈 슬라이드 앞에서 막막할 때, 하고 싶은 말을 먼저 음성으로 녹음하고 그 글을 Claude에게 넘겨 발표 자료로 만드는 방법입니다. 서식 작업은 줄이고 내용과 아이디어에 시간을 쓸 수 있습니다.

  1. 산책하거나 이동하면서 휴대폰 음성 메모로 발표에서 하고 싶은 말을 모두 녹음합니다.
  2. 녹음한 내용을 글로 받아 적습니다.
  3. 받아 적은 글을 Claude에게 보내 발표 자료로 만들어 달라고 요청합니다.
  4. 결과물에서 작은 수정은 직접 고칩니다.
  5. 구성 변경처럼 큰 수정은 댓글로 Claude에게 요청합니다.
예시
아래는 제가 산책하며 녹음한 음성 메모를 받아 적은 글입니다. 이 내용으로 팀 회의용 발표 자료를 만들어 주세요.
  • 말로 할 때는 정리하려 애쓰지 말고 떠오르는 대로 다 녹음하는 것이 요령입니다.
  • Claude가 회사 브랜드 스타일을 알고 있으면 폰트나 템플릿을 따로 찾을 필요가 없습니다.

5. Claude Code 컨텍스트 관리하기

컨텍스트는 Claude의 작업 기억으로, 읽은 파일·실행한 명령·주고받은 메시지가 모두 공간을 차지합니다. 한도에 가까워지면 자동으로 압축되지만 세부 내용이 사라질 수 있으므로, 직접 정리해 주면 답의 정확도와 비용을 함께 지킬 수 있습니다.

  1. 같은 기능 작업을 이어가는데 대화가 길어졌다면 /compact로 지금까지의 내용을 압축합니다.
  2. 새 기능이나 전혀 다른 작업을 시작할 때는 /clear로 컨텍스트를 비웁니다.
  3. 요청은 대상 파일이나 원하는 결과를 구체적으로 적어 Claude가 불필요한 파일을 읽지 않게 합니다.
  4. 지금 작업과 관련 없는 MCP 서버는 끕니다.
  5. 답만 필요한 조사는 서브에이전트에게 맡겨 요약만 돌려받습니다.
  6. 자주 쓰는 작업 방법은 MCP 대신 스킬로 만들어 필요할 때만 불러오게 합니다.
예시
/compact
  • MCP 서버는 기본적으로 모든 도구를 컨텍스트에 올리지만, 스킬은 이름과 설명만 먼저 불러와 컨텍스트를 아낍니다.
  • 서브에이전트는 별도 컨텍스트 창을 쓰고 결과 요약만 돌려주므로 메인 대화가 가벼워집니다.
  • 컨텍스트가 크다고 좋은 게 아닙니다. 정답이 든 짧은 프롬프트(약 300토큰)가 전체 기록(약 11만 3,000토큰)보다 더 정확했다는 실험이 있습니다.
  • 최소한의 지침만 주고 필요한 정보는 모델이 알아서 찾아오게 하는 방식이 권장됩니다.

6. 스킬로 작업 방법 한 번만 가르치기

스킬은 Claude에게 어떤 작업 방법을 한 번 가르쳐 두면 관련 요청이 올 때 자동으로 적용되게 하는 마크다운 파일입니다. 매번 같은 설명을 반복하거나, Claude가 같은 실수를 되풀이할 때 쓰면 좋습니다.

  1. 매번 반복해서 설명하는 작업이나 자주 나오는 실수를 하나 고릅니다.
  2. 나만 쓸 스킬이면 홈 디렉터리의 .claude/skills 폴더에 만들 위치를 정합니다.
  3. 팀과 함께 쓸 스킬이면 저장소 루트의 .claude/skills 폴더에 만들 위치를 정합니다.
  4. 그 폴더 안에 SKILL.md 파일을 만들고 작업 방법을 적습니다.
  5. 어떤 요청일 때 이 스킬을 써야 하는지 설명(description)을 분명하게 적습니다.
  6. 실제로 관련 요청을 해 보고 스킬이 자동으로 적용되는지 확인합니다.
  • Claude는 스킬의 설명(description)을 보고 요청과 맞는 스킬을 고르므로, 설명이 곧 스킬의 성패를 가릅니다.
  • CLAUDE.md는 모든 대화에 항상 불러오고, 스킬은 요청이 맞을 때만 불러옵니다. 늘 지켜야 할 규칙은 CLAUDE.md, 특정 작업 방법은 스킬에 두세요.
  • 실수가 나오면 다시 시키기보다 CLAUDE.md나 스킬에 적어 같은 실수를 막는 것이 권장됩니다.
  • 프로젝트 스킬은 저장소를 클론하면 팀 전체가 자동으로 받습니다.

7. Claude에게 질문받으며 요구사항 정하기

원하는 결과를 처음부터 자세히 적는 대신, 관심 영역만 알려 주고 Claude가 질문을 던져 요구사항을 끌어내게 하는 방법입니다. 모델이 강력해질수록 제약을 줄이고 이렇게 대화로 스펙을 만드는 편이 결과가 좋다고 합니다.

  1. Claude Code에서 Shift+Tab을 눌러 auto mode로 전환합니다.
  2. /effort로 노력 수준을 설정합니다.
  3. 프롬프트에는 만들 것의 관심 영역(예: 대상 사용자)만 적고 결과는 과하게 지정하지 않습니다.
  4. 같은 프롬프트에 ask user question 도구를 써서 나에게 질문하라고 명시합니다.
  5. Claude가 띄우는 질문에 차례로 답합니다.
  6. 답변이 끝나면 Claude가 작성한 스펙을 읽고 확인합니다.
예시
회사 동료들이 점심 식대를 나눠 내는 정산 앱을 만들고 싶어. 대상 사용자는 스마트폰에 익숙하지 않은 직장인이야. 결과를 내가 미리 정하지 않을 테니, ask user question 도구로 나에게 질문하면서 요구사항을 정리하고 스펙을 작성해 줘.
  • '더 좋게 만들어', '실수 없이 만들어' 같은 막연한 프롬프트는 피합니다.
  • 스펙을 빠르게 여러 번 고칠 때는 /fast 모드가 유용합니다.
  • 긴 마크다운 대신 정보 밀도가 높은 HTML 파일로 계획을 받아 사람이 먼저 검토하는 방법도 소개되었습니다.
  • 예전 방식: 계획 모드(Shift+Tab으로 전환)로 읽기 전용 분석과 계획을 먼저 받았지만, 최신 모델에서는 계획 단계 없이 오토 모드를 쓰는 쪽으로 바뀌었습니다.

8. 작업에 맞는 모델과 effort 고르기

작업 비용은 모델, effort(추론 노력), 캐시 세 가지로 정해집니다. 더 똑똑한 모델이 적은 단계로 끝내 오히려 총비용이 낮을 수 있으므로, 작업 종류에 따라 모델과 effort를 골라 쓰면 품질과 사용량을 함께 관리할 수 있습니다.

  1. 지금 작업이 열린 작업(심층 조사, 복잡한 분석, 장시간 에이전트)인지 반복 작업(문서 요약, 메일 초안, 보고서 데이터 추출)인지 구분합니다.
  2. 열린 작업이면 Fable 5.1을 고르고 effort를 medium으로 시작합니다.
  3. 반복 작업이면 Opus나 Sonnet을 기본으로 씁니다.
  4. Opus 5.5는 기본 effort인 medium으로 대부분의 작업을 처리합니다.
  5. 여러 파일이나 프로젝트 전체를 바꾸는 수정이면 effort를 high로 올립니다.
  6. 결과가 부족할 때만 effort를 단계적으로 올리거나 더 강한 모델로 바꿉니다.
  7. 탐색만 하는 서브에이전트는 작은 모델로 돌려 비용을 아낍니다.
  • 토큰 단가가 아니라 작업 한 건당 비용으로 비교하세요. Opus 5.5는 Opus 5보다 토큰당 20% 싸지만 필요한 토큰도 적어 작업당 비용은 약 40% 낮습니다.
  • 더 강력한 모델일수록 낮은 effort로 시작해 필요할 때 올리는 것이 요령입니다.
  • max effort는 low보다 시간·토큰을 약 10배, high는 약 2배 씁니다.
  • 예전 방식: 고르기 어려우면 extra high를 권했지만, 최신 Opus 5.5·Fable 5.1 영상에서는 medium으로 시작해 올리는 방식을 권합니다.

10. 내 사용 패턴으로 모드 추천받기

모드(Mods)는 Claude Code의 모습과 행동 방식을 바꾸는 작은 프로그램으로, Claude가 작업할 때 나가는 신호를 듣고 지켜보거나 살짝 고치거나 대신 처리합니다. 내 세션 기록을 분석해 흐름을 돕고 비용을 아끼는 모드를 추천받아 만들 수 있습니다.

  1. Claude Code 세션 로그를 최대한 훑어 내가 자주 반복하는 말과 작업을 파악해 달라고 요청합니다.
  2. 흐름을 돕고 비용을 아끼며 집중하게 해 줄 모드 다섯 개를 추천해 달라고 요청합니다.
  3. 추천마다 붙은 패턴과 근거를 읽어 봅니다.
  4. 마음에 드는 번호를 골라 만들어 달라고 요청합니다.
예시

  • 스킬·MCP가 밖에서 지식과 도구를 건네는 방식이라면, 모드는 작업 환경 자체를 바꿉니다.

11. 평가 세트로 프롬프트 개선하기

평가(eval)는 특정 용도에서 AI가 얼마나 잘하는지 재는 체계적 테스트로, '느낌'을 확인 가능한 신호로 바꿔 줍니다. 모델을 바꾼 뒤 성능이 떨어졌거나 업무용 프롬프트를 다듬고 싶을 때, 평가를 기준으로 하나씩 고쳐 나가는 방법입니다.

  1. 평소 잘 되는 통제 사례, 이전에 실패한 까다로운 사례, 사람에게 넘기거나 거절해야 할 사례를 모아 평가 세트를 만듭니다.
  2. 사례가 부족하면 상황을 설명하고 예시 한두 개를 준 뒤 Claude에게 테스트 케이스를 늘려 달라고 요청합니다.
  3. 현재 프롬프트로 평가를 돌려 어떤 유형에서 실패하는지 확인합니다.
  4. 사실과 다른 역할 설명과 웹에서 복사해 온 불필요한 내용을 지웁니다.
  5. XML 태그로 역할·가이드라인·정책·말투를 구분해 구조를 만듭니다.
  6. 출력 형식을 정하는 출력 계약을 추가합니다.
  7. 평가를 다시 돌려 실패 유형을 하나씩 고치며 결과를 비교합니다.
예시
고객 문의에 답하는 사내 챗봇을 만들고 있습니다. 아래 테스트 케이스 2개를 참고해서, 일반 문의·까다로운 예외 상황·상담원에게 넘겨야 하는 경우가 고루 섞이도록 테스트 케이스를 50개로 늘려 주세요.
  • 실행마다 결과 편차가 있으니 한 번의 결과로 단정하지 말고 여러 번 돌려 보세요.
  • 판정을 맡긴 AI도 틀릴 수 있으니 코드 기반 검사와 AI 판정을 함께 쓰는 것이 좋습니다.
  • 새 모델에서 성능이 떨어지는 원인은 행동 차이(프롬프트로 조정 가능)와 능력 부족(프롬프트로 해결 불가) 두 가지입니다.
  • 프롬프트가 너무 커지면 생성·평가·수리처럼 여러 프롬프트로 나누는 편이 토큰과 지연을 줄일 수 있습니다.

12. 평가로 내 업무에 맞는 모델 고르기

공개 벤치마크는 방향만 알려 줄 뿐 내 업무에 딱 맞지는 않습니다. 새 모델이 나올 때마다 반복할 수 있도록 작은 평가를 직접 만들어 품질·지연·비용 세 축으로 모델과 설정을 비교하는 방법입니다.

  1. 입력과 성공 기준을 가진 테스트 작업을 모아 평가 데이터 세트를 만듭니다.
  2. 최종 결과뿐 아니라 올바른 단계를 거쳤는지도 점검하는 채점 기준을 작업마다 붙입니다.
  3. 답변 품질 비교에는 AI 판정을, 특정 도구 호출이나 값 확인에는 코드 기반 검사를 씁니다.
  4. 모델과 thinking·effort 설정을 바꿔 가며 각 작업을 여러 번 돌립니다.
  5. 로그를 열어 API·도구 호출 실패 같은 인프라 문제를 모델 실패와 구분합니다.
  6. 통과율, 토큰, 비용, 지연 시간을 비교해 내가 중시하는 기준에 맞는 모델과 설정을 고릅니다.
  • 토큰당 가장 싼 모델이 아니라 성공 한 건당 가장 싼 모델을 고르세요.
  • 결과 편차가 크면 작업 정의나 평가 기준이 불명확하다는 신호입니다.
  • 일반적으로 지능이 필요하면 Opus, 낮은 지연·비용은 Haiku, 균형은 Sonnet이 출발점입니다.
  • 지금 잘 안 되는 작업은 다음 모델에서 나아질 영역의 단서이니 평가 세트에 남겨 두세요.
