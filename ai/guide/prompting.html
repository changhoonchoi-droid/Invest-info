프롬프트·활용 요령

이 분야에서는 AI에게 원하는 답을 끌어내는 프롬프트 쓰는 법, 긴 작업에서 컨텍스트(작업 기억)를 아끼는 법, 결과를 검증해 품질을 높이는 법, 모델과 effort를 골라 비용을 줄이는 법을 익힐 수 있습니다. 먼저 '더 나은 답 얻기'와 '답 검증하기'로 기본기를 다지고, 이어서 Claude Code의 권한 모드·컨텍스트·CLAUDE.md 관리를 익힌 뒤, 모델 고르기와 평가(eval) 같은 응용으로 넘어가면 좋습니다.

프롬프트 작성법, 컨텍스트 관리, 결과 품질 높이기, 비용·사용량 관리 · 영상 23개 기반 · 2026-10-27 갱신

최근 바뀐 점

  • Anthropic이 10월 1일 Claude Code의 화면과 행동 방식을 바꾸는 작은 프로그램인 '모드(Mods)'를 공식 발표했고, 내 세션 로그를 분석해 맞춤 모드를 추천받아 만들 수도 있습니다.
  • 산책하며 휴대폰 음성 메모로 하고 싶은 말을 녹음하고, 받아 적은 글을 Claude에게 보내 발표 자료로 만드는 방식이 소개되었습니다.
  • 라이브 영상 한 편을 Claude에 통째로 넘기고 편수까지 맡겨 롱폼 5편과 쇼츠 22편을 얻은 사례가 소개되었습니다.
  • 여러 작업을 동시에 돌릴 때 사람이 병목이 되지 않도록 권한과 확인 지점을 미리 설계하는 'Human on the loop' 방식이 제시되었습니다.

1. AI에게서 더 나은 답 얻기

AI는 사용자 메시지, 올린 문서, 대화 기록 전체를 보고 답을 한 단어씩 생성합니다. 그래서 내가 누구이고 무엇을 원하는지 맥락을 많이 줄수록 답이 좋아집니다. 업무에 AI를 처음 쓸 때 가장 먼저 익힐 기본기입니다.

  1. 내가 누구이고 지금 무슨 작업 중인지 먼저 알려 줍니다.
  2. 좋은 결과가 어떤 모습인지(분량, 대상 독자, 용도)를 함께 적습니다.
  3. 가격·뉴스 같은 최신 정보가 필요하면 웹 검색을 해 달라고 요청하거나, 검색을 했는지 물어봅니다.
  4. 검색했다면 제시된 출처를 직접 열어 내용이 맞는지 확인합니다.
  5. 초안을 여러 버전으로 요청하거나 다른 어조로 다시 써 달라고 합니다.
  6. 틀리면 문제가 되는 사실은 직접 다시 확인합니다.
예시
저는 마케팅팀 대리이고, 다음 주 팀장 보고용으로 신제품 출시 요약을 쓰고 있습니다. 한 페이지 이내, 핵심 숫자 3개가 들어간 보고서면 좋겠습니다. 초안을 서로 다른 어조로 두 가지 버전 써 주세요.
  • AI는 정해진 답을 꺼내는 게 아니라 새로 생성하므로, 마음에 들 때까지 여러 버전을 요청해도 됩니다.
  • 모델은 훈련 시점 이후의 사실을 검색 없이는 확실히 알지 못합니다. 웹 검색을 했다고 단정하지 말고 직접 물어보세요.
  • 빈 화면 앞에서 막막하면 휴대폰 음성 메모로 하고 싶은 말을 모두 녹음하고, 받아 적은 글을 통째로 보내 정리를 맡겨 보세요.

2. AI 답변 검증하며 쓰기

AI는 잘 모르는 내용도 똑같이 확신 있게 말하며, 그럴듯한 거짓(환각)이나 듣고 싶은 말에 맞춰 주는 아첨을 할 수 있습니다. 신뢰는 스위치가 아니라 다이얼처럼 질문의 중요도에 맞춰 조절해야 합니다. 숫자·출처·건강·법률·금전이 걸린 답을 쓸 때 꼭 필요합니다.

  1. 틀렸을 때 어떤 일이 생기는지 스스로 묻고 확인 강도를 정합니다.
  2. AI에게 답의 근거가 되는 출처를 요청합니다.
  3. 제시된 출처를 직접 열어 실제로 그 내용이 있는지 확인합니다.
  4. 원하는 답을 흘리지 말고 중립적으로 질문합니다.
  5. 미리 '모르면 모른다고 말해 달라'고 허용합니다.
예시
이 결정에 대한 가장 강력한 찬성과 반대 논거는 무엇인가요? 근거가 되는 출처도 함께 알려 주고, 모르는 부분은 모른다고 말해 주세요.
  • 브레인스토밍처럼 위험이 낮은 일은 느슨하게, 상사에게 보일 슬라이드의 통계는 반드시 검증합니다.
  • AI가 실제로 없는 출처를 그럴듯하게 만들어 낼 수도 있습니다.
  • 마이너한 세부 사항, 최근 사건, 비공개 정보는 틀리거나 지어낼 가능성이 높습니다.
  • 깔끔한 문단이나 그래픽, 자신 있는 말투는 정확성의 증거가 아닙니다. 최종 판단은 사람이 합니다.

3. Claude Code 권한 모드 고르기

Claude Code는 컨텍스트 수집 → 행동 → 결과 검증을 반복하는 에이전트로, 권한 모드로 어디까지 혼자 하게 할지 정합니다. 처음 쓸 때는 매번 묻는 모드로 익히고, 익숙해지면 자동 모드로 맡겨 흐름이 끊기지 않게 합니다.

  1. 기본 상태에서는 파일 수정·명령 실행 전마다 허락을 묻는다는 점을 확인합니다.
  2. Shift+Tab을 눌러 권한 모드를 차례로 전환합니다.
  3. 파일 수정·생성을 자동으로 승인하려면 자동 수락 모드를 고릅니다(명령 실행은 여전히 허락을 묻습니다).
  4. 최신 모델로 맡길 때는 Shift+Tab으로 auto mode로 전환합니다.
  5. 작업 요청을 입력하고, 허락을 묻는 명령이 나오면 내용을 읽고 승인합니다.
예시
앱 전체에 다크 모드를 추가하고 헤더에 다크 모드 토글을 만들어 줘
  • auto mode는 다른 모델이 요청의 안전성을 확인해 위험한 명령만 거부합니다.
  • 예전 방식: 읽기 전용으로 코드를 분석하고 계획을 먼저 받는 계획 모드를 많이 썼지만, Claude Code 팀은 최신 모델(4.6 이후)에서는 계획 단계 대신 auto mode를 쓴다고 합니다.
  • 여러 작업을 동시에 돌릴 때는 권한과 확인 지점을 미리 정해 두어야 내가 병목이 되지 않습니다.

4. 컨텍스트 아껴 쓰기

컨텍스트는 Claude의 작업 기억으로, 읽은 파일·실행한 명령·주고받은 메시지가 모두 공간을 차지합니다. 한도에 가까워지면 자동으로 압축되면서 세부 내용이 사라질 수 있으므로, 직접 정리해 주면 긴 작업에서도 품질이 유지됩니다.

  1. 같은 기능 작업을 이어갈 때는 /compact로 지금까지의 대화를 압축합니다.
  2. 전혀 다른 새 기능을 시작할 때는 /clear로 컨텍스트를 비웁니다.
  3. 요청은 구체적으로 써서 Claude가 불필요한 파일을 읽지 않게 합니다.
  4. 지금 작업과 관련 없는 MCP 서버는 끕니다.
  5. 답만 필요한 조사는 서브에이전트에 맡깁니다.
예시
/compact
  • MCP 서버는 기본적으로 모든 도구를 컨텍스트에 올리지만, 스킬은 필요한 부분만 불러와 공간을 덜 씁니다.
  • 서브에이전트는 별도 컨텍스트 창에서 일하고 요약만 돌려주므로 본 대화가 가벼워집니다.
  • Claude Code 팀은 컨텍스트를 최소한만 주고 모델이 필요한 것을 스스로 찾아오게 하는 방식을 권합니다.

5. CLAUDE.md로 실수 막고 다듬기

CLAUDE.md는 Claude Code가 매번 읽는 프로젝트 규칙 파일입니다. 같은 실수를 다시 시키는 대신 규칙으로 적어 두면 반복을 막을 수 있고, 새 모델로 바꿀 때는 지침을 그 모델에 맞게 조정할 수 있습니다.

  1. Claude가 실수하면 다시 시키기 전에 그 원인을 CLAUDE.md나 스킬에 규칙으로 적습니다.
  2. 새 모델(예: Opus 5.5)로 바꿨다면 Claude Code에서 /claude-api prompt-audit를 실행합니다.
  3. CLAUDE.md와 스킬의 지침이 새 모델에 맞게 조정되었는지 확인합니다.
예시
/claude-api prompt-audit
  • /claude-api prompt-audit는 API를 쓰지 않고 Claude Code만 써도 사용할 수 있습니다.
  • 규칙끼리 서로 부딪히면 모델이 엉뚱한 값을 고를 수 있으니, 상충하는 지침이 없는지 함께 점검합니다.

6. 작업에 맞는 모델·effort 고르기

작업 비용은 모델, effort(추론 노력), 캐시 세 가지로 정해집니다. 더 똑똑한 모델이 적은 단계로 끝내 총비용이 오히려 낮을 수 있으므로, 토큰 단가가 아니라 작업당 비용으로 고릅니다. 사용량 한도나 비용이 신경 쓰일 때 특히 유용합니다.

  1. 작업이 열린 작업(심층 조사, 복잡한 분석, 장시간 에이전트)인지 반복 작업(문서 요약, 메일 초안, 보고서 데이터 추출)인지 구분합니다.
  2. 열린 작업이면 Fable 5.1을 고르고 effort를 medium으로 시작합니다.
  3. 결과가 부족하면 /effort로 effort를 단계적으로 올립니다.
  4. 반복 작업이면 Opus나 Sonnet을 기본으로 쓰고, 필요할 때만 Fable로 바꿉니다.
  5. Opus 5.5는 기본 effort medium으로 쓰고, 여러 파일·프로젝트 전체를 바꾸는 수정에만 high를 씁니다.
  6. 탐색만 하는 서브에이전트는 작은(저렴한) 모델로 돌립니다.
예시
/effort
  • 강력한 모델일수록 낮은 effort로 시작해 필요할 때 올립니다. high는 low의 약 2배, max는 약 10배의 토큰과 시간을 씁니다.
  • Opus 5.5는 Opus 5보다 토큰당 20% 싸고 작업당 비용은 약 40% 낮으며, Pro·Max·Team 한도가 25% 더 갑니다.
  • Fable 5.1은 Fable 5와 단가가 같지만 캐시 읽기 비용이 75% 낮아, 긴 에이전트 작업에서 최대 약 45% 비용이 줄어듭니다.
  • 예전 방식: 5월 영상들은 extra high(X high)를 기본·권장값으로 소개했지만, 최근에는 medium으로 시작해 올리는 방식을 권합니다.

7. Claude에게 인터뷰시켜 스펙 만들기

요구사항을 내가 다 적는 대신, Claude가 질문을 던지게 하고 답하면서 스펙(기획서)을 완성하는 방법입니다. 무엇을 만들지 막연할 때나, 남의 자료에 내 해석을 더해 2차 가공할 때 유용합니다.

  1. Shift+Tab으로 auto mode로 전환합니다.
  2. /effort로 노력 수준을 설정합니다.
  3. 프롬프트에는 관심 영역(예: 대상 사용자)만 주고 결과를 과하게 지정하지 않습니다.
  4. 프롬프트에 ask user question 도구를 써서 질문하라고 명시합니다.
  5. Claude가 띄우는 질문에 차례로 답합니다.
  6. 답변이 끝나면 Claude가 작성한 스펙을 검토합니다.
예시
친구들끼리 식사비를 나누는 앱을 만들고 싶어. 대상 사용자는 20~30대 직장인이야. 바로 만들지 말고 ask user question 도구로 나에게 필요한 질문을 하나씩 해서 요구사항을 정리한 스펙을 써 줘.
  • '더 좋게 만들어', '실수 없이 만들어' 같은 막연한 프롬프트는 피합니다.
  • 스펙은 긴 마크다운 대신 정보 밀도가 높은 HTML 파일로 받아 사람이 먼저 검토하는 방법도 있습니다.
  • 빠르게 스펙을 반복할 때는 /fast 모드가 유용합니다.

8. 사용 패턴으로 모드 추천받기

모드(Mods)는 Claude Code의 화면과 행동 방식을 바꾸는 작은 프로그램으로, 10월 1일 공식 발표되었습니다. 내 세션 로그를 Claude에게 분석시켜 자주 반복하는 작업에 맞는 모드를 추천받고 바로 만들 수 있습니다.

  1. Claude Code에서 세션 로그를 최대한 훑어 내가 자주 반복하는 말과 작업을 파악해 달라고 요청합니다.
  2. 흐름을 돕고 비용을 아끼며 집중하게 해 줄 모드 다섯 개를 추천해 달라고 요청합니다.
  3. 추천 목록에서 마음에 드는 번호를 골라 만들어 달라고 요청합니다.

9. 평가 세트로 프롬프트 개선하기

모델을 바꾼 뒤 성능이 떨어졌거나, 중요한 업무용 프롬프트를 다듬을 때 '느낌' 대신 테스트로 개선하는 방법입니다. 평가 세트를 먼저 만들고 고칠 때마다 다시 돌려, 한 곳을 고치다 다른 곳을 망가뜨리는 일을 막습니다.

  1. 통제 사례, 이전에 실패한 엣지 케이스, 사람에게 넘기거나 거절해야 할 사례를 담은 평가 세트를 만듭니다.
  2. 현재 프롬프트로 평가를 돌려 실패 유형을 확인합니다.
  3. 사실과 다른 역할 설명과 웹에서 복사된 불필요한 내용을 지웁니다.
  4. XML 태그로 역할·가이드라인·정책·말투를 구분해 구조를 만듭니다.
  5. 출력 형식을 정하는 출력 계약을 추가합니다.
  6. 평가를 다시 돌려 실패 유형을 하나씩 고치고 결과를 비교합니다.
  • 가이드라인·정책·데이터를 사람이 구분하기 어려우면 모델도 구분하기 어렵습니다. 서로 상충하는 지침이 실패 원인인 경우가 많습니다.
  • 실행마다 편차가 있으니 한 번의 결과로 단정하지 말고, 금지 항목을 길게 나열하는 방식은 피합니다.
  • 큰 프롬프트 하나 대신 생성·평가·수리 세 프롬프트로 나누면 토큰과 지연을 줄일 수 있습니다.
  • 새 모델에서 안 되는 원인이 행동 차이면 프롬프트로 고칠 수 있지만, 능력 부족이면 프롬프트로 해결되지 않습니다.

10. 평가로 내 용도에 맞는 모델 고르기

공개 벤치마크는 방향만 알려 줄 뿐 내 업무와 다를 수 있습니다. 작은 평가라도 직접 만들어 두면 새 모델이 나올 때마다 같은 절차로 품질·지연·비용을 비교해 옮길지 판단할 수 있습니다.

  1. 입력과 성공 기준을 가진 테스트 작업을 모아 평가 데이터 세트를 만듭니다.
  2. 최종 결과뿐 아니라 올바른 단계를 거쳤는지도 점검하는 채점기를 작업마다 붙입니다.
  3. 응답 비교에는 LLM 심사를, 특정 도구 호출이나 인자 확인에는 코드 기반 평가를 씁니다.
  4. 모델과 생각(thinking)·effort 설정을 바꿔 가며 각 작업을 여러 번 돌립니다.
  5. 로그를 열어 API·도구 호출 실패 같은 인프라 문제를 모델 실패와 분리합니다.
  6. 통과율, 토큰, 비용, 지연 시간을 비교해 중시하는 기준에 맞는 모델과 설정을 고릅니다.
  • 토큰당 가장 싼 모델이 아니라 성공 한 건당 가장 싼 모델을 고릅니다.
  • LLM 심사도 틀릴 수 있으니 여러 채점기를 함께 씁니다.
  • 결과 편차가 크면 작업 정의나 평가가 불명확하다는 신호입니다.
  • 지금 안 되는 작업은 다음 모델이 나아질 영역의 단서이니 평가 세트에 남겨 두세요.
