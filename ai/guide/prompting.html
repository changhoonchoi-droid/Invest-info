프롬프트·활용 요령

이 분야에서는 AI에게 상황을 잘 전달해 더 나은 답을 받는 법, 답을 검증하는 법, 작업에 맞는 모델과 노력 수준(effort)을 골라 비용을 아끼는 법, 평가로 프롬프트와 모델을 개선하는 법을 다룹니다. 처음이라면 앞쪽의 입문 가이드 세 개(좋은 답 받기, 답 검증하기, 음성 메모로 초안 만들기)부터 해 보세요. 그다음 모델·비용 관리, CLAUDE.md와 인터뷰 방식 같은 중급 요령으로 넘어가고, 마지막에 평가를 이용한 고급 개선 방법을 보면 됩니다.

프롬프트 작성법, 컨텍스트 관리, 결과 품질 높이기, 비용·사용량 관리 · 영상 20개 기반 · 2026-10-25 갱신

최근 바뀐 점

  • Claude Code의 화면과 행동 방식을 바꾸는 작은 프로그램인 모드(Mods)가 10월 1일 공식 발표되었습니다.
  • Claude Code 세션 로그를 분석해 내가 자주 하는 말과 작업을 찾고, 이에 맞는 모드를 추천받아 바로 만들 수 있습니다.
  • 라이브 한 편을 Claude에 통째로 넘기고 편수까지 맡겨 롱폼 5편과 쇼츠 22편을 얻은 사례가 소개되었습니다. 사람이 매번 붙잡지 않도록 권한과 확인 지점을 미리 정해 두는 'Human on the loop' 방식입니다.
  • Anthropic 디자이너가 산책하며 녹음한 음성 메모를 받아 적은 글을 Claude에 보내 발표 자료를 만드는 방법을 소개했습니다.
내 상황을 알려 주고 더 나은 답 받기AI 답변을 검증하며 쓰기음성 메모로 발표 자료 초안 만들기작업 종류별로 모델과 effort 고르기비용·사용량 아끼며 쓰기CLAUDE.md로 같은 실수 막기Claude에게 인터뷰받아 요구사항 정하기긴 자료 하나로 결과물 여러 개 만들기내 사용 패턴으로 모드 추천받기평가 세트로 프롬프트 개선하기평가로 내 업무에 맞는 모델 고르기
입문

1. 내 상황을 알려 주고 더 나은 답 받기

AI는 내 메시지, 올린 문서, 대화 기록 전체를 보고 다음 단어를 예측하며 답을 만들어 냅니다. 그래서 내가 누구이고 어떤 결과를 원하는지 알려 줄수록 답이 좋아집니다. 답을 꺼내 오는 것이 아니라 새로 만드는 것이라서, 여러 버전을 요청해 고를 수도 있습니다.

  1. 내가 누구이고 무슨 작업을 하는지 첫 메시지에 적습니다.
  2. 좋은 결과가 어떤 모습인지(분량, 대상 독자, 용도)를 함께 적습니다.
  3. 가격·뉴스 같은 최신 정보가 필요하면 웹 검색을 요청하거나, 검색을 했는지 물어봅니다.
  4. 검색을 했다면 답에 나온 출처를 직접 열어 내용이 맞는지 확인합니다.
  5. 초안을 여러 버전으로 받거나 다른 어조로 다시 써 달라고 합니다.
  6. 틀리면 곤란한 사실은 직접 다시 확인합니다.
예시
저는 마케팅팀 3년 차 직장인이고, 다음 주 팀장님께 올릴 신제품 홍보 메일 초안을 쓰고 있습니다. 좋은 결과는 5문장 안팎으로 핵심 일정과 요청 사항이 바로 보이는 메일입니다. 최신 시장 정보가 필요하면 웹 검색을 하고 출처를 함께 알려 주세요. 초안은 정중한 어조와 간결한 어조로 두 가지 써 주세요.
  • AI는 학습 시점 이후의 사실을 검색 도구 없이는 확실히 알지 못합니다.
  • AI가 웹 검색을 했으리라 짐작하지 말고 직접 물어봅니다.
  • 자신 있는 말투나 깔끔한 결과물이 정확하다는 증거는 아닙니다.

2. AI 답변을 검증하며 쓰기

AI는 그럴듯하지만 사실이 아닌 내용을 만들어 내거나(환각), 내가 듣고 싶은 말에 맞춰 줄 때가 있습니다(아첨). 신뢰는 켜고 끄는 스위치가 아니라 다이얼처럼, 질문이 얼마나 중요한지에 따라 조절합니다. 숫자·출처·건강·법률·돈 문제는 반드시 확인합니다.

  1. 답이 틀리면 어떤 일이 생기는지 스스로 묻고, 얼마나 꼼꼼히 확인할지 정합니다.
  2. 질문할 때 미리 모르면 모른다고 말해 달라고 적어 둡니다.
  3. 원하는 답을 흘리지 말고 중립적으로 묻습니다.
  4. 답의 근거가 되는 출처를 달라고 요청합니다.
  5. 받은 출처를 직접 열어 그 내용이 실제로 있는지 확인합니다.
예시
이 결정에 대한 가장 강력한 찬성과 반대 논거는 무엇인가요? 각 논거의 근거 출처도 알려 주고, 확실하지 않거나 모르는 부분은 모른다고 말해 주세요.
  • 파티 주제 브레인스토밍은 검증할 필요가 적지만, 상사에게 보여 줄 슬라이드의 통계는 반드시 확인합니다.
  • 잘 알려진 주제는 비교적 정확하지만, 잘 알려지지 않은 세부 사항·최근 사건·비공개 정보는 틀리기 쉽습니다.
  • AI가 실제로 없는 출처를 그럴듯하게 만들어 낼 수도 있습니다.
  • 최종 판단은 사람이 합니다. 전문 업무에서도 검토 과정에는 사람이 참여해야 합니다.

3. 음성 메모로 발표 자료 초안 만들기

빈 슬라이드 앞에서 막막할 때, 하고 싶은 말을 먼저 말로 녹음해 두고 Claude에게 발표 자료로 정리해 달라고 하는 방법입니다. 서식 작업을 줄이고 내용 자체에 시간을 쓸 수 있습니다.

  1. 산책하거나 이동하면서 휴대폰 음성 메모 앱으로 발표에서 하고 싶은 말을 모두 녹음합니다.
  2. 녹음한 내용을 글로 받아 적습니다.
  3. 받아 적은 글을 Claude에게 보내 발표 자료로 만들어 달라고 요청합니다.
  4. 작은 수정은 직접 고칩니다.
  5. 큰 수정은 댓글로 Claude에게 요청합니다.
예시
아래는 제가 산책하며 녹음한 음성 메모를 받아 적은 글입니다. 이 내용으로 발표 자료를 만들어 주세요. 내용 흐름은 그대로 살리고, 슬라이드마다 핵심 메시지가 하나씩 보이게 정리해 주세요.
  • 영상에서는 Claude가 회사 브랜드 스타일을 이미 알고 있어 폰트나 템플릿을 따로 찾지 않았습니다.

4. 작업 종류별로 모델과 effort 고르기

작업 비용은 모델, effort(추론에 쓰는 노력), 캐시 세 가지로 정해집니다. 더 똑똑한 모델은 적은 단계로 끝내서 오히려 총비용이 낮아질 수 있습니다. 그래서 작업의 성격에 따라 모델과 effort를 골라 씁니다.

  1. 작업이 열린 작업(심층 조사, 복잡한 분석, 오래 걸리는 에이전트 작업)인지, 반복 작업(문서 요약, 메일 초안, 보고서 데이터 추출)인지 구분합니다.
  2. 열린 작업이면 Fable 5.1을 고르고 effort를 medium으로 시작합니다.
  3. 결과가 부족하면 effort를 한 단계씩 올립니다.
  4. 반복 작업이면 Opus나 Sonnet을 기본으로 씁니다.
  5. Opus 5.5는 기본 effort인 medium으로 대부분 충분합니다. 여러 파일이나 프로젝트 전체를 바꾸는 수정에만 high로 올립니다.
  6. Claude Code에서는 /effort로 노력 수준을 바꿉니다.
  • 토큰 단가가 아니라 작업 한 건당 비용으로 비교합니다. Opus 5.5는 Opus 5보다 토큰당 20% 저렴하고, 필요한 토큰도 적어서 작업당 비용이 약 40% 낮습니다.
  • 강력한 모델일수록 낮은 effort로 시작해 필요할 때 올립니다. 지능이 필요한 작업은 effort를 낮추더라도 큰 모델이 낫습니다.
  • effort를 올리면 비용이 크게 늘어납니다. 한 시연에서 high는 low보다 약 2배, max는 약 10배의 토큰과 시간을 썼습니다.
  • 예전 방식: 5월 영상들은 effort를 extra high(X high, 당시 제품 기본값)로 두라고 권했습니다. 지금은 Opus 5.5 기준으로 medium에서 시작합니다.

5. 비용·사용량 아끼며 쓰기

Pro·Max·Team 요금제의 사용 한도나 API 비용을 아끼는 요령입니다. 작업당 비용을 기준으로 보고, 보조 작업에는 작은 모델을 쓰고, 컨텍스트를 가볍게 유지하는 것이 핵심입니다.

  1. 같은 작업을 모델별로 돌려 보고 토큰 단가가 아니라 작업 한 건당 비용과 한도 사용량을 비교합니다.
  2. 자주 쓰는 모델을 새 버전으로 바꿉니다. 영상에서는 같은 버그 수정에 Opus 5가 5시간 한도의 약 6%를 쓴 반면 Opus 5.5는 약 4%를 썼습니다.
  3. 탐색만 하는 서브에이전트처럼 특정 작업만 맡는 보조 작업에는 저렴한 작은 모델부터 적용합니다.
  4. 자주 쓰는 긴 지침은 스킬로 옮겨 필요할 때만 불러오게 합니다.
  5. 반복해서 보내는 같은 내용은 캐시를 활용합니다. Fable 5.1은 캐시 읽기 비용이 Fable 5보다 75% 낮습니다.
  • 시스템 프롬프트와 도구는 꼭 필요한 만큼만 주고, 필요한 정보는 모델이 직접 찾아오게 하는 편이 낫습니다.
  • 코드 실행을 활용하면 토큰과 비용이 줄어듭니다.
  • 오래 도는 에이전트의 컨텍스트를 가볍게 유지하는 방법으로 도구 검색, 프로그램 방식 도구 호출, 컴팩션이 소개되었습니다.
  • 콘텐츠 자동화처럼 많이 생성하는 작업은 작업 종류마다 크레딧 상한을 정해 둡니다(예: 쇼츠 500, 롱폼 1,500).

6. CLAUDE.md로 같은 실수 막기

Claude가 실수했을 때 매번 다시 시키는 대신, 그 내용을 CLAUDE.md나 스킬에 규칙으로 적어 두면 다음부터 같은 실수가 나오지 않습니다. 모델을 바꾼 뒤에는 기존 지침을 새 모델에 맞게 다듬을 수 있습니다.

  1. Claude가 실수하면 같은 요청을 다시 시키지 말고, 무엇이 잘못됐는지 정리합니다.
  2. 다시 하지 말아야 할 일이나 지켜야 할 방법을 CLAUDE.md나 해당 스킬에 한 줄 규칙으로 적습니다.
  3. 새 모델(예: Opus 5.5)로 바꾼 뒤에는 Claude Code에서 /claude-api prompt-audit를 실행합니다.
  4. CLAUDE.md와 스킬의 지침이 새 모델에 맞게 조정되었는지 확인합니다.
예시
/claude-api prompt-audit
  • /claude-api prompt-audit는 API를 쓰지 않고 Claude Code만 써도 쓸 수 있습니다.
  • 지침에 서로 부딪치는 규칙이 있으면 모델이 엉뚱한 값을 고를 수 있으니 새 규칙을 넣을 때 기존 규칙과 겹치지 않는지 봅니다.

7. Claude에게 인터뷰받아 요구사항 정하기

원하는 결과를 내가 일일이 적는 대신, Claude가 나에게 질문하게 해서 요구사항을 끌어내는 방법입니다. 모델이 강해질수록 지시를 줄이고 질문에 답하는 편이 결과가 좋습니다. 남의 영상이나 글을 내 콘텐츠로 다시 만들 때도 인터뷰로 내 해석을 더할 수 있습니다.

  1. Claude Code에서 Shift+Tab을 눌러 auto mode로 바꿉니다.
  2. /effort로 노력 수준을 정합니다.
  3. 프롬프트에는 만들 것의 관심 영역(예: 대상 사용자)만 적고 결과를 지나치게 지정하지 않습니다.
  4. 프롬프트에 ask user question 도구를 써서 나에게 질문하라고 적습니다.
  5. Claude가 띄우는 질문에 차례로 답합니다.
  6. 답변이 끝나면 Claude가 쓴 스펙을 먼저 검토합니다.
예시
회사 동료들끼리 회식비를 나눠 내는 앱을 만들고 싶습니다. 대상 사용자는 스마트폰에 익숙한 20~40대 직장인입니다. 바로 만들지 말고, ask user question 도구로 저에게 질문해서 요구사항을 정리한 뒤 스펙을 작성해 주세요.
  • '더 좋게 만들어', '실수 없이 만들어' 같은 막연한 프롬프트는 피합니다.
  • 스펙을 빠르게 여러 번 고칠 때는 /fast 모드가 쓸모 있습니다.
  • 계획은 긴 마크다운 대신 정보가 촘촘한 HTML 파일로 받아 검토하는 방법도 있습니다.
  • 예전 방식: 5월 영상은 effort를 X high로 권했습니다. 지금은 Opus 5.5의 기본값 medium에서 시작하고, 큰 작업이면 high로 올립니다.

8. 긴 자료 하나로 결과물 여러 개 만들기

라이브 방송이나 긴 회의처럼 분량이 많은 자료를 Claude에 통째로 넘기고, 몇 개로 나눌지까지 맡기는 방법입니다. 한 크리에이터는 라이브 한 편에서 롱폼 5편과 쇼츠 22편을 얻었습니다. 반복되는 작업 규칙은 스킬로 만들어 두고 계속 다시 씁니다.

  1. 긴 자료(라이브 녹취, 회의록 등) 전체를 Claude에게 통째로 넘깁니다.
  2. 결과물을 몇 편으로 나눌지도 Claude가 정하게 요청합니다.
  3. 남의 영상이나 글을 가져와 쓸 때는 Claude가 던지는 질문에 답해 내 해석을 더합니다.
  4. 반응이 좋았던 댓글처럼 독자 반응에서 다음 기획을 얻습니다.
  5. 기획·리서치·대본·검수·업로드처럼 매번 같은 순서는 공통 작업 흐름으로 정리하고, 반복되는 규칙은 스킬로 만들어 둡니다.
  6. 여러 작업을 동시에 돌려도 내가 병목이 되지 않도록 Claude에게 맡길 권한과 내가 확인할 지점을 미리 정합니다.
예시
첨부한 라이브 방송 녹취 전체를 보고, 롱폼 영상과 쇼츠로 각각 몇 편을 만들면 좋을지 직접 정해 주세요. 편마다 제목, 핵심 내용, 녹취 속 해당 구간을 표로 정리해 주세요.
  • 이 크리에이터도 처음에는 영상 하나에 약 30시간이 걸렸습니다. 작업 흐름을 갖춘 뒤에야 속도가 붙었습니다.
  • 사람이 모든 단계를 붙잡지 않고 확인 지점만 지키는 방식을 'Human on the loop'라고 부릅니다.

9. 내 사용 패턴으로 모드 추천받기

모드(Mods)는 Claude Code의 모습과 행동 방식을 바꾸는 작은 프로그램으로, 10월 1일 공식 발표되었습니다. Claude가 작업할 때마다 나가는 신호를 모드가 듣고, 지켜보거나 살짝 고치거나 대신 처리합니다. 내 사용 기록을 분석해 나에게 맞는 모드를 추천받고 바로 만들 수 있습니다.

  1. Claude Code에 세션 로그를 최대한 훑어 내가 자주 반복하는 말과 작업을 찾아 달라고 요청합니다.
  2. 작업 흐름을 돕고 비용을 아끼며 집중하게 해 줄 모드 다섯 개를 추천해 달라고 요청합니다.
  3. 추천마다 붙은 패턴과 근거를 읽어 봅니다.
  4. 마음에 드는 번호를 골라 만들어 달라고 요청합니다.
예시
Claude Code 세션 로그를 최대한 훑어서 제가 자주 반복하는 말과 작업을 파악해 주세요. 그 결과를 바탕으로 제 작업 흐름을 돕고, 비용을 아끼고, 집중하게 해 줄 모드 다섯 개를 추천해 주세요.
  • 스킬·MCP는 밖에서 지식과 도구를 건네고, 모드는 작업 환경 자체를 바꿉니다.
  • 창이나 버튼 같은 화면 요소는 모드로만 만들 수 있습니다.
  • 영상에서는 토큰 사용량 표시, 다음 작업 추천 같은 모드를 데스크톱 앱에서 만들었습니다.

10. 평가 세트로 프롬프트 개선하기

평가(eval)는 특정 용도에서 AI가 얼마나 잘하는지 재는 체계적인 테스트입니다. '느낌'을 확인할 수 있는 숫자로 바꿔 줍니다. 모델을 바꾼 뒤 성능이 떨어졌거나 업무용 프롬프트를 다듬을 때, 평가를 기준으로 하나씩 고치면 한 곳을 고치다 다른 곳을 망가뜨리는 일을 막을 수 있습니다.

  1. 정상 사례, 예전에 실패했던 까다로운 사례, 사람에게 넘기거나 거절해야 할 사례를 모아 평가 세트를 만듭니다.
  2. 지금 쓰는 프롬프트로 평가를 돌려 어떤 식으로 실패하는지 확인합니다.
  3. 사실과 다른 역할 설명과 웹에서 복사해 온 불필요한 내용을 지웁니다.
  4. XML 태그로 역할·가이드라인·정책·말투를 구분해 구조를 잡습니다.
  5. 출력 형식을 정해 두는 출력 계약을 추가합니다.
  6. 평가를 다시 돌리며 실패 유형을 하나씩 고치고 결과를 비교합니다.
예시
<역할>통신사 고객지원 상담원</역할>
<가이드라인>요금·약정 질문에 답하고, 확인되지 않은 내용은 추측하지 않는다.</가이드라인>
<정책>환불·해지 요청은 상담원 연결로 넘긴다.</정책>
<말투>정중하고 짧게.</말투>
<출력 형식>답변 3문장 이내 + 마지막 줄에 '다음 안내: …'</출력 형식>
  • 가이드라인·정책·데이터를 사람이 구분하기 어려우면 모델도 구분하기 어렵습니다.
  • 실행할 때마다 결과가 조금씩 달라지니 한 번 돌린 결과로 단정하지 않습니다.
  • 금지 항목을 길게 늘어놓는 방식은 피합니다.
  • 큰 프롬프트 하나보다 생성·평가·수리 세 프롬프트로 나누면 더 적은 토큰과 짧은 지연으로 모든 테스트를 통과한 사례도 있습니다.

11. 평가로 내 업무에 맞는 모델 고르기

새 모델이 나올 때마다 같은 절차로 비교할 수 있도록, 내 용도에 맞춘 작은 평가를 직접 만들어 모델을 고르는 방법입니다. 품질·지연·비용 세 가지를 함께 봅니다. 공개 벤치마크는 방향만 알려 줄 뿐 내 용도와 다를 수 있습니다.

  1. 입력과 성공 기준을 갖춘 테스트 작업을 모아 평가 데이터 세트를 만듭니다.
  2. 최종 결과뿐 아니라 올바른 단계를 거쳤는지도 점검하는 채점기를 작업마다 붙입니다.
  3. 응답 품질 비교에는 LLM 심사를, 특정 도구 호출이나 값 확인에는 코드 기반 평가를 씁니다.
  4. 모델과 생각(thinking)·노력(effort) 설정을 바꿔 가며 각 작업을 여러 번 돌립니다.
  5. 로그를 열어 API·도구 호출 실패 같은 인프라 문제를 모델 실패와 구분합니다.
  6. 통과율, 토큰, 비용, 지연 시간을 비교해 내가 중요하게 여기는 기준에 맞는 모델과 설정을 고릅니다.
  • 토큰당 가장 싼 모델이 아니라 성공 한 건당 가장 싼 모델을 고릅니다.
  • 결과 편차가 크면 작업 정의나 평가 기준이 불분명하다는 신호입니다.
  • LLM 심사도 틀릴 수 있으니 채점기를 여러 개 함께 씁니다.
  • 새 모델을 받으면 평가부터 돌려 보고, 지금 안 되는 작업을 다음 모델이 나아질 영역의 단서로 삼습니다.
