프롬프트·활용 요령

이 페이지에서는 AI에게 맥락을 알려 주는 기본 습관부터, 답을 검증하고 모델·사용량을 고르는 요령, 컨텍스트 관리와 프롬프트를 평가로 다듬는 방법까지 배웁니다. 앞쪽 가이드부터 순서대로 따라 하면 되고, 뒤로 갈수록 Claude Code나 평가 같은 응용 내용이 나옵니다. 회사 일에 쓰기 전 설정과 답변 검증은 꼭 먼저 확인하세요.

  • Claude Fable 5.2가 출시되어, 기본은 중간 노력 수준의 Opus 5.5로 시작하고 크고 모호한 장기 작업에만 Fable을 쓰라는 선택 기준이 나왔습니다.

1. AI에게 맥락 주고 첫 대화 시작하기

AI를 잘 쓰는 핵심은 완벽한 프롬프트가 아니라 나와 내 상황, 좋은 결과의 기준을 충분히 알려 주는 것입니다. AI를 처음 쓰거나 답이 겉도는 느낌일 때 가장 먼저 해 볼 기본 습관입니다.

  1. 무료 버전으로 먼저 시작합니다. 한도에 자주 막힐 때만 유료로 넘어갑니다.
  2. 완전 처음이면 ChatGPT 앱의 보이스 모드로 말하듯 질문합니다.
  3. 조금 써 봤다면 Claude 데스크톱 앱에서 내 컴퓨터 속 파일을 보여 주고 나를 파악하게 합니다.
  4. 내가 누구이고 무슨 작업 중인지, 좋은 결과가 어떤 모습인지 알려 줍니다.
  5. 파일·캡처 같은 자료를 충분히 붙여 줍니다.
  6. 하루 30분, AI에게 질문하고 AI가 나에게 질문하게 하는 습관을 들입니다.
  7. 작업별로 프로젝트를 나눠 쓰고, 새 채팅에서는 이전 내용을 가져오라고 요청합니다.
예시
나는 중소기업 마케팅팀 3년 차 직원이야. 이번 주 목표는 신제품 소개 보고서 초안이야. 내 업무와 보고서 스타일을 파악하는 데 필요한 질문이 있으면 먼저 하나씩 물어봐 줘.
  • 자료를 많이 줘도 AI의 답은 직접 읽고 판단해야 합니다.
  • 늦게 시작해도 도구 지식보다 마인드셋이 더 중요하다고 합니다.

2. 회사 일 전에 학습 사용 설정 끄기

ChatGPT는 대화 내용이 모델 개선에 쓰이도록 설정되어 있을 수 있습니다. 회사 일에 쓰기 전에 이 설정을 꺼 두는 기본 보안 단계입니다.

  1. ChatGPT 설정(Settings)을 엽니다.
  2. Data controls로 들어갑니다.
  3. Improve the model for everyone 항목을 끕니다.
  4. 개인정보와 기밀 정보는 설정과 관계없이 입력하지 않습니다.
  • 회사 일에 쓰기 전에 반드시 먼저 끕니다.
  • 사내 AI 사용 규정이 있다면 그것이 우선입니다.

3. AI 답변 믿어도 되는지 검증하기

AI는 틀린 내용도 똑같이 확신 있게 말하고(환각), 사용자가 원하는 쪽으로 맞춰 동의하기도 합니다(아첨). 질문의 중요도에 따라 확인 강도를 조절하는 방법입니다.

  1. 틀렸을 때 어떤 일이 생기는지 스스로 묻고 확인 강도를 정합니다.
  2. 미리 모르면 모른다고 말해 달라고 허용합니다.
  3. 주장마다 근거가 되는 출처를 요청합니다.
  4. 제시된 출처를 직접 열어 실제로 그 내용이 있는지 확인합니다.
  5. 의심스러우면 얼마나 확신하는지, 틀릴 만한 부분이 있는지 묻습니다.
  6. 새 대화를 열어 그 답변의 오류를 찾아 달라고 하거나 다른 AI로 교차 검증합니다.
  7. 숫자·날짜·인용·최신 정보는 믿을 만한 자료로 다시 확인합니다.
예시
이 결정에 대한 가장 강력한 찬성과 반대 논거는 무엇인가요? 모르는 부분은 모른다고 말해도 괜찮고, 각 주장마다 출처를 함께 알려 주세요.
  • 브레인스토밍은 느슨하게, 상사에게 보일 통계·건강·법률·금전 문제는 반드시 검증합니다.
  • AI가 없는 출처를 그럴듯하게 만들어 낼 수도 있습니다.
  • 깔끔한 문단이나 자신 있는 말투는 정확성의 증거가 아닙니다.
  • 가격·뉴스 같은 최신 정보는 웹 검색을 했는지 직접 물어봅니다.

4. 말로 요청을 정리해 프롬프트 만들기

타이핑 대신 음성으로 길게 말하면 시간이 줄고 생각도 정리됩니다. 음성 입력 도구로 두서없이 말한 뒤 AI가 알아듣기 좋은 프롬프트로 다듬는 방법입니다.

  1. Typeless 같은 음성 입력 도구로 하고 싶은 요청을 두서없이 말해 입력합니다.
  2. 입력된 문장을 드래그로 선택합니다.
  3. Ask Anything 단축키를 누릅니다.
  4. 무엇이든 물어보세요 칸에 프롬프트를 다듬어 달라고 말합니다.
  5. 약 3초 후 나온 프롬프트를 필요하면 고쳐서 AI에 입력합니다.
예시
더 잘 알아듣는 프롬프트로 다듬어 줘. 타겟·톤·결과물 형식을 구체적으로 넣어 줘.
  • '더 짧게', '더 친근하게' 같은 수정도 같은 방식으로 요청할 수 있습니다.
  • 전문 용어는 가끔 틀리게 인식될 수 있으니 확인하세요.
  • Typeless 무료 사용량은 주당 8,000단어입니다.

5. 업무 메일·보고서 프롬프트 잘 쓰기

영어 메일처럼 맥락이 중요한 업무 글은 번역기가 아니라 현지 직원에게 맡기듯 상황을 적어야 결과가 좋습니다. 보고서 형식은 한 번 정해 두면 매번 같은 포맷을 얻을 수 있습니다.

  1. 받는 사람의 직급을 프롬프트에 적습니다.
  2. 나와 받는 사람의 관계를 적습니다.
  3. 메일이 끝난 뒤 무엇이 일어나야 하는지를 적습니다.
  4. 보고서는 형식을 스킬이나 메모리로 굳혀 매번 같은 포맷이 나오게 합니다.
  5. AI 티가 나는 문장은 다듬은 뒤, 중요한 문서는 직접 읽고 고칩니다.
예시
받는 사람은 미국 지사의 부사장이고, 나와는 처음 연락하는 사이야. 이 메일을 읽고 다음 주까지 화상 회의 일정을 잡아 주는 것이 목표야. 현지 직원이 쓴 것처럼 영어 메일을 써 줘.
  • 번역기는 문장을 바꾸고, 현지 직원은 맥락을 바꿉니다.
  • 오늘 시작할 세 가지: 아침 메일 정리, 보고서 포맷 스킬화, 회의 전 예상 질문·답변.

6. AI를 과외 선생님으로 공부하기

새 분야를 배울 때 AI에게 선생님 역할을 맡겨 커리큘럼을 만들게 하는 방법입니다. 이해하며 질문을 이어 가야 실력이 늘고, 결과는 직접 만들어 보며 굳힙니다.

  1. 배우고 싶은 분야를 말합니다.
  2. 네가 앞으로 과외 선생님으로서 나를 공부할 수 있도록 도와줘라고 요청합니다.
  3. AI가 만들어 주는 커리큘럼을 받습니다.
  4. 답변을 이해하면서 질문과 문제를 이어 갑니다.
  5. AI가 준 답은 '진짜 맞나?', '내 상황은?', '다른 관점은?'으로 검증합니다.
  6. 공부한 결과는 직접 만든 결과물로 남깁니다.
예시
네가 앞으로 과외 선생님으로서 내가 '에이전트 메모리'를 공부할 수 있도록 도와줘. 먼저 내 수준을 파악하는 질문을 하고, 그다음 커리큘럼을 만들어 줘.
  • 답변을 이해하지 않고 복사·붙여 넣기만 하면 실력이 늘지 않습니다.
  • 책을 읽은 뒤 AI에게 저자 역할을 시켜 질문해 볼 수도 있습니다.

7. 구독료와 사용량 한도 관리하기

AI 구독료의 기준은 금액이 아니라 쓰다가 한도에 막히는지 여부입니다. 무료로 시작해 필요할 때만 올리고, 쓴 만큼 성과가 나는지 따져 보는 방법입니다.

  1. 먼저 무료 버전으로 불편 없이 쓸 수 있는지 확인합니다.
  2. 한도에 자주 막힐 때만 유료로 올립니다.
  3. 이미지 생성이 필요하면 ChatGPT, 코딩이 많으면 토큰이 더 싼 Claude를 고려합니다.
  4. 쓴 만큼 돈·시간·성과가 나는지 주기적으로 따져 봅니다.
  • 영상 진행자는 월 200달러 플랜을 여러 개 쓰지만, 이는 개인 사례일 뿐 입문자에게 권하는 수준이 아닙니다.

8. 작업에 맞는 모델과 노력 수준 고르기

작업 비용은 모델, 노력 수준(effort), 캐시 세 가지로 정해집니다. 작업 성격에 따라 모델을 고르고 노력 수준은 낮게 시작해 올리면 비용과 한도를 아낄 수 있습니다.

  1. 기본 시작점으로 중간(medium) 노력 수준의 Opus 5.5를 씁니다.
  2. 결과가 부족하면 모델을 바꾸기 전에 먼저 노력 수준을 올립니다.
  3. 크고 모호한 장기 작업(심층 조사, 복잡한 분석)은 Fable을 고려합니다.
  4. 범위가 분명한 작업은 Sonnet, 요약·분류 같은 대량 저비용 작업은 Haiku를 씁니다.
  5. 여러 파일에 걸친 수정에는 high를 씁니다.
  6. 서브에이전트에는 저렴한 모델부터 적용합니다.
  7. 토큰 단가가 아니라 작업당 비용으로 비교합니다.
  • Fable은 토큰당 가격이 Opus의 두 배이고, Sonnet은 Opus의 절반입니다.
  • Haiku의 가용성과 사용 한도는 요금제마다 다릅니다.
  • 더 강력한 모델일수록 낮은 effort로 시작해 필요할 때 올립니다.
  • 예전 방식: 열린 작업은 Fable 5.1을 medium으로 시작하라고 안내했습니다. 최근 영상은 Opus 5.5 medium을 기본 시작점으로 권합니다.

9. Claude Code 컨텍스트 아껴 쓰기

컨텍스트는 Claude의 작업 기억이며, 읽은 파일과 명령, 주고받은 메시지가 모두 공간을 차지합니다. 한도에 가까워지면 세부 내용이 사라질 수 있어 관리가 필요합니다.

  1. 같은 기능 작업을 이어갈 때는 /compact를 씁니다.
  2. 새 기능을 시작할 때는 /clear로 대화를 비웁니다.
  3. 요청은 구체적으로 해서 불필요한 탐색을 줄입니다.
  4. 관련 없는 MCP 서버는 끕니다.
  5. 답만 필요한 조사는 서브에이전트에 맡깁니다.
  6. 반복하는 작업 방법은 스킬로 만들어 필요할 때만 불러오게 합니다.
  • MCP 서버는 기본적으로 모든 도구를 컨텍스트에 올립니다.
  • 스킬은 이름과 설명만 먼저 불러와 컨텍스트를 아낍니다.
  • 최신 모델에서는 컨텍스트를 최소한만 주고 모델이 알아서 찾게 하는 방식이 권장됩니다.
  • 정답이 든 짧은 프롬프트가 긴 전체 기록보다 더 정확했다는 실험이 있습니다.

10. 같은 실수 막는 CLAUDE.md·스킬 만들기

AI가 실수했을 때 다시 시키지 말고 규칙으로 적어 두면 같은 실수를 막을 수 있습니다. 항상 적용할 규칙은 CLAUDE.md에, 특정 상황의 작업 방법은 스킬에 둡니다.

  1. 실수가 나오면 다시 시키지 말고 원인을 확인합니다.
  2. 항상 지킬 규칙은 CLAUDE.md에 적습니다.
  3. 특정 작업 방법은 SKILL.md 파일의 스킬로 만듭니다.
  4. 개인 스킬은 홈 디렉터리의 .claude/skills에, 팀 공유 스킬은 저장소 루트의 .claude/skills에 둡니다.
  5. 스킬의 설명(description)을 요청과 맞게 써서 자동으로 선택되게 합니다.
  6. 모델을 바꿨다면 Claude Code에서 /claude-api prompt-audit를 실행해 지침을 맞춥니다.
  • CLAUDE.md는 모든 대화에 로드되고, 스킬은 요청이 맞을 때만 로드됩니다.
  • 슬래시 명령은 직접 입력하지만 스킬은 자동으로 적용됩니다.
  • /claude-api prompt-audit는 API 없이 Claude Code만 써도 사용할 수 있습니다.

11. 에이전트 추천에 휘둘리지 않고 결정하기

Anthropic 연구에서 분석가들은 에이전트가 기운 쪽을 86% 따랐고, 스스로 결정했다고 착각하기 쉬웠습니다. 계획 단계에서 내 기준으로 결정하게 돕는 방법입니다.

  1. 에이전트가 방법을 추천하기 전에 내 우선순위부터 묻게 합니다.
  2. 결정이 어려우면 작고 저렴한 모델로 여러 버전의 프로토타입을 병렬로 만듭니다.
  3. 프로토타입을 보고 내가 결정한 뒤 프로토타입은 버립니다.
  4. 결정한 내용을 에이전트에게 전달합니다.
  5. 에이전트가 고른 안에 대해 What would change your advice?라고 묻습니다.
  6. 다른 안이 최적이 되는 조건이 현재 상황에 해당하는지 판단합니다.
예시
추천을 하기 전에 먼저 내 우선순위를 물어봐 줘. 그리고 네가 고른 안에 대해, 어떤 조건이면 다른 안이 더 낫게 되는지 알려 줘.
  • 추천 답을 그대로 선택하는 습관이 가장 쉬운 함정입니다.
  • 프로토타입은 결정용이라 최고 모델을 쓸 필요가 없습니다.
  • 이 연구는 한 분야·한 과제·한 모델만 다뤘다는 한계가 있습니다.

12. 평가로 프롬프트와 모델 다듬기

공개 벤치마크는 방향만 알려 주므로, 내 용도의 작은 평가(eval)를 만들어 프롬프트를 고치고 모델을 고르는 방법입니다. '느낌'을 눈에 보이는 신호로 바꿔 줍니다.

  1. 통제 사례, 이전에 실패한 엣지 케이스, 사람에게 넘기거나 거절해야 할 사례로 평가 세트를 만듭니다.
  2. 예시 케이스가 적으면 한두 개를 주고 Claude에게 50개 정도로 늘려 달라고 합니다.
  3. 현재 프롬프트로 평가를 돌려 실패 유형을 확인합니다.
  4. XML 태그로 역할·가이드라인·정책·말투를 구분하고 출력 형식을 명시합니다.
  5. 실패 유형을 하나씩 고치며 매번 평가를 다시 돌려 비교합니다.
  6. 모델과 생각(thinking)·노력(effort) 설정을 바꿔 가며 각 작업을 여러 번 돌립니다.
  7. 통과율, 토큰, 비용, 지연 시간을 비교해 중시하는 기준에 맞는 조합을 고릅니다.
예시
내가 만들려는 제품 경험은 고객 문의 답변 봇이야. 아래 테스트 케이스 두 개를 참고해서, 비슷한 케이스를 50개로 늘려 줘.
  • 토큰당 가장 싼 모델이 아니라 성공 한 건당 가장 싼 모델을 고릅니다.
  • 실행마다 편차가 있으니 한 번의 결과로 단정하지 않습니다.
  • API·도구 호출 실패 같은 인프라 문제와 모델 실패를 구분합니다.
  • 채점용 AI도 틀릴 수 있어 여러 채점 방법을 함께 씁니다.
