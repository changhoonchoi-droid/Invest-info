프롬프트·활용 요령

이 분야에서는 AI에게 맥락을 잘 주는 법, 답을 검증하고 휘둘리지 않는 법, 컨텍스트와 규칙 파일을 관리하는 법, 모델과 effort를 골라 비용을 아끼는 법을 다룹니다. 처음이라면 맥락 주기와 답변 검증(입문)부터 보세요. 그다음 Claude Code의 컨텍스트·스킬·모델 선택(중급)으로 넘어가고, 평가로 프롬프트와 모델을 고르는 법(고급)으로 마무리하면 됩니다.

1. 나에 대한 맥락을 주고 질문하기

AI는 사용자 메시지, 업로드한 문서, 대화 기록을 모두 고려해 답을 만듭니다. 그래서 내가 누구이고 무엇을 원하는지 알려 줄수록 답이 좋아집니다. AI를 처음 쓸 때, 또는 답이 뻔하게 나올 때 가장 먼저 써 볼 방법입니다.

  1. 내가 누구인지(직무·상황)와 지금 무슨 작업을 하는지 먼저 알려 줍니다.
  2. 좋은 결과가 어떤 모습인지(분량, 대상 독자, 형식)를 함께 적습니다.
  3. 글로 정리하기 어렵다면 휴대폰 음성 메모로 하고 싶은 말을 모두 녹음합니다.
  4. 녹음을 받아 적은 글을 AI에게 보내 자료나 초안으로 만들어 달라고 합니다.
  5. 초안을 여러 버전으로 요청하거나 다른 어조로 다시 써 달라고 합니다.
  6. AI가 나에게 필요한 것을 질문하도록 유도해, 빠진 맥락을 채웁니다.
예시
나는 중견기업 마케팅팀 3년 차 직장인이고, 다음 주 팀장 보고용으로 신제품 홍보 아이디어를 정리하고 있어. 좋은 결과는 A4 한 장 분량에 아이디어 3개와 각각의 예상 비용이 들어간 형태야. 더 좋은 답을 위해 필요한 정보가 있으면 먼저 나에게 질문해 줘.
  • 처음에는 무료로 시작하고, 한도에 자주 걸릴 때 유료로 넘어가도 충분합니다.
  • 회사 일에 쓸 때는 대화 내용이 모델 학습에 쓰이지 않도록 설정을 꺼 둡니다.
  • 하루 30분씩 매일 AI에게 묻고, AI가 나에게 질문하게 하는 습관을 들이면 빨리 늡니다.
  • AI는 정해진 답을 꺼내는 것이 아니라 새로 만들기 때문에, 같은 요청도 여러 번 받아 고를 수 있습니다.

2. AI 답변의 환각을 검증하기

AI는 그럴듯하지만 사실이 아닌 내용(환각)을 만들 수 있고, 맞을 때와 틀릴 때 모두 똑같이 확신 있게 말합니다. 숫자·출처·날짜·건강·법률·금전처럼 틀리면 곤란한 내용을 쓸 때 이 순서로 확인합니다.

  1. 틀렸을 때 어떤 일이 생기는지 스스로 묻고 확인 강도를 정합니다.
  2. 질문하기 전에 "모르면 모른다고 해도 괜찮다"고 미리 알려 줍니다.
  3. 가격·뉴스 같은 최신 정보는 웹 검색을 했는지 묻거나 검색을 요청합니다.
  4. 주장마다 근거가 되는 출처를 찾아 달라고 요청합니다.
  5. 제시된 출처를 직접 열어 그 내용이 실제로 있는지 확인합니다.
  6. 답이 의심스러우면 얼마나 확신하는지, 틀릴 만한 부분이 어디인지 묻습니다.
  7. 새 대화를 열거나 다른 AI에게 그 답변의 오류와 출처를 검증해 달라고 합니다.
  8. 중요한 작업은 믿을 만한 자료와 한 번 더 교차 확인합니다.
예시
아래 보고서 초안에 나온 통계와 인용을 하나씩 검토해 줘. 주장마다 근거가 되는 출처 링크를 붙이고, 출처를 찾지 못한 내용은 '확인 불가'로 표시해 줘. 모르면 모른다고 해도 괜찮아.
  • 파티 주제 브레인스토밍은 느슨하게 써도 되지만, 상사에게 보일 슬라이드의 통계는 반드시 검증합니다.
  • AI가 실제로 없는 논문이나 출처를 그럴듯하게 만들어 낼 수도 있습니다.
  • 자신 있는 말투나 깔끔한 문단·그래픽은 정확하다는 증거가 아닙니다.
  • 환각이 줄어들수록 확인을 건너뛰기 쉬우니, 숫자·날짜·인용은 습관처럼 다시 봅니다.

3. AI 추천에 휘둘리지 않고 결정하기

AI는 사용자가 원하는 답에 맞춰 주거나(아첨) 한쪽으로 기울어진 답을 낼 수 있습니다. 사람은 그 기울기를 그대로 따르면서도 스스로 결정했다고 착각하기 쉽습니다. 방법을 고르거나 의견을 정할 때 이 순서로 질문하면 판단의 주도권을 지킬 수 있습니다.

  1. AI가 방법을 추천하기 전에 내 우선순위(속도·비용·품질 등)를 먼저 묻게 합니다.
  2. 원하는 답을 흘리지 말고 이 결정에 대한 가장 강력한 찬성과 반대 논거는 무엇인가요?처럼 중립적으로 질문합니다.
  3. 답이 한쪽으로 치우쳤다고 느끼면 바로 반박하고, 더 균형 잡힌 접근과 솔직한 논의를 요청합니다.
  4. AI가 고른 안(A)에 대해 "What would change your advice?"(무엇이 바뀌면 조언이 달라지나요?)라고 묻습니다.
  5. 다른 안(B)이 더 나아지는 조건이 지금 내 상황에 해당하는지 직접 판단합니다.
  6. 그래도 결정이 어려우면 작고 저렴한 모델로 여러 안을 시제품으로 만들어 보고, 내가 고른 뒤 시제품은 버립니다.
  7. 결정한 내용을 AI에게 전달해 그 방향으로 작업을 이어 가게 합니다.
예시
추천하기 전에 먼저 내가 이 일에서 무엇을 가장 중요하게 생각하는지 질문해 줘. 그다음 추천안을 주고, 어떤 조건이 바뀌면 다른 안이 더 나아지는지도 함께 알려 줘. (What would change your advice?)
  • 추천 답을 그대로 고르는 습관이 가장 쉬운 함정입니다.
  • 결정용 시제품에는 최고 모델을 쓸 필요가 없습니다.
  • 같은 질문을 다른 각도에서 다시 물어보면 편향을 알아차리기 쉽습니다.
  • 정치 주제가 아닌 업무 판단에서도 똑같이 유용합니다.

4. Claude Code 컨텍스트 관리하기

컨텍스트는 Claude의 작업 기억으로, 읽은 파일, 실행한 명령, 주고받은 메시지가 모두 공간을 차지합니다. 한도에 가까워지면 자동으로 압축되면서 세부 내용이 사라질 수 있습니다. 긴 작업을 하거나 답이 점점 엉뚱해질 때 이 방법으로 정리합니다.

  1. 요청은 구체적으로 적어 Claude가 불필요한 파일을 읽지 않게 합니다.
  2. 같은 기능 작업을 이어 갈 때는 /compact로 대화를 압축합니다.
  3. 새 기능을 시작할 때는 /clear로 컨텍스트를 비우고 시작합니다.
  4. 지금 작업과 관련 없는 MCP 서버는 끕니다.
  5. 답만 필요한 조사는 서브에이전트에게 맡겨, 요약만 돌려받게 합니다.
  6. 자주 쓰는 작업 방법은 MCP 대신 스킬로 만들어 필요할 때만 불러오게 합니다.
예시
/compact
  • MCP 서버는 기본적으로 모든 도구를 컨텍스트에 올리지만, 스킬은 이름과 설명만 먼저 불러옵니다.
  • 서브에이전트는 별도 컨텍스트 창을 쓰므로 메인 대화를 가볍게 유지할 수 있습니다.
  • 컨텍스트 창이 크다고 다 기억하는 것은 아닙니다. 정답이 든 짧은 프롬프트(약 300토큰)가 긴 전체 기록(약 11만 토큰)보다 더 정확했습니다.
  • 컨텍스트는 최소한만 주고, 모델이 필요한 것을 찾아오게 하는 방식이 권장됩니다.

5. CLAUDE.md와 스킬로 실수 막기

Claude가 같은 실수를 반복하면 매번 다시 시키지 말고 규칙 파일에 적어 두는 것이 좋습니다. 모든 대화에 항상 필요한 규칙은 CLAUDE.md에, 특정 상황에서만 쓰는 작업 방법은 스킬(SKILL.md)에 둡니다. 새 모델이 나오면 이 지침을 모델에 맞게 다듬을 수도 있습니다.

  1. Claude가 실수하면 다시 시키기 전에 그 실수를 막을 규칙을 한 줄로 정리합니다.
  2. 모든 작업에 적용할 규칙이면 CLAUDE.md에 적습니다.
  3. 특정 작업에서만 쓰는 방법이면 SKILL.md 파일로 만들고, 어떤 요청에 쓰는지 설명(description)을 분명히 씁니다.
  4. 모든 프로젝트에서 쓸 스킬은 홈 디렉터리의 .claude/skills에 둡니다.
  5. 팀과 공유할 스킬은 저장소 루트의 .claude/skills에 둡니다.
  6. 새 모델로 바꿨다면 Claude Code에서 /claude-api prompt-audit를 실행합니다.
  7. CLAUDE.md와 스킬의 지침이 새 모델에 맞게 조정되었는지 확인합니다.
예시
/claude-api prompt-audit
  • CLAUDE.md는 모든 대화에 불러오고, 스킬은 요청이 맞을 때만 불러와 컨텍스트를 아낍니다.
  • 슬래시 명령은 직접 입력해야 하지만 스킬은 설명에 맞는 요청이 오면 자동으로 적용됩니다.
  • /claude-api prompt-audit는 API를 쓰지 않고 Claude Code만 써도 사용할 수 있습니다.
  • 금지 항목을 길게 나열하거나 서로 부딪히는 규칙을 넣으면 오히려 실패의 원인이 됩니다.

6. 작업에 맞게 모델과 effort 고르기

작업 비용은 모델, effort(추론 노력), 캐시 세 가지로 정해집니다. 더 똑똑한 모델이 적은 단계로 일을 끝내 오히려 싸게 먹히기도 합니다. 사용량 한도가 빨리 차거나 결과가 부족할 때 작업 종류에 따라 조합을 바꿉니다.

  1. 작업이 열린 작업(심층 조사·복잡한 분석·장시간 에이전트)인지 반복 작업(문서 요약·메일 초안·데이터 추출)인지 구분합니다.
  2. 열린 작업이면 Fable 5.1을 고르고 effort를 medium으로 시작합니다.
  3. 반복 작업이면 Opus나 Sonnet을 기본으로 씁니다.
  4. Claude Code에서는 /effort로 노력 수준을 정합니다. Opus 5.5의 기본값은 medium입니다.
  5. 여러 파일이나 프로젝트 전체를 고치는 작업이면 effort를 high로 올립니다.
  6. 결과가 부족할 때만 effort를 한 단계씩 올리거나 더 큰 모델로 바꿉니다.
  7. 탐색만 하는 서브에이전트는 작고 저렴한 모델로 돌립니다.
예시
/effort
  • 토큰 단가가 아니라 작업 한 건당 비용으로 비교합니다. Opus 5.5는 필요한 토큰이 적어 작업당 비용이 약 40% 낮았습니다.
  • 강한 모델일수록 낮은 effort로 시작해 필요할 때 올립니다.
  • 예전 방식: 5월 영상에서는 고민되면 extra high(X high)를 권했지만, 9월 Opus 5.5·Fable 5.1 영상부터는 medium으로 시작해 올리는 방식을 권합니다.
  • effort를 max로 올리면 low 대비 시간과 토큰이 약 10배 들 수 있습니다.

7. Claude에게 인터뷰시켜 스펙 만들기

결과를 자세히 지시하는 대신, Claude가 나에게 질문해서 요구사항을 끌어내게 하는 방법입니다. 무엇을 원하는지 아직 흐릿할 때, 또는 앱·문서를 새로 만들기 시작할 때 씁니다.

  1. Claude Code에서 Shift+Tab을 눌러 auto mode로 바꿉니다.
  2. /effort로 노력 수준을 정합니다.
  3. 만들 것의 관심 영역(예: 대상 사용자)만 주고 결과는 지나치게 정하지 않습니다.
  4. 프롬프트에 ask user question 도구를 써서 질문하라고 명시합니다.
  5. Claude가 띄우는 질문에 하나씩 답합니다.
  6. 답이 끝나면 Claude가 작성한 스펙을 먼저 검토한 뒤 작업을 맡깁니다.
예시
회식비를 팀원끼리 나누는 간단한 앱을 만들고 싶어. 대상 사용자는 20~30명 규모 팀의 총무야. 바로 만들지 말고 ask user question 도구를 써서 나에게 필요한 것을 질문한 다음, 내 답을 바탕으로 스펙을 정리해 줘.
  • '더 좋게 만들어', '실수 없이 만들어' 같은 막연한 지시는 피합니다.
  • 스펙은 긴 마크다운 대신 정보 밀도가 높은 HTML 파일로 받으면 검토하기 쉽습니다.
  • 빠르게 스펙을 여러 번 고칠 때는 /fast 모드가 유용합니다.
  • 예전 방식: 계획 모드(Shift+Tab으로 전환)로 먼저 계획을 받았지만, 6월 회고 영상에서는 최신 모델에서는 계획 모드 대신 오토 모드를 쓴다고 합니다.

8. 사용 패턴으로 모드 추천받기

모드(Mods)는 Claude Code의 화면과 행동 방식을 바꾸는 작은 프로그램으로, 10월 1일 공식 발표되었습니다. 내 세션 기록을 분석해 반복되는 작업을 찾고, 비용을 아끼거나 집중을 돕는 모드를 추천받아 만들 수 있습니다.

  1. Claude Code 세션 로그를 최대한 훑어 내가 자주 반복하는 말과 작업을 파악해 달라고 요청합니다.
  2. 흐름을 돕고 비용을 아끼며 집중하게 해 줄 모드 다섯 개를 추천해 달라고 요청합니다.
  3. 추천 목록에서 마음에 드는 번호를 골라 만들어 달라고 요청합니다.
예시

  • 추천에는 내 사용 패턴과 그 근거가 함께 나옵니다.
  • 스킬·MCP는 지식과 도구를 건네는 방식이고, 모드는 작업 환경 자체를 바꿉니다. 창·버튼 같은 화면 요소는 모드로만 만들 수 있습니다.
  • 영상에서는 토큰 사용량을 보여 주는 모드도 만들어 비용 관리에 활용했습니다.

9. 평가 세트로 프롬프트 개선하기

프롬프트를 고칠 때 느낌으로 판단하지 않고, 테스트 사례를 모은 평가 세트로 결과를 비교하는 방법입니다. 모델을 바꾼 뒤 성능이 떨어졌거나, 반복 업무용 프롬프트를 오래 쓸 계획일 때 씁니다.

  1. 만들려는 업무 상황을 Claude에게 설명하고 예시 테스트 사례를 한두 개 줍니다.
  2. 테스트 사례를 늘려 달라고 해, 정상 사례·이전에 실패한 까다로운 사례·사람에게 넘기거나 거절해야 할 사례를 고루 모읍니다.
  3. 현재 프롬프트로 평가를 돌려 어떤 유형에서 실패하는지 확인합니다.
  4. 사실과 다른 역할 설명과 웹에서 복사해 온 불필요한 내용을 지웁니다.
  5. XML 태그로 역할·가이드라인·정책·말투를 구분해 구조를 정리합니다.
  6. 출력 형식을 정하는 '출력 계약'을 추가합니다.
  7. 평가를 다시 돌려 실패 유형을 하나씩 고치며 결과를 비교합니다.
  • 가이드라인·정책·데이터를 사람이 구분하기 어려우면 모델도 구분하기 어렵습니다.
  • 실행마다 결과가 달라지니 한 번 돌린 결과로 단정하지 않습니다.
  • 모델 기반 채점(LLM 판정)도 틀릴 수 있으니 코드 기반 검사와 함께 씁니다.
  • 영상에서는 예시 1~2개를 약 50개의 테스트 사례로 늘렸습니다.

10. 평가로 내 용도에 맞는 모델 고르기

공개 벤치마크는 방향만 알려 줄 뿐 내 업무에 맞는지는 알려 주지 않습니다. 작은 평가라도 직접 만들어 품질·지연·비용을 비교하면, 새 모델이 나올 때마다 같은 절차로 옮길지 판단할 수 있습니다.

  1. 입력과 성공 기준을 가진 테스트 작업을 모아 평가 데이터 세트를 만듭니다.
  2. 작업마다 최종 결과뿐 아니라 올바른 단계를 거쳤는지도 점검하는 채점 기준을 붙입니다.
  3. 답의 품질 비교는 LLM 판정으로, 특정 도구 호출이나 값 확인은 코드 기반 검사로 채점합니다.
  4. 모델과 thinking·effort 설정을 바꿔 가며 각 작업을 여러 번 돌립니다.
  5. 로그를 열어 API·도구 호출 실패 같은 인프라 문제를 모델 실패와 분리합니다.
  6. 통과율·토큰·비용·지연을 비교해 내가 중시하는 기준에 맞는 조합을 고릅니다.
  • 토큰당 가장 싼 모델이 아니라 성공 한 건당 가장 싼 모델을 고릅니다.
  • 결과 편차가 크면 작업 정의나 채점 기준이 불명확하다는 신호입니다.
  • 새 모델이 나오면 평가부터 백그라운드로 돌려 보는 것이 출시 전 시험 팀들의 방식입니다.
  • 프롬프트 캐싱 같은 컨텍스트 관리로 비용·성능 자체를 개선할 수도 있습니다.

11. 검사 루프부터 만들고 구조 키우기

에이전트 작업 흐름을 복잡한 그래프로 짜기 전에, 결과를 코드로 검사하는 루프 하나로 시작하는 방법입니다. 내 하네스(규칙·도구·작업 흐름)를 그래프로 그려 검사 없이 넘어가는 지점을 찾는 데도 씁니다.

  1. 내 에이전트 하네스 설명(설정 파일, 규칙 문서, 작업 흐름)을 준비합니다.
  2. 영상 설명란의 프롬프트를 복사해 ○○ 자리에 하네스 설명을 붙여 넣습니다.
  3. Claude나 ChatGPT에 붙여 넣어 실행합니다.
  4. 노드·엣지·상태 표와, 엣지마다 코드·모델·사람 중 누가 다음 단계를 정하는지 적힌 결과를 받습니다.
  5. 함께 나온 머메이드 그림에서 검사 없이 넘어가는 엣지를 찾습니다.
  6. 그 지점에 결과를 코드로 확인하는 검사기를 먼저 붙여 루프 하나로 돌려 봅니다.
  7. 병렬 후 취합, 독립 검증, 단계별 다른 모델·권한, 사람 승인, 장시간 작업 저장·재개가 필요할 때만 그래프로 나눕니다.
  • 실험에서 코드 검사 루프는 8.3초·16,688토큰, 그래프는 53.3초·73,692토큰으로 그래프가 4배 넘게 비쌌습니다.
  • 한 번에 다 하는 큰 프롬프트 대신 생성·평가·수리 세 프롬프트로 나누면 토큰과 지연이 줄었다는 사례도 있습니다.
  • 영상 예시에서는 엣지 20개 중 사람이 정하는 것이 2개뿐이었습니다. 사람 확인이 필요한 곳이 빠졌는지 살펴보세요.
  • 프롬프트 전문은 영상 설명란 자료실에서 볼 수 있습니다.
