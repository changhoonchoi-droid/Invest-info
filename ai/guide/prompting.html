프롬프트·활용 요령

이 페이지에서는 AI에게 일을 시키는 말(프롬프트)을 쓰는 법, 대화 기억(컨텍스트)을 관리하는 법, 답의 품질을 확인하는 법, 비용과 사용량을 아끼는 법을 배웁니다. 먼저 보안 설정과 첫 대화 같은 기초를 익히고, 답을 검증하는 습관을 들인 뒤, 컨텍스트 관리와 모델 선택 같은 응용으로 넘어가 보세요.

입문

1. 대화가 학습에 쓰이지 않게 설정하기

회사 일에 AI를 쓰기 전에 내 대화가 모델 학습에 쓰이지 않도록 끄는 설정입니다. 기밀이나 개인정보가 섞일 수 있는 직장인이 가장 먼저 해 둘 일입니다.

  1. ChatGPT 설정(Settings)에서 Data controls로 들어갑니다.
  2. Improve the model for everyone 항목을 끕니다.
  3. 이후 개인정보와 기밀 정보는 입력하지 않는 습관을 들입니다.
  • 회사 일에 쓰기 전에 반드시 먼저 끕니다.
  • 설정을 꺼도 개인정보와 기밀 정보는 입력하지 않는 것이 안전합니다.

2. AI에게 나를 알려 주며 첫 대화 시작하기

AI를 처음 쓸 때는 무조건 써 보는 것이 시작입니다. 핵심은 AI에게 나에 대한 정보, 즉 맥락을 주는 것입니다.

  1. 완전 처음이라면 ChatGPT 앱의 보이스 모드로 말하듯 질문합니다.
  2. 어느 정도 써 봤다면 Claude 데스크톱 앱에서 컴퓨터 속 파일을 보여 주며 나를 파악하게 합니다.
  3. 내가 누구이고 무슨 일을 하는지 알려 줍니다.
  4. 하루 30분, 내가 질문하고 AI도 나에게 질문하도록 유도하는 대화를 이어 갑니다.
  5. 무료로 쓰다가 한도에 막힐 때 유료로 넘어갑니다.
예시
내가 어떤 일을 하는 사람인지 알 수 있도록 나에게 질문을 해 줘. 내 대답을 바탕으로 앞으로 내 업무에 어떻게 도움을 줄 수 있을지 알려 줘.
  • 보이스 모드는 한 시간 제한이 있다고 언급됩니다.
  • 구독 기준은 금액이 아니라 쓰다가 한도에 막히는지 여부입니다.

3. AI를 과외 선생님으로 쓰기

새 분야를 배울 때 AI에게 과외 선생님 역할을 맡기고 커리큘럼을 만들게 하는 방법입니다. 이해하며 이어 가는 것이 핵심입니다.

  1. 배우고 싶은 분야를 말합니다.
  2. 네가 앞으로 과외 선생님으로서 나를 공부할 수 있도록 도와줘라고 요청합니다.
  3. AI가 만들어 주는 커리큘럼을 받습니다.
  4. 답변을 이해하면서 질문과 문제를 이어 갑니다.
예시
네가 앞으로 과외 선생님으로서 나를 공부할 수 있도록 도와줘. 나는 엑셀 데이터 분석을 배우고 싶어. 먼저 커리큘럼부터 만들어 줘.
  • 답변을 이해하지 않고 복사·붙여 넣기만 하면 실력이 늘지 않습니다.
  • 책을 읽은 뒤 AI에게 저자 역할을 시켜 질문해 볼 수 있습니다.

4. AI 답변 검증하며 쓰기

AI는 그럴듯하지만 사실이 아닌 내용(환각)을 만들거나 듣고 싶은 말에 맞춰 동의(아첨)할 수 있습니다. 질문의 중요도에 따라 확인 강도를 조절하는 방법입니다.

  1. 틀렸을 때 어떤 일이 생기는지 스스로 묻고 확인 강도를 정합니다.
  2. 미리 모르면 모른다고 말해 달라고 허용합니다.
  3. 주장마다 근거가 되는 출처를 요청합니다.
  4. 제시된 출처를 직접 열어 실제로 그 내용이 있는지 확인합니다.
  5. 원하는 답을 흘리지 말고 이 결정에 대한 가장 강력한 찬성과 반대 논거는 무엇인가요?처럼 중립적으로 질문합니다.
  6. 답이 의심스러우면 얼마나 확신하는지, 틀릴 만한 부분이 있는지 묻습니다.
  7. 중요한 작업은 새 대화를 열어 오류를 찾게 하거나 다른 AI와 믿을 만한 자료로 교차 확인합니다.
예시
이 결정에 대한 가장 강력한 찬성과 반대 논거는 무엇인가요? 모르는 부분은 모른다고 말해도 괜찮아요.
  • 브레인스토밍은 느슨하게, 상사에게 보일 슬라이드의 통계나 숫자·날짜·인용은 반드시 확인합니다.
  • AI가 실제로 없는 출처를 그럴듯하게 만들어 낼 수도 있습니다.
  • 자신 있는 말투나 깔끔한 문단·그래픽은 정확성의 증거가 아닙니다.
  • 환각이 줄수록 확인을 건너뛰기 쉬우니 주의합니다.

5. 더 나은 답을 얻는 프롬프트 쓰기

AI는 정해진 답을 꺼내는 것이 아니라 매번 생성합니다. 이 점을 활용해 맥락을 주고 여러 버전을 요청하면 더 좋은 결과를 얻습니다.

  1. 내가 누구이고 무슨 작업 중인지, 좋은 결과가 어떤 것인지 알려 줍니다.
  2. 가격·뉴스 등 최신 정보는 웹 검색을 했는지 확인하거나 검색을 요청합니다.
  3. 검색했다면 제시된 출처를 열어 정확성을 확인합니다.
  4. 초안을 여러 버전으로 요청하거나 다른 어조로 다시 써 달라고 합니다.
  5. 틀리면 문제가 되는 사실은 직접 다시 확인합니다.
예시
나는 영업팀 대리이고, 내일 거래처에 보낼 안내 메일을 쓰는 중이야. 정중하지만 짧게, 세 가지 버전으로 초안을 써 줘.
  • AI가 웹 검색을 했다고 단정하지 말고 직접 물어봅니다.
  • 모델은 훈련 시점 이후의 사실을 검색 도구 없이는 확실히 알지 못합니다.
  • 대화 이어가기, 형식·길이 지정, 예시 제공, 부분 수정 요청도 효과적입니다.

6. 에러 상황을 AI에게 잘 전달하기

AI로 웹사이트 등을 만들다 오류가 나면 단서를 충분히 주어야 잘 고쳐 줍니다. 오류 메시지, 발생 시점, 기대 동작을 함께 전달하는 방법입니다.

  1. 문제 화면에서 마우스 오른쪽 버튼을 눌러 검사를 엽니다.
  2. 개발자 도구에서 콘솔 탭의 오류 메시지를 복사하거나 캡처합니다.
  3. 프롬프트 창에 오류 메시지를 붙여 넣습니다.
  4. 언제 발생하는지(예: 스크롤할 때)를 적습니다.
  5. 원래 기대하는 동작과 현재 문제를 함께 적습니다.
  6. 가능하면 발생 화면 스크린샷도 첨부합니다.
  • 언제·어디서·어떻게 발생했는지 단서를 많이 줄수록 해결이 잘 됩니다.
  • 구체적 질문, 이미지 첨부, 공식 문서 제공도 성공률을 높입니다.

7. AI가 인터뷰하게 해서 요구사항 정리하기

모델이 강력해질수록 제약을 줄이고, AI가 사용자에게 질문해 요구사항을 끌어내게 하는 편이 좋습니다. 막연한 아이디어를 구체적인 기획서로 만들 때 씁니다.

  1. Claude Code에서 Shift+Tab으로 auto mode로 전환합니다.
  2. /effort로 노력 수준을 설정합니다(권장 X high).
  3. 프롬프트에서 만들 앱의 관심 영역(예: 대상 사용자)만 주고 결과는 과하게 지정하지 않습니다.
  4. 프롬프트에 ask user question 도구를 쓰라고 명시합니다.
  5. Claude가 띄우는 질문에 차례로 답합니다.
  6. 답변이 끝나면 Claude가 작성하는 스펙을 확인합니다.
  • '더 좋게 만들어', '실수 없이 만들어' 같은 프롬프트는 피합니다.
  • 빠르게 스펙을 반복할 때는 /fast 모드가 유용합니다.
  • 계획은 긴 마크다운보다 정보 밀도가 높은 HTML로 받아 검토하는 방식이 소개되었습니다.

8. 에이전트 추천에 휘둘리지 않고 결정하기

연구에서 분석가들은 에이전트가 기운 쪽을 86% 따랐고, 스스로 결정했다고 착각하기 쉬웠습니다. 추천을 그대로 받아들이지 않고 내 기준으로 결정하는 방법입니다.

  1. 에이전트가 방법을 추천하기 전에 내 우선순위부터 묻게 합니다.
  2. 결정이 어려우면 작고 저렴한 모델로 여러 버전의 프로토타입을 병렬로 만듭니다.
  3. 프로토타입을 보고 내가 결정한 뒤 프로토타입은 버립니다.
  4. 결정한 내용을 에이전트에게 전달합니다.
  5. 에이전트가 고른 안(A)에 대해 "What would change your advice?"라고 묻습니다.
  6. 답을 보고 안(B)이 최적이 되는 조건이 현재 상황에 해당하는지 판단합니다.
예시
추천을 하기 전에 먼저 내 우선순위가 무엇인지 나에게 물어봐 줘. 그리고 네가 고른 안에 대해 What would change your advice?
  • 추천 답을 그대로 선택하는 습관이 가장 쉬운 함정입니다.
  • 프로토타입은 결정용이므로 최고 모델을 쓸 필요가 없습니다.

9. 컨텍스트 아끼며 길게 작업하기

컨텍스트는 AI의 작업 기억이며 읽은 파일, 실행한 명령, 주고받은 메시지가 모두 공간을 차지합니다. 한도에 가까워지면 세부 내용이 사라질 수 있어 관리가 필요합니다.

  1. 같은 기능 작업을 이어 갈 때는 /compact를 씁니다.
  2. 새 기능을 시작할 때는 /clear를 씁니다.
  3. 요청은 구체적으로 합니다.
  4. 관련 없는 MCP 서버는 끕니다.
  5. 답만 필요한 조사는 서브에이전트에 맡겨 요약만 받습니다.
  • MCP 서버는 기본적으로 모든 도구를 컨텍스트에 올리므로 불필요한 서버는 끄는 편이 좋습니다.
  • 스킬은 전체를 컨텍스트에 올리지 않아 MCP보다 부담이 적습니다.
  • 컨텍스트 창이 커져도 정답의 위치와 길이에 따라 정확도가 떨어지므로 컨텍스트는 기억이 아닙니다.
  • 최신 방식은 최소한의 컨텍스트만 주고 모델이 알아서 찾게 하는 것입니다.

10. 같은 실수를 막는 규칙 남기기

AI가 실수했을 때 다시 시키지 않고 CLAUDE.md나 스킬에 적어 두면 같은 실수를 막을 수 있습니다. 스킬은 한 번 가르친 작업 방법이 관련 상황에서 자동 적용되는 파일입니다.

  1. AI가 실수하면 같은 요청을 반복하지 않고 원인을 파악합니다.
  2. 막고 싶은 실수를 CLAUDE.md에 규칙으로 적습니다.
  3. 반복되는 작업 방법은 SKILL.md 파일로 만들고 설명(description)을 분명히 씁니다.

11. 작업별로 모델과 effort 고르기

작업 비용은 모델, effort(추론 노력), 캐시 세 가지로 정해집니다. 작업 종류에 맞게 고르면 품질을 지키면서 비용과 사용량을 줄일 수 있습니다.

  1. 작업이 열린 작업(심층 조사, 복잡한 분석)인지 반복 작업(문서 요약, 메일 초안)인지 구분합니다.
  2. 열린 작업이면 Fable 5.1을 고르고 effort를 medium으로 시작합니다.
  3. 결과가 부족하면 effort를 단계적으로 올립니다.
  4. 반복 작업이면 Opus나 Sonnet을 기본으로 씁니다.
  5. 필요할 때만 Fable로 바꿉니다.
  6. 서브에이전트는 특정 작업만 맡으므로 저렴한 모델부터 적용합니다.
  • 토큰 단가가 아니라 작업당 비용으로 비교합니다.
  • Opus 5.5의 기본 effort는 medium이며 대부분 충분하고, 여러 파일에 걸친 수정에는 high가 필요합니다.
  • effort를 max로 올리면 low보다 시간·토큰이 약 10배 들 수 있습니다.
  • 예전 방식: 계획 모드를 먼저 쓰는 것이 중요했지만, 최신 모델에서는 오토 모드를 쓰는 방식으로 바뀌었습니다.

12. 평가로 프롬프트와 모델 고르기

프롬프트를 고치거나 모델을 바꿀 때 느낌 대신 직접 만든 평가(eval)로 비교하는 방법입니다. 공개 벤치마크는 방향만 알려 주므로 내 업무에 맞는 작은 평가가 더 중요합니다.

  1. 입력과 성공 기준을 가진 테스트 작업을 모아 평가 데이터 세트를 만듭니다. 통제 사례, 과거 실패 사례, 거절해야 할 사례를 포함합니다.
  2. 현재 프롬프트로 평가를 돌려 실패 유형을 확인합니다.
  3. 역할 설명의 사실 오류와 불필요한 내용을 지우고, XML 태그로 역할·가이드라인·정책·말투를 구분합니다.
  4. 출력 형식을 정하는 출력 계약을 추가합니다.
  5. 모델과 생각(thinking)·노력(effort) 설정을 바꿔 가며 각 작업을 여러 번 돌립니다.
  6. 로그를 열어 API·도구 호출 실패 같은 인프라 문제를 모델 실패와 분리합니다.
  7. 통과율, 토큰, 비용, 지연 시간을 비교해 중시하는 기준에 맞는 설정을 고릅니다.
  • 토큰당 가장 싼 모델이 아니라 성공 한 건당 가장 싼 모델을 고릅니다.
  • 결과 편차가 크면 작업 정의나 평가가 불명확하다는 신호입니다.
  • 테스트 케이스가 1~2개뿐이면 Claude에게 상황 설명과 예시를 주고 늘려 달라고 할 수 있습니다.
  • 구조를 늘리기 전에 결과를 코드로 검사하는 검사기부터 만들고, 기본은 루프 하나로 시작합니다.
