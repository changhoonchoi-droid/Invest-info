1. 무료로 시작해 AI와 첫 대화 나누기

AI는 설치나 공부보다 먼저 써 보는 것이 중요합니다. 처음이라면 말로 질문하는 방식으로 부담 없이 시작하고, 한도에 막힐 때 유료로 넘어가는 순서를 따릅니다.

  1. 완전 처음이면 ChatGPT 앱의 보이스 모드로 말하듯 질문합니다.
  2. 어느 정도 해 봤다면 Claude 데스크톱 앱을 설치합니다.
  3. 내가 누구이고 어떤 일을 하는지 AI에게 알려 줍니다.
  4. 컴퓨터 속 파일을 보여 주며 나를 파악하게 합니다.
  5. 하루 30분, 내가 질문하고 AI도 나에게 질문하게 합니다.
  6. 무료 한도에 자주 막힐 때 유료 플랜으로 올립니다.
  • 핵심은 AI에게 맥락, 즉 나에 대한 정보를 주는 것입니다.
  • 구독 기준은 금액이 아니라 쓰다가 한도에 막히는지, 그리고 쓴 만큼 돈·시간·성과가 나는지입니다.
  • 보이스 모드는 한 시간 제한이 있다고 합니다.

2. 회사 일 전에 학습 사용 끄기

ChatGPT에서 내 대화가 모델 학습에 쓰이지 않도록 설정하는 방법입니다. 회사 일에 AI를 쓰기 전에 먼저 해 두어야 합니다.

  1. ChatGPT 설정(Settings)에서 Data controls로 들어갑니다.
  2. Improve the model for everyone 항목을 끕니다.
  • 회사 일에 쓰기 전에 반드시 먼저 끕니다.
  • 개인정보와 기밀 정보는 입력하지 않습니다.

3. AI가 내 질문에 답하는 원리 알기

AI는 정해진 답을 꺼내는 것이 아니라 다음 단어를 예측해 답을 생성합니다. 이 원리를 알면 맥락을 주고 여러 버전을 요청하는 이유를 이해할 수 있습니다.

  1. 내가 누구이고 무슨 작업 중인지, 좋은 결과가 어떤 것인지 알려 줍니다.
  2. 가격·뉴스 등 최신 정보는 웹 검색을 했는지 확인하거나 검색을 요청합니다.
  3. 검색했다면 제시된 출처를 열어 정확성을 확인합니다.
  4. 초안을 여러 버전으로 요청하거나 다른 어조로 다시 써 달라고 합니다.
  5. 틀리면 문제가 되는 사실은 직접 다시 확인합니다.
예시
저는 중소기업 마케팅 담당자입니다. 신제품 소개 메일 초안을 어조를 다르게 해서 3가지 버전으로 써 주세요.
  • AI가 웹 검색을 했다고 단정하지 말고 직접 물어봅니다.
  • 자신 있는 말투나 깔끔한 결과물은 정확성의 증거가 아닙니다.
  • 모델은 훈련 시점 이후의 사실을 검색 도구 없이는 확실히 알지 못합니다.

4. AI 답변 검증하며 쓰기

AI는 없는 내용을 사실처럼 말하는 환각과, 듣고 싶은 말에 맞춰 동의하는 아첨 때문에 틀릴 수 있습니다. 질문의 중요도에 따라 확인 강도를 조절하는 방법입니다.

  1. 틀렸을 때 어떤 일이 생기는지 스스로 묻고 확인 강도를 정합니다.
  2. 미리 모르면 모른다고 말해 달라고 알려 줍니다.
  3. 주장마다 근거가 되는 출처를 찾아 달라고 요청합니다.
  4. 제시된 출처를 직접 열어 실제로 그 내용이 있는지 확인합니다.
  5. 의심스러우면 얼마나 확신하는지, 틀릴 만한 부분이 있는지 묻습니다.
  6. 새 대화를 열어 그 답변의 오류를 찾아 달라고 하고, 중요한 작업은 믿을 만한 자료와 교차 확인합니다.
예시
이 결정에 대한 가장 강력한 찬성과 반대 논거는 무엇인가요? 모르는 부분은 모른다고 말해 주세요.
  • 원하는 답을 흘리지 말고 중립적으로 질문합니다.
  • 숫자·날짜·인용은 특히 다시 확인합니다. AI가 없는 출처를 만들어 낼 수도 있습니다.
  • 상사에게 보일 슬라이드의 통계는 반드시 검증하고, 다른 AI로 교차 검증하는 방법도 있습니다.
  • 편향이 느껴지면 바로 반박하고 같은 질문을 다른 각도에서 다시 물어봅니다.

5. 에러를 AI에게 잘 전달하기

AI가 만든 결과물에 문제가 생겼을 때 단서를 충분히 주면 해결이 훨씬 잘 됩니다. 브라우저의 오류 메시지를 복사해 상황과 함께 전달하는 방법입니다.

  1. 문제 화면에서 마우스 오른쪽 버튼을 눌러 검사를 엽니다.
  2. 개발자 도구에서 콘솔 탭의 오류 메시지를 복사하거나 캡처합니다.
  3. 프롬프트 창에 오류 메시지를 붙여 넣습니다.
  4. 언제 발생하는지(예: 스크롤할 때)를 적습니다.
  5. 원래 기대하는 동작과 현재 문제를 함께 적습니다.
  6. 가능하면 발생 화면 스크린샷도 첨부합니다.
  • 언제·어디서·어떻게 발생했는지 단서를 많이 줄수록 해결이 잘 됩니다.
  • 성공률을 높이는 원칙은 구체적 질문, 이미지 첨부, 공식 문서 제공, 에러 상황의 명확한 설명입니다.

6. Claude Code 컨텍스트 아껴 쓰기

컨텍스트는 Claude의 작업 기억으로, 읽은 파일·명령·메시지가 모두 공간을 차지합니다. 한도에 가까워지면 자동 압축되지만 세부 내용이 사라질 수 있어 직접 관리하는 요령이 필요합니다.

  1. 같은 기능 작업을 이어갈 때는 /compact로 대화를 압축합니다.
  2. 새 기능을 시작할 때는 /clear로 컨텍스트를 비웁니다.
  3. 요청은 구체적으로 합니다.
  4. 관련 없는 MCP 서버는 꺼 둡니다.
  5. 답만 필요한 조사는 서브에이전트에 맡깁니다.
  • MCP 서버는 기본적으로 모든 도구를 컨텍스트에 올립니다.
  • 스킬은 MCP와 비슷하지만 전체를 컨텍스트에 올리지 않습니다.
  • 서브에이전트는 별도 컨텍스트 창을 쓰고 요약만 돌려줍니다.
  • 최신 방식은 최소한의 컨텍스트만 주고 모델이 알아서 찾게 하는 것입니다.

7. 에이전트 추천에 휘둘리지 않고 결정하기

Anthropic 연구에서 분석가의 86%가 에이전트가 기운 쪽을 따랐습니다. 추천을 그대로 고르는 습관을 피하고 내 기준으로 결정하는 방법입니다.

  1. 에이전트가 방법을 추천하기 전에 내 우선순위부터 묻게 합니다.
  2. 결정이 어려우면 작고 저렴한 모델로 여러 버전의 프로토타입을 병렬로 만듭니다.
  3. 프로토타입을 보고 내가 결정한 뒤 프로토타입은 버립니다.
  4. 결정한 내용을 에이전트에게 전달합니다.
  5. 에이전트가 고른 안(A)에 대해 "What would change your advice?"라고 묻습니다.
  6. 답을 보고 안(B)이 최적이 되는 조건이 현재 상황에 해당하는지 판단합니다.
예시
What would change your advice?
  • 추천 답을 그대로 선택하는 습관이 가장 쉬운 함정입니다.
  • 프로토타입은 결정용이므로 최고 모델을 쓸 필요가 없습니다.
  • 연구는 한 분야·한 과제·한 모델만 다룬 한계가 있습니다.

8. Claude에게 인터뷰시켜 스펙 만들기

모델이 강력해질수록 제약을 줄이고 Claude가 질문해 요구사항을 끌어내게 하는 방식이 효과적입니다. 앱의 관심 영역만 주고 인터뷰로 스펙을 완성합니다.

  1. Shift+Tab으로 auto mode로 전환합니다.
  2. /effort로 노력 수준을 설정합니다(권장 X high).
  3. 프롬프트에서 만들 앱의 관심 영역(예: 대상 사용자)만 주고 결과는 과하게 지정하지 않습니다.
  4. 프롬프트에 ask user question 도구를 쓰라고 명시합니다.
  5. Claude가 띄우는 질문에 차례로 답합니다.
  6. 답변이 끝나면 Claude가 작성하는 스펙을 확인합니다.
  • '더 좋게 만들어', '실수 없이 만들어' 같은 프롬프트는 피합니다.
  • 빠르게 스펙을 반복할 때는 /fast 모드가 유용합니다.
  • 계획을 HTML 파일로 받아 먼저 검토하는 방식도 있으며, 이때는 시각 능력이 좋은 Opus 4.7을 권했습니다.

9. 작업별로 모델과 effort 고르기

작업 비용은 모델, effort(추론 노력), 캐시 세 가지로 정해집니다. 토큰 단가가 아니라 작업당 비용으로 보고, 작업 종류에 맞춰 고르는 방법입니다.

  1. 작업이 열린 작업(심층 조사, 복잡한 분석, 장시간 에이전트)인지 반복 작업(문서 요약, 메일 초안, 보고서 데이터 추출)인지 구분합니다.
  2. 열린 작업이면 Fable 5.1을 고르고 effort를 medium으로 시작합니다.
  3. 결과가 부족하면 effort를 단계적으로 올립니다.
  4. 반복 작업이면 Opus나 Sonnet을 기본으로 씁니다.
  5. 필요할 때만 Fable로 바꿉니다.
  6. 서브에이전트는 특정 작업만 맡으므로 저렴한 모델부터 적용합니다.
  • 토큰 단가가 아니라 작업당 비용으로 비교합니다.
  • 더 강력한 모델일수록 낮은 effort로 시작해 필요할 때 올립니다.
  • Opus 5.5의 기본 effort는 medium이며, 여러 파일에 걸친 수정에는 high를 씁니다.
  • Pro·Max·Team 요금제에서는 Opus 5.5 사용 시 한도가 25% 더 늘어납니다.
  • Claude Code만 쓰는 경우 /claude-api prompt-audit로 CLAUDE.md와 스킬 지침을 Opus 5.5에 맞게 점검할 수 있습니다.

10. 기존 프롬프트를 평가로 개선하기

프롬프트를 감으로 고치지 않고 평가 세트로 실패 유형을 확인하며 하나씩 고치는 방법입니다. 모델을 바꾼 뒤 성능이 떨어졌을 때 특히 유용합니다.

  1. 통제 사례, 이전에 실패한 엣지 케이스, 사람에게 넘기거나 거절해야 할 사례를 담은 평가 세트를 만듭니다.
  2. 현재 프롬프트로 평가를 돌려 실패 유형을 확인합니다.
  3. 사실과 다른 역할 설명과 웹에서 복사된 불필요한 내용을 지웁니다.
  4. XML 태그로 역할·가이드라인·정책·말투를 구분해 구조를 만듭니다.
  5. 출력 형식을 정하는 출력 계약을 추가합니다.
  6. 평가를 다시 돌려 실패 유형을 하나씩 고치고 결과를 비교합니다.
  • 가이드라인·정책·데이터를 사람이 구분하기 어려우면 모델도 구분하기 어렵습니다.
  • 실행마다 편차가 있으니 한 번의 결과로 단정하지 않습니다.
  • 금지 항목을 길게 나열하는 방식은 피합니다.
  • 테스트 케이스가 부족하면 예시 한두 개를 주고 Claude에게 더 늘려 달라고 요청할 수 있습니다(영상에서는 약 50개까지 늘림).

11. 내 용도에 맞는 모델을 평가로 고르기

공개 벤치마크는 방향만 알려 주므로, 내 작업으로 작은 평가를 만들어 품질·지연·비용을 직접 비교하는 방법입니다. 새 모델이 나올 때마다 반복할 수 있습니다.

  1. 입력과 성공 기준을 가진 테스트 작업을 모아 평가 데이터 세트를 만듭니다.
  2. 최종 결과뿐 아니라 올바른 단계를 거쳤는지도 점검하는 채점기를 작업마다 붙입니다.
  3. 응답 비교에는 LLM 심사를, 특정 도구 호출이나 인자 확인에는 코드 기반 평가를 씁니다.
  4. 모델과 생각(thinking)·노력(effort) 설정을 바꿔 가며 각 작업을 여러 번 돌립니다.
  5. 로그를 열어 API·도구 호출 실패 같은 인프라 문제를 모델 실패와 분리합니다.
  6. 통과율, 토큰, 비용, 지연 시간을 비교해 중시하는 기준에 맞는 모델과 설정을 고릅니다.
  • 결과 편차가 크면 작업 정의나 평가가 불명확하다는 신호입니다.
  • 토큰당 가장 싼 모델이 아니라 성공 한 건당 가장 싼 모델을 고릅니다.
  • 모델 기반 채점기도 틀릴 수 있으니 여러 채점기를 조합합니다.

12. 내 하네스를 그래프로 그려 점검하기

에이전트 작업 흐름을 노드와 엣지로 그려, 어느 단계가 검사 없이 넘어가는지 확인하는 방법입니다. 다만 비교 실험에서는 코드 검사 루프 하나가 그래프보다 훨씬 빠르고 쌌습니다.

  1. 내 에이전트 하네스 설명(설정 파일, 규칙 문서, 작업 흐름)을 준비합니다.
  2. 영상 설명란의 프롬프트를 복사하거나 화면을 캡처합니다.
  3. 프롬프트의 ○○ 자리에 하네스 설명을 그대로 붙여 넣습니다.
  4. Claude나 ChatGPT에 붙여 넣어 실행합니다.
  5. 노드·엣지·상태 표와, 엣지마다 코드·모델·사람 중 누가 정하는지 적힌 결과를 받습니다.
  6. 함께 나온 머메이드 그림에서 검사 없이 넘어가는 엣지가 어디인지 확인합니다.
  • 기본은 루프 하나로 하고, 병렬 취합·독립 검증·사람 승인 같은 이유가 있을 때만 그래프를 씁니다.
  • 구조를 늘리기 전에 결과를 코드로 검사하는 검사기부터 만듭니다.
  • 실험 평균은 코드 검사 루프 16,688토큰, 그래프 73,692토큰이었습니다.
  • 프롬프트 전문은 설명란 자료실에서 볼 수 있습니다.
