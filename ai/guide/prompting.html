프롬프트·활용 요령

이 분야에서는 AI에게 원하는 답을 끌어내는 질문법부터, 틀린 답을 거르는 검증 요령, 긴 작업에서 컨텍스트를 관리하는 법, 모델과 effort를 골라 비용을 아끼는 법까지 배울 수 있습니다. 처음이라면 '맥락 주기 → 답 검증하기 → 휘둘리지 않고 결정하기' 순서로 기초를 익히세요. 그다음 모델·effort 고르기, Claude Code 컨텍스트·규칙 관리로 넘어가고, 마지막에 평가(eval)로 프롬프트와 모델을 개선하는 고급 가이드를 보면 됩니다.

최근 바뀐 점

  • Anthropic이 10월 1일 Claude Code의 화면과 동작 방식을 바꾸는 작은 프로그램인 '모드(Mods)'를 공식 발표했고, 내 세션 로그를 바탕으로 맞춤 모드를 추천받아 만들 수 있습니다.
  • Anthropic 연구에서 분석가들은 에이전트가 기운 쪽을 86% 따랐습니다. 그래서 추천을 듣기 전에 내 우선순위부터 말하고, 'What would change your advice?'라고 되묻는 습관이 권장됩니다.
  • 같은 과제를 루프와 그래프로 비교한 실험에서 결과를 코드로 검사하는 루프가 가장 빠르고 쌌고, 그래프는 토큰이 4배 넘게 들었습니다. 구조를 늘리기 전에 검사기부터 만들라는 권고가 나왔습니다.
  • 에이전트 메모리 강의에서는 컨텍스트는 기억이 아니며, 정답이 든 약 300토큰 프롬프트가 약 11만3,000토큰짜리 전체 기록보다 모든 모델에서 더 정확했다는 결과를 소개했습니다.

1. 나에 대한 맥락을 주고 더 나은 답 받기

AI는 사용자 메시지, 올린 문서, 대화 기록을 모두 보고 답을 만듭니다. 그래서 내가 누구이고 무엇을 하려는지 알려 줄수록 답이 좋아집니다. AI를 처음 업무에 쓸 때 가장 먼저 익힐 기본기입니다.

  1. 내가 누구이고 지금 무슨 작업을 하는지 먼저 적습니다.
  2. 좋은 결과가 어떤 모습인지(분량, 들어갈 내용, 형식) 함께 적습니다.
  3. 가격·뉴스 같은 최신 정보가 필요하면 웹 검색을 했는지 묻거나 검색해 달라고 요청합니다.
  4. 초안을 여러 버전으로 받거나 다른 어조로 다시 써 달라고 합니다.
  5. 더 필요한 정보가 있으면 AI가 먼저 나에게 질문하도록 요청합니다.
  6. 하루 30분씩 매일 AI에게 질문하는 습관을 들입니다.
예시
나는 중견기업 영업팀 과장이고, 다음 주 월요일 팀 회의 전에 보낼 3분기 실적 요약 메일을 쓰려고 해. 좋은 결과는 핵심 숫자 3개와 다음 분기 할 일 2개가 들어간 5줄 이내 메일이야. 서로 다른 어조로 초안 3개를 써 주고, 더 필요한 정보가 있으면 먼저 나에게 질문해 줘.
  • 전혀 모르면 ChatGPT 보이스로 말을 걸어 시작하고, 조금 써 봤다면 Claude 데스크톱 앱에서 나를 파악하게 해 보라고 권합니다.
  • 무료로 먼저 쓰다가 한도에 막힐 때 유료로 넘어가면 됩니다.
  • AI가 웹 검색을 했다고 단정하지 말고 직접 물어보세요.
  • 자신 있는 말투나 깔끔한 결과물은 정확하다는 증거가 아닙니다.

2. 음성 메모로 발표 자료 초안 만들기

빈 슬라이드 앞에서 막막할 때 하고 싶은 말을 먼저 소리 내어 녹음하고, 받아 적은 글을 Claude에게 넘겨 발표 자료로 만드는 방법입니다. 서식보다 내용에 집중할 수 있어 보고·발표 준비 시간을 줄여 줍니다.

  1. 산책하거나 이동하면서 휴대폰 음성 메모로 하고 싶은 말을 모두 녹음합니다.
  2. 녹음을 받아 적은 글을 준비합니다.
  3. 받아 적은 글을 Claude에게 보내 발표 자료로 만들어 달라고 요청합니다.
  4. 작은 수정은 직접 고칩니다.
  5. 큰 수정은 댓글로 Claude에게 요청합니다.
  • Anthropic 디자이너의 예에서는 Claude가 브랜드 스타일을 알고 있어 폰트나 템플릿을 따로 찾지 않았습니다.
  • 목적은 서식 작업을 줄이고 아이디어 자체에 시간을 쓰는 것입니다.

3. AI 답변 검증해 환각 거르기

AI는 그럴듯하지만 사실이 아닌 내용(환각)을 만들거나 내가 듣고 싶은 말에 맞춰 주기(아첨)도 하며, 틀릴 때도 똑같이 확신 있게 말합니다. 숫자·출처·법률·금전처럼 틀리면 곤란한 내용을 쓸 때 이 순서로 확인합니다.

  1. 틀렸을 때 어떤 일이 생기는지 스스로 묻고 확인 강도를 정합니다.
  2. 질문 전에 '모르면 모른다고 말해도 괜찮다'고 미리 알려 줍니다.
  3. 주장마다 근거가 되는 출처를 찾아 달라고 요청합니다.
  4. 제시된 출처를 직접 열어 그 내용이 실제로 있는지 확인합니다.
  5. 답이 의심스러우면 얼마나 확신하는지, 틀릴 만한 부분이 어디인지 묻습니다.
  6. 새 대화를 열거나 다른 AI에게 그 답변의 오류와 출처를 검증하게 합니다.
  7. 숫자·날짜·인용은 믿을 만한 자료와 교차 확인합니다.
예시
아래 답변에서 사실과 다른 부분을 찾아 주세요. 주장마다 근거 출처를 붙이고, 그 출처가 내용을 실제로 뒷받침하는지 확인해 주세요. 모르면 모른다고 말해도 괜찮습니다.
  • 회사 일에 쓸 때는 대화가 모델 학습에 쓰이지 않도록 학습 사용 설정을 꺼 둡니다.
  • AI가 실제로 없는 출처를 그럴듯하게 만들어 낼 수 있습니다.
  • 파티 주제 브레인스토밍은 느슨하게, 상사에게 보일 슬라이드 통계는 반드시 검증하는 식으로 중요도에 따라 조절합니다.
  • 환각이 줄어들수록 확인을 건너뛰기 쉬우니 오히려 더 주의합니다.

4. AI 추천에 휘둘리지 않고 결정하기

사람은 AI가 기운 쪽을 생각보다 훨씬 많이 따르고, 그러면서도 스스로 결정했다고 착각하기 쉽습니다. 업무 방식이나 도구를 고를 때 AI의 추천이나 치우친 답을 그대로 받아들이지 않기 위한 방법입니다.

  1. AI가 방법을 추천하기 전에 내 우선순위부터 묻게 합니다.
  2. 원하는 답을 흘리지 않고 중립적으로 질문합니다.
  3. 결정이 어려우면 작고 저렴한 모델로 여러 버전의 시안을 만들어 직접 보고 고릅니다.
  4. AI가 고른 안에 대해 'What would change your advice?'라고 묻습니다.
  5. 다른 안이 더 나아지는 조건이 지금 내 상황에 해당하는지 판단합니다.
  6. 답이 한쪽으로 치우쳤다고 느끼면 반박하고 균형 잡힌 접근을 요청합니다.
  7. 같은 질문을 다른 각도에서 다시 물어 답을 비교합니다.
예시
What would change your advice?
  • 연구에서 분석가들은 에이전트가 기운 쪽을 86% 따랐고, 자기 선호가 있던 사람도 에이전트가 반대하면 60%가 생각을 바꿨습니다.
  • 77%가 에이전트의 논거를 썼지만 출처로 밝힌 사람은 15%뿐이었습니다. 추천을 그대로 고르는 습관이 가장 쉬운 함정입니다.
  • 결정용 시안은 운영 버전이 아니므로 최고 모델을 쓸 필요가 없고, 결정한 뒤에는 버립니다.
  • 이 연구는 한 분야·한 과제·한 모델만 다뤘고 에이전트의 기울기를 일부러 강화했다는 한계가 있습니다.

5. 작업별로 모델과 effort 골라 비용 아끼기

작업 비용은 모델, effort(추론 노력), 캐시 세 가지로 정해집니다. 작업 성격에 맞춰 모델과 effort를 고르면 품질을 유지하면서 사용량 한도와 비용을 아낄 수 있습니다.

  1. 작업이 열린 작업(심층 조사, 복잡한 분석, 장시간 에이전트)인지 반복 작업(문서 요약, 메일 초안, 데이터 추출)인지 구분합니다.
  2. 열린 작업이면 Fable 5.1을 고르고 effort를 medium으로 시작합니다.
  3. 결과가 부족할 때만 effort를 단계적으로 올립니다.
  4. 반복 작업과 일상 작업은 Opus 5.5나 Sonnet을 기본으로 쓰고 effort는 medium으로 둡니다.
  5. 여러 파일이나 프로젝트 전체를 바꾸는 수정에는 effort를 high로 올립니다.
  6. Claude Code에서는 /effort로 노력 수준을 바꿉니다.
  7. 탐색만 하는 서브에이전트는 작고 저렴한 모델로 돌립니다.
  • 토큰 단가가 아니라 작업 한 건당 비용으로 비교합니다. 더 똑똑한 모델이 적은 단계로 끝내 총비용이 낮을 수 있습니다.
  • Opus 5.5는 Opus 5보다 토큰당 20% 저렴하고 Pro·Max·Team 한도가 25% 더 가며, 같은 버그 수정에서 5시간 한도를 약 4% 대 6%로 덜 썼습니다.
  • 예전 방식: 5월 영상에서는 고르기 어려우면 extra high를 권했습니다. 데모에서 max는 low보다 시간·토큰이 약 10배, high는 약 2배 들었습니다.
  • task budgets로 토큰·시간·비용 상한을 정해 중간 점검하게 할 수도 있습니다.

6. Claude Code 컨텍스트 가볍게 관리하기

컨텍스트는 Claude의 작업 기억으로, 읽은 파일·실행한 명령·주고받은 메시지가 모두 공간을 차지합니다. 한도에 가까워지면 자동으로 압축되며 세부 내용이 사라질 수 있으므로, 긴 작업일수록 직접 관리하는 편이 좋습니다.

  1. 요청을 구체적으로 적어 Claude가 불필요한 파일을 읽지 않게 합니다.
  2. 같은 기능 작업을 이어갈 때는 /compact로 대화를 압축합니다.
  3. 새 기능을 시작할 때는 /clear로 컨텍스트를 비웁니다.
  4. 지금 작업과 관련 없는 MCP 서버는 끕니다.
  5. 답만 필요한 조사는 서브에이전트에게 맡겨 요약만 받습니다.
  6. 자주 쓰는 작업 방법은 스킬로 만들어 필요할 때만 불러오게 합니다.
  • MCP 서버는 기본적으로 모든 도구를 컨텍스트에 올리지만, 스킬은 이름과 설명만 먼저 불러옵니다.
  • 컨텍스트는 기억이 아닙니다. 실험에서 정답이 든 약 300토큰 프롬프트가 약 11만3,000토큰 전체 기록보다 모든 모델에서 더 정확했습니다.
  • 최소한의 지침과 도구만 주고, 필요한 정보는 모델이 스스로 찾아오게 하는 방식이 권장됩니다.

7. CLAUDE.md와 스킬로 반복 실수 막기

Claude가 같은 실수를 반복하면 매번 다시 시키지 말고, 규칙을 CLAUDE.md나 스킬에 적어 두면 다음부터 자동으로 지킵니다. 모든 대화에 필요한 규칙은 CLAUDE.md, 특정 작업에만 필요한 방법은 스킬로 나눕니다.

  1. Claude가 실수하면 다시 시키기 전에 그 실수를 막을 규칙을 한 줄로 정리합니다.
  2. 모든 대화에서 지켜야 할 규칙이면 CLAUDE.md에 적습니다.
  3. 특정 작업에서만 쓰는 방법이면 SKILL.md 파일로 스킬을 만들고, 언제 쓰는지 설명(description)을 분명히 씁니다.
  4. 나만 쓸 스킬은 홈 디렉터리의 .claude/skills에 둡니다.
  5. 팀과 함께 쓸 스킬은 저장소 루트의 .claude/skills에 둡니다.
  6. 모델을 바꿨다면 Claude Code에서 /claude-api prompt-audit를 실행합니다.
  7. CLAUDE.md와 스킬의 지침이 새 모델에 맞게 조정됐는지 확인합니다.
예시
/claude-api prompt-audit
  • CLAUDE.md는 모든 대화에 불러오고, 스킬은 요청과 설명이 맞을 때만 불러와 컨텍스트를 아낍니다.

8. Claude에게 인터뷰시켜 요구사항 정리하기

만들 결과물을 처음부터 자세히 지정하는 대신, Claude가 나에게 질문하며 요구사항을 끌어내게 하는 방법입니다. 모델이 강해질수록 제약을 줄이고 질문을 맡기는 편이 결과가 좋다고 합니다.

  1. Claude Code에서 Shift+Tab으로 auto mode로 전환합니다.
  2. /effort로 노력 수준을 정합니다.
  3. 만들 것의 관심 영역(예: 대상 사용자)만 주고 결과는 과하게 지정하지 않습니다.
  4. 프롬프트에 ask user question 도구를 써서 질문하라고 명시합니다.
  5. Claude가 띄우는 질문에 차례로 답합니다.
  6. 답변이 끝나면 Claude가 쓴 스펙을 사람이 먼저 검토합니다.
예시
팀원끼리 회식비를 나눠 계산하는 앱을 만들고 싶어. 대상 사용자는 회사 동료들이야. 결과를 미리 정하지 말고 ask user question 도구로 나에게 하나씩 질문해서 요구사항을 끌어낸 뒤 스펙을 작성해 줘.
  • 예전 방식: 계획 모드로 읽기 전용 분석과 질문을 거쳐 계획을 먼저 받았습니다. 최신 모델에서는 계획 모드 대신 오토 모드를 쓴다고 합니다.
  • '더 좋게 만들어', '실수 없이 만들어' 같은 프롬프트는 피합니다.
  • 스펙은 긴 마크다운 대신 정보 밀도가 높은 HTML 파일로 받으면 검토가 쉽습니다.
  • 5월 영상은 effort로 X high를 권했지만, 9월 Opus 5.5 영상은 기본 medium으로도 대부분 충분하다고 합니다.

9. 내 사용 패턴으로 Claude Code 모드 만들기

모드는 Claude Code의 모습과 행동 방식을 바꾸는 작은 프로그램으로, 2026년 10월 1일 공식 발표되었습니다. 내가 자주 반복하는 말과 작업을 분석해 흐름을 돕고 비용을 아껴 줄 모드를 추천받아 만들 수 있습니다.

  1. Claude Code에 세션 로그를 최대한 훑어 내가 자주 반복하는 말과 작업을 파악해 달라고 요청합니다.
  2. 흐름을 돕고 비용을 아끼며 집중하게 해 줄 모드 다섯 개를 추천해 달라고 요청합니다.
  3. 추천마다 함께 나온 패턴과 근거를 읽어 봅니다.
  4. 마음에 드는 번호를 골라 만들어 달라고 요청합니다.
예시
Claude Code 세션 로그를 최대한 훑어서 내가 자주 반복하는 말과 작업을 파악해 줘. 그다음 흐름을 돕고 비용을 아끼며 집중하게 해 줄 모드 다섯 개를 추천해 줘.

  • 영상에서는 데스크톱 앱에서 토큰 표시, 다음 작업 추천 같은 모드를 만들어 봅니다.
  • 창·버튼 같은 화면 요소는 모드로만 만들 수 있다고 설명합니다.

10. 평가 세트로 프롬프트 개선하기

업무에 반복해서 쓰는 프롬프트나 봇의 품질을 '느낌'이 아니라 테스트 결과로 개선하는 방법입니다. 모델을 바꾼 뒤 성능이 떨어졌을 때나, 고친 곳이 다른 곳을 망가뜨리지 않는지 확인할 때 씁니다.

  1. 일반적인 사례, 이전에 실패한 엣지 케이스, 사람에게 넘기거나 거절해야 할 사례로 평가 세트를 만듭니다.
  2. 사례가 부족하면 상황 설명과 예시 한두 개를 Claude에게 주고 케이스를 늘려 달라고 합니다.
  3. 현재 프롬프트로 평가를 돌려 실패 유형을 확인합니다.
  4. 사실과 다른 역할 설명과 웹에서 복사해 온 불필요한 내용을 지웁니다.
  5. XML 태그로 역할·가이드라인·정책·말투를 구분합니다.
  6. 출력 형식을 정하는 출력 계약을 추가합니다.
  7. 평가를 다시 돌려 실패 유형을 하나씩 고치고 결과를 비교합니다.
예시
고객지원 봇 프롬프트를 시험할 평가 케이스를 만들려고 해. 아래 예시 2개를 참고해서 일반 사례, 엣지 케이스, 사람에게 넘기거나 거절해야 할 사례를 섞어 50개로 늘려 줘.
  • 실패가 모델 탓이 아니라 프롬프트 안의 서로 부딪히는 정책 때문인 경우가 있습니다. 사람이 구분하기 어려우면 모델도 어렵습니다.
  • 금지 항목을 길게 나열하는 방식은 피합니다.
  • 실행마다 편차가 있으니 한 번의 결과로 단정하지 않습니다.
  • 채점은 코드 기반(정확한 일치 검사)과 모델 기반(LLM 판정)을 함께 씁니다. 구조를 늘리기 전에 결과를 코드로 검사하는 검사기부터 만드는 것이 좋습니다.

11. 평가로 내 용도에 맞는 모델 고르기

공개 벤치마크는 방향만 알려 줄 뿐 내 업무와 다를 수 있습니다. 작은 평가라도 직접 만들어 두면 새 모델이 나올 때마다 품질·지연·비용을 비교해 옮길지 판단할 수 있습니다.

  1. 입력과 성공 기준을 가진 테스트 작업을 모아 평가 데이터 세트를 만듭니다.
  2. 최종 결과뿐 아니라 올바른 단계를 거쳤는지도 보는 채점기를 작업마다 붙입니다.
  3. 응답 비교에는 LLM 심사를, 특정 도구 호출 확인에는 코드 기반 평가를 씁니다.
  4. 모델과 thinking·effort 설정을 바꿔 가며 각 작업을 여러 번 돌립니다.
  5. 로그를 열어 API·도구 호출 실패 같은 인프라 문제를 모델 실패와 분리합니다.
  6. 통과율·토큰·비용·지연 시간을 비교해 중시하는 기준에 맞는 모델과 설정을 고릅니다.
  • 토큰당 가장 싼 모델이 아니라 성공 한 건당 가장 싼 모델을 고릅니다.
  • 결과 편차가 크면 작업 정의나 평가가 불명확하다는 신호입니다.
  • 새 모델이 나오면 먼저 평가를 백그라운드로 돌려 보고, 지금 안 되는 작업은 다음 모델이 나아질 분야의 단서로 봅니다.
  • 일반적으로 지능이 필요하면 Opus, 낮은 지연·비용은 Haiku, 균형은 Sonnet을 씁니다.

12. 에이전트 작업 흐름 그래프로 점검하기

그래프 엔지니어링은 일을 노드로 쪼개고 엣지로 이으며, 다음 단계를 코드·모델·사람 중 누가 정할지 고르는 설계입니다. 내 에이전트 설정을 그래프로 그려 보면 검사 없이 넘어가는 구간을 찾을 수 있습니다. 다만 기본은 루프 하나로 하고, 이유가 있을 때만 그래프 구조를 씁니다.

  1. 내 에이전트 하네스 설명(설정 파일, 규칙 문서, 작업 흐름)을 준비합니다.
  2. 영상 설명란의 프롬프트를 복사합니다.
  3. 프롬프트의 ○○ 자리에 하네스 설명을 그대로 붙여 넣습니다.
  4. Claude나 ChatGPT에 붙여 넣어 실행합니다.
  5. 노드·엣지·상태 표와 엣지마다 코드·모델·사람 중 누가 정하는지 적힌 결과를 받습니다.
  6. 함께 나온 머메이드 그림에서 검사 없이 넘어가는 엣지를 찾습니다.
  7. 그 구간에 결과를 코드로 검사하는 검사기부터 붙입니다.
  • 실험(5회 평균)에서 코드 검사 루프는 8.3초·16,688토큰, 자기 검사 루프는 18.8초·34,473토큰, 그래프는 53.3초·73,692토큰이 들었습니다.
  • 그래프를 쓸 이유는 병렬 후 취합, 독립 검증, 단계별 다른 모델·도구·권한, 사람 승인, 장시간 작업의 저장·재개 다섯 가지입니다.
  • 멀티에이전트 방식은 성능이 높았지만 토큰을 채팅의 약 15배 썼으니 비용을 함께 따져 봅니다.
  • 영상 예시에서는 엣지 20개 중 사람이 정하는 것이 2개뿐이었습니다.
