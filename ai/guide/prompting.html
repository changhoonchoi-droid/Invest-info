프롬프트·활용 요령

이 페이지는 AI에게 말을 거는 기본기부터 답을 검증하고, 컨텍스트와 비용을 관리하는 요령까지 다룹니다. 먼저 첫 대화와 안전 설정을 익히고, 맥락을 주는 법과 답을 믿어도 되는지 점검하는 법을 배운 뒤, 마지막으로 모델·effort 선택과 평가 같은 응용 단계로 넘어가면 좋습니다.

프롬프트 작성법, 컨텍스트 관리, 결과 품질 높이기, 비용·사용량 관리 · 영상 48개 기반 · 2026-11-09 갱신

최근 바뀐 점

  • 영어 메일을 쓸 때 받는 사람의 직급, 관계, 메일 이후 일어나야 할 일을 적으면 현지 직원이 쓴 듯한 글이 나옵니다(11월 8일).
  • AI를 과외 선생님으로 세워 커리큘럼을 만들고 공부하는 방식이 소개되었습니다(11월 6일).
  • 회사 일에 쓰기 전 ChatGPT의 학습 사용 설정을 끄고, 답이 의심되면 근거를 요구하거나 다른 AI로 교차 검증하라는 입문 안내가 나왔습니다(11월 5일).
  • AI 구독료는 금액이 아니라 한도에 막히는지를 기준으로 정하라는 기준이 제시되었습니다(11월 3일).
내 대화가 학습에 쓰이지 않게 끄기맥락을 주고 첫 대화 시작하기말로 프롬프트 쓰고 다듬기영어 메일을 현지 직원처럼 쓰기AI를 과외 선생님으로 써서 공부하기AI 답변 검증하며 쓰기AI에게 휘둘리지 않고 결정하기Claude에게 인터뷰시켜 스펙 만들기에러를 AI에게 잘 전달하기컨텍스트 아끼며 길게 작업하기실수를 CLAUDE.md와 스킬에 남기기작업별로 모델과 effort 고르기내 용도에 맞는 모델을 평가로 고르기
입문

1. 내 대화가 학습에 쓰이지 않게 끄기

회사 일에 AI를 쓰기 전에 대화 내용이 모델 학습에 쓰이지 않도록 설정하는 가이드입니다. 업무에 AI를 처음 쓸 때 가장 먼저 해 두면 좋습니다.

  1. ChatGPT 설정(Settings)을 엽니다.
  2. Data controls로 들어갑니다.
  3. Improve the model for everyone 항목을 끕니다.
  4. 개인정보와 기밀 정보는 설정과 관계없이 입력하지 않습니다.
  • 회사 일에 쓰기 전에 반드시 먼저 끕니다.
  • 설정을 껐더라도 개인정보와 기밀 정보는 입력하지 않는 것이 안전합니다.

2. 맥락을 주고 첫 대화 시작하기

AI를 잘 쓰는 핵심은 완벽한 프롬프트가 아니라 나와 상황, 기준을 충분히 알려 주는 것입니다. 처음 시작하는 사람이 무료로 부담 없이 써 보는 방법입니다.

  1. 완전 초보라면 ChatGPT 앱의 보이스 모드로 말하듯 질문을 시작합니다.
  2. 어느 정도 써 봤다면 Claude 데스크톱 앱에서 컴퓨터 속 파일을 보여 주며 나를 파악하게 합니다.
  3. 내가 누구이고 무슨 작업 중인지, 좋은 결과가 어떤 것인지 알려 줍니다.
  4. 파일이나 캡처 같은 자료를 많이 붙입니다.
  5. 하루 30분, AI에게 질문하고 AI가 나에게도 질문하도록 유도하는 습관을 들입니다.
예시
내가 어떤 일을 하는지, 어떤 결과물을 원하는지 먼저 물어봐 줘. 내 답을 바탕으로 앞으로 내 업무를 도와줘.
  • 무료로 시작해서 한도에 막힐 때 유료로 넘어가면 됩니다.
  • 작업별로 프로젝트를 나눠 쓰고, 새 채팅에서는 이전 내용을 가져오라고 요청할 수 있습니다.
  • AI의 답은 직접 읽고 검증합니다.

3. 말로 프롬프트 쓰고 다듬기

타이핑 대신 음성으로 길게 말해 요청을 입력하면 시간이 줄고 생각도 정리됩니다. Typeless 같은 음성 입력 도구는 군더더기를 지워 정리된 문장으로 넣어 줍니다.

  1. Typeless로 두서없이 하고 싶은 요청을 말해 입력합니다.
  2. 입력된 문장을 드래그로 선택합니다.
  3. Ask Anything 단축키를 누릅니다.
  4. 무엇이든 물어보세요 칸에 프롬프트를 다듬어 달라고 말합니다.
  5. 약 3초 후 나온 프롬프트를 필요하면 고쳐서 AI에 입력합니다.
예시
더 잘 알아듣는 프롬프트로 다듬어 줘. 타겟·톤·결과물 형식을 구체적으로 넣어 줘.
  • '더 짧게', '더 친근하게' 같은 수정도 같은 방식으로 요청할 수 있습니다.
  • 전문 용어는 가끔 틀리게 입력될 수 있습니다.
  • 무료 사용량은 주당 8,000단어입니다.
  • 음성 받아쓰기는 ChatGPT가 가장 정확하다는 평가도 있습니다.

4. 영어 메일을 현지 직원처럼 쓰기

번역기는 문장을 바꾸지만 현지 직원은 맥락을 바꿉니다. 받는 사람과 관계, 목적을 알려 주면 AI가 맥락에 맞는 영어 메일을 씁니다.

  1. 받는 사람의 직급을 프롬프트에 적습니다.
  2. 나와 받는 사람의 관계를 적습니다.
  3. 메일이 끝난 뒤 무엇이 일어나야 하는지를 적습니다.
  4. 초안을 받아 직접 읽고 고칩니다.
예시
아래 내용으로 영어 메일을 써 줘. 받는 사람은 [직급]이고, 나와는 [관계]야. 이 메일 후에 [원하는 결과]가 일어나야 해.
  • 중요한 문서는 AI 티가 나는 문장을 다듬고 직접 읽고 고칩니다.

5. AI를 과외 선생님으로 써서 공부하기

새 분야를 배울 때 AI에게 선생님 역할을 맡겨 커리큘럼을 만들게 하는 방법입니다. 이해하면서 질문을 이어 가는 것이 핵심입니다.

  1. 배우고 싶은 분야를 말합니다.
  2. 과외 선생님으로서 공부를 도와 달라고 요청합니다.
  3. AI가 만들어 주는 커리큘럼을 받습니다.
  4. 답변을 이해하면서 질문과 문제를 이어 갑니다.
예시
네가 앞으로 과외 선생님으로서 나를 공부할 수 있도록 도와줘. 내가 배우고 싶은 분야는 [분야]야.
  • 답변을 이해하지 않고 복사·붙여 넣기만 하면 실력이 늘지 않습니다.
  • 책을 읽은 뒤 AI에게 저자 역할을 시켜 질문해 볼 수 있습니다.

6. AI 답변 검증하며 쓰기

AI는 그럴듯하지만 사실이 아닌 내용(환각)을 만들거나 사용자가 원하는 답에 맞추는(아첨) 경우가 있습니다. 질문의 중요도에 따라 확인 강도를 조절하는 방법입니다.

  1. 틀렸을 때 어떤 일이 생기는지 스스로 묻고 확인 강도를 정합니다.
  2. 미리 모르면 모른다고 말해도 괜찮다고 알려 줍니다.
  3. 주장마다 근거가 되는 출처를 요청합니다.
  4. 제시된 출처를 직접 열어 실제로 그 내용이 있는지 확인합니다.
  5. 원하는 답을 흘리지 말고 찬성과 반대 논거를 중립적으로 묻습니다.
  6. 의심스러우면 새 대화를 열어 오류와 출처를 점검하게 하거나 다른 AI로 교차 검증합니다.
예시
이 결정에 대한 가장 강력한 찬성과 반대 논거는 무엇인가요? 모르면 모른다고 말해 줘도 괜찮아. 각 주장의 출처도 알려 줘.
  • 숫자·날짜·인용은 특히 다시 확인하세요.
  • AI가 실제로 없는 출처를 그럴듯하게 만들어 낼 수도 있습니다.
  • 자신 있는 말투나 깔끔한 결과물은 정확성의 증거가 아닙니다.
  • 가격·뉴스 등 최신 정보는 웹 검색을 했는지 직접 물어봅니다.

7. AI에게 휘둘리지 않고 결정하기

연구에서 분석가들은 에이전트가 기운 쪽을 86% 따랐고, 자기 결정이라고 착각하기 쉬웠습니다. 추천 답을 그대로 고르지 않고 내 기준으로 결정하는 방법입니다.

  1. 에이전트가 방법을 추천하기 전에 내 우선순위부터 묻게 합니다.
  2. 결정이 어려우면 작고 저렴한 모델로 여러 버전의 프로토타입을 병렬로 만듭니다.
  3. 프로토타입을 보고 내가 결정한 뒤 프로토타입은 버립니다.
  4. 결정한 내용을 에이전트에게 전달합니다.
  5. 에이전트가 고른 안에 대해 "What would change your advice?"라고 묻습니다.
  6. 답을 보고 다른 안이 최적이 되는 조건이 현재 상황에 해당하는지 판단합니다.
예시
추천하기 전에 내 우선순위부터 물어봐 줘. 그리고 네가 고른 안에 대해 What would change your advice?
  • 추천 답을 그대로 선택하는 습관이 가장 쉬운 함정입니다.
  • 프로토타입은 결정용이므로 최고 모델을 쓸 필요가 없습니다.

8. Claude에게 인터뷰시켜 스펙 만들기

모델이 강력해질수록 제약을 줄이고 Claude가 사용자에게 질문해 요구사항을 끌어내게 하는 방식입니다. 처음 프롬프트를 길게 쓰지 않아도 됩니다.

  1. Shift+Tab으로 auto mode로 전환합니다.
  2. /effort로 노력 수준을 설정합니다(권장 X high).
  3. 프롬프트에서 만들 앱의 관심 영역(예: 대상 사용자)만 주고 결과는 과하게 지정하지 않습니다.
  4. 프롬프트에 ask user question 도구를 쓰라고 명시합니다.
  5. Claude가 띄우는 질문에 차례로 답합니다.
  6. 답변이 끝나면 Claude가 작성하는 스펙을 확인합니다.
  • '더 좋게 만들어', '실수 없이 만들어' 같은 프롬프트는 피합니다.
  • 빠르게 스펙을 반복할 때는 /fast 모드가 유용합니다.
  • 계획은 긴 마크다운 대신 HTML 파일로 받아 사람이 먼저 검토하는 방법도 있습니다.

9. 에러를 AI에게 잘 전달하기

AI가 만든 결과에 문제가 생겼을 때 단서를 충분히 주면 해결이 훨씬 잘 됩니다. 개발 지식이 없어도 오류 메시지를 복사해 전달하면 됩니다.

  1. 문제 화면에서 마우스 오른쪽 버튼을 눌러 검사를 엽니다.
  2. 개발자 도구에서 콘솔 탭의 오류 메시지를 복사하거나 캡처합니다.
  3. 프롬프트 창에 오류 메시지를 붙여 넣습니다.
  4. 언제 발생하는지(예: 스크롤할 때)를 적습니다.
  5. 원래 기대하는 동작과 현재 문제를 함께 적습니다.
  6. 가능하면 발생 화면 스크린샷도 첨부합니다.
  • 언제·어디서·어떻게 발생했는지 단서를 많이 줄수록 해결이 잘 됩니다.
  • 구체적 질문, 이미지 첨부, 공식 문서 제공도 성공률을 높입니다.

10. 컨텍스트 아끼며 길게 작업하기

컨텍스트는 Claude의 작업 기억이며 읽은 파일, 실행한 명령, 주고받은 메시지가 모두 공간을 차지합니다. 한도에 가까워지면 자동 압축되어 세부 내용이 사라질 수 있어 관리가 필요합니다.

  1. 같은 기능 작업을 이어갈 때는 /compact를 씁니다.
  2. 새 기능을 시작할 때는 /clear로 비웁니다.
  3. 요청은 구체적으로 합니다.
  4. 관련 없는 MCP 서버는 끕니다.
  5. 답만 필요한 조사는 서브에이전트에 맡깁니다.
  • MCP 서버는 기본적으로 모든 도구를 컨텍스트에 올립니다.
  • 스킬은 전체를 컨텍스트에 올리지 않아 MCP보다 아낍니다.
  • 컨텍스트가 커져도 기억은 아닙니다. 정답이 든 짧은 프롬프트가 긴 전체 기록보다 더 정확했다는 실험이 있습니다.
  • 최신 모델에는 컨텍스트를 최소한만 주고 찾아오게 하는 방식이 권장됩니다.

11. 실수를 CLAUDE.md와 스킬에 남기기

같은 실수를 반복하지 않도록 규칙을 파일에 적어 두는 방법입니다. 모델이 바뀔 때는 지침도 다듬어 줍니다.

  1. Claude가 실수하면 다시 시키지 말고 원인을 확인합니다.
  2. 같은 실수를 막는 규칙을 CLAUDE.md나 스킬에 적습니다.
  3. 반복되는 작업 방법은 SKILL.md 파일로 만들어 둡니다.
  4. 개인용은 홈 디렉터리의 .claude/skills에, 팀 공유용은 저장소 루트의 .claude/skills에 둡니다.
  5. 모델을 바꿨다면 Claude Code에서 /claude-api prompt-audit를 실행합니다.
예시
/claude-api prompt-audit
  • CLAUDE.md는 모든 대화에 로드되고, 스킬은 요청이 맞을 때만 로드됩니다.

  • 보고서 형식도 스킬이나 메모리로 굳히면 매번 같은 포맷이 나옵니다.

12. 작업별로 모델과 effort 고르기

작업 비용은 모델, effort(추론 노력), 캐시 세 가지로 정해집니다. 토큰 단가가 아니라 작업당 비용으로 비교해 알맞은 조합을 고르는 방법입니다.

  1. 작업이 열린 작업(심층 조사, 복잡한 분석)인지 반복 작업(요약, 메일 초안)인지 구분합니다.
  2. 열린 작업이면 Fable 5.1을 고르고 effort를 medium으로 시작합니다.
  3. 결과가 부족하면 effort를 단계적으로 올립니다.
  4. 반복 작업이면 Opus나 Sonnet을 기본으로 씁니다.
  5. 필요할 때만 Fable로 바꿉니다.
  6. 서브에이전트는 저렴한 모델부터 적용합니다.
  • Opus 5.5는 기본 effort가 medium이며 대부분 충분하고, 여러 파일에 걸친 수정에는 high를 씁니다.
  • 구독료는 금액이 아니라 쓰다가 한도에 막히는지로 판단합니다.
  • 더 강력한 모델일수록 낮은 effort로 시작해 필요할 때 올립니다.
  • 예전 방식: 계획 모드가 중요했지만 최신 모델에서는 오토 모드를 쓰는 추세입니다.

13. 내 용도에 맞는 모델을 평가로 고르기

공개 벤치마크는 방향만 알려 주므로 내 작업으로 작은 평가(eval)를 직접 만들어 비교하는 방법입니다. 새 모델이 나올 때마다 같은 절차로 반복할 수 있습니다.

  1. 입력과 성공 기준을 가진 테스트 작업을 모아 평가 데이터 세트를 만듭니다.
  2. 최종 결과뿐 아니라 올바른 단계를 거쳤는지도 점검하는 채점기를 붙입니다.
  3. 응답 비교에는 LLM 심사를, 특정 도구 호출 확인에는 코드 기반 평가를 씁니다.
  4. 모델과 생각(thinking)·노력(effort) 설정을 바꿔 가며 각 작업을 여러 번 돌립니다.
  5. 로그를 열어 API·도구 호출 실패 같은 인프라 문제를 모델 실패와 분리합니다.
  6. 통과율, 토큰, 비용, 지연 시간을 비교해 기준에 맞는 모델과 설정을 고릅니다.
  • 결과 편차가 크면 작업 정의나 평가가 불명확하다는 신호입니다.
  • 토큰당 가장 싼 모델이 아니라 성공 한 건당 가장 싼 모델을 고릅니다.
  • 예시 테스트 케이스 한두 개를 주고 Claude에게 50개 정도로 늘려 달라고 할 수 있습니다.
  • 프롬프트 캐싱 등으로 비용·성능 곡선 자체를 옮길 수 있습니다.
