프롬프트·활용 요령

1. AI에게서 더 나은 답 얻기

AI는 사용자 메시지, 올린 문서, 대화 기록을 모두 고려해 답을 새로 만들어 냅니다. 그래서 내가 누구이고 무엇을 원하는지 알려 줄수록 답이 좋아집니다. 메일 초안, 보고서 문장처럼 일상 업무에서 AI를 처음 쓸 때 가장 먼저 익힐 요령입니다.

  1. 내가 누구이고 무슨 작업을 하는 중인지 먼저 알려 줍니다.
  2. 좋은 결과가 어떤 모습인지(분량, 말투, 용도) 적어 줍니다.
  3. 가격·뉴스처럼 최신 정보가 필요하면 웹 검색을 했는지 묻거나 검색해 달라고 요청합니다.
  4. 검색했다면 제시된 출처를 직접 열어 내용이 맞는지 확인합니다.
  5. 초안을 여러 버전으로 받거나 다른 어조로 다시 써 달라고 합니다.
  6. 틀리면 곤란한 사실은 직접 다시 확인합니다.
예시
저는 중견기업 인사팀에서 일하고, 신입사원에게 보낼 첫 출근 안내 메일을 쓰는 중입니다. 좋은 결과는 A4 반 장 이내, 친근하지만 예의 바른 말투입니다. 초안을 서로 다른 어조로 세 가지 써 주세요.
  • AI는 정해진 답을 꺼내는 것이 아니라 생성하므로, 마음에 들 때까지 여러 버전을 요청해도 됩니다.
  • 모델은 훈련 시점 이후의 사실을 검색 없이는 확실히 알지 못합니다. AI가 웹 검색을 했다고 단정하지 말고 직접 물어보세요.
  • 자신 있는 말투나 깔끔한 결과물은 정확하다는 증거가 아닙니다.

2. AI 답변의 환각 점검하기

AI는 그럴듯하지만 사실이 아닌 내용(환각)을 만들거나, 내가 듣고 싶은 말에 맞춰 동의(아첨)할 수 있습니다. 숫자·출처·건강·법률·금전처럼 틀리면 곤란한 내용을 업무에 쓰기 전에 이 순서로 확인합니다.

  1. 틀렸을 때 어떤 일이 생기는지 스스로 묻고 확인할 강도를 정합니다.
  2. 질문하기 전에 모르면 모른다고 말해 달라고 미리 허용합니다.
  3. 원하는 답을 흘리지 말고 중립적으로 질문합니다.
  4. 주장마다 근거가 되는 출처를 요청합니다.
  5. 제시된 출처를 직접 열어 그 내용이 실제로 있는지 확인합니다.
  6. 답이 의심스러우면 얼마나 확신하는지, 틀릴 만한 부분이 어디인지 묻습니다.
  7. 새 대화를 열어 그 답변의 오류를 찾고 출처가 맞는지 확인해 달라고 합니다.
  8. 중요한 작업은 믿을 만한 자료와 교차 확인합니다.
예시
이 결정에 대한 가장 강력한 찬성과 반대 논거는 무엇인가요? 주장마다 근거가 되는 출처를 함께 알려 주시고, 모르는 부분은 모른다고 말해 주세요.
  • 신뢰는 스위치가 아니라 다이얼입니다. 파티 주제 브레인스토밍은 느슨하게, 상사에게 보일 슬라이드의 통계는 반드시 검증하세요.
  • 구체적 숫자·날짜·이름·인용, 잘 알려지지 않은 주제, 최근 사건에서 환각 가능성이 높습니다.
  • AI가 실제로 없는 출처를 그럴듯하게 만들어 낼 수도 있으니 링크는 직접 열어 봅니다.
  • 환각이 줄어들수록 확인을 건너뛰기 쉬워지니 습관처럼 점검하세요.

3. AI 답변의 편향 점검하기

AI 답변에는 고정관념, 정치적 치우침, 언어별 품질 차이 같은 편향이 섞일 수 있습니다. 답이 한쪽으로 기울었다고 느낄 때 균형 잡힌 답을 다시 받아 내는 방법입니다.

  1. 답변이 한쪽으로 치우쳤다고 느끼면 바로 반박합니다.
  2. 더 섬세하고 균형 잡힌 접근을 요청합니다.
  3. 솔직한 논의를 원한다고 분명히 말합니다.
  4. 근거를 모아 달라고 하고 링크를 직접 열어 확인합니다.
  5. 같은 질문을 다른 관점에서 다시 물어 두 답의 깊이와 성의를 비교합니다.
예시
앞의 답변은 한쪽 입장에 치우친 것 같습니다. 저는 솔직한 논의를 원합니다. 양쪽 관점을 같은 깊이로 정리하고, 각각의 근거 자료 링크도 함께 주세요.
  • 정치 이야기뿐 아니라 제품 비교, 인사 평가 같은 업무 대화에서도 똑같이 쓸 수 있습니다.
  • 같은 주제를 두 관점으로 묻는 '짝지은 질문'은 Anthropic이 편향을 검사할 때 쓰는 방식이기도 합니다.

4. 음성 메모로 발표 자료 만들기

빈 슬라이드 앞에서 막막할 때, 하고 싶은 말을 먼저 말로 쏟아 내고 그 글로 Claude에게 발표 자료를 만들게 하는 방법입니다. 서식 작업 대신 내용과 아이디어에 시간을 쓸 수 있습니다.

  1. 산책하거나 이동하면서 휴대폰 음성 메모로 하고 싶은 말을 모두 녹음합니다.
  2. 녹음을 글로 받아 적습니다.
  3. 받아 적은 글을 Claude에게 보내 발표 자료로 만들어 달라고 요청합니다.
  4. 결과물을 보며 작은 수정은 직접 고칩니다.
  5. 큰 수정은 댓글로 Claude에게 요청합니다.
예시
아래는 제가 산책하며 녹음한 음성 메모를 받아 적은 글입니다. 이 내용을 바탕으로 팀 회의에서 쓸 발표 자료를 만들어 주세요.

(받아 적은 글 붙여넣기)
  • 영상에서는 Claude가 회사 브랜드 스타일을 알고 있어 폰트나 템플릿을 따로 찾지 않았습니다.
  • 말하듯 정리되지 않은 내용이어도 괜찮습니다. 목적은 서식보다 아이디어에 집중하는 것입니다.

5. Claude Code 컨텍스트 관리하기

컨텍스트는 Claude의 작업 기억으로, 읽은 파일·실행한 명령·주고받은 메시지가 모두 공간을 차지합니다. 한도에 가까워지면 자동으로 압축되지만 세부 내용이 사라질 수 있으므로, 긴 작업에서는 직접 정리해 주는 것이 좋습니다.

  1. 같은 기능 작업을 이어갈 때 대화가 길어졌다면 /compact로 지금까지의 내용을 압축합니다.
  2. 새 기능이나 다른 일을 시작할 때는 /clear로 컨텍스트를 비웁니다.
  3. 요청은 구체적으로 써서 Claude가 불필요한 파일을 뒤지지 않게 합니다.
  4. 지금 작업과 관련 없는 MCP 서버는 끕니다.
  5. 답만 필요한 조사는 서브에이전트에 맡겨 요약만 돌려받습니다.
예시
/compact
  • MCP 서버는 기본적으로 모든 도구를 컨텍스트에 올리지만, 스킬은 필요한 부분만 불러와 공간을 덜 씁니다.
  • 서브에이전트는 별도의 컨텍스트 창에서 일하고 요약만 돌려주므로 본 대화가 가벼워집니다.
  • 최소한의 지시만 주고 Claude가 필요한 정보를 스스로 찾아오게 하는 방식이 권장됩니다.

6. 실수를 CLAUDE.md 규칙으로 막기

Claude가 실수했을 때 매번 다시 시키는 대신, 규칙을 CLAUDE.md나 스킬에 적어 같은 실수가 반복되지 않게 하는 방법입니다. 새 모델로 바꾼 뒤에는 기존 지침을 새 모델에 맞게 다듬을 수도 있습니다.

  1. Claude가 실수하면 같은 요청을 다시 하기 전에 무엇이 틀렸는지 정리합니다.
  2. 그 내용을 앞으로 지킬 규칙으로 CLAUDE.md나 스킬에 적습니다.
  3. 다음 작업에서 같은 실수가 사라졌는지 확인합니다.
  4. 새 모델로 바꿨다면 Claude Code에서 /claude-api prompt-audit를 실행합니다.
  5. CLAUDE.md와 스킬의 지침이 새 모델(Opus 5.5)에 맞게 조정되었는지 확인합니다.

7. 작업별로 모델과 effort 고르기

작업 비용은 모델, effort(추론 노력), 캐시 세 가지로 정해집니다. 열린 작업과 반복 작업을 구분해 모델과 effort를 고르면 품질은 지키면서 사용량과 비용을 줄일 수 있습니다.

  1. 할 일이 열린 작업(심층 조사, 복잡한 분석, 오래 도는 에이전트)인지 반복 작업(문서 요약, 메일 초안, 보고서 데이터 추출)인지 구분합니다.
  2. 열린 작업이면 Fable 5.1을 고르고 effort를 medium으로 시작합니다.
  3. 결과가 부족하면 effort를 한 단계씩 올립니다.
  4. 반복 작업이면 Opus나 Sonnet을 기본으로 씁니다.
  5. Opus 5.5는 기본 effort medium으로 대부분 충분하고, 여러 파일이나 프로젝트 전체를 바꾸는 수정에는 high를 씁니다.
  6. Claude Code에서는 /effort로 노력 수준을 바꿉니다.
  7. 탐색만 하는 서브에이전트는 작고 저렴한 모델부터 적용합니다.
  • 토큰 단가가 아니라 작업 한 건당 비용으로 비교하세요. 똑똑한 모델이 적은 단계로 끝내 총비용이 더 낮을 수 있습니다.
  • Opus 5.5는 Opus 5보다 토큰당 20% 저렴하고 Pro·Max·Team 요금제 한도가 25% 더 갑니다. Fable 5.1은 Fable 5보다 캐시 읽기 비용이 75% 낮습니다.
  • 더 강한 모델일수록 낮은 effort로 시작해 필요할 때 올립니다. effort를 올리면 시간과 토큰이 크게 늘어(데모에서 max는 low의 약 10배) 대기 시간과 비용이 함께 커집니다.
  • 예전 방식: 5월 영상에서는 고르기 어려우면 extra high(당시 제품 기본값)를 권했지만, 9월 Opus 5.5 안내에서는 기본 medium으로 시작하라고 합니다.

8. Claude에게 질문받아 기획서 만들기

만들고 싶은 것을 자세히 지정하는 대신, Claude가 나에게 질문을 던지며 요구사항을 끌어내게 하는 방법입니다. 모델이 강해질수록 제약을 줄이고 질문에 답하는 쪽이 더 좋은 스펙(기획서)을 얻습니다.

  1. Claude Code에서 Shift+Tab을 눌러 auto mode로 바꿉니다.
  2. /effort로 노력 수준을 정합니다.
  3. 프롬프트에는 관심 영역(예: 대상 사용자)만 적고 결과를 과하게 지정하지 않습니다.
  4. 프롬프트에 ask user question 도구를 써서 질문해 달라고 명시합니다.
  5. Claude가 띄우는 질문에 차례로 답합니다.
  6. 답변이 끝나면 Claude가 작성한 스펙을 검토합니다.
예시
사회초년생을 위한 가계부 앱을 만들고 싶어. ask user question 도구로 나에게 질문해 가며 요구사항을 정리하고, 다 끝나면 스펙을 작성해 줘.
  • '더 좋게 만들어', '실수 없이 만들어' 같은 막연한 프롬프트는 피합니다.
  • 계획은 긴 마크다운 대신 정보가 촘촘한 HTML 파일로 받아 먼저 검토하는 방법도 소개되었습니다.
  • 스펙을 빠르게 여러 번 고칠 때는 /fast 모드가 유용합니다.
  • 예전 방식: 계획 모드(Shift+Tab으로 전환, 읽기 전용으로 분석 후 계획 제시)를 먼저 썼지만, 최신 모델에서는 계획 모드 대신 오토 모드를 쓴다고 합니다.

9. 내 사용 패턴으로 모드 추천받기

모드(Mods)는 Claude Code의 모습과 행동 방식을 바꾸는 작은 프로그램으로, 10월 1일 공식 발표되었습니다. 스킬·MCP가 지식과 도구를 건네는 방식이라면, 모드는 작업 환경 자체를 바꿉니다. 내 세션 기록을 바탕으로 나에게 맞는 모드를 추천받아 만들 수 있습니다.

  1. Claude Code에 세션 로그를 최대한 훑어 내가 자주 반복하는 말과 작업을 파악해 달라고 요청합니다.
  2. 흐름을 돕고, 비용을 아끼고, 집중하게 해 줄 모드 다섯 개를 추천해 달라고 요청합니다.
  3. 추천 목록과 그 근거를 읽어 봅니다.
  4. 마음에 드는 번호를 골라 만들어 달라고 요청합니다.
예시
내 Claude Code 세션 로그를 최대한 훑어서 내가 자주 반복하는 말과 작업을 파악해 줘. 그걸 바탕으로 흐름을 돕고 비용을 아끼며 집중하게 해 줄 모드 다섯 개를 추천해 줘.
  • 추천에는 내 사용 패턴과 그 근거가 함께 나옵니다.
  • 영상에서는 데스크톱 앱에서 토큰 사용량 표시, 다음 작업 추천 같은 모드를 만들었습니다.
  • 창·버튼 같은 화면 요소는 모드로만 만들 수 있다고 설명합니다.

10. 평가 세트로 프롬프트 개선하기

모델을 바꾼 뒤 성능이 떨어졌거나 업무용 프롬프트를 다듬고 싶을 때, 테스트 사례(평가 세트)를 만들어 놓고 고칠 때마다 결과를 비교하는 방법입니다. '느낌'이 아니라 통과율로 개선 여부를 판단할 수 있습니다.

  1. 정상 사례, 이전에 실패한 까다로운 사례, 사람에게 넘기거나 거절해야 할 사례를 모아 평가 세트를 만듭니다.
  2. 현재 프롬프트로 평가를 돌려 어떤 유형에서 실패하는지 확인합니다.
  3. 사실과 다른 역할 설명과 웹에서 복사해 온 불필요한 내용을 지웁니다.
  4. XML 태그로 역할·가이드라인·정책·말투를 구분해 구조를 만듭니다.
  5. 출력 형식을 정하는 '출력 계약'을 추가합니다.
  6. 평가를 다시 돌려 실패 유형을 하나씩 고치며 결과를 비교합니다.
예시
<역할>당신은 통신사 고객지원 상담원입니다.</역할>
<가이드라인>고객의 질문에 정확하고 짧게 답합니다.</가이드라인>
<정책>요금 환불은 직접 처리하지 않고 담당 부서로 안내합니다.</정책>
<말투>정중한 존댓말</말투>
<출력형식>답변 3문장 이내, 마지막 줄에 다음 할 일 1개</출력형식>
  • 가이드라인·정책·데이터를 사람이 구분하기 어려우면 모델도 구분하기 어렵습니다.
  • 실행할 때마다 결과가 조금씩 다르니 한 번의 결과로 단정하지 않습니다.
  • 금지 항목을 길게 나열하는 방식은 피합니다. 실패는 모델이 아니라 서로 부딪히는 지시 때문인 경우도 많습니다.
  • 새 에이전트를 만들 때는 큰 프롬프트 하나 대신 생성·평가·수리 세 프롬프트로 나누면 토큰과 지연이 줄었다는 사례가 있습니다.

11. 평가로 내 업무에 맞는 모델 고르기

공개 벤치마크는 방향만 알려 줄 뿐 내 업무와 다를 수 있습니다. 작은 평가라도 직접 만들어 두면 새 모델이 나올 때마다 품질·지연·비용을 비교해 옮길지 판단할 수 있습니다.

  1. 입력과 성공 기준을 갖춘 테스트 작업을 모아 평가 데이터 세트를 만듭니다.
  2. 최종 결과뿐 아니라 올바른 단계를 거쳤는지도 보는 채점기를 작업마다 붙입니다.
  3. 응답 품질 비교에는 LLM 심사를, 특정 도구 호출이나 값 확인에는 코드 기반 채점을 씁니다.
  4. 모델과 thinking·effort 설정을 바꿔 가며 각 작업을 여러 번 돌립니다.
  5. 로그를 열어 API·도구 호출 실패 같은 인프라 문제를 모델 실패와 구분합니다.
  6. 통과율, 토큰, 비용, 지연 시간을 비교해 내가 중시하는 기준에 맞는 모델과 설정을 고릅니다.
  • 토큰당 가장 싼 모델이 아니라 성공 한 건당 가장 싼 모델을 고릅니다.
  • 결과 편차가 크면 작업 정의나 평가 기준이 불명확하다는 신호입니다.
  • LLM 심사도 틀릴 수 있으니 여러 채점기를 함께 씁니다.
  • 새 모델을 받으면 평가부터 백그라운드로 돌려 두면 좋습니다. 모델만 바꿔도 성공률이 약 20% 오른 사례가 있습니다.
