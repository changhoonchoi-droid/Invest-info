1. Opus 5.5와 Sonnet 5.5 골라 쓰기

Claude 5.5 모델 계열은 생각이 많이 필요한 일과 빠른 손질이 필요한 일에 맞춰 나눠 쓰도록 권장됩니다. 일의 단계에 따라 모델을 바꾸면 품질과 속도를 함께 챙길 수 있습니다.

  1. 오늘 맡길 일이 '방향을 찾는 단계'인지 '빠르게 고치는 단계'인지 먼저 나눕니다.
  2. 기획안 뼈대 잡기, 복잡한 계획 세우기처럼 방향을 찾는 일은 Opus 5.5로 시작합니다.
  3. Opus 5.5가 낸 초안의 방향이 마음에 들면 그 결과를 기준으로 정합니다.
  4. 문장 다듬기, 표 수정처럼 빠른 손질은 Sonnet 5.5로 바꿔서 맡깁니다.
  5. 결과가 기대보다 얕으면 다시 Opus 5.5로 돌아가 방향부터 다시 잡습니다.
  • Factory는 복잡한 계획과 조율에 Opus를 써서 계획을 거의 확인하지 않아도 될 만큼 감독이 줄었다고 말합니다.
  • 예전 방식: 2026년 2월에는 Free·Pro 플랜의 claude.ai와 Cowork 기본 모델이 Sonnet 4.6이었습니다.
  • Fable 5는 2026년 6월 공개 당시 일반 공개 모델 중 가장 뛰어난 모델로 소개됐고, 코딩·장시간 작업·문서·슬라이드·스프레드시트 업무에 강하다고 합니다.

2. 하나로 합쳐진 Claude에 일 맡기기

채팅과 Cowork가 하나의 Claude로 합쳐져 이제 모드를 고르지 않고 원하는 결과만 말하면 Claude가 방법을 찾습니다. 작업이 클라우드에서 돌아가므로 오래 걸리는 일을 맡겨 두고 자리를 비워도 됩니다.

  1. Claude를 열고 모드를 고르지 말고 원하는 결과를 한 문장으로 적습니다.
  2. 결과물이 쓰일 곳(보고 대상, 분량, 마감)을 덧붙여 원하는 바를 분명히 합니다.
  3. 작업이 시작되면 노트북을 닫아도 되니 다른 일을 합니다.
  4. 이동 중에는 휴대폰으로 진행 상황을 확인합니다.
  5. 결과를 받으면 고칠 점만 짧게 다시 요청합니다.
  • 예전 방식: 채팅과 Cowork 중 어느 모드로 할지 먼저 골라야 했습니다. 기존 Cowork 작업은 통합 뒤에도 그대로 남아 있습니다.
  • Claude Code 팀처럼 '할 일 하나하나'보다 '이루고 싶은 목표'를 맡기는 쪽으로 요청을 바꿔 보세요.
  • LLM은 질문에 맞춰 답하려는 경향이 있으니, 실제로 필요한 것을 정확히 요청하는 것이 중요합니다.

3. 대화에서 슬라이드·문서 만들기

Claude Slides, Claude Design, Claude Docs를 쓰면 대화를 벗어나지 않고 발표 자료, 소셜 이미지, 한 장짜리 요약 문서를 만들 수 있습니다. 앞서 나눈 대화 내용을 바탕으로 만들어지고, 결과물의 원하는 부분에 코멘트를 달아 고칠 수 있습니다.

  1. 만들 자료의 바탕이 될 브리프(출시 안내, 회의 내용, 자주 묻는 질문 등)를 대화에 붙여 넣습니다.
  2. 필요한 결과물 종류(발표 슬라이드, 소셜 이미지 세트, 한 장 요약 문서)를 한 번에 요청합니다.
  3. 만들어진 결과물에서 고칠 부분을 골라 코멘트를 답니다.
  4. 코멘트를 Claude에게 보내 그 부분만 고치게 합니다.
  5. 함께 다듬을 문서는 Claude Docs에서 팀원과 Claude가 동시에 편집합니다.

4. Claude 데이터 보관 방식 확인하기

회사 업무에 AI를 쓰기 전에 내 입력이 얼마나, 누구에게 보관되는지 알아야 보안 담당자를 설득할 수 있습니다. Claude Fable 5부터는 안전 모니터링을 위해 최근 30일의 프롬프트와 출력이 저장되며, 기업은 Enterprise Frontier Safeguards(EFS)로 보관 위치를 직접 통제할 수 있습니다.

  1. 업무에 쓰는 모델이 Claude Fable 5 이후 모델인지 확인합니다.
  2. Fable 5 이후 모델이면 최근 30일의 프롬프트와 출력이 안전 모니터링용으로 저장된다는 점을 팀에 공유합니다.
  3. 저장된 데이터는 자동 시스템이 분석하고, 사람은 유해 가능성이 표시된 드문 경우에만 승인된 소수 검토자가 본다는 점을 확인합니다.
  4. 엔터프라이즈 요금제라면 명시적 허가 없이 데이터가 학습에 쓰이지 않는다는 점을 확인합니다.
  5. 자체 클라우드 보관이 필요한 조직이면 IT·보안 담당자와 EFS 도입 여부를 논의합니다.
  • EFS는 제로 데이터 보존(ZDR)의 프라이버시와 오남용 탐지 세이프가드를 합친 것으로, 로그는 고객이 통제하고 검토는 기계로만 이뤄집니다.
  • EFS는 2026년 가을 이후 단계적으로 제공되며, 그 전까지 대상 조직은 Fable 5와 5.1에서 데이터 보관 없음(ZDR)을 받습니다.
  • 사람이 검토한 접근 기록은 변조할 수 없는 로그에 남습니다.

5. Claude Duet 미리 알아두기

Claude Duet은 Claude가 주의가 필요한 일을 먼저 알려 주고, 사용자가 폰을 내려놓은 뒤에도 계속 일하는 새 앱입니다. 무엇이 지금 확인할 일이고 무엇이 미뤄도 되는 일인지 판단해 주므로, 일이 여러 곳에 흩어진 직장인에게 맞습니다.

  1. 내 요금제가 Pro 또는 Max인지, 이용 지역이 대상(미국)인지 확인합니다.
  2. 대상이면 연구 프리뷰 대기자 명단에 신청합니다.
  3. 쓰게 되면 Claude가 먼저 알려 주는 일 중 지금 확인할 것과 미룰 것을 구분해 봅니다.
  4. Claude가 나를 대신해 행동하기 전에 확인을 요청하면 내용을 읽고 승인하거나 거절합니다.
  • 연구 프리뷰라 2026년 10월 기준 한국에서는 바로 쓰기 어렵습니다. 소식만 먼저 알아 두세요.
  • 사용자들은 맥락 이해와 선제적 판단, Slack에서 필요한 내용을 먼저 가져다주는 점을 장점으로 꼽았습니다.

6. AI로 만든 콘텐츠 공개 방식 정하기

AI로 영상·글을 만들 수 있게 되면서 그대로 공개해도 되는지 고민이 생깁니다. 한 유튜버가 정리한 네 가지 선택지를 기준으로 내 채널·사내 자료의 방침을 정할 수 있습니다.

  1. 네 가지 선택지(① AI로 다 하기 ② AI 콘텐츠는 다른 채널·쇼츠로 분리 ③ AI를 쓰되 사람의 몫 넣기 ④ AI 쓰지 않기) 중 내 상황에 맞는 것을 고릅니다.
  2. ③을 고른다면 어떤 부분에 내 경험·판단을 넣을지 정합니다.
  3. 공개 전에 사실관계를 사람이 직접 검수·검증합니다.
  4. AI를 썼다는 점을 독자·시청자에게 솔직하게 알리고 반응을 봅니다.
  • 영상에서는 사람의 가치가 완벽함보다 진실성에 있다고 봅니다.
  • AI 콘텐츠일수록 검수·검증과 신뢰가 중요해진다는 의견입니다.
  • 영상에서는 ElevenLabs V4 API 이후 AI 음성이 훨씬 나아졌다고 언급합니다.

7. Slack에서 Claude Tag로 팀 일 맡기기

Claude Tag는 Slack 채널에서 팀과 함께 일하는 Claude입니다. 스레드에서 태그하면 채널 맥락을 파악해 작업하고, 끝나거나 입력이 필요할 때 알려 주며, 며칠 걸리는 일도 후속 확인까지 이어 갑니다.

  1. 회사 요금제가 Team 또는 Enterprise인지 확인합니다(Slack에서 베타 제공).
  2. 맡길 일이 있는 Slack 스레드에서 Claude를 태그하고 원하는 결과를 적습니다.
  3. 같은 스레드에서 다른 팀원도 필요한 조건을 덧붙여 함께 지시합니다.
  4. Claude가 작업을 마치거나 입력이 필요하다고 알리면 그 스레드에서 답합니다.
  5. 채널에서 반복되는 지시는 Claude가 기억하므로, 채널별 규칙을 한 번 분명히 알려 둡니다.
  • 데이터 질문 답변, PR 작성, 버그 수정, 사내 문의 응대 등에 쓰이며, Anthropic 제품 PR의 약 65%를 Tag가 작성합니다.
  • Claude는 자기 계정과 권한을 갖고, 채널별로 접근 범위가 나뉘며, 모든 자격 증명 사용이 기록됩니다. 비공개 채널·DM에서 배운 내용은 그 안에만 남습니다.
  • 다른 사람이 Tag를 쓰는 방법을 보며 모범 사례가 퍼지므로 공개 채널에서 써 보는 것이 좋습니다.
  • Microsoft Teams 등으로 확대할 계획이 발표됐습니다.

8. 새 모델이 나오면 직접 평가하기

모델이 약 두 달마다 바뀌므로, 발표 내용만 믿지 말고 내 업무로 직접 시험해야 실제로 나아졌는지 알 수 있습니다. 출시 전에 모델을 먼저 받는 고객 팀들은 자동 평가와 실제 어려운 작업을 함께 돌려 봅니다.

  1. 평소 자주 하는 업무 중 정답을 알고 있는 과제 몇 개를 평가 세트로 모아 둡니다.
  2. 새 모델이 나오면 평가 세트를 먼저 돌려 기존 모델과 결과를 비교합니다.
  3. 법률 문서 초안처럼 지금 모델이 잘 못하던 복잡한 실제 작업을 맡겨 봅니다.
  4. 판단 기준으로 지능과 의사결정 능력을 가장 먼저 봅니다.
  5. 여전히 안 되는 작업은 다음 모델이 나아질 영역으로 기록해 둡니다.
  6. 모델이 약점을 넘었으면, 그 약점을 메우려고 만들었던 우회 방법은 과감히 지웁니다.
  • 모델 교체만으로 테스트 에이전트 성공률이 약 20% 오른 사례가 있습니다.
  • Factory는 모델이 하니스를 흡수하므로 매달 기존 해법을 다시 의심해야 한다고 말합니다.

9. 큰 모델·작은 모델 나눠 쓰기

Shopify CTO가 권하는 '배벨 전략'은 개발·테스트·연구에는 가장 큰 모델을, 반복 운영에는 저렴한 모델을 쓰는 방식입니다. AI 사용이 늘어 비용이 신경 쓰이는 팀에 맞습니다.

  1. 팀이 AI로 하는 일을 '새로 만들고 시험하는 일'과 '매일 반복 돌리는 일'로 나눕니다.
  2. 새로 만들고 시험하는 일에는 가장 큰 모델을 쓰고 토큰을 아끼지 않습니다.
  3. 결과가 안정된 반복 업무는 저렴한 모델로 옮깁니다.
  4. 자동으로 계속 도는 작업에는 폭주할 때 멈추게 하는 서킷 브레이커(사용량·횟수 상한)를 둡니다.

  • 업무를 덜어 주는 '바닥 올리기'보다 예전에 불가능했던 일을 하는 '천장 올리기'에 큰 모델을 쓰라고 권합니다.
  • 품질을 속도보다 중시하는 Emergent는 Opus를 주력 모델로 씁니다.

10. Claude Code 루틴으로 반복 일 맡기기

루틴은 사람이 매번 지시하지 않아도 정해진 계기에 Claude Code가 스스로 작업하게 하는 기능입니다. 일정, 웹훅, API 호출로 시작할 수 있고 로컬이나 원격 클라우드에서 실행되므로 세션을 열어 두지 않아도 됩니다.

  1. 매일·매주 반복하는 일 중 판단 기준이 분명한 일 하나를 고릅니다.
  2. 그 일을 언제 시작할지 정합니다: 일정, 웹훅, API 호출 중 하나.
  3. 실행 위치를 로컬과 원격 클라우드 중에서 고릅니다(노트북을 꺼도 돌아야 하면 클라우드).
  4. 루틴에 줄 지시를 적되, 확신이 높은 것만 처리하고 나머지는 보고만 하게 범위를 좁힙니다.
  5. 처음 몇 번은 결과를 직접 확인한 뒤 범위를 넓힙니다.
예시
매일 들어온 피드백을 모아 중요도별로 분류하고, 확신이 높은 것만 고쳐 줘.
  • 런던 행사에서는 루틴이 사람 대신 Claude Code에 지시하고 CI 자동 수정까지 맡는 흐름을 시연했습니다.
  • Claude Code에는 루틴 외에도 원격 제어, 자동 모드, 자동 메모리, 자동 코드 리뷰, 에이전트 뷰가 추가됐습니다.
  • 도쿄 행사에서 발표된 동적 워크플로는 Claude Code 데스크톱 앱에서 쓸 수 있습니다.

11. AI 시대에 맞게 팀 업무 절차 고치기

AI로 코딩·작성이 빨라지면 병목은 검증·리뷰·유관 부서 협업·보안으로 옮겨 갑니다. Anthropic의 Claude Code 팀처럼 예전 절차를 하나씩 점검하고, 품질은 AI의 판단이 아니라 사람의 승인과 시스템 장치로 지키는 방법입니다.

  1. 팀에서 가장 소모적인 업무 절차 하나를 고릅니다.
  2. 그 절차가 지금도 필요한지, Claude로 줄일 수 있는지 팀과 점검합니다.
  3. 긴 장기 계획 대신 필요한 때 계획하는 JIT 방식으로 바꿀 수 있는지 봅니다.
  4. AI가 원인이나 해결책을 제안하면, 확인·적용 범위 결정·승인은 사람이 맡도록 역할을 정합니다.
  5. 권한 제한, 데이터 분리, 점진적 배포처럼 AI 판단과 무관하게 작동하는 보호 장치를 둡니다.
  6. 모델이 좋아질 때마다 AI를 얼마나 믿고 얼마나 검증할지 다시 평가합니다.
  • 프로세스는 스스로 사라지지 않고 계속 쌓이므로 의식적으로 정리해야 합니다.
  • Stripe는 이 방식으로 엔지니어 2~3명이 약 2개월 만에 Stripe Projects를 출시했고, 한 엔지니어가 AI로 쓴 PR 600개 이상 중 되돌린 것은 1건뿐이었습니다.
  • Factory의 은행 COBOL 현대화에서는 첫 작업에 엔지니어가 함께했고 다음 작업부터 사람 개입이 90% 줄었습니다.
  • 기술 논쟁은 말보다 코드(프로토타입)로 먼저 보여 주는 방식으로 바꿨다고 합니다.
