1. 화제의 AI 소식 출처 확인하기

SNS에서 크게 퍼진 AI 소식은 숫자나 주장이 원래 뜻과 다르게 전해지는 경우가 많습니다. 작성자, 링크, 원 논문 세 가지만 확인해도 소식이 전혀 다르게 보일 수 있습니다. 새 기능·모델 소식을 업무에 반영하기 전에 먼저 해 두면 좋은 습관입니다.

  1. 화제가 된 글에서 핵심 주장과 숫자 하나를 골라 적습니다.
  2. 작성자의 프로필을 열어 그 회사·프로젝트와 어떤 관계인지 확인합니다.
  3. 글에 걸린 링크가 공식 저장소나 공식 발표인지 확인합니다.
  4. 숫자가 논문에서 나왔다면 원 논문을 열어 몇 명·몇 건을 분석했는지 확인합니다.
  5. 그 숫자가 정확히 무엇의 비율인지 원문 문장으로 다시 읽습니다.
  6. 확인한 내용과 처음 글의 주장이 다르면, 원문 기준으로 메모해 팀에 공유합니다.
예시
이 글의 주장과 숫자를 원 논문 기준으로 다시 정리해 줘. 연구 대상 수, 숫자가 가리키는 정확한 대상, 글과 원문이 다른 점을 나눠서 알려 주고, 확인이 필요한 부분은 따로 표시해 줘.
  • 사례: 챗GPT 메모리 '96%' 글의 원 논문은 사용자 80명의 메모리 2,050개를 분석했고, 96%는 사용자가 요청하지 않고 GPT가 스스로 만든 메모리 비율이었습니다.
  • 반대로 조회수 200만 '슈퍼베이스 6시간 복제' 글은 작성자가 슈퍼베이스 CEO였고 링크도 공식 저장소였습니다. 확인 결과 믿을 만한 소식일 수도 있습니다.
  • 깃허브 별 수처럼 빠르게 바뀌는 숫자는 조사한 날짜를 함께 적어 두세요 (REA는 10월 13일 16만 개에서 몇 주 만에 37만 개로 늘었습니다).

2. Opus 5.5와 Sonnet 5.5 나눠 쓰기

지금 Claude는 Claude 5.5 모델 계열이 뒷받침합니다. 방향을 잡는 큰 작업에는 Opus 5.5, 빠르게 고치는 작업에는 Sonnet 5.5를 쓰는 것이 공식 권장 방식입니다. 비용과 품질을 함께 챙기고 싶을 때 씁니다.

  1. 오늘 할 일을 '방향을 정하는 일'과 '이미 정한 것을 다듬는 일'로 나눕니다.
  2. 기획안 뼈대, 보고서 구조, 복잡한 분석처럼 방향을 찾는 일은 Opus 5.5에 맡깁니다.
  3. 문장 손보기, 표 서식 수정, 작은 고침처럼 빠른 수정은 Sonnet 5.5로 처리합니다.
  4. 결과가 기대보다 약하면 같은 요청을 Opus 5.5로 다시 돌려 비교합니다.
  5. 자주 하는 작업별로 어떤 모델이 잘 맞았는지 메모해 두고 다음부터 그대로 고릅니다.
  • Shopify의 '배벨 전략': 개발·테스트·자동 연구처럼 품질이 중요한 곳에는 가장 큰 모델, 반복 운영에는 저렴한 모델을 씁니다.
  • 자동으로 계속 도는 작업은 비용이 폭주하지 않도록 멈춤 장치(서킷 브레이커)를 함께 생각해 두세요.
  • 예전 방식: 2026년 2월에는 Free·Pro 플랜의 claude.ai와 Cowork 기본 모델이 Sonnet 4.6이었습니다.

3. 대화에서 문서·슬라이드 만들기

이제 어떤 대화에서든 Claude에게 문서, 슬라이드, 디자인을 만들어 달라고 할 수 있고, 지금까지 나눈 대화 내용을 바탕으로 만들어집니다. Claude Slides·Design·Docs가 베타로 공개되어, 브리프 하나로 발표 자료와 이미지, 한 장 요약까지 대화를 벗어나지 않고 만들 수 있습니다. 보고·출시·행사 준비처럼 같은 내용을 여러 형식으로 만들어야 할 때 유용합니다.

  1. 대화창에 출시 브리프나 기획 내용을 먼저 붙여 넣거나 설명합니다.
  2. 모드를 고르지 말고, 원하는 결과물(발표 자료, 소셜 이미지, 한 장 문서)을 그대로 말합니다.
  3. 만들어진 결과물에서 고치고 싶은 부분에 코멘트를 달아 Claude에게 보냅니다.
  4. 같은 대화에서 다른 형식의 결과물을 이어서 요청해 내용이 일관되게 만듭니다.
  5. 팀원과 함께 다듬을 문서는 Claude Docs에서 팀원과 Claude가 동시에 편집합니다.
  6. 오래 걸리는 작업은 클라우드에서 계속 돌아가므로 노트북을 닫고, 진행 상황은 휴대폰으로 확인합니다.
예시
이 출시 브리프로 발표 자료, 소셜 이미지 세트, 현장에서 나눠 줄 한 장짜리 요약 문서를 만들어 줘.
  • Claude Design을 쓸 때는 회사 디자인 시스템(색상·폰트·컴포넌트)을 먼저 만들어 두면 이후 프로젝트에 자동 적용되고, 결과물이 덜 'AI스럽게' 나옵니다.
  • Claude Design은 Pro·Max·Team·Enterprise 구독이 필요하고 사용량 한도가 채팅과 따로 관리됩니다. 한 실습에서는 Max 플랜으로 앱·PPT·디자인 시스템을 만들고 한도의 62%를 썼습니다.
  • 예전 방식: 채팅과 Cowork를 따로 골라 썼고, Claude Design은 4월에 웹 전용 리서치 프리뷰로 먼저 나왔습니다. 기존 Cowork 작업은 통합 뒤에도 그대로 남아 있습니다.

4. Claude 모바일 앱 새 기능 쓰기

10월 말 Claude 모바일 앱 업데이트로 계정 전환, 큰 화면 나란히 보기, 더 빠른 음성 모드, 33개 언어가 지원됩니다. 회사 계정과 개인 계정을 함께 쓰거나, 이동 중에 Claude와 대화하는 직장인에게 특히 편리합니다.

  1. iOS나 Android에서 Claude 앱을 최신 버전으로 업데이트합니다.
  2. 업무용 계정과 개인 계정에 모두 로그인해 두고, 로그아웃 없이 필요할 때 전환합니다.
  3. iPad에서는 Claude가 만든 아티팩트를 대화 옆 열에 띄워 두 창을 나란히 보며 작업합니다.
  4. 운전 중에는 iPhone을 Apple CarPlay에 연결해 음성 모드로 대화합니다.
  5. 사진을 고르면 업로드 중에도 바로 채팅에 표시되므로 기다리지 말고 이어서 질문을 씁니다.
  6. Chromebook이나 폴더블에서는 사이드바 크기를 조절하고 마우스 우클릭과 Claude Desktop과 같은 단축키를 씁니다.
  • 당겨서 검색은 iPhone·iPad에 곧 제공될 예정이고, 웹과 데스크톱에는 이미 있습니다 (Mac은 Command K).
  • 앱 인터페이스에 24개 언어가 추가돼 총 33개 언어를 지원합니다.

5. AI 답변의 환각 줄이고 검증하기

환각은 AI가 없는 논문, 가짜 통계, 틀린 이름·날짜를 사실처럼 말하는 현상입니다. 1년 전보다 크게 줄었지만 아직 해결된 문제는 아니어서, 보고서나 대외 자료에 쓸 답변은 따로 확인해야 합니다. 몇 가지 질문 습관만으로 위험을 크게 줄일 수 있습니다.

  1. 답변에서 구체적인 숫자, 인용, 날짜, 이름이 나온 부분을 표시합니다.
  2. 그 부분의 출처를 알려 달라고 요청합니다.
  3. 각 내용을 얼마나 확신하는지 Claude에게 묻습니다.
  4. 새 대화를 열어 같은 사실을 다시 물어 답이 같은지 확인합니다.
  5. 출처 링크를 직접 열어 실제로 그 내용이 있는지 확인한 뒤에 사용합니다.
예시
방금 답변에 나온 숫자·인용·날짜마다 출처를 붙이고, 각각 얼마나 확신하는지 높음·중간·낮음으로 표시해 줘. 모르는 것은 모른다고 말해 줘.
  • 구체적 사실·통계·인용, 잘 알려지지 않은 주제, 최신 내용, 정확한 날짜·이름·숫자에서 환각 가능성이 높습니다.
  • 환각이 줄어들수록 확인을 건너뛰기 쉬우니, 중요한 자료일수록 습관처럼 확인하세요.
  • AI 편향도 비슷하게 점검할 수 있습니다. Anthropic은 같은 주제를 두 관점으로 묻는 '짝지은 프롬프트'로 답변의 깊이를 비교합니다.

6. Claude 데이터 보관 정책 확인하기

Claude Fable 5부터 안전 모니터링을 위해 최근 30일간의 프롬프트와 출력이 저장됩니다. 회사 자료를 Claude에 넣기 전에 무엇이 얼마 동안 보관되고 누가 볼 수 있는지 알아 두어야 합니다. 보안 담당자나 팀장에게 도입을 설명할 때도 필요합니다.

  1. 우리 회사가 어떤 요금제(개인, Team, Enterprise)로 Claude를 쓰는지 확인합니다.
  2. Fable 5 이후 모델은 최근 30일의 프롬프트와 출력이 안전 모니터링용으로 저장된다는 점을 팀에 공유합니다.
  3. 저장된 데이터는 자동 시스템이 분석하고, 기본적으로 Anthropic 직원은 읽을 수 없다는 점을 확인합니다.
  4. Enterprise라면 데이터가 명시적 허가 없이 학습에 쓰이지 않는다는 점을 보안 담당자와 확인합니다.
  5. 모니터링 데이터를 자체 클라우드에 두고 싶다면 Enterprise Frontier Safeguards(EFS) 제공 시기를 담당 영업에 문의합니다.
  • 사람의 검토는 자동 시스템이 유해 가능성을 표시한 드문 경우에만, 승인된 소수 검토자가 하며 접근 기록은 변조 불가 로그에 남습니다.
  • EFS는 올가을 이후 단계적으로 제공되고, 그 전까지 대상 조직은 Fable 5와 5.1에서 데이터 보관 없음(ZDR)을 받습니다.
  • EFS에서는 로그를 고객이 통제하고, 검토는 기계로만 하며, 결과는 고객 콘텐츠가 아니라 정해진 탐지 항목으로만 나옵니다.

7. AI 조언에 휩쓸리지 않고 결정하기

Anthropic 연구에 따르면 사람들은 AI가 기운 쪽을 86% 따랐고, 그러면서도 스스로 결정했다고 착각하기 쉬웠습니다. 기획안 선택, 분석 방법 결정, 코딩 에이전트의 계획 단계처럼 AI와 함께 판단하는 순간에 쓰는 세 가지 요령입니다.

  1. AI에게 추천을 묻기 전에, 내가 중요하게 여기는 우선순위를 먼저 적어 둡니다.
  2. AI에게 그 우선순위를 먼저 말하고 나서 선택지를 비교하게 합니다.
  3. 말로 결정하기 어려운 선택은 작은 프로토타입이나 시안을 각각 만들어 보고 결과로 정합니다.
  4. AI의 추천을 받으면 '어떤 조건이면 이 조언이 바뀌는지' 묻습니다.
  5. 최종 결정을 설명할 때 AI에게서 가져온 논거는 출처를 밝혀 기록합니다.
예시
내 우선순위는 1) 유지보수 쉬움 2) 비용 3) 속도 순이야. 이 기준으로 두 방안을 비교해 주고, 어떤 조건이 바뀌면 네 추천이 달라지는지도 알려 줘.
  • 자기 선호가 있던 사람도 AI가 반대하면 60%가 생각을 바꿨고, AI가 동의할 때 바꾼 사람은 6%였습니다. 반대 의견을 들었을 때 특히 한 번 더 따져 보세요.
  • 연구 한계: AI의 기울기를 일부러 강화했고, 한 분야·한 과제·한 모델만 다뤘습니다.
  • AI는 질문에 맞춰 답하려는 경향이 있어, 실제로 필요한 것을 정확히 요청하는 판단력이 더 중요합니다.

8. 새 모델을 내 업무로 비교하기

새 모델이 나오면 벤치마크 점수보다 내 업무에서 실제로 나아졌는지가 중요합니다. 앞서 모델을 시험하는 고객 팀들은 자기 업무 과제로 평가를 먼저 돌리고, 지금 안 되는 일을 다음 모델의 신호로 봅니다. 모델 교체만으로 성공률이 약 20% 오른 사례도 있습니다.

  1. 내 업무에서 자주 하는 과제 3~5개를 골라 같은 프롬프트로 고정해 둡니다.
  2. 지금 쓰는 모델로 결과를 받아 기준 답으로 저장합니다.
  3. 새 모델이 나오면 같은 프롬프트를 그대로 넣어 결과를 받습니다.
  4. 필요하면 다른 회사 도구에서도 같은 프롬프트로 결과를 받아 나란히 비교합니다.
  5. 디자인 완성도, 오류, 요청 반영 여부를 항목별로 표에 적습니다.
  6. 지금 모델이 못 하는 과제는 따로 목록으로 남겨 다음 모델이 나올 때 다시 시험합니다.
  • 벤치마크와 실전 경험은 다르니 직접 써 보고 고르세요. 한 비교에서는 디자인 완성도는 Claude, 게임 애니메이션은 Codex가 앞섰지만, Claude가 만든 PPT에 키보드 방향이 반대인 오류도 있었습니다.
  • 평가는 백그라운드로 먼저 돌려 두고, 그동안 법률 문서 초안처럼 복잡한 실제 업무를 맡겨 보는 방식이 많이 쓰입니다.
  • 모델이 몇 달마다 바뀌므로, 예전 모델의 약점을 메우려고 만든 우회 방법도 새 모델에서 아직 필요한지 다시 확인하세요.

9. 소모적인 업무 절차 하나 점검하기

Claude Code 팀은 AI로 코딩이 빨라지자 병목이 검증·리뷰·협업으로 옮겨 갔고, 예전 절차가 조용히 쓸모없어졌다고 말합니다. 절차는 저절로 사라지지 않고 쌓이므로 의식적으로 정리해야 합니다. 팀 업무 방식을 AI에 맞게 바꾸고 싶을 때 가장 작게 시작하는 방법입니다.

  1. 우리 팀에서 가장 시간을 많이 잡아먹는 업무 절차 하나를 고릅니다.
  2. 그 절차가 처음 생긴 이유를 적고, 그 이유가 지금도 유효한지 확인합니다.
  3. 그 절차 중 Claude로 줄이거나 대신할 수 있는 부분을 표시합니다.
  4. 말로 길게 논의하던 안건은 Claude로 시안이나 프로토타입을 먼저 만들어 보여 주는 방식으로 바꿔 봅니다.
  5. 바꾼 뒤에 새로 병목이 된 부분(검증, 리뷰)을 누가 맡을지 정합니다.
  6. 몇 주 뒤 다시 점검해 신뢰와 검증의 균형을 조정합니다.
  • Claude Code 팀은 6개월 로드맵 대신 필요할 때 계획하는 JIT 방식으로 바꿨습니다.
  • Shopify는 업무를 덜어 주는 '바닥 올리기'보다 예전에 불가능했던 일을 가능하게 하는 '천장 올리기'에 초점을 둡니다.
  • Factory는 모델이 하니스를 흡수하므로 매달 기존 해법을 다시 의심해야 한다고 말합니다.

10. Slack에서 Claude Tag에 일 맡기기

Claude Tag는 Slack 채널에서 팀과 함께 일하는 Claude입니다. 스레드에서 태그하면 채널 맥락을 파악해 작업하고, 끝나거나 입력이 필요할 때 알려 주며, 며칠~몇 주 걸리는 일도 후속 확인까지 이어 갑니다. 데이터 질문 답변, 사내 문의 응대, 버그 수정 같은 팀 업무에 씁니다.

  1. 회사가 Team 또는 Enterprise 요금제인지 확인합니다 (Claude Tag는 이 요금제에서 베타로 제공).
  2. Claude Tag를 쓸 Slack 채널을 정하고, 채널별로 접근 범위를 나눠 둡니다.
  3. 맡길 일이 생긴 스레드에서 Claude를 태그하고 원하는 목표를 적습니다.
  4. 같은 스레드에서 다른 팀원도 함께 지시를 더하거나 방향을 고칩니다.
  5. Claude가 입력을 요청하거나 완료를 알리면 결과를 확인하고 승인합니다.
  6. 채널에서 반복해 지시한 내용은 메모리로 쌓이므로, 채널 규칙을 한 번 정리해 알려 둡니다.
  • 비공개 채널이나 DM에서 배운 내용은 그 안에만 남고, Claude 계정의 모든 자격 증명 사용이 기록됩니다.
  • 다른 팀원이 Tag를 어떻게 쓰는지 채널에서 보며 좋은 사용법을 따라 하기 쉽습니다.
  • 예전 방식: 프롬프트를 주고 권한 요청을 하나씩 승인했지만, 지금 Claude Code 팀은 작업이 아니라 목표를 맡기고 일의 70~80%를 Tag에서 처리합니다.
  • Microsoft Teams 등으로 확대할 계획이 발표됐습니다.

11. 루틴으로 반복 작업 자동화하기

루틴은 사람이 매번 지시하지 않아도 정해진 계기에 Claude Code가 작업을 시작하게 하는 기능입니다. 일정, 웹훅, API 호출로 시작할 수 있고 로컬이나 원격 클라우드에서 실행됩니다. 매일 들어오는 피드백 정리처럼 세션 밖에서 계속 돌아야 하는 일에 씁니다.

  1. 매일 또는 매주 반복하는 작업 하나를 고릅니다 (예: 들어온 피드백 정리).
  2. 루틴을 시작할 계기를 일정, 웹훅, API 호출 중에서 정합니다.
  3. 노트북을 꺼도 돌아야 하면 원격 클라우드 실행을, 내 PC 파일이 필요하면 로컬 실행을 고릅니다.
  4. 루틴에게 줄 목표를 적습니다: 피드백을 모아 중요도별로 분류하고, 확신이 높은 것만 고치기.
  5. 처음 몇 번은 결과를 직접 확인하고, 안전하게 맡길 범위를 정합니다.
  6. 범위가 확인되면 CI 자동 수정처럼 더 많은 일을 루틴에 넘깁니다.
  • 런던 기조연설에서는 사람이 Claude Code에 지시하는 대신 루틴이 지시하고 CI 자동 수정까지 맡는 흐름을 시연했습니다.
  • 확신이 높은 것만 자동으로 고치게 하고, 나머지는 사람이 보도록 분류만 시키는 것이 안전합니다.
  • Stripe처럼 품질은 AI의 판단에만 맡기지 말고 권한 분리·점진적 배포 같은 장치로 지키세요.
