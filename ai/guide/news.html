발표·소식

「발표·소식」에서는 Claude의 새 기능과 모델 출시, 데이터 보관 정책, 실제 기업 사례를 바탕으로 업무에 바로 쓸 수 있는 것만 골라 정리했습니다. 처음이라면 하나로 합쳐진 Claude로 결과물 만들기와 슬라이드·문서 만들기부터 해 보세요. 다음으로 모델 고르기와 데이터 보관 정책을 확인하고, 마지막에 Slack 팀 협업, 루틴 자동화, 새 모델 평가, 안전장치 같은 응용으로 넘어가면 됩니다.

1. 하나로 합쳐진 Claude에 원하는 결과 말하기

9월 업데이트로 채팅과 Cowork가 하나의 Claude로 합쳐져서 이제 모드를 고르지 않아도 됩니다. 원하는 결과만 말하면 Claude가 방법을 찾습니다. 작업은 클라우드에서 돌아가므로 오래 걸리는 일도 맡겨 두고 다른 일을 할 수 있습니다.

  1. Claude 대화창을 열고 모드를 따로 고르지 않은 채 시작합니다.
  2. '무엇을 할지'보다 '어떤 결과가 필요한지'를 한두 문장으로 적습니다.
  3. 앞서 나눈 대화가 있다면, 그 내용을 바탕으로 문서·슬라이드·디자인 중 필요한 것을 만들어 달라고 요청합니다.
  4. 작업이 시작되면 노트북을 닫아도 됩니다. 작업은 클라우드에서 계속됩니다.
  5. 이동 중에는 휴대폰으로 진행 상황을 확인합니다.
  6. 예전에 Cowork에서 하던 작업이 그대로 남아 있는지 확인합니다.
예시
지금까지 나눈 대화 내용을 바탕으로 팀 공유용 발표 자료를 만들어 줘.
  • 예전 방식: 채팅과 Cowork 중에서 모드를 골라 시작해야 했지만, 이제는 하나의 Claude에서 바로 시작합니다.
  • 기존 Cowork 작업은 통합 후에도 그대로 유지됩니다.
  • 이 변화는 Claude 5.5 모델 계열이 뒷받침합니다.

2. 브리프 하나로 슬라이드·이미지·문서 만들기

Claude Slides, Claude Design, Claude Docs를 쓰면 출시 브리프 하나로 발표 자료, 소셜 이미지 세트, 한 장짜리 요약 문서를 대화창을 벗어나지 않고 만들 수 있습니다. 결과물 일부에 코멘트를 달면 그 부분만 고쳐 줍니다. 신제품 출시, 행사 준비, 고객 안내문 작성에 알맞습니다.

  1. 출시 브리프(제품명, 대상, 핵심 메시지, 일정)를 대화창에 붙여 넣습니다.
  2. 같은 대화에서 발표 자료(Claude Slides)를 만들어 달라고 요청합니다.
  3. 이어서 소셜 이미지 세트(Claude Design)를 요청합니다.
  4. 현장에서 나눠 줄 한 장짜리 요약 문서(Claude Docs)를 요청합니다.
  5. 고칠 부분에 코멘트를 달아 Claude에게 보냅니다.
  6. Claude Docs 문서는 팀원과 함께 열어 Claude와 동시에 편집합니다.
예시
이 출시 브리프로 발표 자료, 소셜 이미지 세트, 현장용 한 장 요약 문서를 만들어 줘.
  • Slides·Design·Docs는 베타로 제공됩니다.
  • 그동안 받은 고객 질문을 모아 주면 한 장짜리 안내문(팩트 시트)으로 정리할 수 있습니다. 양봉가 사례에서 이렇게 활용했습니다.
  • Claude Design은 일상 언어로 설명해도 제작 수준의 결과물을 만들도록 설계되었습니다.

3. Claude Duet 대기자 명단 신청하기

Claude Duet은 주의가 필요한 일을 Claude가 먼저 알려 주고, 폰을 내려놓은 뒤에도 계속 일하는 새 앱입니다. 지금 확인해야 할 일과 미뤄도 되는 일을 구분해 주고, 사용자를 대신해 행동하기 전에는 꼭 확인을 받습니다. 지금은 연구 프리뷰 단계입니다.

  1. 신청 대상인지 확인합니다. 현재는 미국의 Pro·Max 구독자만 신청할 수 있습니다.
  2. 대상이라면 대기자 명단에 등록합니다.
  3. 이용이 열리면 Claude가 먼저 알려 주는 '주의가 필요한 일' 목록을 확인합니다.
  4. Claude가 대신 행동하겠다고 확인을 요청하면 내용을 읽고 승인할지 정합니다.
  5. Slack 등 업무 도구에서 Claude가 먼저 가져다준 내용이 맞는지 점검합니다.
  • 연구 프리뷰라서 기능과 이용 대상이 바뀔 수 있습니다.
  • 한국 사용자는 아직 대상이 아니므로 공지를 계속 확인하세요.
  • Claude는 대신 행동하기 전에 확인을 받으므로, 승인 요청은 꼼꼼히 읽고 결정하세요.

4. 작업 단계에 맞춰 모델 나눠 쓰기

작업 성격에 따라 모델을 나눠 쓰면 결과의 질과 비용을 함께 챙길 수 있습니다. Claude 5.5 계열에서는 방향을 찾는 단계에 Opus 5.5를, 빠르게 고치는 단계에 Sonnet 5.5를 쓰라고 권합니다. Shopify는 개발에는 가장 큰 모델을, 운영에는 저렴한 모델을 쓰는 '배벨 전략'을 소개했습니다.

  1. 지금 하는 일이 '방향을 찾는 단계'인지 '빠르게 고치는 단계'인지 먼저 구분합니다.
  2. 기획이나 구조 잡기처럼 방향을 찾는 단계에는 Opus 5.5를 고릅니다.
  3. 문구 수정이나 형식 맞추기처럼 빠른 수정 단계에는 Sonnet 5.5로 바꿉니다.
  4. 개발·테스트·자동 연구처럼 품질이 중요한 일에는 가장 큰 모델을 씁니다.
  5. 매일 반복해서 돌리는 운영 작업에는 저렴한 모델을 씁니다.
  6. 요청을 보내기 전에 실제로 필요한 것이 무엇인지 구체적으로 적었는지 점검합니다.
  • 예전 방식: 2026년 2월에는 Free·Pro 플랜의 claude.ai와 Cowork 기본 모델이 Sonnet 4.6이었습니다.
  • LLM은 질문에 맞춰 답하려는 경향이 있습니다. 질문이 엉뚱하면 답도 엉뚱해지므로 원하는 것을 정확히 요청하세요.
  • 몇 시간씩 이어지는 엔지니어링 작업에는 Fable 5.1이 강점을 보인다고 소개되었습니다.
  • 자동으로 돌아가는 작업이 폭주할 때를 대비해 멈춤 장치(서킷 브레이커)를 함께 마련하세요.

5. Claude 데이터 보관 정책 확인하기

Claude Fable 5부터는 안전 모니터링을 위해 최근 30일간의 프롬프트와 출력이 저장됩니다. 회사에서 Claude를 도입하기 전에 이 정책과 Enterprise Frontier Safeguards(EFS) 같은 조직용 선택지를 확인해 두면, 보안팀과 이야기할 때 도움이 됩니다.

  1. Fable 5 이후 모델을 쓰면 최근 30일의 프롬프트와 출력이 안전 모니터링용으로 저장된다는 점을 확인합니다.
  2. 저장된 데이터는 자동 시스템이 분석하며, 기본적으로 Anthropic 직원은 읽을 수 없다는 점을 확인합니다.
  3. 사람이 검토하는 경우는 자동 시스템이 유해 가능성을 표시한 드문 경우뿐이고, 접근 기록은 변조할 수 없는 로그에 남는다는 점을 정리합니다.
  4. 엔터프라이즈 데이터는 명시적 허가 없이 학습에 쓰이지 않는다는 점을 보안팀에 공유합니다.
  5. 우리 조직이 EFS 대상인지 확인합니다. EFS를 쓰면 모니터링 데이터를 자체 클라우드에 보관할 수 있습니다.
  6. EFS가 제공되기 전까지 대상 조직은 Fable 5와 5.1에서 데이터 보관 없음(ZDR)을 받는다는 점을 확인합니다.
  • EFS는 올가을부터 단계적으로 제공됩니다.
  • EFS에서는 로그를 고객이 통제하고, 검토는 기계로만 이뤄집니다. 결과도 고객 콘텐츠가 아니라 정해진 탐지 항목으로만 나옵니다.
  • EFS는 Salesforce, Visa, Uber, KPMG의 피드백을 반영해 만들어졌습니다.

6. Slack에서 Claude Tag로 팀 일 맡기기

Claude Tag는 Slack 팀 채널에서 함께 일하는 Claude입니다. 스레드에서 태그하면 채널 맥락을 파악해 작업하고, 일이 끝나거나 사람의 입력이 필요할 때 알려 줍니다. 데이터 질문 답변, 사내 문의 응대, 버그 수정처럼 며칠씩 걸리는 일도 후속 확인까지 이어서 합니다.

  1. 회사가 Team 또는 Enterprise 요금제인지 확인합니다. 두 요금제에서 베타로 제공됩니다.
  2. 작업할 Slack 스레드에서 Claude를 태그하고 맡길 일을 적습니다.
  3. 할 일 목록을 하나하나 주기보다 달성할 목표를 맡깁니다.
  4. 같은 스레드에서 다른 팀원도 함께 지시하게 합니다.
  5. 채널에서 계속 지킬 규칙을 알려 주면 Claude가 채널별로 기억합니다.
  6. 작업이 끝났거나 입력이 필요하다는 알림이 오면 결과를 확인하고 답합니다.
예시
(스레드에서 Claude를 태그한 뒤) 이 채널에 올라온 사내 문의를 모아 답변 초안을 만들고, 내가 확인해야 할 건은 따로 알려 줘.
  • Claude는 자기 계정과 권한을 가지며 채널별로 접근 범위가 나뉩니다. 자격 증명을 쓸 때마다 기록이 남습니다.
  • 비공개 채널이나 DM에서 배운 내용은 그 안에만 남습니다.
  • Claude Code 팀원 한 명은 작업의 70~80%를 Tag에서 처리하고, 나머지만 직접 다듬는다고 합니다.
  • Microsoft Teams 등으로 확대할 계획이 있습니다.

7. 루틴으로 매일 반복 업무 맡기기

Claude 작업이 로컬에서 클라우드로 옮겨 가면서, 세션을 열어 두지 않아도 정해진 때에 돌아가는 루틴을 쓸 수 있게 되었습니다. 매일 들어오는 피드백 정리처럼 반복되는 일을 맡기기에 좋습니다.

  1. 매일 반복하는 업무 하나를 고릅니다. 예: 고객 피드백 정리
  2. 루틴이 할 일을 '모으기 → 중요도별 분류 → 확신이 높은 것만 처리' 순서로 적습니다.
  3. 확신이 낮은 항목은 고치지 말고 사람에게 넘기라는 조건을 넣습니다.
  4. 루틴을 등록하고 첫 실행 결과를 직접 검토합니다.
  5. 이후에는 휴대폰 등으로 실행 결과를 확인하고 지시를 다듬습니다.
예시
매일 들어온 피드백을 모아 중요도별로 분류하고, 확신이 높은 것만 고쳐 줘. 나머지는 목록으로 남겨 줘.
  • 루틴은 Claude Code 새 기능 소개에서 워크플로용 기능으로 다뤄졌습니다.
  • 개발 플랫폼의 Managed Agents에도 예약 배포와 환경 변수를 보관하는 vault 기능이 추가되었습니다.
  • 모델이 좋아지면 약점을 메우려고 넣었던 단계(예: 할 일 목록)는 과감히 줄여도 됩니다.

8. 새 모델이 나오면 평가부터 돌려 보기

Claude 모델은 약 두 달마다 바뀝니다. 앞서가는 고객 팀들은 새 모델을 받으면 자동화 평가(evals)부터 돌려 보고 어디에 쓸지 정합니다. 우리 업무에 맞는 시험 문제를 미리 만들어 두면 새 모델로 바꿀지 빠르게 판단할 수 있습니다.

  1. 업무에서 자주 하는 작업으로 시험 문제 묶음(평가 세트)을 만들어 둡니다.
  2. 새 모델이 나오면 평가 세트를 먼저 백그라운드로 돌립니다.
  3. 법률 문서 초안처럼 복잡한 실제 작업을 하나 맡겨 결과를 직접 읽어 봅니다.
  4. 이전 모델과 비교해 성공률, 지능, 의사결정 능력이 어떻게 달라졌는지 기록합니다.
  5. 아직 안 되는 작업은 따로 적어 두고, 다음 모델이 나오면 다시 시험합니다.
  6. 새 모델이 충분히 잘하는 부분은 예전에 덧대 둔 보완 단계를 걷어 냅니다.
  • 모델만 바꿨는데 테스트 에이전트 성공률이 약 20% 오른 사례가 있습니다.
  • 지금 안 되는 일이 다음 모델이 잘하게 될 분야의 신호라고 봅니다.
  • Lovable은 모델이 출시될 때마다 평가 루프를 반드시 통과하게 합니다.
  • 모델이 바뀔수록 시스템이 저절로 좋아지게 설계하라는 조언도 있습니다(Legora).

9. AI 작업에 안전장치 두기

AI에게 일을 많이 맡길수록 품질을 AI의 판단에만 맡기지 않는 장치가 필요합니다. Stripe는 권한 분리와 점진적 배포로 품질을 지키고, Shopify는 폭주에 대비해 멈춤 장치를 둡니다. 개발이 아닌 업무에서도 사람이 검토하고 최종 승인하는 원칙은 그대로 적용됩니다.

  1. AI가 접근할 수 있는 데이터와 권한을 업무별로 나눕니다.
  2. AI가 만든 변경은 한꺼번에 적용하지 말고 작은 범위부터 점진적으로 적용합니다.
  3. 자동 작업이 예상보다 오래 돌거나 많이 실행되면 멈추는 기준(서킷 브레이커)을 정합니다.
  4. AI가 원인이나 해결책을 제안하면 사람이 확인하고 적용 범위를 정한 뒤 승인합니다.
  5. AI로 만든 콘텐츠를 외부에 공개하기 전에 사람이 검수·검증합니다.
  • Stripe는 모든 개발자에게 Claude Code가 미리 설치된 격리 개발 환경(devbox)을 제공합니다.
  • Stripe에서는 한 엔지니어가 AI로 작성한 PR 600개 이상을 병합했고, 되돌린 것은 1건뿐이었습니다.
  • Fable 5.1 디버깅 사례에서도 원인 확인과 배포 범위 결정, 수정 승인은 개발자가 맡습니다.
  • AI 콘텐츠일수록 검수와 신뢰가 더 중요해진다는 의견이 있습니다.
