1. 통합된 Claude에 일 맡기기

9월 업데이트로 채팅과 Cowork가 하나의 Claude로 합쳐졌습니다. 원하는 결과를 말하면 Claude가 방법을 찾고, 작업은 클라우드에서 돌아가므로 자리를 비워도 계속 진행됩니다.

  1. Claude를 열고 모드를 따로 고르지 않은 채 대화를 시작합니다.
  2. 해야 할 '작업 순서' 대신 얻고 싶은 '결과'를 문장으로 설명합니다.
  3. Claude가 방법을 정해 작업을 시작하면 노트북을 닫아도 됩니다. 작업은 클라우드에서 계속 실행됩니다.
  4. 이동 중에는 휴대폰으로 진행 상황을 확인합니다.
  5. 예전에 Cowork에서 만든 작업이 있다면 그대로 남아 있는지 확인하고 이어서 씁니다.
  • 예전 방식: 채팅과 Cowork 중 어느 모드를 쓸지 먼저 골라야 했지만, 지금은 하나의 Claude에서 바로 시작합니다.
  • 작업이 클라우드에서 돌아가므로 오래 걸리는 일도 맡겨 두고 다른 일을 할 수 있습니다.
  • 결과를 받으면 숫자·날짜·인용은 직접 확인합니다 (환각 줄이기 가이드 참고).

2. 대화에서 문서·슬라이드·디자인 만들기

Claude Slides, Claude Design, Claude Docs로 대화를 벗어나지 않고 발표 자료, 소셜 이미지, 한 장짜리 문서를 만들 수 있습니다. 기존 대화 내용을 바탕으로 만들어지고, 결과물에 코멘트를 달아 부분 수정도 할 수 있습니다.

  1. 만들 결과물의 바탕이 될 브리프(출시 안내, 자주 묻는 질문 모음 등)를 대화에 붙여 넣거나 그동안의 대화 내용을 활용합니다.
  2. 같은 대화에서 발표용 슬라이드를 만들어 달라고 요청합니다.
  3. 이어서 소셜 이미지 세트나 현장용 한 장 요약 문서도 같은 브리프로 요청합니다.
  4. 결과물에서 고칠 부분에 코멘트를 달아 Claude에게 보냅니다.
  5. Claude가 코멘트를 단 부분만 고쳐 주면 다시 확인합니다.
  6. 팀과 함께 다듬을 문서는 Claude Docs에서 팀원과 Claude가 동시에 편집합니다.
예시
지금까지 모은 고객의 자주 묻는 질문을 정리해서, 고객에게 나눠 줄 한 장짜리 안내문으로 만들어 줘.
  • Slides·Design·Docs는 베타로 제공됩니다.
  • 브리프 하나로 슬라이드·이미지·문서를 함께 만들면 내용이 서로 어긋나지 않습니다.
  • Claude Design은 일상 언어 설명만으로 결과물을 만드니, 디자인 용어를 몰라도 원하는 느낌을 그대로 적으면 됩니다.

3. AI 환각 줄이며 답 확인하기

환각은 AI가 없는 논문, 가짜 통계, 틀린 인물·사건 정보를 사실처럼 말하는 현상입니다. 많이 줄었지만 해결된 문제는 아니므로, 업무에 쓰기 전에 몇 가지 요령으로 확인해야 합니다.

  1. 답에 구체적 사실·통계·인용, 잘 알려지지 않은 주제, 최신 내용, 정확한 날짜·이름·숫자가 있는지 먼저 살핍니다.
  2. 그런 내용이 있으면 Claude에게 출처를 알려 달라고 요청합니다.
  3. 각 내용에 얼마나 확신하는지 함께 물어봅니다.
  4. 중요한 내용은 새 대화를 열어 같은 질문으로 다시 검증합니다.
  5. 출처가 없거나 확신이 낮은 내용은 원문을 직접 찾아 확인한 뒤에만 씁니다.
예시
방금 답에 쓴 통계와 인용의 출처를 하나씩 알려 주고, 각 내용을 얼마나 확신하는지도 말해 줘.
  • 환각이 드물어질수록 확인을 건너뛰기 쉬우니 습관처럼 확인하세요.
  • 자료가 적은 주제일수록 AI가 추측해 틀린 답을 낼 가능성이 큽니다.
  • 편향도 비슷하게, 같은 주제를 두 관점으로 각각 물어 답의 깊이를 비교해 보면 드러납니다.

4. Claude 데이터 보관 방식 확인하기

Claude Fable 5부터 안전 모니터링을 위해 최근 30일간의 프롬프트와 출력이 저장됩니다. 회사 자료를 넣기 전에 무엇이 저장되고 누가 볼 수 있는지 알아 두면 보안 담당자와 이야기하기 쉬워집니다.

  1. 사용하는 모델이 Fable 5 이후 모델이면 최근 30일의 프롬프트와 출력이 안전 모니터링용으로 저장된다는 점을 확인합니다.
  2. 저장된 데이터는 자동 시스템이 분석하며, 기본적으로 Anthropic 직원은 읽을 수 없다는 점을 사내에 공유합니다.
  3. 사람의 검토는 자동 시스템이 유해 가능성을 표시한 드문 경우에만 승인된 소수가 하며, 접근 기록이 변조 불가 로그에 남는다는 점을 확인합니다.
  4. 엔터프라이즈 요금제라면 명시적 허가 없이 데이터가 학습에 쓰이지 않는다는 점을 확인합니다.
  5. 모니터링 데이터를 회사 클라우드에 두어야 하는 조직이면 Enterprise Frontier Safeguards(EFS) 도입을 보안팀과 검토합니다.
  • EFS는 제로 데이터 보존(ZDR)의 프라이버시와 오남용 탐지 세이프가드를 결합한 방식입니다.
  • EFS는 올가을 이후 단계적으로 제공되며, 그 전까지 대상 조직은 Fable 5와 5.1에서 데이터 보관 없음(ZDR)을 받습니다.
  • EFS에서는 로그를 고객이 통제하고, 검토는 기계로만 하며, 결과는 정해진 탐지 항목으로만 제한됩니다.

5. 작업 단계에 맞는 모델 고르기

모델마다 잘하는 일과 비용이 다릅니다. 방향을 찾거나 품질이 중요한 일에는 큰 모델을, 빠른 수정이나 반복 운영에는 빠르고 저렴한 모델을 나눠 쓰면 효율이 좋아집니다.

  1. 지금 하는 일이 '방향을 찾는 단계'인지 '빠르게 고치는 단계'인지 구분합니다.
  2. 방향을 찾거나 복잡한 계획·정교한 문서 초안이 필요하면 Opus 5.5를 고릅니다.
  3. 방향이 정해진 뒤 빠른 수정을 반복할 때는 Sonnet 5.5로 바꿉니다.
  4. 개발·테스트·자동 연구처럼 결과 품질이 중요한 일에는 가장 큰 모델을 씁니다.
  5. 매일 반복되는 운영 작업에는 저렴한 모델을 쓰는 '배벨 전략'을 적용합니다.
  • 예전 방식: 2월에는 Free·Pro 플랜의 claude.ai와 Cowork 기본 모델이 Sonnet 4.6이었습니다. 지금은 5.5 계열을 단계별로 나눠 쓰기를 권합니다.
  • 법률 문서처럼 기존 문체에 맞춘 섬세한 초안에는 Opus가 강하다는 평가가 많습니다.
  • LLM은 질문에 맞춰 답하려는 경향이 있어, 어떤 모델이든 실제로 필요한 것을 정확히 요청하는 것이 더 중요합니다.

6. Slack에서 Claude Tag로 일 맡기기

Claude Tag는 Slack 채널에서 팀과 함께 일하는 Claude입니다. 스레드에서 태그하면 채널 맥락을 파악해 작업하고, 며칠 걸리는 일도 후속 확인까지 이어서 합니다.

  1. 회사가 Team 또는 Enterprise 요금제인지 확인합니다 (Slack 베타로 제공).
  2. 작업을 맡길 Slack 스레드에서 Claude를 태그하고 원하는 목표를 적습니다.
  3. Claude가 채널 맥락을 파악해 작업하는 동안 기다립니다. 끝나거나 입력이 필요하면 알려 줍니다.
  4. 같은 스레드에서 다른 팀원도 함께 지시를 더할 수 있습니다.
  5. 채널별로 자주 쓰는 지시를 알려 주면 메모리로 쌓여 다음 작업에 반영됩니다.
  6. 비공개 채널이나 DM에서 다룬 내용은 그 안에만 남는다는 점을 팀에 공유합니다.
  • 예전 방식: 프롬프트를 주고 권한 요청을 하나씩 승인했지만, 지금은 작업이 아니라 목표를 맡기는 식으로 씁니다.
  • 데이터 질문 답변, PR 작성, 버그 수정, 사내 문의 응대 등에 쓰입니다.
  • Claude는 자기 계정과 권한을 가지며 모든 자격 증명 사용이 기록됩니다.
  • 다른 팀원이 Tag를 어떻게 쓰는지 보면 좋은 사용법을 빨리 배울 수 있습니다.

7. AI 시대에 맞게 팀 업무 절차 점검하기

AI로 작업 속도가 빨라지면 병목이 검증·리뷰·협업·보안으로 옮겨 갑니다. 예전에 도움이 된 절차가 조용히 작동을 멈추므로, 주기적으로 절차를 다시 점검해야 합니다.

  1. 팀에서 가장 시간을 많이 잡아먹는 업무 절차 하나를 고릅니다.
  2. 그 절차가 지금도 꼭 필요한지 따져 봅니다.
  3. 필요하다면 Claude로 줄이거나 대신할 수 있는지 검토합니다.
  4. 작업 속도가 빨라진 뒤 새로 막히는 지점(검증, 리뷰, 유관 부서 협업, 보안)을 찾습니다.
  5. 긴 장기 계획 대신 필요한 시점에 계획하는 방식(JIT)이 맞는지 검토합니다.
  6. 새 모델이 나올 때마다 AI를 얼마나 믿고 맡길지, 어디까지 검증할지를 다시 정합니다.
  • 절차는 스스로 사라지지 않고 계속 쌓이므로 의식적으로 정리해야 합니다.
  • 모델이 약해서 만들었던 보완 장치는 모델이 좋아지면 과감히 지웁니다. 모델은 약 두 달마다 바뀝니다.
  • 기술 논쟁은 말보다 코드나 시제품으로 먼저 보여 주는 방식이 효과적이었다고 합니다.
  • 한 번 정한 해법도 매달 다시 의심해 보라는 조언이 있습니다.

8. AI 작업에 안전장치 걸기

AI가 많은 일을 대신할수록 품질을 AI 판단에만 맡기면 위험합니다. 권한·데이터 분리 같은 구조적 장치와 사람의 최종 승인을 함께 두면 속도와 신뢰성을 같이 지킬 수 있습니다.

  1. AI가 접근할 데이터와 권한을 업무에 필요한 범위로만 나눕니다.
  2. 결과물을 한꺼번에 반영하지 않고 조금씩 점진적으로 배포합니다.
  3. 작업이 폭주할 때 자동으로 멈추게 하는 서킷 브레이커를 둡니다.
  4. AI가 문제의 원인을 제안하면 사람이 직접 확인합니다.
  5. 적용 범위를 사람이 정하고 최종 수정을 승인합니다.
  • Stripe는 품질을 AI의 판단이 아니라 인프라 차원의 보호 장치와 하드 가드레일로 지킵니다.
  • Stripe에서는 한 엔지니어가 AI로 작성한 PR 600개 이상을 병합하고 되돌린 것은 1건뿐이었습니다.
  • AI가 만든 결과물일수록 검수·검증과 신뢰가 더 중요해집니다.

9. Claude Code 루틴으로 반복 작업 돌리기

루틴은 사람이 매번 지시하지 않아도 정해진 조건에 Claude Code가 작업을 시작하게 하는 기능입니다. 매일 피드백 정리나 CI 오류 자동 수정처럼 반복되는 일에 씁니다.

  1. 매일 또는 특정 사건마다 반복되는 작업 하나를 고릅니다 (예: 들어온 피드백 정리).
  2. 루틴을 시작할 방식을 정합니다: 일정, 웹훅, API 호출 중 하나.
  3. 실행 위치를 로컬 또는 원격 클라우드 중에서 고릅니다.
  4. 루틴이 할 일을 '모으기 → 중요도별 분류 → 확신이 높은 것만 고치기'처럼 단계로 적습니다.
  5. 실행 결과를 확인하고, 사람이 볼 것과 자동으로 처리할 것의 경계를 조정합니다.
  • 클라우드 실행으로 넘어오면서 세션 밖에서도 돌아가는 루틴과 루프가 가능해졌습니다.
  • 에이전트 뷰를 함께 쓰면 여러 작업의 진행을 한 화면에서 관리할 수 있습니다.
  • 처음에는 확신이 높은 일만 자동으로 고치게 하고, 나머지는 사람에게 넘기도록 하세요.

10. 새 모델 나오면 평가로 시험하기

모델은 몇 달마다 바뀌므로 새 모델이 나올 때마다 내 업무에서 실제로 나아졌는지 확인해야 합니다. 앞서가는 고객 팀들은 자동화 평가(evals)를 먼저 돌리고 어려운 실제 업무를 맡겨 봅니다.

  1. 내 업무를 대표하는 질문·과제 묶음(평가 세트)을 미리 만들어 둡니다.
  2. 빠르게 반복할 수 있도록 약 1분 안에 끝나는 작은 평가 세트도 따로 둡니다.
  3. 새 모델이 나오면 먼저 자동화 평가를 백그라운드로 돌립니다.
  4. 그동안 문서 초안 작성 같은 복잡한 실제 업무를 새 모델에 맡겨 봅니다.
  5. 모델만 바꿨을 때와 프롬프트·도구를 함께 조정했을 때의 결과를 비교합니다.
  6. 아직 안 되는 작업은 기록해 두고 다음 모델이 나올 때 다시 시험합니다.
  • 모델 교체만으로 테스트 에이전트 성공률이 약 20% 오른 사례가 있습니다.
  • 지금 안 되는 일이 다음 모델이 잘할 분야의 신호라고 봅니다.
  • 모델을 고를 때 가장 중시하는 기준으로 지능과 의사결정 능력이 꼽힙니다.
  • 같은 결과라면 사용한 토큰이 적은 쪽이 더 효율적인 설정입니다.
