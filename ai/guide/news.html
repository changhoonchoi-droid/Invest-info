1. 화제의 AI 소식 출처 확인하기

X·커뮤니티에서 퍼지는 AI 소식은 숫자나 결론만 떼어 전달되는 경우가 많습니다. 작성자, 링크, 원 논문을 확인하면 같은 글도 전혀 다르게 읽힙니다. 회의나 보고에 AI 소식을 인용하기 전에 쓰면 좋습니다.

  1. 화제가 된 글에서 핵심 주장(숫자·결론)을 한 문장으로 적어 둡니다.
  2. 작성자 프로필을 열어 누구인지(회사 대표, 연구자, 홍보 계정 등) 확인합니다.
  3. 글에 걸린 링크가 공식 저장소나 공식 발표인지 확인합니다.
  4. 숫자가 나오면 원 논문을 찾아 표본 크기와 그 숫자가 무엇의 비율인지 읽습니다.
  5. 원문 내용과 글의 주장을 비교해 과장되거나 다르게 해석된 부분을 메모합니다.
  6. 확인한 링크만 보고서나 공유 글에 붙입니다.
  • 예: 챗GPT 메모리 '96%' 글의 논문은 사용자 80명의 메모리 2,050개를 분석했고, 96%는 사용자가 요청하지 않고 GPT가 스스로 만든 메모리의 비율이었습니다.
  • 반대로 '슈퍼베이스 6시간 복제' 글처럼 작성자가 실제 CEO이고 링크가 공식 저장소인 경우도 있으니 의심만 하지 말고 확인합니다.
  • 깃허브 별 수처럼 빠르게 바뀌는 숫자는 확인한 날짜를 함께 적습니다.

2. 환각 줄이며 AI 답 확인하기

환각은 AI가 없는 논문·가짜 통계·틀린 인물 정보를 사실처럼 말하는 현상입니다. Claude의 환각은 1년 전보다 크게 줄었지만 해결된 문제는 아니므로, 사실·숫자가 들어간 업무 문서에는 확인 요령을 함께 씁니다.

  1. 답에 구체적 사실·통계·인용, 정확한 날짜·이름·숫자가 있는지 먼저 표시합니다.
  2. 표시한 부분에 대해 출처를 알려 달라고 요청합니다.
  3. 각 주장을 얼마나 확신하는지 물어 확신이 낮은 부분을 골라냅니다.
  4. 새 대화를 열어 같은 사실을 다시 물어보고 답이 일치하는지 비교합니다.
  5. 무명 주제나 최신 내용이면 받은 출처 링크를 직접 열어 확인합니다.
예시
방금 답에서 숫자·날짜·인용이 들어간 문장마다 출처를 알려 주고, 각 문장을 얼마나 확신하는지 높음·중간·낮음으로 표시해 줘.
  • 자료가 적은 주제, 최신 소식, 정확한 숫자에서 환각 가능성이 높습니다.
  • 환각 횟수가 줄수록 확인을 건너뛰기 쉬우니 중요한 문서일수록 습관처럼 확인합니다.

3. Claude 모바일 앱 새 기능 쓰기

10월 말 Claude 모바일 앱 업데이트로 계정 전환, 태블릿 나란히 보기, 더 빨라진 음성 모드 등이 추가됐습니다. 출퇴근길이나 이동 중에 업무와 개인 용도로 Claude를 함께 쓰는 사람에게 유용합니다.

  1. iOS 또는 Android에서 Claude 앱을 최신 버전으로 업데이트합니다.
  2. 업무용 계정과 개인 계정에 모두 로그인해 두고, 로그아웃 없이 두 계정을 전환해 씁니다.
  3. iPad에서는 Claude가 만든 아티팩트를 대화 옆 열에 열어 두 창을 나란히 봅니다.
  4. iPhone에서 사진을 골라 보내면 업로드 중에도 채팅에 바로 표시되는지 확인합니다.
  5. 운전 중에는 iPhone 음성 모드를 Apple CarPlay로 연결해 씁니다.
  6. Chromebook·폴더블 Android 앱에서는 크기 조절 사이드바와 마우스 우클릭, Claude Desktop과 같은 단축키를 씁니다.
  • 앱 화면은 24개 언어가 추가돼 총 33개 언어를 지원합니다.
  • 당겨서 검색은 iPhone·iPad에 곧 제공될 예정이고, 웹과 데스크톱에는 이미 있습니다(Mac은 Command K).

4. 대화에서 문서·슬라이드 만들기

채팅과 Cowork가 하나의 Claude로 합쳐져, 어떤 대화에서든 문서·슬라이드·디자인을 만들 수 있습니다. 기존 대화 내용을 바탕으로 만들어지고, 결과물에 코멘트를 달아 원하는 부분만 고칠 수 있어 보고서·발표 자료 준비에 좋습니다.

  1. 보고서 주제나 출시 브리프 같은 바탕 자료를 Claude 대화에 먼저 정리합니다.
  2. 같은 대화에서 원하는 결과물(발표 슬라이드, 한 장 요약 문서, 소셜 이미지 등)을 말로 요청합니다.
  3. 결과물에서 고치고 싶은 부분에 코멘트를 달아 Claude에게 보냅니다.
  4. 작업이 클라우드에서 계속 돌아가므로 노트북을 닫고 휴대폰으로 진행 상황을 확인합니다.
  5. 팀과 함께 다듬을 문서는 Claude Docs에서 팀원과 Claude가 동시에 편집합니다.
예시
지금까지 이 대화에서 정리한 내용을 바탕으로 10장짜리 발표 슬라이드와 현장에서 나눠 줄 한 장 요약 문서를 만들어 줘.
  • Claude Slides·Design·Docs는 9월 공개 때 베타로 제공됐습니다.
  • 모드를 따로 고를 필요가 없고, 기존 Cowork 작업도 그대로 유지됩니다.
  • 예전 방식: 채팅과 Cowork를 나눠 골라서 써야 했습니다.

5. 작업에 맞는 Claude 모델 고르기

Claude는 모델마다 강점이 달라 작업 단계에 맞춰 고르면 품질과 비용을 함께 잡을 수 있습니다. 방향을 잡는 어려운 일에는 큰 모델, 빠른 수정·반복 운영에는 가벼운 모델을 쓰는 것이 공식 영상과 기업 사례의 공통 조언입니다.

  1. 지금 하려는 일이 '방향 찾기'(기획·설계·복잡한 분석)인지 '빠른 수정'(문장 손보기·작은 변경)인지 나눕니다.
  2. 방향 찾기 단계에는 Opus 5.5를 씁니다.
  3. 빠른 수정 단계에는 Sonnet 5.5로 바꿔 씁니다.
  4. 몇 시간 이어지는 개발이나 근본 원인을 찾는 디버깅처럼 긴 작업에는 Fable 5 계열을 검토합니다.
  5. 자동으로 계속 돌아가는 운영 업무는 저렴한 모델로 돌리고, 비용이 폭주하지 않게 멈춤 장치(서킷 브레이커)를 둡니다.
  • Shopify의 배벨 전략: 개발·테스트·자동 연구에는 가장 큰 모델, 운영과 파인튜닝에는 저렴한 모델을 씁니다.
  • LLM은 질문에 맞춰 답하려는 경향이 있어, 어떤 모델이든 실제로 필요한 것을 정확히 요청하는 것이 중요합니다.
  • 예전 방식: Free·Pro 플랜의 claude.ai·Cowork 기본 모델은 Sonnet 4.6(2026년 2월)이었습니다.

6. AI 조언에 휘둘리지 않고 결정하기

Anthropic 연구에서 분석가들은 에이전트가 임의로 기운 쪽을 86% 따랐고, 스스로 결정했다고 착각하기 쉬웠습니다. 기획·분석 방향이나 코딩 계획처럼 중요한 선택을 AI와 함께할 때 이 방법으로 내 판단을 지킵니다.

  1. AI에게 추천을 받기 전에 이번 결정의 우선순위(속도·비용·품질 등)를 먼저 정해 적습니다.
  2. AI가 내 우선순위를 먼저 묻고 그 기준으로 추천하게 합니다.
  3. 말로 비교하기 어려운 선택지는 작은 프로토타입을 만들어 직접 보고 결정합니다.
  4. 추천을 받으면 어떤 조건이 바뀌면 조언이 달라지는지 묻습니다.
  5. 최종 결정을 설명할 때 AI에게서 온 논거는 출처를 밝혀 적습니다.
예시
추천하기 전에 이번 결정에서 내가 무엇을 가장 중요하게 보는지 먼저 물어봐 줘. 그리고 추천을 준 뒤에는 어떤 조건이 바뀌면 추천이 달라지는지도 알려 줘.
  • 자기 선호가 있던 사람도 에이전트가 반대하면 60%가 선호를 바꿨습니다(동의할 때는 6%).
  • 77%가 에이전트의 논거를 썼지만 출처로 밝힌 사람은 15%뿐이었습니다.
  • 연구는 에이전트의 기울기를 일부러 강화했고 한 분야·한 과제·한 모델만 봤다는 한계가 있습니다.

7. Slack에서 Claude Tag 쓰기

Claude Tag는 Slack 채널에 들어와 팀과 함께 일하는 Claude입니다. 스레드에서 태그하면 채널 맥락을 파악해 작업하고, 며칠~몇 주 걸리는 일도 후속 확인까지 이어 갑니다. 데이터 질문, 사내 문의 응대, 버그 수정 등에 씁니다.

  1. 회사가 Team 또는 Enterprise 요금제인지 확인합니다(Slack 베타로 제공).
  2. 작업을 맡길 Slack 스레드에서 Claude를 태그하고 원하는 목표를 적습니다.
  3. 같은 스레드에서 다른 팀원도 함께 지시를 보태게 합니다.
  4. Claude가 작업을 마치거나 입력이 필요하다고 알리면 스레드에서 답합니다.
  5. 채널마다 반복할 지시는 남겨 두어 채널별 메모리로 쌓이게 합니다.
  • Claude는 자기 계정과 권한을 가지며 채널별로 접근 범위가 나뉘고, 모든 자격 증명 사용이 기록됩니다.
  • 비공개 채널이나 DM에서 배운 내용은 그 안에만 남습니다.
  • Claude Code 팀원 한 명은 작업의 70~80%를 Tag에서 하고 나머지만 직접 다듬습니다. 작업이 아니라 목표를 맡기는 것이 요령입니다.
  • Microsoft Teams 등으로 확대할 계획입니다.

8. Claude 데이터 보관 방식 알아두기

회사에서 Claude를 쓰려면 입력한 내용이 어떻게 저장·검토되는지 알아야 보안 검토를 통과할 수 있습니다. Claude Fable 5부터 안전 모니터링을 위한 30일 보관이 시작됐고, 기업용으로는 Enterprise Frontier Safeguards(EFS)가 나왔습니다.

  1. 회사에서 쓰는 Claude 모델이 Fable 5 이후 모델인지 확인합니다.
  2. Fable 5부터 최근 30일의 프롬프트와 출력이 안전 모니터링용으로 저장된다는 점을 보안 담당자와 공유합니다.
  3. 자동 시스템이 분석하며 기본적으로 Anthropic 직원은 읽을 수 없다는 점을 확인합니다.
  4. 엔터프라이즈 계약이면 명시적 허가 없이 학습에 쓰지 않는다는 조건을 확인합니다.
  5. 모니터링 데이터를 자체 클라우드에 두어야 하는 조직이면 EFS 도입을 검토합니다.
  • 사람의 검토는 자동 시스템이 유해 가능성을 표시한 드문 경우에만, 승인된 소수 검토자가 하며 접근 기록은 변조 불가 로그에 남습니다.
  • EFS는 올가을 이후 단계적으로 제공되며, 그 전까지 대상 조직은 Fable 5와 5.1에서 데이터 보관 없음(ZDR)을 받습니다.
  • EFS에서는 검토가 기계로만 이뤄지고 결과는 고객 콘텐츠가 아니라 정해진 탐지 항목으로 제한됩니다.

9. 소모적인 업무 절차 AI로 줄이기

Anthropic 팀에서는 코딩이 더 이상 느린 단계가 아니고 검증·리뷰·협업이 새 병목이 됐습니다. 예전에 도움이 된 절차가 조용히 쓸모를 잃는 경우가 많아, 하나씩 골라 지금도 필요한지 점검해 보라는 제안입니다.

  1. 우리 팀에서 가장 소모적인 업무 절차 하나를 고릅니다.
  2. 그 절차가 처음 생긴 이유를 적고, 지금도 그 이유가 유효한지 따져 봅니다.
  3. Claude로 줄이거나 대신할 수 있는 부분을 표시합니다.
  4. 말로 길게 논쟁할 일은 먼저 결과물(프로토타입)로 보여 주고 결정합니다.
  5. 줄인 뒤 새로 생기는 병목(검증·리뷰)을 누가 맡을지 정합니다.
예시
우리 팀에서 시간이 가장 많이 드는 업무 절차는 '[절차 설명]'입니다. 이 절차가 지금도 필요한지, Claude로 줄일 수 있는 부분은 어디인지, 줄이면 무엇을 따로 검증해야 하는지 점검해 줘.
  • 프로세스는 스스로 사라지지 않고 계속 쌓이므로 의식적으로 정리해야 합니다.
  • 계획은 6개월 로드맵 대신 필요한 때 하는 방식(JIT)으로 바꾼 사례가 있습니다.
  • 모델이 계속 좋아지므로 AI에 맡길 범위와 검증의 균형은 주기적으로 다시 봅니다.

10. 새 모델 나오면 내 업무로 평가하기

새 Claude 모델은 몇 달마다 나오고, 모델만 바꿔도 결과가 크게 달라집니다. 미리 모델을 써 보는 고객 팀처럼 내 업무로 만든 평가(evals)를 준비해 두면 바꿀지 말지 근거를 갖고 정할 수 있습니다.

  1. 내 업무에서 자주 하는 작업과 정답(또는 좋은 결과의 기준)을 묶어 평가 세트를 만듭니다.
  2. 새 모델이 나오면 가장 먼저 이 평가를 백그라운드로 돌립니다.
  3. 평가와 별도로 법률 문서 초안처럼 복잡한 실제 작업을 하나 맡겨 봅니다.
  4. 기존 모델과 결과를 비교해 좋아진 점과 아직 안 되는 점을 기록합니다.
  5. 공정성이 중요한 업무면 같은 주제를 두 관점으로 묻는 짝지은 프롬프트로 답의 깊이와 노력을 비교합니다.
  • 모델 교체만으로 테스트 에이전트 성공률이 약 20% 올랐다는 사례가 있습니다.
  • 지금 안 되는 작업은 다음 모델이 나아질 영역의 단서로 기록해 둡니다.
  • Anthropic의 정치 편향 평가 데이터셋은 공개되어 같은 테스트를 해 볼 수 있습니다.

11. AI 결과를 검증 루프로 확인하기

AI가 만든 코드나 결과물은 테스트를 통과해도 다른 면에서 틀릴 수 있습니다. 읽기→사양서 쓰기→다시 만들기→원본과 비교를 반복하고, 정확성은 테스트로, 속도는 측정으로 따로 확인하는 방법입니다.

  1. AI에게 대상(기존 기능·코드)을 읽게 합니다.
  2. 읽은 내용을 사양서 spec.md로 정리하게 합니다.
  3. 사양서만 보고 다시 만들게 합니다.
  4. 다시 만든 결과를 원본과 비교하고, 다르면 사양서와 결과를 고쳐 반복합니다.
  5. 정확성은 테스트로 확인합니다.
  6. 속도·성능은 실제 사용 조건(예: 여러 스레드 동시 사용)에서 따로 측정합니다.
예시
이 기능의 동작을 읽고 사양서를 spec.md로 써 줘. 그다음 사양서만 보고 다시 만들어 원본과 결과를 비교하고, 다른 점이 있으면 원인을 적은 뒤 같을 때까지 반복해 줘.
  • 실험에서 테스트 33개를 모두 통과한 Rust 버전이 12스레드 공유 시 초당 10.7MB로 Python(20.2MB)보다 느렸습니다.
  • 같은 프로젝트에서 Rust 속도 향상은 조건에 따라 2.8~18.4배로 크게 달랐습니다. 숫자는 반드시 내 조건에서 잽니다.
  • 남의 앱을 역공학할 때는 라이선스와 이용 약관을 먼저 확인합니다.

12. Claude Code 루틴으로 반복 맡기기

루틴은 사람이 매번 지시하지 않아도 정해진 때에 Claude Code가 일하게 하는 기능입니다. 로컬 노트북에서 클라우드 실행으로 넘어가면서 세션 밖에서 도는 작업이 가능해졌고, 피드백 정리나 CI 자동 수정 같은 반복 업무에 씁니다.

  1. 매일·매주 반복하는 개발 업무 하나를 고릅니다(예: 피드백 모으기, CI 실패 수정).
  2. 루틴을 시작할 방법을 정합니다: 일정, 웹훅, API 호출 중 하나.
  3. 실행 위치를 로컬과 원격 클라우드 중에서 고릅니다.
  4. 루틴이 할 일을 '모으기 → 중요도별 분류 → 확신이 높은 것만 고치기'처럼 단계로 적습니다.
  5. 처음 몇 번은 결과를 직접 검토하고, 믿을 만해지면 맡기는 범위를 넓힙니다.
  • 루틴이 사람 대신 Claude Code에 지시하고 CI 자동 수정까지 맡는 흐름이 런던 기조연설에서 시연됐습니다.
  • 모델이 약 두 달마다 바뀌므로, 모델의 약점을 메우려고 만든 단계는 필요 없어지면 지웁니다.
  • 에이전트 뷰로 여러 작업을 한눈에 관리할 수 있습니다.
