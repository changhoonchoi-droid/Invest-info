1. 통합된 Claude에 일 맡기기

채팅과 Cowork가 하나의 Claude로 합쳐져서, 원하는 결과를 말하면 Claude가 방법을 찾아 일합니다. 작업은 클라우드에서 돌기 때문에 노트북을 닫아도 이어지고, 휴대폰으로 진행 상황을 볼 수 있습니다.

  1. Claude를 열고 모드를 고르지 말고 새 대화를 시작합니다.
  2. 할 일의 방법보다 원하는 결과를 한두 문장으로 적습니다.
  3. 작업이 시작되면 노트북을 닫아도 된다는 점을 기억하고 다른 일을 합니다.
  4. 이동 중에는 휴대폰에서 같은 작업의 진행 상황을 확인합니다.
  5. 예전에 Cowork에서 하던 작업도 그대로 남아 있는지 확인합니다.
  • 예전 방식: 채팅과 Cowork를 따로 골라 써야 했습니다. 지금은 하나로 합쳐졌고 기존 Cowork 작업도 그대로 유지됩니다.
  • 예전 방식: 2026년 2월에는 Free·Pro 플랜의 claude.ai와 Cowork 기본 모델이 Sonnet 4.6이었습니다. 9월 업데이트부터는 Claude 5.5 계열이 바탕입니다.

2. 대화에서 슬라이드·문서 만들기

Claude Slides, Claude Design, Claude Docs(베타)로 대화를 벗어나지 않고 발표 자료, 소셜 이미지, 한 장짜리 문서를 만듭니다. 결과물의 고칠 부분에 코멘트를 달면 Claude가 그 부분만 고칩니다.

  1. 대화창에 출시 브리프나 업무 메모처럼 바탕이 될 내용을 붙여 넣습니다.
  2. 같은 내용으로 발표 자료, 소셜 이미지 세트, 한 장 요약 문서 중 필요한 것을 만들어 달라고 요청합니다.
  3. 만들어진 결과물을 처음부터 끝까지 훑어보고 고칠 부분을 찾습니다.
  4. 고칠 부분에 코멘트를 달아 Claude에게 보냅니다.
  5. 팀과 같이 다듬을 문서는 Claude Docs에서 팀원과 Claude가 동시에 편집합니다.
예시
위 출시 브리프로 사내 발표용 슬라이드, 소셜 이미지 세트, 현장에서 나눠 줄 한 장짜리 요약 문서를 만들어 줘.
  • 기존 대화 내용을 바탕으로 만들어지므로, 필요한 자료를 먼저 대화에 넣어 두면 결과가 좋아집니다.
  • 고객이 자주 묻는 질문을 모아 한 장짜리 안내문으로 정리하는 데도 쓸 수 있습니다(양봉가 사례).
  • Claude Design은 문서보다 프로토타입을 먼저 만들어 보는 방식에 맞습니다.

3. 작업 단계별로 모델 나눠 쓰기

모델마다 맞는 작업이 달라서, 방향을 잡는 큰 고민과 빠른 수정에 서로 다른 모델을 쓰면 효율이 좋아집니다. Anthropic은 Opus 5.5와 Sonnet 5.5를 단계별로 나눠 쓰라고 권합니다.

  1. 지금 하는 일이 방향을 찾는 단계인지, 정해진 방향으로 빠르게 고치는 단계인지 구분합니다.
  2. 기획·계획·복잡한 판단처럼 방향을 찾는 단계에는 Opus 5.5를 고릅니다.
  3. 문구 다듬기나 작은 수정처럼 빠르게 고치는 단계에는 Sonnet 5.5로 바꿉니다.
  4. 반복해서 돌리는 운영 작업은 더 저렴한 모델로 바꿔도 결과가 괜찮은지 확인합니다.
  • Shopify의 '배벨 전략': 개발·테스트·자동 연구에는 가장 큰 모델을, 운영과 파인튜닝에는 저렴한 모델을 씁니다.
  • Factory는 복잡한 계획과 조율에 Opus를 쓰며, 계획을 거의 확인하지 않아도 될 만큼 감독이 줄었다고 말합니다.
  • LLM은 질문에 맞춰 답하려는 경향이 있으니, 실제로 필요한 것을 정확히 요청하는 것이 모델 선택만큼 중요합니다.

4. 내 대화 데이터 보관 방식 확인하기

Claude Fable 5부터는 안전 모니터링을 위해 최근 30일간의 프롬프트와 출력이 저장됩니다. 회사 업무에 쓰기 전에 무엇이 저장되고 누가 볼 수 있는지 알아 두면 보안 담당자와 이야기하기 쉬워집니다.

  1. 업무에 쓰는 모델이 Fable 5 이후 모델인지 확인합니다.
  2. 이 모델들은 최근 30일의 프롬프트와 출력이 안전 모니터링용으로 저장된다는 점을 사내 보안 담당자와 공유합니다.
  3. 이 데이터는 자동 시스템이 분석하고, 기본적으로 Anthropic 직원은 읽을 수 없다는 점을 확인합니다.
  4. 사람 검토는 자동 시스템이 유해 가능성을 표시한 드문 경우에만 승인된 소수가 하고, 접근 기록이 변조 불가 로그에 남는다는 점을 확인합니다.
  5. 엔터프라이즈 조직이면 모니터링 데이터를 자체 클라우드에 보관하는 Enterprise Frontier Safeguards(EFS)를 쓸 수 있는지 담당자에게 문의합니다.
  • 엔터프라이즈 데이터는 명시적으로 허가하지 않으면 학습에 쓰지 않습니다.
  • EFS는 올가을 이후 단계적으로 제공되며, 그 전까지 대상 조직은 Fable 5와 5.1에서 데이터 보관 없음(ZDR)을 받습니다.
  • EFS에서는 로그를 고객이 통제하고, 검토는 기계로만 하며, 결과는 고객 콘텐츠가 아니라 정해진 탐지 항목으로만 나옵니다.

5. Claude Duet 연구 프리뷰 신청하기

Claude Duet은 주의가 필요한 일을 Claude가 먼저 알려 주고, 폰을 내려놓은 뒤에도 계속 일하는 새 앱입니다. 지금은 연구 프리뷰여서 대기자 명단으로 신청합니다.

  1. 내 구독이 Pro 또는 Max인지, 미국 대상 조건에 맞는지 확인합니다.
  2. 조건이 맞으면 대기자 명단에 신청합니다.
  3. 쓰기 시작하면 Claude가 알려 주는 일 가운데 지금 확인할 것과 미뤄도 되는 것을 나눠 봅니다.
  4. Claude가 나를 대신해 행동하기 전에 확인을 요청하면 내용을 읽고 승인할지 정합니다.
  • 한국 사용자는 아직 대상이 아니므로 공식 발표로 지원 범위가 넓어지는지 지켜보세요.
  • 영상 속 사용자들은 Slack에서 필요한 내용을 먼저 가져다주는 점을 장점으로 꼽았습니다.

6. AI로 만든 콘텐츠 공개 원칙 정하기

편집부터 영상 제작까지 AI로 자동화하면 시간은 줄지만 구독자 반응은 갈릴 수 있습니다. AI 결과물을 어떻게 내보낼지 미리 원칙을 정해 두면 신뢰를 지키기 쉽습니다.

  1. AI로 만들려는 콘텐츠가 무엇이고, 누가 볼 것인지 적습니다.
  2. 네 가지 선택지 가운데 하나를 고릅니다: ① AI로 다 해 보기 ② AI 콘텐츠는 다른 채널이나 쇼츠로 분리 ③ AI를 쓰되 사람의 몫을 넣기 ④ AI 쓰지 않기.
  3. 내보내기 전에 사람이 검수·검증할 항목을 정합니다.
  4. 독자나 시청자에게 의견을 묻고 반응을 보며 원칙을 고칩니다.
  • 영상에서는 사람이 만든 콘텐츠의 가치가 완벽함보다 진실성에 있다고 봅니다.
  • AI가 만든 콘텐츠일수록 검수와 신뢰가 더 중요해집니다.

7. 소모적인 업무 절차 하나 줄이기

AI로 작성이 빨라지면서 병목은 검증·리뷰·유지보수로 옮겨 갔습니다. Claude Code 팀처럼 팀 규칙을 다시 보고, 가장 소모적인 절차 하나를 골라 줄여 봅니다.

  1. 팀에서 가장 시간이 많이 들고 지치는 업무 절차 하나를 고릅니다.
  2. 그 절차가 지금도 꼭 필요한지 팀원과 따져 봅니다.
  3. 필요하다면 Claude로 줄일 수 있는 부분을 찾아 시험 삼아 맡겨 봅니다.
  4. 말로 길게 논쟁하는 대신 결과물을 먼저 만들어 보여 주는 방식을 써 봅니다.
  5. 검증과 리뷰를 누가 맡을지 정해 새 병목이 생기지 않게 합니다.
  • Shopify는 업무를 덜어 주는 '바닥 올리기'보다, 예전에 불가능했던 일을 가능하게 하는 '천장 올리기'를 핵심으로 봅니다.
  • 할 수 있는 일이 3개에서 300개로 늘어도 핵심 역량에 집중해야 한다는 조언도 있습니다(Factory).

8. Slack에서 Claude Tag 쓰기

Claude Tag는 Slack에서 팀과 함께 일하는 Claude입니다. 스레드에서 태그하면 채널 맥락을 파악해 작업하고, 끝나거나 입력이 필요할 때 알려 주며, 며칠~몇 주 걸리는 일도 후속 확인까지 이어서 합니다.

  1. 회사가 Team 또는 Enterprise 요금제인지 확인합니다(베타 제공).
  2. Slack 스레드에서 Claude를 태그하고 맡길 일을 적습니다.
  3. 작업 하나하나보다 이루고 싶은 목표를 맡깁니다.
  4. 같은 스레드에서 다른 팀원도 함께 지시하게 합니다.
  5. Claude가 완료나 추가 입력을 알려 오면 확인하고 답합니다.
  6. 채널마다 반복할 지시는 Claude가 기억하도록 그 채널에서 알려 둡니다.
  • Claude는 자기 계정과 권한을 쓰고, 채널별로 접근 범위가 나뉘며, 모든 자격 증명 사용이 기록됩니다.
  • 비공개 채널이나 DM에서 배운 내용은 그 안에만 남습니다.
  • Claude Code 팀원 한 명은 작업의 70~80%를 Tag로 하고, 나머지만 직접 다듬는다고 합니다.
  • Microsoft Teams 등으로 넓힐 계획이 발표됐습니다.

9. 새 모델이 나오면 내 업무로 시험하기

모델은 약 두 달마다 바뀌고, 모델만 바꿔도 결과가 크게 좋아지기도 합니다. 출시 전 모델을 먼저 받아 보는 고객 팀들처럼 나만의 시험 세트를 두고 새 모델을 바로 점검합니다.

  1. 자주 하는 업무 가운데 결과를 비교하기 쉬운 작업 몇 개를 시험 세트로 정해 둡니다.
  2. 새 모델이 나오면 이 시험 세트를 먼저 돌려 이전 결과와 비교합니다.
  3. 법률 문서 초안처럼 지금 모델로 잘 안 되던 복잡한 작업도 맡겨 봅니다.
  4. 안 되는 작업은 다음 모델이 나아질 영역의 신호로 기록해 둡니다.
  5. 예전 모델의 약점을 메우려고 만든 우회 방법이 아직 필요한지 다시 따져 보고, 필요 없으면 없앱니다.
  • 모델만 바꿨는데 테스트 에이전트 성공률이 약 20% 오른 사례가 있습니다.
  • 가장 중시하는 평가 기준으로 지능과 의사결정 능력을 꼽은 창업자들이 많았습니다.
  • Factory는 모델이 하니스(모델을 감싸는 도구)를 흡수하므로 매달 기존 해법을 의심하라고 조언합니다.

10. 루틴으로 반복 작업 맡기기

루틴은 사람이 매번 지시하지 않아도 정해진 계기에 Claude Code가 일하게 하는 기능입니다. 일정, 웹훅, API 호출로 시작할 수 있고 로컬이나 원격 클라우드에서 돌아 세션 밖에서도 일이 이어집니다.

  1. 매일 또는 매주 반복하는 작업 하나를 고릅니다.
  2. 그 작업을 시작할 계기를 일정, 웹훅, API 호출 가운데에서 정합니다.
  3. 로컬과 원격 클라우드 가운데 어디서 돌릴지 정합니다.
  4. 루틴이 할 일을 목표 중심으로 적고, 확신이 높은 것만 처리하도록 기준을 넣습니다.
  5. 처음 며칠은 결과를 매일 확인하며 지시를 다듬습니다.
예시
매일 들어온 피드백을 모아 중요도별로 분류하고, 확신이 높은 것만 고쳐 줘.
  • 런던 기조연설에서는 루틴이 사람 대신 Claude Code에 지시하고 CI 자동 수정까지 맡는 흐름을 시연했습니다.
  • 예전 방식: 로컬 노트북에서만 돌렸지만, 지금은 원격 개발 박스·웹용 Claude Code·루틴으로 세션 밖에서도 돌릴 수 있습니다.

11. AI 자동화에 안전장치 걸기

AI에게 맡기는 일이 많아질수록 품질은 AI의 판단보다 시스템의 안전장치로 지켜야 합니다. Stripe와 Shopify가 쓰는 방식을 참고해, 사람 승인과 인프라 차원의 보호 장치를 함께 둡니다.

  1. AI가 실행할 작업을 격리된 환경에서 돌리고, 접근할 데이터와 권한을 필요한 만큼만 줍니다.
  2. 결과를 한꺼번에 내보내지 말고 조금씩 단계적으로 배포합니다.
  3. 작업이 폭주하면 자동으로 멈추는 서킷 브레이커를 둡니다.
  4. 원인 확인, 배포 범위 결정, 최종 수정 승인은 사람이 맡습니다.
  5. 장애와 되돌린 작업 수를 꾸준히 기록해 신뢰성이 유지되는지 확인합니다.
  • Stripe의 한 엔지니어는 상반기에 AI로 작성한 PR 600개 이상을 병합했고, 되돌린 것은 1건뿐이었습니다.
  • Stripe는 모든 개발자에게 Claude Code가 설치된 격리 개발 환경(devbox)을 주고, Slack이나 웹에서 프롬프트로 일을 맡깁니다.
  • Claude Duet처럼 대신 행동하기 전에 확인받는 구조가 개인 업무용 에이전트의 기본이 되고 있습니다.
