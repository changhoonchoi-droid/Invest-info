1. 하나로 합쳐진 Claude에 목표 맡기기

9월 업데이트로 채팅과 Cowork가 하나의 Claude로 합쳐졌습니다. 이제 모드를 고르지 않고 원하는 결과만 말하면 Claude가 방법을 찾습니다. 시간이 걸리는 작업은 클라우드에서 계속 돌아가므로 맡겨 두고 다른 일을 하면 됩니다.

  1. Claude에서 새 대화를 엽니다. 채팅과 Cowork 중 하나를 고르는 단계는 없어졌습니다.
  2. 할 일을 하나하나 지시하지 말고, 얻고 싶은 결과(목표)를 한 문단으로 적습니다.
  3. 필요한 배경 자료나 앞선 대화 내용이 있으면 함께 알려 줍니다.
  4. 작업이 시작되면 노트북을 닫아도 됩니다. 작업은 클라우드에서 계속 진행됩니다.
  5. 이동 중에는 휴대폰으로 진행 상황을 확인합니다.
  6. 결과를 받으면 고칠 부분을 말해 다듬습니다.
  • 예전에 Cowork에서 하던 작업은 통합 뒤에도 그대로 남아 있습니다.
  • 예전 방식: 채팅과 Cowork를 따로 골라 썼고, 작업이 내 컴퓨터에서 돌았습니다.
  • LLM은 질문에 맞춰 답하려는 경향이 있습니다. 실제로 필요한 것이 무엇인지 정확히 적을수록 결과가 좋아집니다.

2. 대화에서 슬라이드·디자인·문서 만들기

Claude Slides, Claude Design, Claude Docs를 쓰면 대화를 벗어나지 않고 발표 자료, 소셜 이미지, 한 장 요약 문서를 만들 수 있습니다. 기존 대화 내용을 바탕으로 만들어지므로, 브리프 하나로 여러 결과물을 한 번에 준비할 때 좋습니다.

  1. 대화창에 출시 브리프나 기획 내용을 붙여 넣습니다.
  2. 만들 결과물(발표 슬라이드, 소셜 이미지 세트, 한 장 요약 문서)을 일상 언어로 요청합니다.
  3. 만들어진 결과물을 처음부터 끝까지 훑어봅니다.
  4. 고칠 부분에 코멘트를 달아 Claude에게 보냅니다.
  5. Claude가 그 부분을 고치면 다시 확인하고, 마음에 들 때까지 반복합니다.
예시
이 출시 브리프를 바탕으로 발표 슬라이드, 소셜 이미지 세트, 현장에서 나눠 줄 한 장짜리 요약 문서를 만들어 줘.
  • 세 기능은 아직 베타입니다. 중요한 결과물은 반드시 직접 검토하세요.
  • Claude Design은 브랜드에 맞는 제작 수준의 결과물을 목표로 합니다. 브랜드 색이나 톤을 함께 알려 주면 좋습니다.
  • 예전 방식: 9월 중순 베타 공개 때는 결과물별로 따로 소개됐지만, 지금은 어떤 대화에서든 바로 만들 수 있습니다.

3. Claude Docs로 팀과 함께 편집하기

Claude Docs는 팀원과 Claude가 같은 문서를 동시에 편집하는 기능입니다. 보고서나 기획서를 여럿이 쓰면서 Claude에게 일부 수정을 맡기고 싶을 때 씁니다.

  1. 대화에서 Claude에게 문서 초안을 만들어 달라고 요청합니다.
  2. 만들어진 Claude Docs 문서를 팀원과 함께 엽니다.
  3. 팀원들이 각자 맡은 부분을 직접 편집합니다.
  4. Claude가 고쳐야 할 부분에는 코멘트를 달아 Claude에게 보냅니다.
  5. Claude가 고친 내용을 팀원과 함께 확인하고 마무리합니다.
  • 코멘트는 문서 어느 부분에든 달 수 있습니다. 범위를 좁혀 요청하면 Claude가 그 부분만 정확히 고칩니다.
  • Claude Docs는 베타로 공개되었습니다.

4. 작업 단계에 맞는 모델 고르기

Claude 모델은 종류마다 강점이 다릅니다. 새 5.5 계열에서는 방향을 찾을 때 Opus 5.5, 빠르게 고칠 때 Sonnet 5.5를 쓰라고 권합니다. 일의 단계와 비용에 맞춰 모델을 나눠 쓰면 품질과 속도를 함께 챙길 수 있습니다.

  1. 지금 하는 일이 방향을 찾는 단계인지, 정해진 결과물을 빠르게 고치는 단계인지 나눕니다.
  2. 기획, 구조 잡기, 어려운 문제 풀기처럼 방향을 찾는 단계에는 Opus 5.5를 고릅니다.
  3. 문장 다듬기나 작은 수정처럼 빠르게 고치는 단계에는 Sonnet 5.5로 바꿉니다.
  4. 수개월 치 데이터와 여러 자료를 뒤져 근본 원인을 찾는 긴 엔지니어링 작업이라면 Fable 5.1을 검토합니다.
  5. 자주 반복하는 운영 업무는 저렴한 모델로 돌려 비용을 아낍니다.
  • Shopify의 '배벨 전략': 개발·테스트·자동 연구에는 가장 큰 모델을, 운영과 파인튜닝에는 저렴한 모델을 씁니다.
  • Fable 5.1이 원인을 제안해도 원인 확인, 배포 범위 결정, 수정 승인은 사람이 맡습니다.
  • 예전 방식: 2026년 2월부터 Free·Pro 플랜에서는 claude.ai와 Cowork의 기본 모델이 Sonnet 4.6이었습니다(100만 토큰 컨텍스트 베타).

5. 데이터 보관 방식 확인하기

Claude Fable 5부터는 안전 모니터링을 위해 최근 30일간의 프롬프트와 출력이 저장됩니다. 회사 자료를 Claude에 넣기 전에 어떤 데이터가 얼마 동안 어떻게 보관되는지 알고, 필요하면 조직 차원의 선택지를 검토합니다.

  1. 지금 쓰는 모델이 Fable 5 이후 모델인지 확인합니다. 해당되면 최근 30일의 프롬프트와 출력이 저장됩니다.
  2. 저장된 데이터는 자동 시스템이 분석하고, 기본적으로 Anthropic 직원은 읽을 수 없다는 점을 확인합니다.
  3. 엔터프라이즈 데이터는 명시적으로 허가하지 않으면 학습에 쓰이지 않는다는 점을 사내 보안 담당자와 공유합니다.
  4. 모니터링 데이터를 회사 클라우드에 직접 보관해야 하는 조직이라면 Enterprise Frontier Safeguards(EFS) 도입을 관리자와 논의합니다.
  5. EFS가 나오기 전까지 대상 조직이 Fable 5와 5.1에서 데이터 보관 없음(ZDR)을 받을 수 있는지 관리자에게 확인합니다.
  • 사람의 검토는 자동 시스템이 유해 가능성을 표시한 드문 경우에만, 승인된 소수 검토자가 합니다. 접근 기록은 변조할 수 없는 로그에 남습니다.
  • EFS는 올가을부터 단계적으로 제공됩니다. EFS에서는 로그를 고객이 통제하고, 검토는 기계로만 하며, 결과는 정해진 탐지 항목으로 제한됩니다.
  • 비밀번호·API 키 같은 민감 정보는 정책과 관계없이 대화에 넣지 않는 것이 안전합니다.

6. AI로 새로 가능한 일 찾기

기존 일을 덜어 주는 '바닥 올리기'를 넘어, 예전에는 엄두를 못 내던 일을 해내는 '천장 올리기'를 찾는 방법입니다. 다른 회사와 현장 사례를 참고해 우리 팀에서 시도할 과제를 고릅니다.

  1. 너무 크거나 오래 걸려 미뤄 둔 프로젝트를 목록으로 적습니다.
  2. 그중 데이터를 모으고도 분석할 시간이 없어 못 쓰고 있는 일을 표시합니다.
  3. 표시한 일 하나를 골라, 분석의 출발점을 제안해 달라고 Claude에게 요청합니다.
  4. Claude의 제안을 바탕으로 실험과 판단은 사람이 맡아 진행합니다.
  5. 결과가 좋으면 같은 방식을 다른 과제로 넓힙니다.
  • Shopify는 회사를 행동의 연속으로 표현해 가맹점 성장을 예측하는 디지털 트윈을 만들었습니다.
  • IRC 나이지리아 현장에서는 수집한 데이터의 약 50%가 분석 시간 때문에 쓰이지 못합니다. 손으로 적은 카드를 촬영해 바로 분석하는 방식을 기대하고 있습니다.
  • Frontier Day의 스타트업들은 수년 걸리던 생물학 분석을 몇 분~몇 시간으로 줄였다고 말합니다. 과학 분야에는 Claude Science가 작업대로 소개되었습니다.

7. 루틴으로 반복 업무 맡기기

작업이 클라우드에서 돌면서, 세션 밖에서도 정해진 일을 반복하는 루틴과 루프가 가능해졌습니다. 매일 들어오는 피드백 정리처럼 반복되는 일을 맡기면 됩니다.

  1. 매일 또는 매주 반복하는 업무 하나를 고릅니다.
  2. 그 업무의 목표와 처리 기준(분류 기준, 직접 고쳐도 되는 범위)을 적습니다.
  3. Claude Code의 루틴으로 그 업무를 등록합니다.
  4. 결과를 처음 며칠 동안 직접 확인하며 기준을 다듬습니다.
  5. 믿을 만해지면 결과 확인 주기를 늘립니다.
예시
매일 들어온 사용자 피드백을 모아 중요도별로 분류하고, 확신이 높은 것만 고쳐 줘. 나머지는 목록으로 정리해 줘.
  • Claude Code 팀은 작업이 아니라 목표를 맡기고, 대부분을 Slack 기반 에이전트 Claude Tag로 처리합니다.
  • 예전 방식: 프롬프트를 주고 권한 요청을 하나씩 승인하며 내 노트북에서 실행했습니다.
  • Claude Code에는 원격 제어, 자동 모드, 자동 메모리, 자동 코드 리뷰, 에이전트 뷰 같은 기능도 함께 추가되었습니다.

8. AI 작업에 안전장치 두기

AI에게 많은 일을 맡길수록 품질과 안전은 AI의 판단이 아니라 시스템 차원의 장치로 지켜야 합니다. Stripe와 Shopify가 실제로 쓰는 원칙을 팀 업무에 적용합니다.

  1. AI가 접근할 수 있는 데이터와 권한의 범위를 정하고, 중요한 데이터는 분리합니다.
  2. AI가 작업하는 공간을 실제 운영 환경과 떨어진 격리 환경으로 둡니다.
  3. 결과를 한 번에 모두 반영하지 말고 조금씩 넓혀 가는 점진적 배포 규칙을 정합니다.
  4. 작업이 폭주하면 자동으로 멈추는 서킷 브레이커 기준(시간, 비용, 횟수 등)을 정합니다.
  5. 최종 승인은 사람이 하도록 승인 단계를 둡니다.
  • Stripe는 모든 개발자에게 Claude Code가 미리 설치된 격리 개발 환경(devbox)을 주고, Slack이나 웹에서 Minions로 작업을 맡깁니다.
  • Stripe의 한 엔지니어는 상반기에 AI로 작성한 PR 600개 이상을 병합했고, 되돌린 것은 1건뿐이었습니다.
  • Stripe Projects는 엔지니어 2~3명이 약 2개월 만에 출시했습니다. 예전 방식이면 더 큰 팀이 6개월 걸렸을 것으로 봅니다.

9. 새 모델이 나오면 평가로 점검하기

모델은 몇 달마다 바뀌므로, 새 모델이 나올 때마다 우리 업무 기준으로 평가(evals)하고 일하는 방식을 고쳐야 합니다. AI를 팀이나 제품에 깊이 넣은 조직일수록 꼭 필요합니다.

  1. 우리 업무에서 자주 나오는 대표 과제를 골라 평가용 묶음을 만듭니다.
  2. 과제마다 좋은 결과의 기준을 적어 둡니다.
  3. 새 모델이 나오면 같은 평가를 폭넓게 돌려 이전 모델과 비교합니다.
  4. 지능과 의사결정 능력처럼 우리에게 중요한 기준으로 도입 여부를 정합니다.
  5. 새 모델이 잘하게 된 부분을 메우려고 만들었던 보조 절차는 과감히 없앱니다.
  • Lovable은 모든 모델 출시가 평가 루프를 통과해야 합니다. 월 6억 건 이상의 세션을 처리합니다.
  • Claude Code 팀은 모델 기반이 약 두 달마다 바뀌어서, 할 일 목록처럼 필요 없어진 기능은 제거합니다.
  • Delivery Hero는 하루 100건 이상의 PR을 병합하는 자율 에이전트를 운영하고, monday.com은 코드를 모르는 사용자를 위해 Claude를 제품에 넣었습니다.
