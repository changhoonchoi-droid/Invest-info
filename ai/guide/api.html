1. Managed Agents로 업무 에이전트 기획하기

Claude Managed Agents는 에이전트 실행에 필요한 인프라를 Anthropic이 맡아 주는 방식으로, 직접 서버를 만들지 않고도 업무용 에이전트를 빠르게 내놓을 수 있습니다. 반복 업무를 팀이 일하는 곳(예: Slack)에서 AI 동료에게 맡기고 싶을 때 씁니다.

  1. 보고서 수집, 소셜 게시물 작성, 회의 전 브리프처럼 자주 반복되는 업무를 하나 고릅니다.
  2. 에이전트가 일할 장소를 팀이 이미 쓰는 도구로 정합니다. 예: Slack 공개 채널.
  3. 가장 단순한 첫 버전을 정하고 짧은 기간 안에 내놓는 것을 목표로 잡습니다.
  4. 공개 채널에서 동료들이 서로의 프롬프트를 볼 수 있게 해 잘 쓰는 방식이 퍼지게 합니다.
  5. 써 본 결과를 보고 다룰 업무 범위를 조금씩 넓힙니다.
  6. 비용과 응답 지연(콜드 스타트)을 따져 계속 Managed Agents로 갈지, 일부는 직접 만들지 판단합니다.
  • Wispr는 회의 어시스턴트 첫 버전을 하루 만에, Actively는 영업 보고 에이전트를 2주 만에 Managed Agents로 만들었습니다.
  • Managed Agents는 어려운 작업에 잘 맞습니다. 비용 조절 수단이 적고 콜드 스타트 지연이 있어서 단순한 작업은 직접 만드는 편이 나을 수 있습니다.
  • 모델이 좋아지면서 업무 절차 틀(하네스)은 점점 얇아지는 추세라, 처음부터 복잡하게 짤 필요는 없습니다.

2. 프롬프트 캐싱과 컨텍스트로 비용 줄이기

오래 실행되는 에이전트는 대화와 도구 결과가 쌓이면서 비용이 늘고 느려집니다. Claude 플랫폼의 프롬프트 캐싱, 도구 검색, 프로그램 방식 도구 호출, 컴팩션을 쓰면 비용을 줄이고 컨텍스트를 가볍게 유지할 수 있습니다.

  1. 에이전트가 매번 똑같이 보내는 긴 지시문이나 참고 자료가 무엇인지 찾습니다.
  2. 반복되는 부분에 프롬프트 캐싱을 적용해 같은 내용을 다시 처리하는 비용을 줄입니다.
  3. 연결된 도구가 많다면 도구 검색을 써서 필요한 도구만 불러오게 합니다.
  4. 도구를 여러 번 이어서 호출하는 작업은 프로그램 방식 도구 호출로 묶어 중간 결과가 컨텍스트에 쌓이지 않게 합니다.
  5. 장시간 작업에는 컴팩션을 써서 지난 대화를 줄인 뒤 작업을 이어 갑니다.
  • 이 기능들은 비용 절감, 컨텍스트 관리, 지능 향상이라는 세 가지 목표에 맞춰 함께 쓰는 것이 좋습니다.
  • 세부 설정 방법은 Claude 공식 문서에서 최신 내용을 꼭 확인하세요.

3. 과거 수정 기록으로 스킬 만들기

사람이 그동안 고친 기록을 모아 스킬로 만들면, 그 사람의 기준대로 에이전트가 작업합니다. 교정·검토처럼 담당자의 노하우가 중요한 업무를 자동화할 때 씁니다.

  1. 노하우를 옮기고 싶은 사람의 과거 수정 기록을 모읍니다. 예: 편집장의 원고 수정 이력.
  2. 모은 수정 기록으로 그 사람의 기준을 담은 스킬을 만듭니다.
  3. 에이전트가 스킬을 써서 문서에 바로 고치지 않고 수정 제안을 달게 합니다. 예: Google Docs의 제안 수정.
  4. 에이전트의 제안 뒤에 사람이 추가로 고친 내용을 추적합니다.
  5. 추적한 수정 내용을 스킬에 다시 반영해 계속 개선합니다.
  • Every는 편집장이 과거에 한 수정 3만 건으로 교정 스킬을 만들었습니다.
  • 처음부터 완벽할 필요는 없습니다. 사람의 수정을 반영할수록 정확해집니다.
  • 에이전트를 쓸수록 할 일이 오히려 늘었다는 경험담도 있으니, 남는 시간을 어디에 쓸지 미리 생각해 두세요.

4. Outcomes로 에이전트 결과 검증하기

Managed Agents의 Outcomes는 에이전트에 평가 기준(루브릭)을 주고, 그 기준을 만족할 때까지 반복해서 작업하게 하는 기능입니다. 틀린 결과가 사용자에게 나가면 안 되는 업무에 씁니다.

  1. 사용자에게 중요한 기준을 모두 나열합니다. 예: 올바른 인물의 LinkedIn인지, 읽기 쉬운지.
  2. 나열한 기준을 에이전트에 줄 루브릭으로 정리합니다.
  3. 객관적으로 확인되는 항목과 표시 방식·순서 같은 사용성 항목을 루브릭에 함께 넣습니다.
  4. 에이전트가 루브릭을 만족할 때까지 반복해서 작업하게 합니다.
  5. 작업 에이전트와 분리된 독립 컨텍스트의 검증 에이전트가 결과를 평가하게 합니다.
  6. 회의 24시간 전처럼 여유를 두고 실행해 평가와 반복에 쓸 시간을 확보합니다.
  7. 기준을 통과하지 못한 결과는 사용자에게 아무것도 보여 주지 않도록 처리합니다.
예시
다음 루브릭을 모두 만족할 때까지 회의 전 브리프를 다시 작성하세요. 1) 참석자 LinkedIn이 올바른 인물의 것인지 확인했다 2) 핵심 내용이 읽기 쉽게 정리되어 있다 3) 중요한 정보가 위에 오도록 순서가 정해져 있다
  • 틀린 정보를 보여 주는 것보다 아예 보여 주지 않는 편이 낫습니다.
  • 평가 결과를 에이전트의 초기 루프에 반영하면 처음부터 더 정확해집니다.
  • Outcomes에서는 루브릭과 함께 반복 시도 횟수도 정할 수 있습니다.

5. 평가(evals)로 모델 교체에 대비하기

평가(evals)는 정해 둔 과제로 에이전트나 모델의 성능을 꾸준히 측정하는 방법입니다. 모델이 빠르게 좋아지므로 새 모델로 바꿔도 되는지, 워크플로를 어떻게 고칠지 판단할 때 씁니다.

  1. 에이전트가 꼭 잘해야 하는 대표 작업을 평가 과제로 정합니다.
  2. 과제마다 성공과 실패를 가를 기준을 정합니다.
  3. 현재 모델과 설정으로 평가를 돌려 기준 점수를 기록합니다.
  4. 새 모델이 나오면 쓰기 전에 같은 평가를 통과하는지 확인합니다.
  5. 평가 결과를 보고 필요 없어진 절차는 걷어내는 등 워크플로를 조정합니다.
  • Lovable은 모든 모델 출시가 평가 루프를 통과해야 쓰도록 운영합니다.
  • 모델이 좋아지면 예전에 필요했던 복잡한 절차가 오히려 걸림돌이 될 수 있습니다.

6. 어드바이저 전략으로 성능 높이기

어드바이저 전략은 평소에는 비용이 적게 드는 모델로 작업하다가, 막히는 순간에만 더 똑똑한 모델에 조언을 구하는 방식입니다. 적은 비용으로 결과의 질을 높이고 싶을 때 씁니다.

  1. 작업을 맡을 기본 모델을 정합니다.
  2. 조언을 구할 더 높은 성능의 모델을 정합니다.
  3. 기본 모델이 어떤 상황을 '막혔다'고 판단할지 기준을 정합니다.
  4. 막혔을 때만 어드바이저 모델에 질문하고, 받은 조언으로 작업을 이어 가게 합니다.
  5. 평가로 비용과 결과 품질을 비교해 기준을 조정합니다.
  • 항상 가장 비싼 모델을 쓰지 않아도 되므로 비용을 아끼면서 지능을 끌어올릴 수 있습니다.

7. 여러 에이전트가 협업하게 구성하기

에이전트 여러 개가 경쟁하거나 서로 반박하게 하면 혼자 일할 때보다 결과가 좋아질 수 있습니다. 에이전트끼리는 API나 얇은 MCP 서버로 서로 호출합니다.

  1. 업무를 나눠 맡길 에이전트별 역할을 정합니다.
  2. 협업 방식을 고릅니다. 예: 여러 에이전트가 같은 과제를 두고 경쟁하기, 한 에이전트가 아이디어를 내고 다른 에이전트가 반박하기.
  3. 다른 에이전트가 호출할 수 있게 각 에이전트를 API나 얇은 MCP 서버로 노출합니다.
  4. 도구는 에이전트별로 꼭 필요한 것만 알맞은 크기로 설계합니다.
  5. 평가로 협업 구성이 단일 에이전트보다 나은지 확인합니다.
  • 앞으로 에이전트는 자체 정체성과 서비스 계정을 갖고, 필요한 권한은 사람에게 요청해 승인받는 방식으로 발전할 것으로 보입니다.
  • Omni는 분석 에이전트 Blobby를 멀티 에이전트 구조로 만들고 평가로 효과를 측정했습니다.

8. Agent SDK 에이전트에 가드레일 두기

Agent SDK로 백그라운드에서 일하는 코딩 에이전트를 만들 수 있습니다. 팀의 표준화와 가드레일을 갖춰 두면 에이전트도 더 빠르고 안전하게 일합니다.

  1. 에이전트에 맡길 백그라운드 작업을 정합니다. 예: 여러 코드에 반복 적용하는 마이그레이션.
  2. Agent SDK로 이 작업을 하는 에이전트를 만듭니다.
  3. 에이전트를 팀이 이미 쓰는 내부 플랫폼이나 카탈로그와 연결해 필요한 정보를 얻게 합니다.
  4. 사람 팀에게 쓰던 표준과 규칙을 에이전트에도 똑같이 적용합니다.
  5. 에이전트가 벗어나면 안 되는 범위를 가드레일로 정합니다.
  • Spotify는 엔지니어의 96%가 AI로 코딩해 PR 빈도가 60% 늘었고, 병목이 코드 작성에서 코드 조율로 옮겨 갔습니다.
  • Spotify의 Honk는 Agent SDK 기반 백그라운드 코딩 에이전트로, 마이그레이션 플랫폼 Fleetshift와 소프트웨어 카탈로그 Backstage에 연결해 씁니다.
  • 단단한 가드레일은 제약이 아니라 가속기 역할을 합니다.
