1. 내 용도에 맞는 모델 고르기

Opus·Sonnet·Haiku 중 무엇을 쓸지 감으로 정하지 않고, 내 업무로 작은 평가(eval)를 만들어 비교하는 방법입니다. 새 모델이 나올 때마다 같은 절차로 다시 고를 수 있습니다.

  1. 모델 선택 기준을 품질, 지연, 비용 세 가지로 정합니다.
  2. 내 업무에서 실제로 쓰는 질문과 작업으로 작은 평가 세트를 만듭니다.
  3. 최종 결과뿐 아니라 과정도 점검하도록 평가 항목을 정합니다.
  4. Opus, Sonnet, Haiku와 사고(thinking) 설정별로 같은 작업을 돌립니다.
  5. 같은 작업을 여러 번 돌려 인프라 실패와 모델 실패를 구분합니다.
  6. 통과율, 토큰, 비용, 지연을 표로 비교해 내 기준에 맞는 조합을 고릅니다.
  • 일반적으로 높은 지능이 필요하면 Opus, 낮은 지연·비용은 Haiku, 균형은 Sonnet을 씁니다.
  • 공개 벤치마크는 방향만 알려 주므로 작더라도 직접 만든 평가가 더 중요합니다.
  • 시연에서는 Opus 4.7(사고 켬, 높은 effort)이 통과율은 가장 높았지만 가장 비쌌고, 사고를 켠 Haiku는 Sonnet과 비슷한 통과율을 보였습니다.

2. effort로 Claude의 생각량 조절하기

Claude는 추론에 토큰을 더 쓸수록 어려운 문제를 더 잘 풉니다. effort 설정으로 품질과 비용·대기 시간의 균형을 맞추는 방법입니다.

  1. Claude의 토큰이 생각, 도구 호출, 텍스트 세 가지로 쓰이고 모두 비용과 대기 시간으로 이어진다는 점을 확인합니다.
  2. 가능하면 생각(thinking)을 켭니다.
  3. effort를 low부터 max까지 다이얼처럼 바꿔 가며 같은 작업을 돌립니다.
  4. 평가(eval)로 모델과 effort 조합의 결과 곡선을 비교합니다.
  5. 어느 쪽이 좋을지 고민되면 기본값인 extra high로 시작합니다.
  6. 토큰·시간·비용의 상한이 필요하면 task budgets로 예산을 정해 중간 점검하게 합니다.
  • 시연에서 low는 약 4,600 출력 토큰에 약 50초, high는 약 2배, max는 약 10배의 토큰과 시간이 들었습니다.
  • 지능이 필요한 작업은 effort를 낮추더라도 큰 모델이 낫습니다.
  • 예전 방식: 도구 호출 뒤에도 이어지는 interleaved thinking을 썼지만, 지금은 모델이 생각 시점을 스스로 정하는 adaptive thinking으로 발전했습니다.

3. 프롬프트 고치기와 에이전트 프롬프트 나누기

모델을 바꾼 뒤 성능이 떨어진 프롬프트를 고치거나, 새 에이전트 프롬프트를 처음부터 설계하는 순서입니다. 평가 세트를 먼저 만들고 실패 유형을 하나씩 고치는 것이 핵심입니다.

  1. 통제 사례, 엣지 케이스, 사람에게 넘겨야 할 사례로 평가 세트를 만듭니다.
  2. 프롬프트 구조를 정리하고 출력 형식을 명시합니다.
  3. 평가를 돌려 실패 유형을 분류합니다.
  4. 행동 차이(프롬프트로 조정 가능)인지 능력 부족(프롬프트로 해결 불가)인지 구분합니다.
  5. 행동 차이는 실패 유형별로 하나씩 프롬프트를 고치며 다시 평가합니다.
  6. 새 에이전트는 큰 프롬프트 하나 대신 생성·평가·수리 세 프롬프트로 나눕니다.
  7. 평가 프롬프트에 런타임 소프트 조건을 넣어, 코드를 고치지 않고 기준을 조절합니다.
  • 시연에서는 생성·평가·수리로 나눈 방식이 Sonnet 4.6에 개선한 프롬프트를 쓴 것보다 토큰과 지연이 적었습니다.
  • 능력 부족이 원인이면 프롬프트를 아무리 고쳐도 해결되지 않으니 모델 변경을 검토합니다.

4. 캐싱·컨텍스트 관리로 비용 줄이기

프롬프트 캐싱과 컨텍스트 정리로 비용을 줄이고 긴 작업에서도 에이전트가 가볍게 움직이게 하는 방법입니다. 오래 일하는 에이전트나 도구를 많이 쓰는 앱에서 특히 효과가 큽니다.

  1. 비용 관리의 첫 번째 권장 사항인 프롬프트 캐싱부터 적용합니다.
  2. 대화 중간에 effort나 시스템 프롬프트를 바꿔도 캐싱이 깨지지 않는다는 점을 알고 설계합니다.
  3. 도구 설명에 입력뿐 아니라 출력 스키마(예: ID, 제목, 스니펫, 점수)도 적어 왕복 횟수를 줄입니다.
  4. N턴마다 오래된 도구 결과(스크린샷, 검색 결과, 파일 읽기)를 지우고 결정만 남깁니다.
  5. 긴 작업에는 도구 검색, 프로그램 방식 도구 호출, 컴팩션을 사용합니다.
  6. Claude Code에서는 /context로 컨텍스트 사용 현황을 확인합니다.

5. Managed Agents 시작하기

Managed Agents는 에이전트 운영에 필요한 인프라(자격 증명, 샌드박스, 상태 관리, 관측)를 Anthropic이 맡아 주는 API 모음입니다. 직접 에이전트 루프를 만들지 않고 업무용 에이전트를 빠르게 띄울 때 씁니다.

  1. 에이전트를 정의합니다. 시스템 프롬프트, 모델, 스킬, 도구, 권한을 정합니다.
  2. 에이전트가 실행될 환경을 만듭니다. 네트워크 허용 목록과 사전 설치 패키지를 정합니다.
  3. 필요하면 세션을 만들 때 GitHub 저장소나 파일을 미리 불러옵니다.
  4. 세션을 시작해 에이전트에게 작업을 맡깁니다.
  5. 이벤트 스트림을 구독해 에이전트가 무엇을 왜 하는지 관찰합니다.
  • 구성은 에이전트(템플릿), 환경(샌드박스 템플릿), 세션(진행 중인 대화), 이벤트(스트림)로 나뉩니다.
  • 세션 하나는 컨테이너 하나에서 실행되므로 여러 작업을 동시에 병렬로 처리할 수 있습니다.
  • Cloudflare·Modal·Vercel 같은 자체 샌드박스도 연결할 수 있습니다.
  • 에이전트와 실행 환경을 분리한 설계 덕분에 자격 증명 보안이 강화되고 첫 토큰까지의 지연이 줄어듭니다.

6. 에이전트 작업에 사람 승인 걸기

에이전트가 위험한 도구를 마음대로 실행하지 않도록 도구별 권한을 나누고, 작업 도중 사람이 개입하는 방법입니다. 결제·발송처럼 되돌리기 어려운 작업이 있을 때 씁니다.

  1. 에이전트가 쓰는 도구를 모두 나열합니다.
  2. 도구별로 자동 실행과 명시적 승인(human-in-the-loop) 중 하나를 정합니다.
  3. 세션을 시작하고 이벤트 스트림에서 승인 요청 이벤트를 확인합니다.
  4. 승인 확인 이벤트를 보내 허용하거나 거절합니다.
  5. 작업이 잘못된 방향으로 가면 인터럽트 이벤트로 방향을 바로잡습니다.
  • 이벤트는 사용자·에이전트·세션·구간(span) 네 종류로 나뉩니다.
  • 에이전트는 앞으로 자체 정체성과 서비스 계정을 갖고, 필요한 권한을 사람에게 요청해 승인받는 방식으로 발전할 것이라는 전망이 나왔습니다.

7. 세션이 끝나도 기억하는 메모리 붙이기

에이전트는 세션마다 앞선 대화를 잊어버립니다. 메모리 스토어를 세션에 붙이면 여러 세션에 걸쳐 배운 내용을 읽고 쓸 수 있습니다.

  1. CLI로 메모리 스토어를 만들고 name(예: CWC memory)과 간단한 설명을 지정합니다.
  2. 콘솔의 manage agents → memory stores에서 상태가 active인지, 파일 시스템 뷰어가 비어 있는지 확인합니다.
  3. 세션을 만들 때 요청에 메모리 스토어 ID를 리소스로 넘깁니다.
  4. 필요하면 prompt 값으로 무엇을 기억할지 에이전트를 유도합니다.
  5. access 필드로 읽기/쓰기 권한을 정합니다. 기본값은 읽기·쓰기이고, 읽기 전용으로 바꿀 수 있습니다.
  6. 세션에 새 정보를 담은 메시지를 보냅니다.
  7. 다른 새 세션에서 같은 내용을 물어 기억하는지 확인합니다.
  • 메모리 스토어는 사용자별·작업공간별 등 원하는 경계로 여러 개 만들 수 있습니다.
  • 읽기 전용으로 붙이면 에이전트가 메모리를 수정하지 못합니다.
  • 메모리는 파일 시스템으로 마운트되어 Claude가 bash·grep으로 직접 탐색하며, 버전 관리와 diff, 작성 에이전트 표시를 지원합니다.
  • 메모리는 Managed Agents에서 공개 베타 단계입니다.

8. 드리밍으로 에이전트 메모리 정리하기

메모리가 계속 쌓이면 중복되고 오래된 정보가 남습니다. 드리밍은 과거 세션 기록을 분석해 메모리를 정리·보강하는 백그라운드 작업입니다.

  1. 콘솔에서 메모리 저장소를 열어 채워진 파일을 확인합니다.
  2. Dreams 탭으로 이동합니다.
  3. 드림을 시작하고 대상 메모리 저장소를 고릅니다.
  4. 분석할 세션을 고릅니다. 데모에서는 최근 7일 중 약 5개였습니다.
  5. Start dreaming으로 실행합니다.
  6. 진행 중인 드림을 열어 입력 세션과 만들어지는 출력 메모리 저장소를 확인합니다.
  7. 완료 후 메모리 저장소 변경 diff를 검토합니다.
  • UI뿐 아니라 API로도 실행할 수 있어 수동·매시간·매일 밤·세션 종료 이벤트 등으로 자동화할 수 있습니다.
  • 결과는 중복 통합, 낡은 항목 삭제, 검증 메모 추가로 나타납니다.
  • 드리밍은 연구 프리뷰 단계이며 Managed Agents와 함께 씁니다.
  • 토큰을 많이 쓰지만 대부분 캐시되어 약 95%의 캐시 적중률을 예상한다고 합니다.

9. Outcomes로 에이전트 결과 검증하기

Outcomes는 평가 기준(루브릭)을 주면 에이전트가 기준을 만족할 때까지 스스로 점검하며 반복하는 기능입니다. 틀린 결과가 사용자에게 보이면 곤란한 업무에서 씁니다.

  1. 사용자에게 중요한 기준을 모두 나열합니다. 예: 올바른 인물의 LinkedIn인지, 읽기 쉬운지.
  2. 그 기준을 에이전트에 줄 루브릭으로 만듭니다.
  3. 객관적으로 확인되는 항목과 표시 방식·순서 같은 UX 항목을 함께 넣습니다.
  4. 에이전트가 루브릭을 만족할 때까지 반복 작업하게 하고 반복 횟수를 정합니다.
  5. 작업 에이전트와 분리된 독립 컨텍스트의 검증 에이전트(채점기)가 결과를 평가하게 합니다.
  6. 회의 24시간 전처럼 시간 여유를 두고 실행해 평가와 반복 시간을 확보합니다.
  7. 기준을 통과하지 못하면 사용자에게 아무것도 보여 주지 않도록 처리합니다.
  • 틀린 정보를 보여 주는 것보다 아예 보여 주지 않는 편이 낫습니다.
  • 평가 결과를 에이전트 초기 루프에 반영하면 처음부터 더 정확해집니다.
  • Outcomes와 멀티 에이전트 조율은 연구 프리뷰로 제공되며 신청서로 조기 접근을 요청할 수 있습니다.
  • 여러 에이전트가 경쟁하거나, 한 에이전트가 아이디어를 내고 다른 에이전트가 반박하는 방식, 막히면 더 똑똑한 모델에 묻는 advisor 전략도 있습니다.
