1. 내 용도에 맞는 Claude 모델 고르기

Opus·Sonnet·Haiku 가운데 내 업무에 맞는 모델을 품질·지연·비용 세 가지 기준으로 고르는 방법입니다. 새 모델이 나올 때마다 같은 절차로 다시 비교할 수 있습니다.

  1. 모델을 품질, 지연(응답 속도), 비용 세 가지 기준으로 비교한다고 정합니다.
  2. 기본 원칙부터 잡습니다. 지능이 필요하면 Opus, 빠르고 싸야 하면 Haiku, 균형이 필요하면 Sonnet입니다.
  3. 내 실제 업무에서 뽑은 작은 평가 세트(테스트 문제 모음)를 만듭니다.
  4. 같은 평가 세트를 모델별·사고 설정별로 실행합니다.
  5. 통과율, 사용 토큰, 비용, 지연을 표로 정리해 비교합니다.
  6. 같은 작업을 여러 번 돌려, 인프라 문제로 생긴 실패와 모델이 틀린 실패를 나눠 봅니다.
  7. 새 모델이 나오면 같은 평가 세트로 다시 비교합니다.
  • 공개 벤치마크는 대략적인 방향만 알려 줍니다. 작더라도 내 업무용 평가를 직접 만드는 편이 정확합니다.
  • 최종 답만 보지 말고 결과에 이르는 과정도 점검하세요.
  • 시연에서는 사고를 켠 Haiku가 사고를 켠 Sonnet과 통과율이 비슷했습니다. 작은 모델도 꼭 같이 시험해 보세요.
  • 지능이 필요한 작업이라면 effort를 낮추더라도 큰 모델을 쓰는 편이 낫다고 합니다.

2. effort로 생각량 조절하기

Claude는 답하기 전에 토큰을 더 많이 써서 생각할수록 어려운 문제를 더 잘 풉니다. effort 다이얼(low~max)이나 task budget 같은 예산으로 생각량을 조절해 품질과 비용·시간의 균형을 맞춥니다.

  1. 되도록 생각(thinking) 기능을 켜 둡니다.
  2. effort를 low에서 max 사이 값으로 정합니다.
  3. 같은 작업을 low, high, max로 각각 돌려 결과와 토큰·시간을 비교합니다.
  4. 작업 전체에 쓸 양을 정하고 싶으면 task budget 같은 예산으로 제한합니다.
  5. 평가 세트로 품질과 비용이 가장 잘 맞는 단계를 고릅니다.
  • 시연에서 high는 low보다 토큰과 시간을 약 2배, max는 약 10배 썼습니다.
  • 어느 단계를 쓸지 고민되면 extra high(제품 기본값)를 권합니다.
  • 예전 방식: 도구 호출 뒤에도 생각을 이어 가는 interleaved thinking. 지금은 모델이 생각할 시점을 스스로 정하는 adaptive thinking으로 발전했습니다.

3. 평가 세트로 프롬프트 고치기

모델을 바꾼 뒤 기존 프롬프트의 성능이 떨어졌을 때, 평가 세트를 먼저 만들고 실패 유형을 하나씩 고치는 방법입니다. 고객지원 봇처럼 정해진 업무를 하는 프롬프트에 잘 맞습니다.

  1. 평가 세트를 만듭니다. 일반적인 통제 사례, 엣지 케이스(예외 상황), 사람에게 넘겨야 하는 사례를 함께 넣습니다.
  2. 지금 프롬프트로 평가 세트를 돌려 어디서 실패하는지 기록합니다.
  3. 프롬프트 구조를 정리하고 출력 형식을 분명히 적는 기본 정리부터 합니다.
  4. 실패를 유형별로 나눠 한 번에 한 유형씩 고칩니다.
  5. 고칠 때마다 평가 세트를 다시 돌려 다른 사례가 망가지지 않았는지 확인합니다.
  • 새 모델에서 성능이 떨어지는 원인은 두 가지입니다. 행동 차이는 프롬프트로 고칠 수 있지만 능력 부족은 프롬프트로 해결되지 않습니다.
  • 능력 부족으로 판단되면 더 큰 모델이나 다른 구조(생성·평가·수리 루프)를 검토하세요.

4. 생성·평가·수리 루프로 에이전트 짜기

새 에이전트를 만들 때 하나의 큰 프롬프트 대신 생성, 평가, 수리 세 개의 프롬프트로 나누는 방법입니다. 시연에서는 이 방식이 더 적은 토큰과 낮은 지연으로 모든 테스트를 통과했습니다.

  1. 먼저 통제 사례·엣지 케이스·사람에게 넘길 사례로 평가 세트를 만듭니다.
  2. 답을 만드는 생성 프롬프트를 씁니다.
  3. 생성된 답이 기준에 맞는지 판정하는 평가 프롬프트를 씁니다.
  4. 평가에서 걸린 부분만 고치는 수리 프롬프트를 씁니다.
  5. 생성 → 평가 → (실패하면) 수리 순서로 돌도록 연결합니다.
  6. 평가 세트로 전체 루프를 돌려 통과율·토큰·지연을 확인합니다.
  • 실행 중에 바뀌는 조건(런타임 소프트 조건)은 평가 프롬프트에 넣으면 코드를 고치지 않아도 됩니다.
  • 막힐 때 더 똑똑한 모델에 묻는 advisor 전략이나, 한 에이전트가 낸 안을 다른 에이전트가 반박하게 하는 방식도 함께 소개되었습니다.

5. 업무 노하우를 스킬로 만들기

사람이 해 온 작업 방식(예: 편집장의 교정 기록)을 마크다운 문서 형태의 스킬로 만들어 에이전트가 똑같이 하게 하는 방법입니다. 실무자에게 익숙한 문서 형태라서 함께 고치고 버전을 관리하기 쉽습니다.

  1. 에이전트에게 맡길 반복 업무를 하나 고릅니다 (예: 원고 교정, 보고서 수집).
  2. 그 업무를 잘하는 사람이 남긴 과거 기록을 모읍니다 (예: 편집장의 과거 수정 내역).
  3. 기록에서 찾은 규칙과 작업 순서를 마크다운 파일로 정리해 스킬로 만듭니다.
  4. 에이전트가 스킬을 써서 작업하게 합니다 (예: Google Docs에 교정 제안 달기).
  5. 사람이 에이전트 결과를 추가로 고친 내용을 추적합니다.
  6. 추적한 수정을 스킬에 다시 반영해 계속 개선합니다.
  • Slack처럼 공개된 곳에서 에이전트에게 지시하면, 잘 쓰는 사람의 지시 방식이 동료에게 자연스럽게 퍼집니다.
  • 에이전트는 기존 업무 방식에 맞춰야 정착합니다. AirOps는 스킬을 마케터용 Playbooks라는 문서 형태로 바꿔 제공했습니다.
  • 예전 방식: 노드 기반 워크플로 빌더로 절차를 하나하나 그렸습니다. 새 모델이 나올 때마다 고쳐야 해서, 지금은 마크다운 파일과 스킬로 구성한 Agent SDK 기반 에이전트로 옮겨 가는 추세입니다.

6. Managed Agents 시작하기

Claude Managed Agents는 에이전트 운영에 필요한 호스팅, 샌드박스, 자격 증명 보관, 재시도·오류 복구, 관측을 Anthropic이 맡아 주는 플랫폼입니다. API 키로 쓰며 에이전트·환경·세션·이벤트 네 가지만 알면 시작할 수 있습니다.

  1. 에이전트를 정의합니다. 시스템 프롬프트, 모델, 스킬, 도구, 권한을 정합니다.
  2. 에이전트가 일할 환경(샌드박스)을 만듭니다. 네트워크 허용 목록과 미리 설치할 패키지를 지정합니다.
  3. 세션을 시작해 에이전트에게 작업을 맡깁니다. 필요하면 GitHub 저장소나 파일을 미리 불러옵니다.
  4. 이벤트 스트림을 구독해 에이전트가 무엇을 왜 하는지 지켜봅니다.
  5. 방향이 틀어지면 인터럽트 이벤트를 보내 바로잡습니다.
  6. 개발자 콘솔에서 실행 중인 에이전트를 실시간으로 디버깅합니다.
  • 에이전트(두뇌)와 환경(손)이 분리되어 있어 자격 증명이 더 안전하고, 첫 토큰이 나오기까지의 지연도 줄었습니다.
  • 이벤트는 사용자·에이전트·세션·구간(span) 네 종류입니다.
  • Cloudflare·Modal·Vercel 같은 자체 샌드박스나 자체 호스팅 환경도 연결할 수 있습니다.
  • 예전 방식: Messages API나 Agent SDK로 에이전트 루프와 호스팅을 직접 만들었습니다. 지금은 에이전트 루프가 서버 쪽에서 실행됩니다. 다만 비용 조절 수단이 적고 콜드 스타트 지연이 있어, 어려운 작업이 아니면 직접 만드는 쪽도 검토하라는 의견이 있습니다.

7. 도구 권한과 사람 승인 설정하기

에이전트가 쓰는 도구마다 자동 실행할지, 사람의 승인을 받고 실행할지를 정하는 방법입니다. 메일 발송이나 데이터 수정처럼 되돌리기 어려운 작업에 꼭 필요합니다.

  1. 에이전트를 정의할 때 쓸 도구 목록을 정합니다.
  2. 도구마다 자동 실행할지, 명시적 승인을 받을지 나눕니다.
  3. 되돌리기 어려운 도구에는 사람 확인(human-in-the-loop)을 겁니다.
  4. 세션 중 승인 요청이 오면 사용자 이벤트의 승인 확인으로 응답합니다.
  5. 외부 서비스 자격 증명은 Vaults에 저장해 사용자·세션별로 관리합니다.
  • Vaults는 자격 증명을 별도 저장소에 암호화해 보관합니다.
  • 앞으로 에이전트는 자체 정체성과 서비스 계정을 갖고, 필요한 권한을 사람에게 요청해 승인받는 방식으로 발전할 것으로 봅니다.

8. Outcomes로 결과 검증하기

Outcomes는 에이전트에게 '좋은 결과의 기준'(루브릭)을 주고, 기준을 만족할 때까지 스스로 점검하며 반복하게 하는 Managed Agents 기능입니다. 틀린 결과가 사용자에게 가면 안 되는 업무에 씁니다.

  1. 사용자 입장에서 중요한 기준을 모두 적습니다 (예: 올바른 인물의 LinkedIn인지, 읽기 쉬운지).
  2. 적은 기준을 에이전트에게 줄 루브릭으로 정리합니다.
  3. 객관적으로 확인할 수 있는 항목과 표시 방식·순서 같은 UX 항목을 함께 넣습니다.
  4. 루브릭과 반복 시도 횟수를 정해 outcome으로 넘깁니다.
  5. 작업 에이전트와 분리된 독립 컨텍스트의 검증 에이전트가 결과를 평가하게 합니다.
  6. 회의 24시간 전처럼 넉넉한 시점에 실행해 평가와 반복에 쓸 시간을 확보합니다.
  7. 기준을 통과하지 못한 결과는 사용자에게 보여 주지 않도록 처리합니다.

9. 에이전트에 메모리 스토어 붙이기

에이전트는 세션이 끝나면 배운 것을 잊습니다. 메모리 스토어는 파일 시스템처럼 세션에 마운트되어, 에이전트가 여러 세션에 걸쳐 기억을 읽고 쓸 수 있게 합니다.

  1. CLI로 메모리 스토어를 만들고 name(예: CWC memory)과 간단한 설명을 정합니다.
  2. 콘솔의 manage agents → memory stores에서 상태가 active인지, 파일 시스템 뷰어가 비어 있는지 확인합니다.
  3. 세션을 만들 때 요청에 메모리 스토어 ID를 리소스로 넘깁니다.
  4. 필요하면 prompt 값으로 무엇을 기억할지 에이전트를 유도합니다.
  5. access 필드로 권한을 정합니다. 기본값은 읽기·쓰기이고, 읽기 전용으로 바꿀 수 있습니다.
  6. 세션에 새 정보를 담은 메시지를 보냅니다.
  7. 새 세션을 열어 같은 내용을 물어보고 기억하는지 확인합니다.
  • 메모리 스토어는 사용자별·작업공간별처럼 원하는 단위로 여러 개 만들 수 있습니다.
  • 여러 에이전트가 같은 저장소를 읽기 전용·읽기/쓰기로 나눠 공유할 수 있고, 쓰기 충돌은 낙관적 동시성 제어로 막습니다.
  • 메모리는 버전 관리, diff, 작성한 에이전트 표시, 내보내기·삭제(redaction)를 지원하며, 콘솔에서 직접 열어 고칠 수도 있습니다.

10. 드리밍으로 에이전트 메모리 정리하기

에이전트마다 메모리를 쓰다 보면 중복되거나 조각나고 오래된 정보가 남습니다. 드리밍은 세션 사이에 과거 대화 기록을 분석해 반복되는 실수를 찾고, 메모리를 확인·정리·보강하는 백그라운드 작업입니다.

  1. 콘솔에서 정리할 메모리 저장소를 열어 들어 있는 파일을 확인합니다.
  2. Dreams 탭으로 이동합니다.
  3. 드림을 시작하고 대상 메모리 저장소를 고릅니다.
  4. 분석할 세션을 고릅니다 (데모에서는 최근 7일 중 약 5개).
  5. Start dreaming을 눌러 실행합니다.
  6. 진행 중인 드림을 열어 입력 세션과 새로 만들어지는 출력 메모리 저장소를 확인합니다.
  7. 완료되면 메모리 저장소의 변경 diff를 검토합니다.
  • UI 말고 API로도 실행할 수 있어 수동, 매시간, 매일 밤, 세션 종료 시점 등으로 자동화할 수 있습니다.
  • 드리밍은 연구 프리뷰 단계이며 Managed Agents와 함께 씁니다.
  • 토큰을 많이 쓰지만 대부분 캐시되어 약 95% 캐시 적중률이 예상된다고 합니다.
  • Harvey는 드리밍으로 법률 벤치마크 완료율이 6배 늘었다고 합니다.
