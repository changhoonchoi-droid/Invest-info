API·개발자 플랫폼

Claude API와 Managed Agents로 업무용 에이전트를 만드는 방법을 모았습니다. 먼저 모델과 추론 강도(effort)를 고르고 비용을 관리하는 기본기를 익힌 뒤, Managed Agents를 시작하고 결과 검증, 메모리, 드리밍 순서로 보면 따라가기 좋습니다. 대부분 개발자 콘솔과 API 키가 있으면 시도할 수 있고, 일부 기능은 연구 프리뷰라 신청이 필요할 수 있습니다.

최근 바뀐 점

  • Claude Managed Agents가 봄에 출시되었고, 모델 발전에 맞춰 샌드박스·스킬·보안 자격 증명 관리 같은 기본 요소를 묶어 제공합니다.
  • 대화 도중 effort나 시스템 프롬프트를 바꿔도 프롬프트 캐싱이 깨지지 않도록 개선되어 비용 관리가 쉬워졌습니다.

  • 드리밍이 세션 기록을 보고 메모리의 잘못 굳은 내용을 고쳐 주며, 일정에 따라 오프라인으로 돌릴 수 있습니다.

1. 내 용도에 맞는 모델 고르기

Claude에는 Opus, Sonnet, Haiku처럼 성격이 다른 모델이 있습니다. 새 모델이 나올 때마다 품질·지연·비용 세 축으로 내 업무에 맞는 모델을 직접 비교하는 방법입니다.

  1. 내 업무에서 자주 하는 작업 몇 개를 골라 작은 평가(eval) 세트로 만듭니다.
  2. 평가에 정답 기준을 정해 둡니다. 최종 결과뿐 아니라 과정도 확인할 항목에 넣습니다.
  3. 같은 작업을 Opus, Sonnet, Haiku로 각각 여러 번 돌립니다.
  4. 사고(thinking) 설정을 켠 경우와 끈 경우도 나눠 돌려 봅니다.
  5. 통과율, 토큰 수, 비용, 지연을 표로 비교합니다.
  6. 인프라 실패와 모델 실패를 구분해서 보고, 품질·지연·비용 중 가장 중요한 축에 맞는 조합을 고릅니다.
  • 일반적으로 지능이 필요하면 Opus, 낮은 지연·비용은 Haiku, 균형은 Sonnet을 씁니다.
  • 공개 벤치마크는 방향만 알려 주므로 작더라도 직접 만든 평가가 더 중요합니다.
  • 시연에서는 사고를 켠 Haiku가 Sonnet과 비슷한 통과율을 보이기도 했습니다. 직접 돌려 확인하세요.

2. 추론 강도(effort)로 비용·속도 조절하기

Claude는 생각에 토큰을 더 쓸수록 어려운 문제를 잘 풉니다. effort 다이얼과 작업 예산으로 이 추론량을 조절해 품질과 비용·대기 시간의 균형을 맞춥니다.

  1. 생각·도구 호출·텍스트 세 가지가 모두 토큰이며 비용과 대기 시간으로 이어진다는 점을 먼저 이해합니다.
  2. 가능하면 생각(적응형 사고)을 켭니다.
  3. effort를 low부터 max까지 바꿔 가며 같은 작업을 돌립니다.
  4. 결과 품질과 토큰·시간을 비교하는 평가 곡선을 그립니다.
  5. 토큰·시간·비용 상한이 필요하면 task budgets로 정합니다.
  6. 고르기 어려우면 extra high로 시작합니다.
  • 시연에서 high는 low의 약 2배, max는 약 10배의 토큰과 시간을 썼습니다.
  • 지능이 필요한 작업은 effort를 낮추더라도 큰 모델이 낫다고 합니다.
  • 예전 방식: 확장 사고를 직접 설정했지만, 지금은 모델이 생각 시점을 정하는 적응형 사고로 바뀌었고 한동안 이전 방식으로 되돌릴 수 있습니다.

3. 프롬프트 캐싱과 컨텍스트로 비용 줄이기

프롬프트 캐싱은 Anthropic이 비용 관리의 첫 번째로 권하는 방법입니다. 긴 작업을 하는 에이전트는 컨텍스트도 가볍게 유지해야 비용이 덜 듭니다.

  1. 반복해서 보내는 시스템 프롬프트와 자료를 요청 앞부분에 고정해 캐싱이 되게 합니다.
  2. 대화 중간에 effort나 시스템 프롬프트를 바꿔도 캐싱이 유지된다는 점을 활용합니다.
  3. N턴마다 오래된 도구 결과(스크린샷, 검색 결과, 파일 읽기)를 지우고 결정만 남깁니다.
  4. 컨텍스트가 길어지는 에이전트에는 도구 검색, 프로그램 방식 도구 호출, 컴팩션을 검토합니다.
  5. Claude Code에서는 /context로 컨텍스트 사용 현황을 확인합니다.
  • 도구 설명에 입력뿐 아니라 출력 스키마(ID, 제목, 스니펫, 점수 등)도 적어 두면 왕복이 줄어듭니다.
  • 모델이 좋아지면 보완용 코드는 수명이 짧아지니, 내 데이터·도구를 연결하는 코드에 투자하세요.

4. 프롬프트 평가 세트 만들고 고치기

모델을 바꾼 뒤 성능이 떨어졌을 때, 평가 세트를 먼저 만들고 실패 유형을 하나씩 고치는 방법입니다. 에이전트를 새로 만들 때는 프롬프트를 나누는 구성도 소개됩니다.

  1. 통제 사례, 엣지 케이스, 사람에게 넘길 사례로 평가 세트를 만듭니다.
  2. 프롬프트 구조를 정리하고 출력 형식을 명시합니다.
  3. 평가를 돌려 실패한 유형을 나눕니다.
  4. 실패가 행동 차이인지 능력 부족인지 구분합니다. 행동 차이만 프롬프트로 고칠 수 있습니다.
  5. 실패 유형을 하나씩 고치고 매번 평가를 다시 돌립니다.
  6. 에이전트를 새로 만든다면 큰 프롬프트 하나 대신 생성·평가·수리 세 프롬프트로 나눠 봅니다.
  • 평가 프롬프트에 런타임 소프트 조건을 넣으면 코드를 고치지 않고도 기준을 바꿀 수 있습니다.
  • 시연에서는 세 프롬프트로 나눈 방식이 토큰과 지연이 더 적었습니다.

5. Managed Agents 시작하기

Claude Managed Agents는 에이전트 인프라(샌드박스, 자격 증명, 상태 관리, 관측)를 Anthropic이 맡아 주는 API 모음입니다. API 키로 쓰며, 에이전트가 격리된 컨테이너에서 파일 시스템, bash, 웹 검색을 써서 일합니다.

  1. 에이전트(두뇌)를 정의합니다. 시스템 프롬프트, 모델, 스킬, 도구, 권한을 정합니다.
  2. 환경(손)을 만듭니다. 네트워크 허용 목록과 사전 설치 패키지를 정합니다.
  3. 세션을 시작해 에이전트에게 작업을 맡깁니다. 필요하면 GitHub 저장소나 파일을 미리 불러옵니다.
  4. 이벤트 스트림을 구독해 에이전트가 무엇을 왜 하는지 관찰합니다.
  5. 도구별로 자동 실행과 사용자 승인을 나눠 설정합니다.
  6. 개발자 콘솔에서 실행 중인 에이전트를 실시간으로 디버깅합니다.
  • 세션 하나가 컨테이너 하나에서 실행되므로 여러 작업을 동시에 병렬로 처리할 수 있습니다.
  • 작업이 잘못 가면 인터럽트 이벤트로 방향을 바로잡을 수 있습니다.
  • Cloudflare·Modal·Vercel 같은 자체 샌드박스도 연결할 수 있습니다.
  • Managed Agents는 Messages API 위에 만들어졌고, 에이전트 루프·파일 관리·코드 실행을 직접 만들지 않아도 됩니다.

6. Outcomes로 에이전트 결과 검증하기

Outcomes는 평가 기준(루브릭)을 주면 에이전트가 그 기준을 만족할 때까지 스스로 점검하며 반복하는 기능입니다. 틀린 결과가 사용자에게 가기 전에 걸러야 할 때 씁니다.

  1. 사용자에게 중요한 기준을 모두 나열합니다. 예: 올바른 인물의 LinkedIn인지, 읽기 쉬운지.
  2. 그 기준을 에이전트에 줄 루브릭으로 만듭니다.
  3. 객관적으로 확인되는 항목과 표시 방식·순서 같은 UX 항목을 함께 넣습니다.
  4. 에이전트가 루브릭을 만족할 때까지 반복 작업하게 하고, 반복 횟수를 정합니다.
  5. 작업 에이전트와 분리된 독립 컨텍스트의 검증 에이전트가 결과를 평가하게 합니다.
  6. 회의 24시간 전처럼 시간 여유를 두고 실행해 평가와 반복 시간을 확보합니다.
  7. 기준을 통과하지 못하면 사용자에게 아무것도 보여 주지 않도록 처리합니다.
  • 틀린 정보를 보여 주는 것보다 아예 보여 주지 않는 편이 낫습니다.
  • 평가 결과를 에이전트 초기 루프에 반영하면 처음부터 더 정확해집니다.
  • Outcomes는 한때 제한된 연구 프리뷰였으니 사용 가능 여부를 콘솔에서 확인하세요.

7. 에이전트 세션에 메모리 붙이기

에이전트는 세션이 끝나면 앞선 대화에서 배운 것을 잊습니다. 메모리 스토어는 파일 시스템처럼 세션에 마운트되어 여러 세션에 걸쳐 읽고 쓸 수 있게 합니다.

  1. CLI로 메모리 스토어를 만들고 name과 간단한 설명을 지정합니다.
  2. 콘솔의 manage agents → memory stores에서 상태가 active인지, 파일 시스템 뷰어가 비어 있는지 확인합니다.
  3. 세션을 만들 때 요청에 메모리 스토어 ID를 리소스로 넘깁니다.
  4. 필요하면 prompt 값으로 무엇을 기억할지 에이전트를 유도합니다.
  5. access 필드로 읽기/쓰기 권한을 정합니다. 기본은 읽기·쓰기입니다.
  6. 세션에 새 정보를 담은 메시지를 보내고, 새 세션에서 같은 내용을 물어 기억하는지 확인합니다.
  • 메모리 스토어는 사용자별·작업공간별 등 원하는 경계로 여러 개 만들 수 있습니다.
  • 읽기 전용으로 붙이면 에이전트가 메모리를 수정하지 못합니다.
  • Claude는 bash·grep으로 메모리를 직접 탐색하고, 버전 기록과 작성 에이전트 표시, 감사 기록을 지원합니다.

8. 드리밍으로 에이전트 메모리 정리하기

메모리가 계속 쌓이면 중복되고 낡은 정보가 남습니다. 드리밍은 세션 사이에 과거 기록을 분석해 메모리를 정리·보강하는 배치 작업으로, 현재 연구 프리뷰입니다.

  1. 콘솔에서 메모리 저장소를 열어 채워진 파일을 확인합니다.
  2. Dreams 탭으로 이동합니다.
  3. 드림을 시작하고 대상 메모리 저장소를 고릅니다.
  4. 분석할 세션을 고릅니다. 데모에서는 최근 7일 중 약 5개였습니다.
  5. Start dreaming으로 실행합니다.
  6. 진행 중인 드림을 열어 입력 세션과 만들어지는 출력 메모리 저장소를 확인합니다.
  7. 완료 후 메모리 저장소 변경 diff를 검토합니다.
  • API로도 실행할 수 있어 수동·매시간·매일 밤·세션 종료 이벤트 등으로 자동화할 수 있습니다.
  • 토큰을 많이 쓰지만 대부분 캐시되어 약 95% 적중률을 예상한다고 합니다.
