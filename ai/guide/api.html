API·개발자 플랫폼

API·개발자 플랫폼 분야에서는 Claude API와 Agent SDK, Claude Managed Agents로 업무용 AI 에이전트를 직접 만들 수 있습니다. 에이전트에 기억을 붙이고, 결과를 검증하고, 비용을 관리하는 일도 이 분야에 들어갑니다. 먼저 Managed Agents의 기본 구조와 간단한 API 활용 사례를 익히고, 이어서 만들 방식을 고르는 법, 메모리·검증·스킬 같은 응용 기능, 비용 관리와 평가 순서로 보면 좋습니다.

1. Managed Agents 기본 구조 이해하기

Claude Managed Agents는 에이전트의 호스팅, 확장, 샌드박스, 관측을 Anthropic이 맡아 주는 플랫폼입니다. 메시지 API와 Agent SDK 다음 단계로, 서버를 직접 운영하지 않고 에이전트를 프로덕션에 올리고 싶을 때 씁니다.

  1. 에이전트를 만드는 세 가지 길을 구분합니다. 메시지 API로 직접 호출하기, Agent SDK로 직접 만들기, Managed Agents에 운영 맡기기입니다.
  2. Managed Agents의 첫 번째 자원인 '에이전트'(두뇌)를 정합니다. 모델과 시스템 프롬프트, 스킬, MCP 서버 같은 구성이 여기에 들어갑니다.
  3. 두 번째 자원인 '환경'(손)을 준비합니다. 에이전트가 실제로 작업할 샌드박스입니다.
  4. 세 번째 자원인 '세션'으로 에이전트와 환경을 연결해 작업을 시작합니다.
  5. 에이전트 루프가 내 컴퓨터가 아니라 Anthropic 서버에서 실행된다는 점을 기억해 둡니다.
  6. API 키 같은 자격 증명은 Vaults에 보관합니다. Vaults는 별도 저장소에 암호화해 두고 사용자·세션별로 관리합니다.
  • 두뇌(에이전트)와 손(환경)을 분리한 구조라 자격 증명이 더 안전하고, 첫 토큰이 나오기까지의 시간(TTFT)이 P95 기준 90% 넘게 줄었다고 합니다.
  • 모델이 좋아지면서 하네스(업무 절차 틀)는 점점 얇아지고 있습니다. 새 모델이 나오면 프롬프트와 절차를 다시 점검합니다.
  • 에이전트끼리 서로 호출해야 하면 API나 얇은 MCP 서버로 노출하는 방식을 쓸 수 있습니다.

2. Claude API로 답장 초안 도우미 만들기

Claude API에 시스템 프롬프트와 업무 자료를 함께 주면, 내 말투로 이메일 답장 초안을 만들어 주는 도구를 만들 수 있습니다. 코딩 경험이 없는 영업 담당자가 Claude Code로 이런 도구를 만들어 하루 2~3시간을 아꼈습니다.

  1. 매일 시간을 많이 잡아먹는 반복 업무를 하나 고릅니다. 예를 들면 고객 이메일에 답장하기입니다.
  2. 내 말투와 답장 원칙을 시스템 프롬프트로 적습니다.
  3. 답장에 필요한 맥락 자료를 모아 둡니다. Google Docs에 정리한 제품 정보나 계정 정보 같은 것입니다.
  4. Claude Code에 원하는 도구를 설명하고, Claude API를 호출해 초안을 만드는 프로그램을 함께 만듭니다.
  5. 실제 이메일로 초안을 만들어 보고, 말투가 어색한 부분은 시스템 프롬프트를 고쳐 다듬습니다.
  6. 초안을 직접 확인한 뒤 보내는 흐름을 지킵니다.
  • 만든 사람은 계정 600~700개를 관리하던 영업 담당자였고, 이 도구로 수천 통의 이메일이 나갔습니다.
  • API 키는 코드나 공유 문서에 직접 적지 않습니다.

3. Managed Agents와 직접 구축 중 고르기

Managed Agents에 운영을 맡길지, Agent SDK로 직접 만들지 판단하는 방법입니다. 작업 난이도, 비용, 응답 속도, 우리 조직의 업무 방식을 기준으로 고릅니다.

  1. 만들 에이전트의 작업이 얼마나 어렵고 오래 걸리는지 적어 봅니다.
  2. 어렵고 오래 걸리는 작업이면 Managed Agents를 우선 검토합니다. 회의 어시스턴트 첫 버전을 하루 만에 내놓거나 영업 보고 에이전트를 2주 만에 만든 사례가 있습니다.
  3. 빠른 응답이 중요하면 콜드 스타트 지연(처음 시작할 때 생기는 지연)이 문제가 되지 않는지 확인합니다.
  4. 실행 횟수가 많으면 비용을 미리 계산합니다. Managed Agents에는 비용을 조절할 수단이 아직 적습니다.
  5. 자체 시스템과 가드레일에 깊이 붙여야 하면 Agent SDK로 직접 만드는 방법을 검토합니다. Spotify의 백그라운드 코딩 에이전트 Honk가 이런 경우입니다.
  6. 어느 쪽이든 에이전트를 사용자의 기존 업무 방식과 도구에 맞춥니다.
  • 창업자들은 Managed Agents가 어려운 작업에는 잘 맞지만, 그 밖의 작업은 직접 만드는 편이 나을 수 있다고 말합니다.
  • 표준화와 단단한 가드레일은 사람에게처럼 에이전트에게도 제약이 아니라 가속기가 됩니다.
  • AirOps는 노드 기반 워크플로 빌더에서 Agent SDK와 마크다운·스킬로 만든 에이전트로 옮겼습니다. 보통 최소 한 달 걸리던 고객 도입을 1주로 줄였습니다.

4. 메모리 스토어로 세션 기억 붙이기

에이전트는 세션마다 따로 동작해서 앞에서 배운 내용을 잊어버립니다. Managed Agents의 메모리 스토어를 세션에 붙이면 에이전트가 여러 세션에 걸쳐 같은 기억을 읽고 쓸 수 있습니다.

  1. CLI로 메모리 스토어를 만들고 name(예: CWC memory)과 간단한 설명을 정합니다.
  2. 콘솔의 manage agents → memory stores에서 상태가 active인지, 파일 시스템 뷰어가 비어 있는지 확인합니다.
  3. 세션을 만들 때 요청에 메모리 스토어 ID를 리소스로 넘깁니다.
  4. 필요하면 prompt 값으로 에이전트가 무엇을 기억할지 안내합니다.
  5. access 필드로 권한을 정합니다. 기본값은 읽기·쓰기이고, 읽기 전용으로 바꿀 수 있습니다.
  6. 세션에 새 정보를 담은 메시지를 보냅니다.
  7. 새 세션을 열고 같은 내용을 물어 에이전트가 기억하는지 확인합니다.
  • 메모리 스토어는 사용자별, 작업공간별처럼 원하는 단위로 여러 개 만들 수 있습니다.
  • 읽기 전용으로 붙이면 에이전트가 메모리를 고칠 수 없습니다.
  • 메모리 스토어는 세션 안에 파일 시스템처럼 연결되어, 에이전트가 bash·grep·파일 읽기로 내용을 찾습니다.
  • 메모리가 쌓이면 지저분해지고 오래된 정보가 남습니다. 드리밍이라는 백그라운드 작업이 과거 세션 기록을 바탕으로 사실 확인, 정리, 중복 제거를 합니다.

5. Outcomes로 에이전트 결과 검증하기

Outcomes는 에이전트에 평가 기준(루브릭)과 반복 횟수를 정해 주고, 기준을 만족할 때까지 작업을 되풀이하게 하는 Managed Agents 기능입니다. 틀린 결과가 사용자에게 그대로 전달되면 안 되는 업무에 씁니다.

  1. 사용자에게 중요한 기준을 모두 나열합니다. 예를 들면 올바른 인물의 LinkedIn인지, 읽기 쉬운지 같은 것입니다.
  2. 그 기준을 에이전트에 줄 루브릭으로 정리합니다.
  3. 객관적으로 확인할 수 있는 항목과, 표시 방식·순서 같은 사용성 항목을 함께 넣습니다.
  4. 루브릭과 반복 시도 횟수를 정해, 기준을 만족할 때까지 에이전트가 작업을 되풀이하게 합니다.
  5. 작업 에이전트와 분리된 독립 컨텍스트의 검증 에이전트가 결과를 평가하게 합니다.
  6. 회의 24시간 전처럼 시간을 넉넉히 두고 실행해 평가하고 다시 시도할 시간을 확보합니다.
  7. 기준을 통과하지 못한 결과는 사용자에게 보여 주지 않도록 처리합니다.
  • 틀린 정보를 보여 주는 것보다 아예 보여 주지 않는 편이 낫습니다.
  • 평가 결과를 에이전트의 초기 작업 단계에 반영하면 처음부터 더 정확해집니다.
  • 여러 에이전트를 경쟁시키거나, 한 에이전트가 아이디어를 내고 다른 에이전트가 반박하게 하는 방식도 함께 쓸 수 있습니다.

6. 업무 노하우를 스킬로 만들기

잘하는 사람의 판단 기준과 과거 작업 기록을 스킬로 정리해 에이전트에 주면, 그 사람의 방식대로 일하게 할 수 있습니다. 교정, 콘텐츠 작성처럼 품질 기준이 분명한 업무에 잘 맞습니다.

  1. 노하우를 옮기고 싶은 업무와 기준이 되는 사람을 정합니다. 예를 들면 편집장의 교정 방식입니다.
  2. 그 사람이 과거에 한 수정과 작업 기록을 모읍니다.
  3. 모은 기록을 바탕으로 판단 기준을 마크다운 문서 형태의 스킬로 만듭니다.
  4. 에이전트가 실제 문서에 수정 제안을 달게 합니다. 예를 들면 Google Docs의 제안 수정입니다.
  5. 에이전트 제안 뒤에 사람이 추가로 고친 내용을 추적합니다.
  6. 추적한 수정을 스킬에 다시 반영해 계속 개선합니다.
  • Every는 편집장의 과거 수정 3만 건으로 교정 스킬을 만들었습니다.
  • Slack처럼 공개된 곳에서 에이전트에게 요청하면, 잘 쓰는 사람의 요청 방식이 동료에게 자연스럽게 퍼집니다.
  • 비개발자 동료가 쓸 거라면 AirOps의 Playbooks처럼 익숙한 문서 형태로 스킬을 보여 주고, 협업·권한 관리·버전 관리를 함께 챙깁니다.

7. 캐싱·컨텍스트 관리로 비용 줄이기

오래 일하는 에이전트는 토큰을 많이 써서 비용이 커지고 컨텍스트도 무거워집니다. 프롬프트 캐싱, 도구 검색, 프로그램 방식 도구 호출, 컴팩션, 어드바이저 전략으로 비용은 줄이고 성능은 지킬 수 있습니다.

  1. 매번 반복해서 보내는 긴 내용(시스템 프롬프트, 참고 자료)을 찾아 프롬프트 캐싱 대상으로 정합니다.
  2. 도구가 많으면 모든 도구를 컨텍스트에 넣지 말고, 도구 검색으로 필요한 도구만 불러오게 합니다.
  3. 여러 번 이어지는 도구 호출은 프로그램 방식 도구 호출로 묶어 컨텍스트를 가볍게 유지합니다.
  4. 긴 작업에는 컴팩션(대화 기록 압축)을 써서 컨텍스트가 넘치지 않게 합니다.
  5. 평소에는 비용이 적은 모델로 작업하고, 막힐 때만 더 똑똑한 모델에 묻는 어드바이저 전략을 적용합니다.
  • 드리밍처럼 토큰을 많이 쓰는 작업도 대부분 캐시되면 약 95%의 캐시 적중률을 기대할 수 있다고 합니다.
  • 배치 API처럼 실행 시간을 달리 예약하면 50% 할인받는 방식 등 저비용 옵션을 검토 중이라고 합니다. 바로 응답할 필요가 없는 작업은 이런 옵션이 나오는지 지켜봅니다.
  • 이 가이드의 근거 영상 가운데 하나는 자막 없이 챕터 정보만 있어서 세부 설정값은 공식 문서에서 확인합니다.

8. 평가(evals)로 에이전트 개선하기

에이전트를 고칠 때마다 정해 둔 평가를 돌려 실제로 좋아졌는지 숫자로 확인하는 방법입니다. 새 모델이 나올 때마다 워크플로를 다시 맞춰야 하는 개발 팀에 꼭 필요합니다.

  1. 에이전트의 목표를 숫자로 정합니다. 예를 들면 5분 안에 캔 다이아몬드 수입니다.
  2. 약 1분 안에 끝나는 빠른 평가 세트를 만들어 수정할 때마다 돌립니다.
  3. 한 번에 한 가지만 바꿔 봅니다. 대회에서는 my_agent.py의 모델, 시스템 프롬프트, 스킬, MCP 서버를 조정했습니다.
  4. 점수가 같으면 결과 대비 토큰 사용량 같은 효율 지표로 비교합니다.
  5. 가장 좋은 설정을 기록해 두고, 새 모델이 나오면 같은 평가로 다시 확인합니다.
  • Lovable은 모든 모델 출시가 평가 루프를 통과해야 적용됩니다.
  • 에이전트가 프로그램을 즉석에서 만들어 실행하는 시스템이라면 평가가 어려워, 평가 전담 팀을 두기도 합니다.
  • 결과만 보지 말고 결과가 만들어진 과정도 사람이나 다른 에이전트가 확인할 수 있게 설계하면 신뢰도가 높아집니다.
