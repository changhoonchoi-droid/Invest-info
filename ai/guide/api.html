API·개발자 플랫폼

Claude API와 개발자 플랫폼을 쓰면 회사 업무에 맞춘 AI 도우미나 에이전트를 직접 만들어 돌릴 수 있습니다. 먼저 모델 고르기, 생각량 조절, 프롬프트 개선으로 기초를 다집니다. 그다음 Managed Agents로 에이전트를 띄우고, 루브릭 검증, 메모리, 드리밍, 스킬 순서로 기능을 더해 가면 됩니다.

1. 내 용도에 맞는 모델 고르기

Opus·Sonnet·Haiku 중 내 업무에 맞는 모델을 고르는 절차입니다. 공개 벤치마크는 방향만 알려 주므로 내 업무로 작은 평가(eval)를 직접 만들어 비교합니다. 새 모델이 나올 때마다 같은 절차를 다시 돌리면 됩니다.

  1. 품질, 지연(응답 속도), 비용 중 내 업무에서 무엇이 가장 중요한지 정합니다.
  2. 실제 업무에서 쓰는 작업 몇 개를 골라 작은 평가 세트를 만듭니다.
  3. 최종 결과뿐 아니라 그 결과가 나오기까지의 과정도 점검할 기준을 적습니다.
  4. 같은 작업을 모델마다 여러 번 돌려 결과가 들쭉날쭉한지 확인합니다.
  5. 실패하면 네트워크 같은 인프라 문제인지, 모델 능력 문제인지 나눠 기록합니다.
  6. 모델과 사고 설정별 통과율, 토큰, 비용, 지연을 표로 비교해 고릅니다.
  • 보통 지능이 필요하면 Opus, 낮은 지연과 비용이 중요하면 Haiku, 균형이 필요하면 Sonnet을 씁니다.
  • 시연에서 Opus 4.7(사고 켬, 높은 effort)은 통과율이 가장 높았고 Sonnet보다 토큰과 지연도 적었지만 가장 비쌌습니다.
  • 시연에서 사고를 켠 Haiku는 사고를 켠 Sonnet과 비슷한 통과율을 보였습니다. 싼 모델도 꼭 같이 시험해 보세요.

2. effort로 생각량 조절하기

Claude는 답하기 전에 토큰을 더 쓸수록 어려운 문제를 더 잘 풉니다. 대신 비용과 대기 시간도 늘어납니다. effort 수준과 작업 예산(task budgets)으로 품질과 비용의 균형을 맞춥니다.

  1. 가능하면 생각(thinking)을 켜고 시작합니다.
  2. effort를 low, high, max처럼 단계별로 바꿔 같은 작업을 돌려 봅니다.
  3. 단계마다 출력 토큰, 걸린 시간, 결과 품질을 기록합니다.
  4. 평가 결과로 모델과 effort 조합별 곡선을 그려 비교합니다.
  5. 비용이나 시간 상한이 필요하면 task budget으로 토큰·시간·비용 한도를 정합니다.
  • 데모에서 low는 약 50초에 출력 약 4,600토큰이었습니다. high는 그 약 2배, max는 약 10배의 시간과 토큰을 썼습니다.
  • 고르기 어려우면 제품 기본값인 extra high를 권합니다. 특히 코딩 작업이 그렇습니다.
  • 지능이 필요한 작업이면 작은 모델의 effort를 올리기보다 큰 모델의 effort를 낮추는 편이 낫습니다.
  • 예전 방식: 도구 호출 사이에도 생각을 이어 가는 interleaved thinking을 썼습니다. 지금은 모델이 생각할 시점을 스스로 정하는 adaptive thinking으로 발전했습니다.

3. 평가 세트로 프롬프트 고치기

모델을 바꾼 뒤 기존 프롬프트 성능이 떨어졌거나 새 에이전트를 만들 때 쓰는 방법입니다. 평가 세트를 먼저 만들고 실패 유형을 하나씩 고칩니다. 감으로 고치는 것보다 확실합니다.

  1. 평범한 통제 사례, 까다로운 엣지 케이스, 사람에게 넘겨야 할 사례를 모아 평가 세트를 만듭니다.
  2. 프롬프트의 구조를 정리하고 원하는 출력 형식을 명시합니다.
  3. 평가 세트를 돌려 실패한 사례를 유형별로 묶습니다.
  4. 실패 유형을 하나씩 골라 프롬프트를 고치고 다시 평가합니다.
  5. 새 에이전트라면 하나의 큰 프롬프트 대신 생성·평가·수리 세 프롬프트로 나눕니다.
  6. 평가 프롬프트에 업무 조건을 넣어, 조건이 바뀌면 코드 대신 이 프롬프트만 고칩니다.
  • 성능이 떨어지는 원인은 두 가지입니다. 행동 차이는 프롬프트로 고칠 수 있지만, 능력 부족은 프롬프트로 해결되지 않으니 모델을 바꿔야 합니다.
  • 시연에서는 생성·평가·수리로 나눈 방식이 프롬프트 하나를 다듬은 방식보다 토큰과 지연이 적었습니다.

4. 도구 설명과 컨텍스트 아끼기

에이전트가 오래 일하면 도구 결과가 쌓여 컨텍스트가 무거워지고 비용이 늘어납니다. 도구 설명을 잘 쓰고 오래된 결과를 지우면 왕복과 토큰을 줄일 수 있습니다. Claude Code에서는 사용 현황을 눈으로 확인할 수도 있습니다.

  1. 도구 설명에 입력값과 함께 출력 형식도 적습니다. 예: ID, 제목, 스니펫, 점수.
  2. 몇 턴마다 오래된 도구 결과(스크린샷, 검색 결과, 파일 읽기)를 지우고 결정 사항만 남깁니다.
  3. Claude Code에서 /context를 실행해 컨텍스트 사용 현황을 색 격자로 확인합니다.
  4. Claude Code 설정에 도구 호출 전후 Hooks를 정의해 위험한 호출을 막거나 출력을 기록합니다.
예시
/context
  • 긴 작업용 에이전트에는 도구 검색, 프로그램 방식 도구 호출, 컴팩션(압축)이 컨텍스트 관리 수단으로 소개되었습니다.
  • 같은 앞부분을 반복해서 보내는 작업은 프롬프트 캐싱으로 비용을 줄입니다.
  • 모델 불안정을 메우려고 짠 코드는 몇 달이면 쓸모가 없어집니다. 내 데이터·도구·맥락을 연결하는 코드에 시간을 쓰세요.

5. Managed Agents 시작하기

Claude Managed Agents는 에이전트 실행에 필요한 인프라를 Anthropic이 맡아 주는 API 모음입니다. 호스팅, 샌드박스, 자격 증명 보관, 재시도, 관측이 여기에 들어갑니다. 에이전트 루프를 직접 만들지 않고 API 키만으로 장시간 작업을 맡길 수 있습니다.

  1. 에이전트를 정의합니다. 시스템 프롬프트, 모델, 스킬, 도구, 권한을 정합니다.
  2. 에이전트가 일할 환경을 만듭니다. 네트워크 허용 목록과 미리 설치할 패키지를 정합니다.
  3. 도구마다 자동 실행할지, 사람이 승인해야 실행할지 권한을 나눕니다.
  4. 세션을 시작해 작업을 맡깁니다. 필요하면 GitHub 저장소나 파일을 미리 불러옵니다.
  5. 이벤트 스트림을 구독해 에이전트가 무엇을 왜 하는지 지켜봅니다.
  6. 방향이 틀어지면 인터럽트 이벤트를 보내 바로잡습니다.
  7. 개발자 콘솔에서 세션 기록을 보며 에이전트를 디버깅하고 개선합니다.
  • 세션 하나가 컨테이너 하나에서 돌아가므로 티켓 여러 개를 병렬로 처리할 수 있습니다.
  • API 키 같은 자격 증명은 Vaults에 암호화해 두고 사용자·세션별로 관리합니다.
  • Cloudflare·Modal·Vercel 같은 자체 샌드박스나 자체 호스팅 환경도 연결할 수 있습니다.
  • 비용 조절 수단이 적고 처음 시작할 때 지연이 있습니다. 어려운 작업에 잘 맞고, 간단한 작업은 직접 만드는 쪽도 검토하세요.

6. Outcomes 루브릭으로 결과 검증하기

Outcomes는 에이전트에 '좋은 결과의 기준(루브릭)'을 주는 Managed Agents 기능입니다. 에이전트는 그 기준을 만족할 때까지 스스로 점검하며 반복합니다. 틀린 결과가 사용자에게 가면 안 되는 업무에 씁니다.

  1. 사용자에게 중요한 기준을 모두 적습니다.
  2. 객관적으로 확인되는 항목과 표시 방식·순서 같은 읽기 편의 항목을 함께 넣어 루브릭을 만듭니다.
  3. 루브릭과 최대 반복 횟수를 정해 에이전트에 넘깁니다.
  4. 작업 에이전트와 분리된 별도 컨텍스트의 채점기가 결과를 평가하게 합니다.
  5. 평가와 반복에 쓸 시간 여유를 둡니다. 예: 회의 24시간 전에 실행합니다.
  6. 기준을 끝내 통과하지 못하면 사용자에게 아무것도 보여 주지 않게 처리합니다.
예시
올바른 인물의 LinkedIn 프로필인지 확인할 것. 처음 읽는 사람도 쉽게 읽을 수 있을 것.
  • 틀린 정보를 보여 주는 것보다 아예 보여 주지 않는 편이 낫습니다.
  • 평가에서 나온 결과를 에이전트의 초기 루프에 반영하면 처음부터 더 정확해집니다.
  • 막히면 더 똑똑한 모델에 묻는 advisor 전략이나, 한 에이전트가 낸 안을 다른 에이전트가 반박하는 방식도 함께 쓸 수 있습니다.
  • Outcomes는 신청서로 조기 접근을 요청하는 연구 프리뷰로 소개되었습니다.

7. 메모리 스토어로 기억 남기기

에이전트는 원래 세션이 끝나면 배운 것을 잊습니다. 메모리 스토어는 세션에 파일 시스템처럼 붙어, 에이전트가 여러 세션에 걸쳐 내용을 읽고 쓰게 해 줍니다. 사용자별·팀별로 쌓이는 업무 지식을 남길 때 씁니다.

  1. CLI로 메모리 스토어를 만들고 name과 간단한 설명을 지정합니다.
  2. 콘솔의 manage agents → memory stores에서 상태가 active인지 확인합니다.
  3. 세션을 만들 때 요청에 메모리 스토어 ID를 리소스로 넘깁니다.
  4. 필요하면 prompt 값으로 무엇을 기억할지 에이전트에게 알려 줍니다.
  5. access 필드로 권한을 정합니다. 기본값은 읽기·쓰기이고 읽기 전용으로 바꿀 수 있습니다.
  6. 한 세션에서 새 정보를 알려 준 뒤, 새 세션에서 같은 내용을 물어 기억하는지 확인합니다.
  • 메모리 스토어는 사용자별·작업공간별처럼 원하는 단위로 여러 개 만들 수 있습니다.
  • 여러 에이전트가 한 저장소를 함께 써도 됩니다. 쓰기가 부딪히는 일은 낙관적 동시성 제어로 막아 줍니다.
  • 버전 기록, diff, 작성한 에이전트 표시, 내보내기·삭제를 지원하고 콘솔에서 직접 열어 고칠 수 있습니다.
  • 메모리는 Managed Agents에서 공개 베타로 출시되었습니다.

8. 드리밍으로 메모리 정리하기

메모리가 계속 쌓이면 중복되거나 낡은 정보가 남습니다. 드리밍은 세션 사이에 과거 대화 기록을 분석하는 백그라운드 작업입니다. 중복을 합치고 낡은 항목을 지우며 반복되는 실수 패턴을 메모리에 반영합니다.

  1. 콘솔에서 메모리 저장소를 열어 채워진 파일을 확인합니다.
  2. Dreams 탭으로 이동합니다.
  3. 드림을 시작하고 대상 메모리 저장소를 고릅니다.
  4. 분석할 세션을 고릅니다. 데모에서는 최근 7일 중 약 5개를 골랐습니다.
  5. Start dreaming으로 실행합니다.
  6. 진행 중인 드림을 열어 입력 세션과 만들어지는 출력 메모리 저장소를 확인합니다.
  7. 완료 후 메모리 저장소 변경 diff를 검토합니다.
  • API로도 실행할 수 있어 매시간, 매일 밤, 세션 종료 때 등으로 자동화할 수 있습니다.
  • 드리밍은 연구 프리뷰 단계이고 Managed Agents와 함께 씁니다.
  • 토큰을 많이 쓰지만 대부분 캐시되어 캐시 적중률이 약 95%로 예상된다고 합니다.

9. 업무 노하우를 스킬로 만들기

잘하는 사람의 방식이나 과거 작업 기록을 스킬로 만들어 에이전트에 붙이는 방법입니다. 교정, 보고서 작성처럼 사내 기준이 있는 반복 업무에 쓰면 결과 품질이 그 기준에 가까워집니다. 사람이 고친 내용을 계속 반영하면 스킬도 점점 좋아집니다.

  1. 과거 수정 이력이나 잘된 결과물처럼 기준이 되는 자료를 모읍니다.
  2. 자료에서 반복되는 규칙을 마크다운 문서로 정리해 스킬을 만듭니다.
  3. 에이전트를 정의할 때 이 스킬을 붙입니다.
  4. 에이전트가 결과물에 바로 쓰지 않고 제안 수정으로 달게 해 사람이 검토합니다.
  5. 사람이 추가로 고친 부분을 추적해 스킬에 다시 반영합니다.
  • Every는 편집장의 과거 수정 3만 건으로 교정 스킬을 만들었습니다.
  • AirOps는 스킬을 마케터에게 익숙한 문서 형태(Playbooks)로 바꿔 협업과 버전 관리를 쉽게 했습니다.
  • 공개된 Slack 채널에서 에이전트에게 요청하면 잘 쓰는 사람의 방식이 동료에게 자연스럽게 퍼집니다.
