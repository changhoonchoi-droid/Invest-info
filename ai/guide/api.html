API·개발자 플랫폼

이 분야에서는 Claude API와 Agent SDK, Claude Managed Agents로 업무용 에이전트를 만들고, 비용과 컨텍스트를 관리하며, 결과 품질을 평가하는 방법을 다룹니다. 처음이라면 먼저 비용을 줄이는 프롬프트 캐싱과 '어떤 방식으로 만들지' 고르는 가이드를 보세요. 그다음 스킬과 평가(evals)로 품질을 끌어올리고, 마지막으로 Outcomes 검증과 긴 작업용 컨텍스트 관리로 넘어가면 됩니다.

1. 프롬프트 캐싱으로 API 비용 줄이기

프롬프트 캐싱은 요청마다 반복해서 보내는 긴 내용을 캐시에 저장해 두고 다시 쓰는 방식으로 Claude 플랫폼 비용을 줄이는 기능입니다. 같은 지침이나 자료를 붙여 여러 번 호출하는 업무 자동화나 에이전트에 특히 효과가 큽니다.

  1. 지금 만들고 있는 API 호출에서 매번 똑같이 들어가는 부분(긴 지침, 참고 문서, 도구 설명 등)을 표시합니다.
  2. 매번 바뀌는 부분(사용자 질문, 오늘 날짜 등)과 바뀌지 않는 부분을 나눕니다.
  3. 바뀌지 않는 부분을 프롬프트 앞쪽에 모읍니다.
  4. Claude 플랫폼 공식 문서의 프롬프트 캐싱 안내에 따라 반복되는 부분에 캐싱을 적용합니다.
  5. 적용 전과 후의 비용을 비교해 실제로 줄었는지 확인합니다.
  • 원본 세션은 자막이 없어 제목·설명·챕터만 확인된 상태입니다. 정확한 설정 방법은 공식 문서에서 확인하세요.
  • 반복되는 내용이 길고 호출 횟수가 많을수록 절감 효과가 커집니다.

2. Managed Agents와 직접 구축 중 고르기

에이전트를 만들 때 Claude Managed Agents를 쓸지, Agent SDK 등으로 직접 만들지 정하는 기준입니다. 빨리 첫 버전을 내야 하는지, 비용과 응답 속도가 얼마나 중요한지에 따라 선택이 달라집니다.

  1. 에이전트에게 맡길 업무를 한 문장으로 적습니다. 예: 회의 전 브리프 작성, 계정 간 영업 보고.
  2. 그 업무가 여러 단계에 걸친 어려운 작업인지, 단순 반복 작업인지 구분합니다.
  3. 어려운 작업이고 빨리 만들어야 한다면 Managed Agents로 첫 버전을 만들어 봅니다.
  4. 비용 조절이 중요하거나 즉시 응답해야 하는 업무라면 Agent SDK 등으로 직접 만드는 것을 검토합니다.
  5. 직접 만든다면 코드 규칙, 도구 연결 방식 같은 팀 표준과 가드레일을 먼저 정해 에이전트에게 똑같이 적용합니다.
  • Wispr는 회의 어시스턴트 첫 버전을 하루 만에, Actively는 영업 보고 에이전트 Watchtower를 2주 만에 Managed Agents로 만들었습니다.
  • 창업자들은 Managed Agents에 비용을 줄일 수단이 적고 콜드 스타트 지연이 있다는 점을 단점으로 꼽았습니다. 유연/배치 모드가 생기면 50% 정도 절감할 수 있겠다는 의견도 있었습니다.
  • Spotify는 Agent SDK로 백그라운드 코딩 에이전트 Honk를 만들어 사내 도구에 연결했습니다. 더 단단한 가드레일은 제약이 아니라 속도를 높여 준다고 말합니다.

3. 과거 작업 기록으로 스킬 만들기

사람이 그동안 해 온 수정이나 판단 기록을 모아 에이전트가 쓸 스킬로 만드는 방법입니다. 교정, 검토처럼 잘하는 사람의 노하우가 중요한 업무를 에이전트에게 맡길 때 씁니다.

  1. 맡기려는 업무에서 잘하는 사람의 과거 작업 기록(수정 내역, 피드백 등)을 모읍니다.
  2. 모은 기록을 바탕으로 그 사람의 기준과 방식을 담은 스킬을 만듭니다.
  3. 에이전트가 스킬을 써서 결과물에 바로 고치지 않고 '제안 수정'으로 달게 합니다.
  4. 사람이 에이전트 제안에 더 손댄 부분을 추적합니다.
  5. 추적한 수정을 다시 스킬에 반영해 계속 개선합니다.
  • Every는 편집장의 과거 수정 3만 건으로 교정 스킬을 만들어 Google Docs에 제안 수정을 달고 있습니다.
  • 에이전트를 공개된 Slack 채널에서 쓰면, 잘 쓰는 동료의 프롬프트를 다른 사람들이 보고 따라 배울 수 있습니다.
  • Every는 에이전트를 쓸수록 할 일이 오히려 늘었다고 말합니다. 시간이 남는다기보다 할 수 있는 일이 넓어진다고 생각하세요.

4. 평가(evals)로 모델 변경 점검하기

평가(evals)는 정해 둔 문제 세트로 모델이나 에이전트의 성능을 재는 방법입니다. 새 모델이 나오거나 프롬프트·도구를 바꿀 때 품질이 좋아졌는지 나빠졌는지 확인하는 데 씁니다.

  1. 에이전트가 실제로 처리하는 대표 업무 사례를 모아 평가용 문제 세트를 만듭니다.
  2. 사례마다 '좋은 결과'의 기준을 적어 둡니다.
  3. 지금 쓰는 모델과 설정으로 평가를 돌려 기준 점수를 기록합니다.
  4. 새 모델이 나오거나 설정을 바꾸면 같은 평가를 다시 돌립니다.
  5. 점수를 비교해 평가를 통과했을 때만 실제 서비스에 반영합니다.
  6. 사용자가 막혔던 사례를 찾아 평가 세트에 계속 추가합니다.
  • Lovable은 모든 모델 출시를 반드시 평가 루프에 통과시킵니다.
  • 모델 능력은 빠르게 좋아지므로, 평가 결과를 보고 워크플로도 계속 조정해야 합니다.
  • 참고 세션들은 자막이 없어 제목·설명·챕터 기준으로 정리했습니다.

5. Outcomes 루브릭으로 결과 검증하기

Outcomes는 Claude Managed Agents에 루브릭(채점 기준)을 주고, 기준을 만족할 때까지 에이전트가 반복 작업하게 하는 기능입니다. 틀린 정보가 사용자에게 나가면 곤란한 업무, 예를 들어 회의 전 인물 브리프에 씁니다.

  1. 사용자에게 중요한 기준을 모두 적습니다. 예: 올바른 인물의 LinkedIn인지, 읽기 쉬운지.
  2. 그 기준을 에이전트에게 줄 루브릭으로 정리합니다.
  3. 사실 확인처럼 객관적으로 따질 수 있는 항목과 표시 방식·순서 같은 UX 항목을 함께 넣습니다.
  4. 에이전트가 루브릭을 만족할 때까지 반복 작업하도록 설정합니다.
  5. 작업 에이전트와 분리된, 독립 컨텍스트의 검증 에이전트가 결과를 평가하게 합니다.
  6. 회의 24시간 전처럼 시간 여유를 두고 실행해 평가와 반복에 쓸 시간을 확보합니다.
  7. 기준을 통과하지 못한 결과는 사용자에게 보여 주지 않도록 처리합니다.
예시
다음 루브릭을 모두 만족할 때까지 회의 상대 브리프를 다시 작성하세요. 1) 링크한 LinkedIn 프로필이 회의 상대 본인의 것인지 회사명과 직함으로 확인한다. 2) 핵심 정보는 맨 앞 3줄에 둔다. 3) 한 화면 안에서 읽을 수 있는 길이로 쓴다. 기준을 하나라도 만족하지 못하면 결과를 내지 말고 실패 이유만 남기세요.
  • 틀린 정보를 보여 주는 것보다 아예 보여 주지 않는 편이 낫습니다.
  • 평가 결과를 에이전트의 초기 작업 루프에 반영하면 처음부터 더 정확해집니다.

6. 긴 작업 에이전트 컨텍스트 줄이기

오래 실행되는 에이전트는 대화와 도구 결과가 쌓여 컨텍스트가 무거워집니다. 도구 검색, 프로그램 방식 도구 호출, 컴팩션으로 컨텍스트를 가볍게 유지하면 비용을 아끼고 성능 저하를 막을 수 있습니다.

  1. 에이전트가 쓰는 도구 목록과 한 번 실행할 때 쌓이는 컨텍스트 양을 점검합니다.
  2. 도구가 많다면 필요한 도구만 그때그때 찾아 쓰는 도구 검색을 적용합니다.
  3. 도구를 여러 번 연달아 부르는 작업은 프로그램 방식 도구 호출로 묶어 중간 결과가 컨텍스트에 덜 쌓이게 합니다.
  4. 작업이 길어지면 컴팩션으로 지난 내용을 요약해 컨텍스트를 줄입니다.
  5. 적용 전과 후의 비용과 결과 품질을 평가로 비교합니다.
  • 원본 세션은 자막이 없어 기능 이름만 확인됐습니다. 정확한 사용법은 Claude 플랫폼 공식 문서에서 확인하세요.
  • 같은 세션에서는 적은 비용으로 지능을 높이는 어드바이저 전략도 소개했습니다.
  • Omni는 멀티 에이전트 시스템에서 도구를 설계하고 크기를 조절하는 일을 중요하게 다뤘습니다.
