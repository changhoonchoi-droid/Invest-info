1. 내 용도에 맞는 모델 고르기

Opus·Sonnet·Haiku 가운데 내 업무에 맞는 모델을 고르는 방법입니다. 공개 벤치마크는 방향만 알려 주므로, 내 작업으로 만든 작은 평가(eval)로 품질·지연·비용을 직접 비교합니다. 새 모델이 나올 때마다 같은 절차를 반복하면 됩니다.

  1. 모델 선택 기준을 품질, 지연(응답 속도), 비용 세 축으로 정합니다.
  2. 실제 업무에서 자주 하는 작업 몇 개를 골라 작은 평가 세트를 만듭니다.
  3. 최종 결과뿐 아니라 그 결과에 이른 과정도 점검 항목에 넣습니다.
  4. Opus·Sonnet·Haiku를 사고(thinking) 켬/끔, effort 설정별로 같은 평가 세트에 돌립니다.
  5. 같은 작업을 여러 번 돌려, 인프라 실패와 모델 실패를 구분합니다.
  6. 조합별 통과율, 토큰, 비용, 지연을 표로 비교해 고릅니다.
  • 일반적으로 지능이 필요하면 Opus, 낮은 지연·비용은 Haiku, 균형은 Sonnet입니다.
  • 시연에서 Opus 4.7(사고 켬, 높은 effort)은 통과율이 가장 높고 Sonnet보다 토큰·지연이 적었지만 가장 비쌌습니다.
  • 사고를 켠 Haiku가 사고를 켠 Sonnet과 비슷한 통과율을 보인 경우도 있으니, 직접 재 보는 것이 중요합니다.

2. effort로 생각량 조절하기

Claude는 답하기 전에 토큰을 더 쓸수록 어려운 문제를 더 잘 풉니다. effort 수준(low~max)과 작업 예산(task budgets)으로 생각량과 비용·시간의 균형을 맞춥니다. 같은 작업도 effort에 따라 품질과 대기 시간이 크게 달라집니다.

  1. 가능하면 생각(thinking)을 켭니다.
  2. effort를 low에서 max 사이에서 정합니다.
  3. 같은 작업을 low, high, max로 돌려 결과와 토큰·시간을 비교합니다.
  4. 토큰·시간·비용 상한이 필요하면 task budgets로 예산을 정합니다.
  5. 평가(eval) 곡선을 그려 모델과 effort 조합 가운데 가장 균형이 좋은 것을 고릅니다.
  • 데모에서 low는 약 50초·출력 약 4,600 토큰, high는 그 약 2배, max는 약 10배가 들었습니다.
  • 고르기 어렵다면 extra high(제품 기본값)를 권장합니다. 특히 코딩 작업에 그렇습니다.
  • 지능이 필요한 작업은 effort를 낮추더라도 큰 모델을 쓰는 편이 낫습니다.
  • 예전 방식: 도구 호출 뒤에도 생각을 이어 가는 interleaved thinking → 지금은 모델이 생각할 시점을 스스로 정하는 adaptive thinking입니다.

3. 평가 세트로 프롬프트 고치기

모델을 바꾼 뒤 성능이 떨어졌거나 새 에이전트를 만들 때, 감으로 고치지 않고 평가 세트를 기준으로 프롬프트를 개선하는 방법입니다. 실패 유형을 하나씩 잡아 나가며, 필요하면 프롬프트를 생성·평가·수리 세 개로 나눕니다.

  1. 정상 처리되어야 할 통제 사례, 엣지 케이스, 사람에게 넘겨야 할 사례로 평가 세트를 만듭니다.
  2. 기존 프롬프트의 구조를 정리하고 출력 형식을 분명히 적습니다.
  3. 평가 세트를 돌려 실패한 사례를 유형별로 묶습니다.
  4. 실패 원인이 행동 차이(프롬프트로 조정 가능)인지 능력 부족(프롬프트로 해결 불가)인지 가립니다.
  5. 행동 차이로 생긴 실패 유형을 하나씩 프롬프트에서 고치고 다시 평가합니다.
  6. 새 에이전트라면 큰 프롬프트 하나 대신 생성·평가·수리 세 프롬프트로 나눕니다.
  7. 평가 프롬프트에 런타임 조건을 넣어, 코드를 고치지 않고도 기준을 바꿉니다.
  • 능력 부족이 원인이면 프롬프트를 아무리 고쳐도 안 되므로 모델이나 effort를 바꿉니다.
  • 시연에서는 생성·평가·수리 방식이 개선한 단일 프롬프트보다 토큰과 지연이 적으면서 모든 테스트를 통과했습니다.

4. 도구 설명과 컨텍스트 가볍게 하기

에이전트가 도구를 많이 쓰고 오래 일하면 컨텍스트가 금방 차고 비용이 늘어납니다. 도구 설명을 잘 쓰고, 오래된 도구 결과를 지우고, 사용 현황을 확인해 컨텍스트를 가볍게 유지합니다.

  1. 도구 설명에 입력뿐 아니라 출력 스키마(예: ID, 제목, 스니펫, 점수)도 적어 왕복 호출을 줄입니다.
  2. N턴마다 오래된 도구 결과(스크린샷, 검색 결과, 파일 읽기)를 지우고 내린 결정만 남깁니다.
  3. Claude Code에서 /context를 실행해 컨텍스트 사용 현황을 색 격자로 확인합니다.
  4. Claude Code 설정에 도구 호출 전후 Hooks를 정의해 위험한 호출을 막거나 출력을 기록합니다.
  5. 긴 작업에는 도구 검색, 프로그램 방식 도구 호출, 컴팩션(압축)을 함께 검토합니다.
예시
/context
  • 모델의 불안정을 보완하는 코드는 몇 달이면 쓸모가 없어지지만, 내 데이터·도구·맥락을 연결하는 코드는 계속 쌓입니다.
  • 도구 라우팅·재시도, 컨텍스트 관리, 코드 실행은 점점 모델과 API 안으로 들어오고 있습니다(100만 토큰 컨텍스트, 서버 측 압축·컨텍스트 편집, 호스팅 샌드박스).
  • 프롬프트 캐싱은 비용을 줄이는 핵심 수단으로 소개되었습니다.

5. Managed Agents 시작하기

Claude Managed Agents는 에이전트 루프, 호스팅, 샌드박스, 관측을 Anthropic이 맡아 주는 API 모음입니다. 에이전트 루프를 직접 만들지 않고 에이전트·환경·세션만 정의하면, Claude가 격리된 컨테이너에서 파일 시스템·bash·웹 검색으로 작업합니다.

  1. 에이전트(두뇌)를 정의합니다: 시스템 프롬프트, 모델, 스킬, 도구, 권한.
  2. 환경(손)을 만듭니다: 네트워크 허용 목록, 미리 설치할 패키지.
  3. 필요하면 세션을 만들 때 GitHub 저장소나 파일을 미리 불러오도록 지정합니다.
  4. 세션을 시작해 에이전트에게 작업을 맡깁니다.
  5. 이벤트 스트림을 구독해 에이전트가 무엇을 왜 하는지 관찰합니다.
  6. 잘못된 방향으로 가면 인터럽트 이벤트를 보내 바로잡습니다.
  7. 개발자 콘솔에서 실행 중인 에이전트를 실시간으로 디버깅합니다.
  • 이벤트는 사용자·에이전트·세션·구간(span) 네 종류입니다.
  • 세션 하나가 컨테이너 하나에서 돌기 때문에 여러 작업을 동시에 병렬로 처리할 수 있습니다.
  • Cloudflare·Modal·Vercel 같은 자체 샌드박스나 자체 호스팅 환경도 연결할 수 있습니다.
  • 예전 방식: Messages API나 Agent SDK로 에이전트 루프·파일 관리·코드 실행을 직접 구현 → 지금은 Managed Agents가 이 계층을 맡습니다.

6. 도구 권한과 사람 승인 설정하기

에이전트가 실제 업무 시스템을 건드릴 때, 도구마다 자동 실행할지 사람 승인을 받을지 나눠 안전하게 운영하는 방법입니다. 자격 증명은 에이전트와 분리된 저장소에 두어 보안을 높입니다.

  1. 에이전트가 쓸 도구 목록을 정리합니다.
  2. 읽기처럼 위험이 낮은 도구는 자동 실행으로 설정합니다.
  3. 외부 발송·수정처럼 되돌리기 어려운 도구는 명시적 승인(human-in-the-loop)으로 설정합니다.
  4. 자격 증명은 Vaults에 암호화해 두고 사용자·세션별로 관리합니다.
  5. 실행 중 승인 요청이 오면 사용자 이벤트의 승인 확인으로 응답합니다.
  • 두뇌(에이전트)와 손(환경)을 분리한 설계 덕분에 자격 증명 보안이 강화됩니다.
  • 에이전트가 필요한 권한을 사람에게 요청해 승인받는 방식으로 발전할 것으로 소개되었습니다.

7. 에이전트에 메모리 스토어 붙이기

에이전트는 세션이 끝나면 배운 내용을 잊습니다. 메모리 스토어를 세션에 파일 시스템처럼 마운트하면 에이전트가 여러 세션에 걸쳐 기억을 읽고 씁니다. 사용자별·팀별로 기억을 나눠 둘 수 있습니다.

  1. CLI로 메모리 스토어를 만들고 name과 간단한 설명을 지정합니다.
  2. 콘솔의 manage agents → memory stores에서 상태가 active이고 파일 시스템 뷰어가 비어 있는지 확인합니다.
  3. 세션을 만들 때 요청에 메모리 스토어 ID를 리소스로 넘깁니다.
  4. 필요하면 prompt 값으로 무엇을 기억할지 에이전트를 유도합니다.
  5. access 필드로 권한을 정합니다(기본값 읽기·쓰기, 읽기 전용으로 변경 가능).
  6. 세션에 새 정보를 담은 메시지를 보냅니다.
  7. 다른 새 세션에서 같은 내용을 물어 기억하는지 확인합니다.
  • 메모리 스토어는 사용자별·작업공간별 등 원하는 경계로 여러 개 만들 수 있습니다.
  • 여러 에이전트가 한 저장소를 공유할 때는 읽기 전용·읽기쓰기로 범위를 나누고, 쓰기 충돌은 낙관적 동시성 제어가 막습니다.
  • 메모리는 버전 기록, diff, 작성 에이전트 표시, 내보내기·삭제를 지원하며 콘솔에서 직접 열어 고칠 수 있습니다.
  • 예전 방식: 4월에는 제한된 연구 프리뷰(신청 필요) → 5월부터 공개 베타입니다.

8. 드리밍으로 메모리 정리하기

메모리가 계속 쌓이면 중복되고 낡은 정보가 남습니다. 드리밍은 과거 세션 기록을 분석해 중복을 합치고 낡은 항목을 지우며, 반복되는 실수 패턴을 찾아 메모리를 보강하는 백그라운드 작업입니다.

  1. 콘솔에서 메모리 저장소를 열어 채워진 파일을 확인합니다.
  2. Dreams 탭으로 이동합니다.
  3. 드림을 시작하고 대상 메모리 저장소를 고릅니다.
  4. 분석할 세션을 고릅니다(데모에서는 최근 7일 중 약 5개).
  5. Start dreaming으로 실행합니다.
  6. 진행 중인 드림을 열어 입력 세션과 만들어지는 출력 메모리 저장소를 확인합니다.
  7. 완료 후 메모리 저장소의 변경 diff를 검토합니다.
  • API로도 실행할 수 있어 수동·매시간·매일 밤·세션 종료 시점 등으로 자동화할 수 있습니다.
  • 드리밍은 연구 프리뷰 단계이며 Managed Agents와 함께 씁니다.
  • 토큰을 많이 쓰지만 대부분 캐시되어 약 95% 캐시 적중률이 예상된다고 합니다.

9. Outcomes 루브릭으로 결과 검증하기

Outcomes는 에이전트에 '좋은 결과의 기준(루브릭)'을 주고, 별도 채점기가 통과라고 판단할 때까지 고쳐서 다시 내게 하는 기능입니다. 틀린 결과를 사용자에게 보여 주는 일을 줄여 업무 품질을 높입니다.

  1. 사용자에게 중요한 기준을 모두 나열합니다(예: 올바른 인물의 LinkedIn인지, 읽기 쉬운지).
  2. 객관적으로 확인되는 항목과 표시 방식·순서 같은 UX 항목을 함께 넣어 루브릭을 만듭니다.
  3. 루브릭과 반복 시도 횟수를 정해 에이전트에 줍니다.
  4. 작업 에이전트와 분리된 독립 컨텍스트의 채점기가 결과를 평가하게 합니다.
  5. 채점 피드백을 받아 에이전트가 수정·재제출하며 기준을 만족할 때까지 반복하게 합니다.
  6. 회의 24시간 전처럼 시간 여유를 두고 실행해 평가·반복 시간을 확보합니다.
  7. 끝내 기준을 통과하지 못하면 사용자에게 아무것도 보여 주지 않도록 처리합니다.
예시
다음 기준을 모두 만족해야 통과입니다. 1) 회의 참석자의 LinkedIn 프로필이 정확히 그 사람의 것인가 2) 핵심 내용이 맨 위에 오고 한 화면에 읽기 쉬운가 3) 출처를 확인할 수 없는 정보는 넣지 않았는가
  • 틀린 정보를 보여 주는 것보다 아예 보여 주지 않는 편이 낫습니다.
  • 평가 결과를 에이전트의 초기 루프에 반영하면 처음부터 더 정확해집니다.
  • 막히면 더 똑똑한 모델에 묻는 advisor 전략, 한 에이전트가 내고 다른 에이전트가 반박하는 방식도 함께 쓸 수 있습니다.
  • 예전 방식: 4월에는 제한된 연구 프리뷰로 신청서를 내야 쓸 수 있었습니다.

10. 배포 전후 에이전트 평가 루프 돌리기

에이전트를 서비스로 운영하려면 모델이나 프롬프트를 바꿀 때마다 품질을 확인하는 평가 루프가 필요합니다. 배포 전에는 실제 사용 사례 벤치마크를 관문으로, 배포 후에는 실사용 기록 분석으로 문제를 찾아 계속 개선합니다.

  1. 실제 사용 사례에서 대표 작업을 뽑아 자연어 명세(PRD) 형태의 평가 입력을 만듭니다.
  2. 평가자 에이전트가 결과물을 직접 열어 보고 자연어 테스트 계획을 단계별로 수행해 채점하게 합니다.
  3. 모델·프롬프트를 바꿀 때마다 이 오프라인 벤치마크를 통과해야 배포하도록 관문을 둡니다.
  4. 배포 후에는 A/B 테스트로 변경 효과를 비교합니다.
  5. 실행 기록(트레이스)을 비슷한 것끼리 묶어 반복되는 문제를 찾아 고칩니다.
  • Replit은 실제 사용 사례 20개 PRD로 앱을 처음부터 만들고 AI 평가자가 브라우저로 눌러 보며 채점하는 ViBench를 만들었습니다.
  • Lovable은 모든 모델 출시를 평가 루프에 통과시킨 뒤 적용합니다.
  • 숫자만 보지 말고 사용자층을 이해하는 사람의 안목으로 결과를 함께 검토합니다.
