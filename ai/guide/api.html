1. 내 용도에 맞는 모델 고르기

Opus·Sonnet·Haiku 가운데 내 업무에 가장 알맞은 모델을 고르는 절차입니다. 새 모델이 나올 때마다 같은 절차를 반복하면 감이 아니라 내 데이터로 판단할 수 있습니다.

  1. 품질·지연(응답 속도)·비용 세 가지 중 내 업무에서 무엇이 가장 중요한지 정합니다.
  2. 일반 원칙으로 후보를 좁힙니다: 지능이 필요하면 Opus, 낮은 지연·비용은 Haiku, 균형은 Sonnet.
  3. 실제 업무에서 뽑은 작은 평가(eval) 세트를 직접 만듭니다.
  4. 최종 결과뿐 아니라 답에 이르는 과정도 점검 항목에 넣습니다.
  5. 같은 작업을 여러 번 돌려 인프라 실패와 모델 실패를 구분합니다.
  6. 모델과 사고(thinking) 설정별로 통과율·토큰·비용·지연을 표로 비교해 고릅니다.
  • 공개 벤치마크는 방향만 알려 줍니다. 작은 평가라도 직접 만드는 것이 더 중요합니다.
  • 시연에서는 사고를 켠 Haiku가 사고를 켠 Sonnet과 비슷한 통과율을 보였습니다. 작은 모델도 설정에 따라 충분할 수 있습니다.
  • Opus 4.7(사고 켬, 높은 effort)은 통과율이 가장 높고 토큰·지연도 적었지만 가장 비쌌습니다.

2. effort로 생각량 조절하기

Claude는 답하기 전에 토큰을 더 많이 써서 생각할수록 어려운 문제를 더 잘 풉니다. effort 다이얼(low~max)이나 예산으로 생각량을 조절해 품질과 비용·시간의 균형을 맞출 때 씁니다.

  1. 가능하면 사고(thinking)를 켭니다.
  2. effort 값을 low·high·max 등으로 바꿔 가며 같은 작업을 돌려 봅니다.
  3. 결과 품질과 함께 출력 토큰 수·걸린 시간을 기록합니다.
  4. 평가(evals) 결과를 보고 업무에 맞는 effort를 정합니다.
  5. 작업 전체의 상한이 필요하면 task budget 같은 예산 방식으로 조절합니다.
  • 시연에서 high는 low의 약 2배, max는 약 10배의 토큰과 시간을 썼습니다.
  • 고민될 때는 제품 기본값인 extra high를 권합니다.
  • 지능이 필요한 작업은 effort를 낮추더라도 큰 모델을 쓰는 편이 낫습니다.
  • 예전 방식: 도구 호출 뒤에도 생각을 이어 가는 interleaved thinking → 지금은 모델이 생각할 시점을 스스로 정하는 adaptive thinking으로 발전했습니다.

3. 평가 세트로 프롬프트 고치기

모델을 바꾼 뒤 성능이 떨어진 기존 프롬프트를 체계적으로 고치는 방법입니다. 감으로 고치지 않고 평가 세트로 실패 유형을 찾아 하나씩 해결합니다.

  1. 평가 세트를 만듭니다: 통제 사례, 엣지 케이스, 사람에게 넘겨야 할 사례를 고루 넣습니다.
  2. 프롬프트 구조를 정리하고 원하는 출력 형식을 명시하는 기본 정리부터 합니다.
  3. 평가를 돌려 실패한 사례를 유형별로 묶습니다.
  4. 각 실패가 행동 차이(프롬프트로 조정 가능)인지 능력 부족(프롬프트로 해결 불가)인지 가립니다.
  5. 행동 차이에 해당하는 실패 유형을 하나씩 고치고 매번 평가를 다시 돌립니다.
  • 능력 부족이 원인이면 프롬프트를 아무리 고쳐도 안 됩니다. 모델이나 effort를 바꾸는 쪽을 검토하세요.
  • 한 번에 여러 곳을 고치지 말고 실패 유형 하나씩 고쳐야 무엇이 효과였는지 알 수 있습니다.

4. 생성·평가·수리 3단계로 나누기

에이전트를 처음 만들 때 하나의 큰 프롬프트 대신 생성·평가·수리 세 프롬프트로 나누는 방법입니다. 시연에서는 이 방식이 더 적은 토큰과 낮은 지연으로 모든 테스트를 통과했습니다.

  1. 먼저 평가 세트(통제 사례·엣지 케이스·사람에게 넘길 사례)를 준비합니다.
  2. 답을 만드는 생성 프롬프트를 씁니다.
  3. 생성된 답이 기준을 지키는지 판단하는 평가 프롬프트를 따로 씁니다.
  4. 평가에서 걸린 부분만 고치는 수리 프롬프트를 씁니다.
  5. 생성 → 평가 → 수리 순서로 돌리고, 평가 세트로 전체 통과 여부를 확인합니다.
  • 평가 프롬프트에 런타임 소프트 조건(그때그때 바뀌는 규칙)을 넣으면 코드를 고치지 않아도 됩니다.
  • 시연에서는 개선한 단일 프롬프트를 Sonnet 4.6에 쓴 것보다 토큰과 지연이 적었습니다.

5. 도구 설명·컨텍스트 아끼기

도구를 쓰는 에이전트가 오래 일하면 컨텍스트가 쌓여 비용이 늘고 성능이 떨어집니다. 도구 설명을 잘 쓰고 오래된 결과를 정리해 컨텍스트를 가볍게 유지하는 요령입니다.

  1. 도구 설명에 입력뿐 아니라 출력 스키마(예: ID, 제목, 스니펫, 점수)도 적어 왕복 호출을 줄입니다.
  2. N턴마다 오래된 도구 결과(스크린샷, 검색 결과, 파일 읽기)를 지우고 내린 결정만 남깁니다.
  3. Claude Code에서는 /context를 실행해 컨텍스트 사용 현황을 색 격자로 확인합니다.
  4. Claude Code 설정에 도구 호출 전후 Hooks를 정의해 위험한 호출을 막거나 출력을 기록합니다.
  5. 긴 작업에는 도구 검색, 프로그램 방식 도구 호출, 컴팩션(압축) 기능 활용을 검토합니다.
예시
/context
  • 모델 불안정을 보완하는 코드는 수명이 몇 달에 불과합니다. 내 데이터·도구·맥락을 연결하는 코드에 투자하세요.
  • 도구 라우팅·재시도, 컨텍스트 관리, 코드 실행은 이미 모델과 API 안으로 많이 옮겨 왔습니다(100만 토큰 컨텍스트, 서버 측 압축·컨텍스트 편집, 호스팅 샌드박스).
  • 비용 절감에는 프롬프트 캐싱을, 적은 비용으로 지능을 높이려면 막힐 때 더 똑똑한 모델에 묻는 어드바이저 전략을 함께 검토합니다.

6. Managed Agents 시작하기

Claude Managed Agents는 호스팅·확장·샌드박스·자격 증명 보관·관측을 Anthropic이 맡아 주는 에이전트 플랫폼입니다. 에이전트 루프를 직접 만들지 않고 API 키만으로 운영용 에이전트를 빠르게 띄울 때 씁니다.

  1. 에이전트를 정의합니다: 시스템 프롬프트, 모델, 스킬, 도구, 권한.
  2. 도구별로 자동 실행할지, 사용자 승인을 받을지 나눠 설정합니다.
  3. 에이전트가 실행될 환경을 만듭니다: 네트워크 허용 목록, 사전 설치 패키지.
  4. 세션을 시작해 작업을 맡깁니다. 필요하면 GitHub 저장소나 파일을 미리 불러옵니다.
  5. 이벤트 스트림을 구독해 에이전트가 무엇을 왜 하는지 관찰합니다.
  6. 방향이 틀리면 인터럽트 이벤트로 바로잡고, 개발자 콘솔에서 실시간으로 디버깅합니다.
  • 구성은 에이전트(두뇌·템플릿), 환경(손·샌드박스), 세션(둘을 연결한 진행 중 대화), 이벤트(스트림)입니다.
  • 두뇌와 손을 분리한 설계 덕분에 자격 증명은 Vaults에 암호화해 사용자·세션별로 관리되고, 첫 토큰까지 시간이 P95 기준 90% 이상 줄었습니다.
  • Cloudflare·Modal·Vercel 같은 자체 샌드박스나 자체 호스팅 환경도 연결할 수 있습니다.
  • 비용 조절 수단이 적고 콜드 스타트 지연이 있어, 쉬운 작업은 직접 만드는 편이 나을 수 있습니다.

7. Outcomes로 결과 검증하기

Outcomes는 에이전트에 좋은 결과의 기준(루브릭)을 주고, 그 기준을 만족할 때까지 스스로 점검하며 반복하게 하는 Managed Agents 기능입니다. 틀린 결과를 사용자에게 보여 주면 안 되는 업무에 씁니다.

  1. 사용자에게 중요한 기준을 모두 적습니다 (예: 올바른 인물의 LinkedIn인지, 읽기 쉬운지).
  2. 객관적으로 확인되는 항목과 표시 방식·순서 같은 UX 항목을 함께 넣어 루브릭을 만듭니다.
  3. 루브릭과 반복 시도 횟수를 정해 에이전트에 줍니다.
  4. 작업 에이전트와 분리된 독립 컨텍스트의 검증 에이전트가 결과를 평가하게 합니다.
  5. 회의 24시간 전처럼 여유 있게 실행해 평가·반복 시간을 확보합니다.
  6. 기준을 통과하지 못하면 사용자에게 아무것도 보여 주지 않도록 처리합니다.
예시
다음 기준을 모두 만족할 때까지 회의 전 브리프를 고쳐 주세요. 1) 참석자 LinkedIn이 정확히 그 인물의 것인지 확인했다 2) 3분 안에 읽을 수 있다 3) 핵심 안건이 맨 위에 있다.
  • 틀린 정보를 보여 주는 것보다 아예 보여 주지 않는 편이 낫습니다.
  • 평가 결과를 에이전트 초기 루프에 반영하면 처음부터 더 정확해집니다.
  • 여러 에이전트를 경쟁시키거나, 한 에이전트가 낸 아이디어를 다른 에이전트가 반박하게 하는 방식도 함께 쓸 수 있습니다.

8. 세션에 메모리 스토어 붙이기

에이전트는 세션이 끝나면 배운 것을 잊습니다. 메모리 스토어는 세션에 파일 시스템처럼 마운트되어, 에이전트가 여러 세션에 걸쳐 기억을 읽고 쓰게 해 줍니다.

  1. CLI로 메모리 스토어를 만들고 name(예: CWC memory)과 간단한 설명을 지정합니다.
  2. 콘솔의 manage agents → memory stores에서 상태가 active인지, 파일 시스템 뷰어가 비어 있는지 확인합니다.
  3. 세션을 만들 때 요청에 메모리 스토어 ID를 리소스로 넘깁니다.
  4. 필요하면 prompt 값으로 무엇을 기억할지 에이전트를 유도합니다.
  5. access 필드로 권한을 정합니다 (기본값 읽기·쓰기, 읽기 전용으로 변경 가능).
  6. 세션에 새 정보를 보낸 뒤, 다른 새 세션에서 같은 내용을 물어 기억하는지 확인합니다.
  • 메모리 스토어는 사용자별·작업공간별 등 원하는 경계로 여러 개 만들 수 있습니다.
  • 여러 에이전트가 같은 저장소를 읽기 전용·읽기/쓰기로 나눠 공유할 수 있고, 쓰기 충돌은 낙관적 동시성 제어로 막습니다.

9. 드리밍으로 메모리 정리하기

메모리가 쌓이면 중복·단편화·오래된 정보가 생깁니다. 드리밍은 세션 사이에 과거 대화 기록을 분석해 반복되는 실수를 찾고 메모리를 정리·보강하는 백그라운드 작업입니다.

  1. 콘솔에서 메모리 저장소를 열어 채워진 파일을 확인합니다.
  2. Dreams 탭으로 이동합니다.
  3. 드림을 시작하고 대상 메모리 저장소를 고릅니다.
  4. 분석할 세션을 고릅니다 (데모에서는 최근 7일 중 약 5개).
  5. Start dreaming으로 실행합니다.
  6. 진행 중인 드림을 열어 입력 세션과 만들어지는 출력 메모리 저장소를 확인합니다.
  7. 완료 후 메모리 저장소 변경 diff를 검토합니다.
  • API로도 실행할 수 있어 수동·매시간·매일 밤·세션 종료 이벤트 등으로 자동화할 수 있습니다.
  • 드리밍은 연구 프리뷰 단계이며 Managed Agents와 함께 씁니다.
  • 토큰을 많이 쓰지만 대부분 캐시되어 약 95% 캐시 적중률이 예상된다고 합니다.
  • Rakuten은 1차 오류가 97% 줄었고, Harvey는 법률 벤치마크 완료율이 6배 늘었다고 합니다.

10. 업무 노하우를 스킬로 만들기

잘하는 사람의 작업 방식이나 과거 수정 기록을 스킬(마크다운 문서)로 정리해 에이전트에 붙이는 방법입니다. 복잡한 워크플로 빌더 대신 문서 형태라 비개발자도 고치고 관리하기 쉽습니다.

  1. 사람이 해 온 작업 기록을 모읍니다 (예: 편집장의 과거 수정 기록).
  2. 기록에서 반복되는 기준과 방식을 마크다운 문서로 정리해 스킬을 만듭니다.
  3. 스킬을 에이전트에 붙여 실제 업무(예: Google Docs에 제안 수정 달기)를 맡깁니다.
  4. 에이전트 결과 위에 사람이 추가로 한 수정을 추적합니다.
  5. 추적한 수정을 스킬에 다시 반영해 계속 개선합니다.
  • Every는 편집장의 과거 수정 3만 건으로 교정 스킬을 만들었습니다.
  • AirOps는 스킬을 마케터에게 익숙한 문서 형태의 Playbooks로 만들어 협업·거버넌스·버전 관리를 지원했고, 한 고객은 1주 만에 가동했습니다.
  • 에이전트는 기존 업무 방식에 맞아야 쓰입니다. Slack처럼 팀이 이미 쓰는 곳에 두면 잘 쓰는 사람의 방식이 자연스럽게 퍼집니다.
