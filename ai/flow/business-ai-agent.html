맡길 업무와 확인 지점 정하기

Claude 앱

무엇을 맡길지와 어디서 사람이 확인할지를 먼저 정합니다. 권한은 넉넉히 주되 되돌리기 어려운 지점에만 확인을 두어야 내가 병목이 되지 않습니다.

따라 하기

  1. 팀에서 시간을 가장 많이 잡아먹는 업무 하나를 고릅니다(예: 회의 전 브리프).
  2. 매번 순서가 같은 반복 업무인지, 상황마다 단계가 달라지는 업무인지 나눕니다.
  3. 에이전트가 할 일 가운데 되돌리기 쉬운 일과 어려운 일을 나눕니다.
  4. 대외 발송이나 데이터 수정처럼 되돌리기 어려운 지점은 실행 전에 사람 확인을 받도록 정합니다.
  5. 한 번에 크게 나가는 비용에는 상한을 정하고, 폭주하면 멈출 장치를 계획합니다.
  • Shopify CTO는 프로세스가 폭주할 때 멈춰 세울 서킷 브레이커가 필요하다고 강조합니다.
  • 결과를 한꺼번에 내보내지 말고 조금씩 단계적으로 넓힙니다.

평가 세트 먼저 만들기

평가(eval)

평가는 '느낌'을 확인할 수 있는 숫자로 바꿔 줍니다. 에이전트를 만들기 전에 평가 세트를 먼저 두면, 한 곳을 고치다 다른 곳을 망가뜨리는 일을 막을 수 있습니다.

따라 하기

  1. 실제 업무에서 정상 사례, 까다로운 엣지 케이스, 사람에게 넘기거나 거절해야 할 사례를 모읍니다.
  2. 사례마다 입력과 성공 기준을 적습니다.
  3. 응답 품질은 LLM 심사로, 특정 도구 호출이나 값 확인은 코드 기반 평가로 채점하게 합니다.
  4. 최종 결과뿐 아니라 올바른 단계를 거쳤는지도 점검합니다.
  5. 같은 작업을 여러 번 돌려 인프라 실패와 모델 실패를 나눠 봅니다.
  • 결과 편차가 크면 작업 정의나 평가 기준이 불분명하다는 신호입니다.
  • LLM 심사도 틀릴 수 있으니 채점기를 여러 개 함께 씁니다.
  • 큰 프롬프트 하나보다 생성·평가·수리 세 프롬프트로 나누면 더 적은 토큰으로 모든 테스트를 통과한 사례가 있습니다.

업무 노하우를 스킬로 만들기

Skills

사람이 해 온 작업 방식을 마크다운 문서 형태의 스킬로 만들면 에이전트가 같은 방식으로 일합니다. 실무자에게 익숙한 문서 형태라 함께 고치고 버전을 관리하기 쉽습니다.

따라 하기

  1. 그 업무를 잘하는 사람이 남긴 과거 기록을 모읍니다(예: 편집장의 수정 내역).
  2. 기록에서 찾은 규칙과 작업 순서를 마크다운 파일로 정리해 스킬로 만듭니다.
  3. 스킬에는 해야 할 일 목록보다 어떻게 판단할지에 대한 원칙을 적습니다.
  4. 에이전트 결과를 사람이 추가로 고친 내용을 추적해 스킬에 다시 반영합니다.
  • 예전 방식: 노드 기반 워크플로 빌더로 절차를 그렸지만, 새 모델이 나올 때마다 고쳐야 해서 지금은 마크다운 파일과 스킬로 옮겨 가는 추세입니다.
  • AirOps는 스킬을 마케터용 Playbooks라는 문서 형태로 바꿔 기존 업무 방식에 맞췄습니다.

에이전트와 환경 정의하기

Claude Managed Agents

Managed Agents는 호스팅, 샌드박스, 자격 증명 보관, 재시도 같은 인프라를 Anthropic이 맡습니다. 에이전트·환경·세션·이벤트 네 가지만 알면 시작할 수 있습니다.

따라 하기

  1. Claude API 키를 준비하고 개발자 콘솔을 엽니다.
  2. 에이전트를 정의합니다. 시스템 프롬프트, 모델, 스킬, 도구, 권한을 정합니다.
  3. 에이전트가 일할 환경(샌드박스)을 만들고 네트워크 허용 목록과 미리 설치할 패키지를 지정합니다.
  4. 세션을 시작해 작업을 맡깁니다. 필요하면 GitHub 저장소나 파일을 미리 불러옵니다.
  5. 이벤트 스트림을 구독해 에이전트가 무엇을 왜 하는지 지켜보고, 방향이 틀어지면 인터럽트 이벤트로 바로잡습니다.
  • 비용 조절 수단이 적고 콜드 스타트 지연이 있어 어려운 작업에 잘 맞습니다. 그 밖의 작업은 직접 만드는 선택도 검토하라는 의견이 있습니다.
  • 예전 방식: Messages API나 Agent SDK로 에이전트 루프와 호스팅을 직접 만들었습니다. 지금은 루프가 서버 쪽에서 실행됩니다.

Claude Managed Agents

설계 단계에서 정한 확인 지점을 실제 설정으로 옮깁니다. 메일 발송이나 데이터 수정처럼 되돌리기 어려운 도구에는 사람 승인을 겁니다.

따라 하기

  1. 에이전트가 쓸 도구 목록을 정합니다.

  3. 되돌리기 어려운 도구에는 사람 확인(human-in-the-loop)을 겁니다.

  5. 외부 서비스 자격 증명은 Vaults에 저장해 사용자·세션별로 관리합니다.
  • Vaults는 자격 증명을 별도 저장소에 암호화해 보관합니다.
  • 에이전트(두뇌)와 환경(손)이 분리되어 있어 자격 증명이 더 안전합니다.

따라 하기

Outcomes로 결과 검증하기

Claude Managed Agents (Outcomes)

틀린 결과가 사용자에게 가면 안 되는 업무라면, 좋은 결과의 기준(루브릭)을 주고 기준을 만족할 때까지 에이전트가 스스로 점검하며 반복하게 합니다.

따라 하기

  1. 사용자 입장에서 중요한 기준을 모두 적어 루브릭으로 정리합니다.
  2. 객관적으로 확인할 수 있는 항목과 표시 방식·순서 같은 UX 항목을 함께 넣습니다.
  3. 루브릭과 반복 시도 횟수를 정해 outcome으로 넘깁니다.
  4. 작업 에이전트와 분리된 독립 컨텍스트의 검증 에이전트가 결과를 평가하게 합니다.
  5. 회의 24시간 전처럼 넉넉한 시점에 실행해 반복할 시간을 확보합니다.
  6. 기준을 통과하지 못한 결과는 사용자에게 보여 주지 않도록 처리합니다.
예시 프롬프트
다음 기준을 모두 만족할 때까지 회의 전 브리프를 다시 작성하세요. 1) 참석자의 LinkedIn 프로필이 올바른 인물인지 확인했다 2) 핵심 내용이 맨 위에 있고 읽기 쉽다 3) 확인되지 않은 정보는 넣지 않았다.
  • 틀린 정보를 보여 주는 것보다 아예 보여 주지 않는 편이 낫습니다.
  • 평가 결과를 에이전트의 초기 루프에 반영하면 처음부터 더 정확해집니다.

메모리 스토어 붙이기

Claude Managed Agents (Memory)

에이전트는 세션이 끝나면 배운 것을 잊습니다. 메모리 스토어를 세션에 마운트하면 여러 세션에 걸쳐 기억을 읽고 쓸 수 있습니다.

따라 하기

  1. CLI로 메모리 스토어를 만들고 name과 간단한 설명을 정합니다.
  2. 콘솔의 manage agents → memory stores에서 상태가 active인지 확인합니다.
  3. 세션을 만들 때 메모리 스토어 ID를 리소스로 넘깁니다.
  4. access 필드로 권한을 정합니다. 기본값은 읽기·쓰기이고 읽기 전용으로 바꿀 수 있습니다.
  5. 새 세션을 열어 이전 내용을 기억하는지 확인합니다.
  • 사용자별·작업공간별처럼 원하는 단위로 메모리 스토어를 여러 개 만들 수 있습니다.
  • 메모리는 버전 관리, diff, 내보내기·삭제를 지원하고 콘솔에서 직접 고칠 수도 있습니다.

드리밍으로 메모리 정리하기

Claude Managed Agents (Dreaming)

메모리를 오래 쓰면 중복되거나 오래된 정보가 남습니다. 드리밍은 과거 세션을 분석해 반복되는 실수를 찾고 메모리를 정리·보강하는 백그라운드 작업입니다.

따라 하기

  1. 콘솔에서 정리할 메모리 저장소를 열어 파일을 확인합니다.
  2. Dreams 탭으로 이동해 드림을 시작하고 대상 메모리 저장소를 고릅니다.
  3. 분석할 세션을 고릅니다.
  4. Start dreaming을 눌러 실행합니다.
  5. 완료되면 메모리 저장소의 변경 diff를 검토합니다.
  • 드리밍은 연구 프리뷰 단계입니다.
  • API로도 실행할 수 있어 매일 밤이나 세션 종료 시점 등으로 자동화할 수 있습니다.
  • 토큰을 많이 쓰지만 대부분 캐시되어 약 95% 캐시 적중률이 예상된다고 합니다.
