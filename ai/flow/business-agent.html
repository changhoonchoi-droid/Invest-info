맡길 업무와 구축 방식 정하기

Claude Managed Agents

에이전트에게 맡길 업무 하나를 정하고, 운영을 Managed Agents에 맡길지 Agent SDK로 직접 만들지 판단합니다. 작업 난이도, 응답 속도, 실행 횟수에 따른 비용이 기준입니다.

따라 하기

  1. 에이전트에게 맡길 업무 하나를 정합니다(예: 회의 전 브리프 작성, 영업 보고).
  2. 작업이 얼마나 어렵고 오래 걸리는지 적어 봅니다.
  3. 어렵고 오래 걸리는 작업이면 Managed Agents를 우선 검토합니다.
  4. 빠른 응답이 중요하면 콜드 스타트 지연이 문제가 되지 않는지 확인합니다.
  5. 실행 횟수가 많으면 비용을 미리 계산합니다.
  6. 자체 시스템과 가드레일에 깊이 붙여야 하면 Agent SDK로 직접 만드는 방법을 검토합니다.
  • 회의 어시스턴트 첫 버전을 하루 만에, 영업 보고 에이전트를 2주 만에 만든 사례가 있습니다.
  • 어려운 작업이 아니면 직접 만드는 편이 나을 수 있다는 창업자들의 의견도 있습니다.

에이전트·환경·세션 설계하기

Claude Managed Agents

Managed Agents는 에이전트(두뇌), 환경(손), 세션(둘을 연결) 세 자원으로 이뤄집니다. 에이전트 루프는 Anthropic 서버에서 돌고, 자격 증명은 Vaults에 따로 보관합니다.

따라 하기

  1. 에이전트에 모델, 시스템 프롬프트, 스킬, MCP 서버 구성을 정합니다.
  2. 에이전트가 실제로 작업할 샌드박스 환경을 준비합니다.
  3. 세션으로 에이전트와 환경을 연결해 작업을 시작합니다.
  4. API 키 같은 자격 증명은 Vaults에 저장해 사용자·세션별로 관리합니다.
  5. 에이전트가 행동할 때 필요한 권한은 사람에게 요청해 승인받도록 합니다.
  • 두뇌와 손을 분리한 구조라 자격 증명이 더 안전합니다.
  • API 키는 코드나 공유 문서에 직접 적지 않습니다.

업무 노하우를 스킬로 담기

Skills

잘하는 사람의 판단 기준과 과거 작업 기록을 스킬로 만들어 주면 에이전트가 그 방식대로 일합니다. 사람이 추가로 고친 내용을 다시 반영해 계속 개선합니다.

따라 하기

  1. 노하우를 옮길 업무와 기준이 되는 사람을 정합니다.
  2. 그 사람의 과거 수정과 작업 기록을 모읍니다.
  3. 판단 기준을 마크다운 문서 형태의 스킬로 만듭니다.
  4. 에이전트가 실제 문서에 수정 제안을 달게 합니다.
  5. 에이전트 제안 뒤에 사람이 추가로 고친 내용을 추적해 스킬에 다시 반영합니다.
  • 지침을 수정→검토→병합하는 방식으로 관리하면 팀의 판단이 에이전트에 쌓입니다.
  • 늘 필요하지 않은 지침은 스킬로 떼어 내 필요할 때만 불러오게 하면 컨텍스트가 가벼워집니다.

메모리 스토어 붙이기

Claude Console

에이전트는 세션마다 따로 동작해 앞에서 배운 내용을 잊습니다. 메모리 스토어를 세션에 붙이면 여러 세션에 걸쳐 같은 기억을 읽고 씁니다.

따라 하기

  1. CLI로 메모리 스토어를 만들고 name과 간단한 설명을 정합니다.
  2. 콘솔의 manage agents → memory stores에서 상태가 active인지 확인합니다.
  3. 세션을 만들 때 메모리 스토어 ID를 리소스로 넘깁니다.
  4. access 필드로 권한을 정합니다. 기본값은 읽기·쓰기입니다.
  5. 새 세션을 열고 같은 내용을 물어 기억하는지 확인합니다.
  • 메모리가 쌓이면 오래된 정보가 남습니다. 드리밍이 과거 세션 기록으로 사실 확인, 정리, 중복 제거를 합니다.
  • 읽기 전용으로 붙이면 에이전트가 메모리를 고칠 수 없습니다.

Outcomes로 결과 기준 정하기

Claude Managed Agents

Outcomes는 평가 기준(루브릭)과 반복 횟수를 정해 기준을 만족할 때까지 작업을 되풀이하게 합니다. 틀린 결과가 사용자에게 그대로 가면 안 되는 업무에 씁니다.

따라 하기

  1. 사용자에게 중요한 기준을 모두 나열합니다(예: 올바른 인물 정보인지, 읽기 쉬운지).
  2. 객관적 확인 항목과 표시 방식 같은 사용성 항목을 루브릭으로 정리합니다.
  3. 루브릭과 반복 시도 횟수를 정합니다.
  4. 작업 에이전트와 분리된 독립 컨텍스트의 검증 에이전트가 결과를 평가하게 합니다.
  5. 회의 24시간 전처럼 시간을 넉넉히 두고 실행합니다.
  6. 기준을 통과하지 못한 결과는 사용자에게 보여 주지 않도록 처리합니다.
  • 틀린 정보를 보여 주는 것보다 아예 보여 주지 않는 편이 낫습니다.

평가 세트로 품질 재기

Evals

평가는 '좀 이상한데' 같은 느낌을 숫자로 바꿔 줍니다. 수정이나 모델 교체가 다른 곳을 망가뜨리지 않았는지 확인하는 근거가 됩니다.

따라 하기

  1. 좋은 결과의 성공 기준을 먼저 글로 정합니다.
  2. 공개 벤치마크 대신 내 업무의 실제 사례로 테스트 세트를 만듭니다.
  3. 형식·필수 문구는 코드 기반 채점기로, 문장 품질은 모델 기반 채점기로 평가합니다.
  4. 현재 상태로 평가를 돌려 기준 점수를 기록합니다.
  5. 프롬프트나 구조를 한 번에 하나씩 바꾸며 점수를 비교합니다.
  • 판정 모델도 틀릴 수 있으니 채점기 여러 개를 함께 씁니다.
  • 결과가 만들어진 과정도 사람이나 다른 에이전트가 확인할 수 있게 설계하면 신뢰도가 높아집니다.

비용·컨텍스트 줄이기

Claude API

오래 일하는 에이전트는 토큰을 많이 써서 비용이 커지고 컨텍스트도 무거워집니다. 반복되는 앞부분은 캐싱하고 필요한 것만 불러오게 해 비용과 정확도를 함께 챙깁니다.

따라 하기

  1. 매번 반복해서 보내는 긴 내용(시스템 프롬프트, 참고 자료)을 프롬프트 캐싱 대상으로 정합니다.
  2. 도구가 많으면 도구 검색으로 필요한 도구만 불러오게 합니다.
  3. 긴 작업에는 컴팩션(대화 기록 압축)을 씁니다.

  5. 구조를 바꿀 때마다 평가를 다시 돌려 실제로 나아졌는지 확인합니다.
  • 만들고 시험할 때는 큰 모델, 안정적으로 운영할 때는 저렴한 모델로 바꾸는 배벨 전략도 있습니다.

안전장치 두고 팀에 배포하기

Claude Managed Agents

AI에게 일을 많이 맡길수록 품질을 AI 판단에만 맡기지 않는 장치가 필요합니다. 권한을 나누고 작은 범위부터 배포하며, 폭주에 대비한 멈춤 장치를 둡니다.

따라 하기

  1. 에이전트가 접근할 데이터와 권한을 업무별로 나눕니다.
  2. 보안·규정 준수 요건을 확인하고 접근을 관리할 구조를 정합니다.
  3. 자동 작업이 예상보다 오래 돌거나 많이 실행되면 멈추는 기준(서킷 브레이커)을 정합니다.
  4. 작은 팀부터 배포하고 평가로 신뢰를 쌓은 뒤 범위를 넓힙니다.
  5. 에이전트가 제안한 행동은 사람이 확인하고 승인하게 합니다.
  • 표준화와 단단한 가드레일은 에이전트에게도 제약이 아니라 가속기가 됩니다.

Claude 모델은 약 두 달마다 바뀝니다. 새 모델이 나오면 평가 세트부터 돌려 옮길지 판단하고, 충분히 잘하는 부분은 예전에 덧댄 보완 단계를 걷어 냅니다.

따라 하기

  1. 새 모델이 나오면 평가 세트를 먼저 백그라운드로 돌립니다.
  2. 복잡한 실제 작업을 하나 맡겨 결과를 직접 읽어 봅니다.
  3. 이전 모델과 성공률과 비용을 비교해 기록합니다.
  4. 아직 안 되는 작업은 따로 적어 두고 다음 모델에서 다시 시험합니다.
  5. 새 모델이 잘하는 부분은 하네스와 보완 단계를 얇게 줄입니다.
  • 모델만 바꿨는데 테스트 에이전트 성공률이 약 20% 오른 사례가 있습니다.
  • 지금 안 되는 작업은 지우지 말고 남겨 두세요. 다음 모델이 잘하게 될 분야의 신호입니다.
