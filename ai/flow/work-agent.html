맡길 업무와 일터 정하기

Claude Managed Agents

Managed Agents는 실행 인프라를 Anthropic이 맡아 직접 서버를 만들지 않고 에이전트를 내놓을 수 있습니다. 자주 반복되는 업무 하나를 고르고 팀이 이미 쓰는 곳을 일터로 정합니다.

따라 하기

  1. 보고서 수집, 소셜 게시물 작성, 회의 전 브리프처럼 자주 반복되는 업무를 하나 고릅니다.
  2. 매번 단계가 같은 일인지, 단계를 미리 알 수 없는 일인지 판단합니다.
  3. 에이전트가 일할 장소를 팀이 이미 쓰는 도구(예: Slack 공개 채널)로 정합니다.
  4. 가장 단순한 첫 버전의 범위와 출시 목표 날짜를 정합니다.
  • Wispr는 회의 어시스턴트 첫 버전을 하루 만에, Actively는 영업 보고 에이전트를 2주 만에 만들었습니다.
  • Managed Agents는 어려운 작업에 잘 맞습니다. 단순한 작업은 직접 만드는 편이 나을 수 있습니다.

노하우를 스킬로 옮기기

Skills

사람이 그동안 고친 기록을 모아 스킬로 만들면 에이전트가 그 사람의 기준대로 일합니다. 할 일 목록보다 어떻게 판단할지 원칙을 적는 편이 효과적입니다.

따라 하기

  1. 노하우를 옮길 사람의 과거 수정 기록을 모읍니다(예: 편집장의 원고 수정 이력).
  2. 수정 기록에서 반복되는 판단 기준을 뽑습니다.
  3. 할 일 나열보다 어떻게 생각할지를 원칙 중심으로 스킬에 씁니다.
  4. 스킬을 작은 샘플에 돌려 기준대로 동작하는지 확인합니다.
  • Every는 편집장의 과거 수정 3만 건으로 교정 스킬을 만들었습니다.
  • 처음부터 완벽할 필요는 없습니다. 사람의 수정을 반영할수록 정확해집니다.

단순한 첫 버전 내놓기

Claude Managed Agents

처음에는 가장 단순한 형태로 빨리 내놓고 써 보며 넓힙니다. 문서에 바로 고치지 않고 제안 수정을 달게 하면 사람이 최종 판단을 지킬 수 있습니다.

따라 하기

  1. 정한 범위만 하는 첫 버전 에이전트를 Managed Agents로 띄웁니다.
  2. 에이전트가 문서에 바로 고치지 않고 제안 수정을 달게 합니다(예: Google Docs의 제안 수정).
  3. 공개 채널에서 동료들이 서로의 요청을 볼 수 있게 운영합니다.
  4. 써 본 결과를 보고 다룰 업무 범위를 조금씩 넓힙니다.
  • 모델이 좋아지면서 업무 절차 틀(하네스)은 점점 얇아지는 추세라 처음부터 복잡하게 짤 필요가 없습니다.

루브릭으로 결과 검증하기

Outcomes

Outcomes에 평가 기준(루브릭)과 반복 횟수를 주면 에이전트가 기준을 만족할 때까지 다시 시도합니다. 틀린 결과가 나가면 안 되는 업무라면 통과하지 못한 결과는 아예 보여 주지 않습니다.

따라 하기

  1. 사용자에게 중요한 기준을 모두 나열합니다.
  2. 객관적으로 확인되는 항목과 표시 방식·순서 같은 사용성 항목을 루브릭에 함께 넣습니다.
  3. 기준을 못 넘을 때 몇 번까지 다시 시도할지 정합니다.
  4. 작업 에이전트와 분리된 독립 컨텍스트의 검증 에이전트가 결과를 평가하게 합니다.
  5. 회의 24시간 전처럼 여유를 두고 실행해 반복할 시간을 확보합니다.
  6. 기준을 통과하지 못한 결과는 사용자에게 보여 주지 않도록 처리합니다.
예시 프롬프트
다음 루브릭을 모두 만족할 때까지 회의 전 브리프를 다시 작성하세요. 1) 참석자 LinkedIn이 올바른 인물의 것인지 확인했다 2) 핵심 내용이 읽기 쉽게 정리되어 있다 3) 중요한 정보가 위에 오도록 순서가 정해져 있다
  • 틀린 정보를 보여 주는 것보다 아예 보여 주지 않는 편이 낫습니다.
  • 평가 결과를 에이전트의 초기 루프에 반영하면 처음부터 더 정확해집니다.

평가 과제로 기준점 잡기

Evals

평가(evals)는 정해 둔 과제로 에이전트 성능을 꾸준히 재는 방법입니다. 기준 점수를 남겨 두면 새 모델로 바꿀지, 절차를 걷어낼지 근거를 갖고 판단할 수 있습니다.

따라 하기

  1. 에이전트가 꼭 잘해야 하는 대표 작업을 평가 과제로 정합니다.
  2. 과제마다 성공과 실패를 가를 기준을 정합니다.
  3. 현재 모델과 설정으로 평가를 돌려 기준 점수를 기록합니다.
  4. 새 모델이 나오면 쓰기 전에 같은 평가를 통과하는지 확인합니다.
  5. 결과를 보고 필요 없어진 절차는 걷어냅니다.
  • Lovable은 모든 모델 출시가 평가 루프를 통과해야 쓰도록 운영합니다.
  • 모델이 좋아지면 예전에 필요했던 복잡한 절차가 오히려 걸림돌이 될 수 있습니다.

사람의 수정 다시 반영하기

Skills

에이전트의 제안 뒤에 사람이 추가로 고친 내용이 가장 좋은 학습 자료입니다. 이를 모아 스킬에 반영하는 과정을 매일 돌리면 기준이 바뀌어도 시스템을 다시 만들 필요가 없습니다.

따라 하기

  1. 에이전트의 제안 뒤에 사람이 추가로 고친 내용을 추적합니다.
  2. 추적한 수정을 스킬에 다시 반영합니다.
  3. 지침 변경은 코드처럼 수정·검토·병합 절차로 관리합니다.
  4. 이 피드백 과정이 매일 돌아가도록 반복 작업으로 만듭니다.
  • 기준을 고정하지 않고 담당자의 결정에서 계속 배우게 하면 선호가 바뀔 때마다 다시 만들 필요가 없습니다.
  • 알게 된 것을 글로 남기면 동료의 학습 자료이자 에이전트가 읽을 자료가 됩니다.

비용 따져 범위 넓히기

Claude Managed Agents

오래 도는 에이전트는 컨텍스트가 쌓이며 비용이 늘고 느려집니다. 비용 절감 기능과 모델 배분을 점검한 뒤, 계속 Managed Agents로 갈지 일부는 직접 만들지 판단합니다.

따라 하기

  1. 매번 똑같이 보내는 긴 지시문이나 참고 자료에 프롬프트 캐싱을 적용합니다.
  2. 장시간 작업에는 컴팩션으로 지난 대화를 줄인 뒤 이어 가게 합니다.
  3. 평소에는 저렴한 모델로 일하다 막힐 때만 더 똑똑한 모델에 묻는 어드바이저 전략을 검토합니다.
  4. 폭주에 대비해 일정 조건이 되면 멈추는 서킷 브레이커를 정해 둡니다.
  5. 비용과 콜드 스타트 지연을 따져 계속 Managed Agents로 갈지 판단합니다.
  • 새로 만들고 시험할 때는 큰 모델을, 안정된 반복 운영에는 저렴한 모델을 쓰는 배벨 전략이 권장됩니다.
  • 세부 설정 방법은 Claude 공식 문서에서 최신 내용을 확인하세요.
